扩展函数不参与多态：你以为的重写，编译期就被定成了重载

📅 2026-11-22 18:43:00 ⏱️ 14 min read 👤 张小猛
Kotlin 静态分派 多态 API 设计

一个「加了方法」的错觉

fun Article.render(): String 这种写法，读起来像是在给 Article 加一个方法。调用点也像：article.render()，点号、参数、返回值，和成员函数没有区别。于是很多人顺手把它当成成员函数用——指望子类能换掉它，指望不同的实现类走不同的逻辑，指望升级一个库之后行为还归自己管。

这三件事一件都不成立。

扩展函数在 JVM 上被编译成一个静态方法，接收者变成第一个参数。它没有进类的虚方法表，没有槽位，也就没有「运行期再决定调哪个」这回事。调用点写下的那一刻，编译器就把目标签名钉死了：看的是接收者的静态（声明）类型，加上当前作用域里可见的那个扩展。

这不是语法层面的小陷阱，而是把一个编译期机制当成了运行期机制。下面的内容把「想改变一个类型的行为」拆成三条可走的路，按绑定时机排一遍，再给一张表、三组对照，最后落到能执行的规则。

三条路：先按绑定时机排队

同一个需求——让某个类型在做某件事时表现不同——在 Kotlin 里至少有三种落点。它们的差别不在写法，而在「什么时候决定调用谁」。

路线一：接口方法，由实现类决定

接口声明签名，实现类提供行为。调用方只依赖接口，具体走哪段代码在运行期由对象的实际类型决定。

interface Syncable {
    fun sync(): Result
}

class LocalStore : Syncable {
    override fun sync(): Result = pushToLocalDisk()
}

class RemoteStore : Syncable {
    override fun sync(): Result = pushToServer()
}

fun runAll(items: List<Syncable>) {
    items.forEach { it.sync() }   // 这里只认 Syncable，具体实现运行期才定
}

绑定时机是运行期。依据是对象的实际类型，JVM 通过接口方法表找到对应的实现。可覆盖：任何实现类都能给出自己的版本，新增实现不需要改调用方。

代价是类型的所有权。接口得是你写的那一个，或者至少是你能改的那一个。给一个已经发布的接口加抽象方法，所有实现方都会编译失败；想加默认实现又会被 JVM 默认方法的规则和 Kotlin 的兼容性策略牵制。第三方库里的类型，这条路走不通。

路线二：open 类成员，由实际类型决定

类比接口更重，但分派规则一样：open 成员在子类里 override 之后，调用点根据对象的实际类型选实现。

open class Repository {
    open fun refresh() { /* 默认实现 */ }
}

class CachedRepository : Repository() {
    override fun refresh() { /* 先读缓存，再决定要不要回源 */ }
}

fun warmUp(repo: Repository) {
    repo.refresh()   // 实际类型是 CachedRepository 时，走的是覆盖版本
}

绑定时机同样是运行期，依据同样是实际类型。可覆盖的范围限于继承体系内部：子类能改，体系外的人改不了。

这条路的限制也很明确。类必须是 open 的，方法必须是 open 的。Kotlin 的类默认 final，这不是风格偏好，是在逼你在设计时表态：这个行为允不允许被替换。一旦标了 open，你就把「子类可以改变行为」写进了契约，之后不能再当成实现细节随手改。反过来说，如果一个类被标了 final，或者方法没开 open，你在外面写多少个同名扩展都改变不了它的行为。

路线三：扩展函数，由静态类型和可见性决定

扩展函数的调用目标，在编译期由两件事决定：调用点处接收者的声明类型，以及那一刻作用域里能看见哪个扩展。

// com.example.app/model/Article.kt
class Article(val title: String)

// com.example.app/ui/Render.kt
package com.example.app.ui
fun Article.render(): String = "[ui] $title"

// com.example.app.export/Plain.kt
package com.example.app.export
fun Article.render(): String = title

// 调用方
import com.example.app.ui.render
fun show(a: Article) = a.render()   // 用哪个实现，由这条 import 决定

两个文件里可以存在两个同名、同签名的扩展，只要它们在不同的包里。调用方 import 了哪一个，a.render() 就绑到哪一个；两个都 import 进来，编译器会报重载歧义（ambiguity），而不是在运行期挑一个。这条规则本身就说明了问题：选择发生在编译期，依据是名字解析，不是对象。

绑定时机是编译期。依据是静态类型加可见性。不能覆盖——子类写一个同名扩展，得到的不是 override，是一个全新的函数。失效场景最多：成员函数同名时被旁路、换一个文件换一个 import 就换实现、被调方升级后行为可能悄悄换轨。

类内定义的扩展：两个接收者，两套规则

有一种写法容易让人误以为扩展也参与运行期分派：在类内部定义扩展。

class Presenter {
    fun Article.render(): String = format(title)   // 分发接收者 Presenter，扩展接收者 Article
}

这里有两个接收者，规则不同。外层那个（Presenter）叫分发接收者，它按运行期解析，子类可以覆盖；里层那个（Article）叫扩展接收者，它仍然按静态类型解析。也就是说，Presenter 的多态能生效，Article 的多态不能。把这两层混在一起谈「扩展是不是多态」，结论必然是拧的。

一张表：三种机制的绑定时机

把三条路放进同一张表，差别一目了然。

机制 绑定时机 依据 可覆盖 失效场景
接口方法 运行期 对象的实际类型，走接口方法表 实现类可以给出自己的实现 类型不归你所有；给已发布接口加抽象方法会打断所有实现方
open 类成员 运行期 对象的实际类型，走虚方法表 子类可以 override 类或方法没开 open；类型不归你所有
扩展函数 编译期 调用点接收者的静态类型 + 当前可见的 import 不能覆盖；子类同名扩展是另一个函数 成员同名时被旁路；换文件、换 import 就换实现；依赖升级后可能静默换轨

表的最后一行值得单独读一遍。「不能覆盖」和「可以被重写」是两种完全不同的能力，不是程度差别。前两行的失效场景是「你拿不到这个类型」，第三行的失效场景是「你拿到了类型，但你以为的那套运行期规则根本不存在」。

三组对照：看着一样，落点不同

下面三组写法，语法上都成立，行为上的差别不在运行期，而在编译器看代码的那一刻。

对照一：成员和扩展同名，成员赢

class Report {
    fun export(): String = "member"
}

fun Report.export(): String = "extension"

fun main() {
    println(Report().export())   // 输出 member
}

同一个类上既有成员函数、又有同名同签名的扩展，调用总走成员函数。这是 Kotlin 的解析顺序决定的：成员优先，扩展只在成员缺位时参与候选。

需要说清楚的是，编译器并不是完全无声。在扩展的声明处，通常会给一条「extension is shadowed by a member」的警告。但它是警告，不是错误；调用点不会有任何提示；如果这个扩展定义在另一个模块、由别人维护，或者构建日志被刷过去，你看到的就是一段「写了但没生效」的代码。行为已经切成成员版本，代码还在原地，谁都没被告知。

对照二：子类写同名扩展，不是重写

open class Animal
class Dog : Animal()

fun Animal.describe(): String = "animal"
fun Dog.describe(): String = "dog"

fun printAnimal(a: Animal) = println(a.describe())   // 静态类型 Animal → animal
fun printDog(d: Dog) = println(d.describe())         // 静态类型 Dog → dog

如果 printAnimal(Dog()) 走的是运行期分派，输出应该是 dog；实际输出是 animal。原因不复杂：a 的声明类型是 Animal，编译器在这一行只看得见 fun Animal.describe()，于是生成对 Animal 那个静态方法的调用。传进来的是 Dog 还是 Cat，与这次调用无关。

这也解释了为什么「子类扩展不覆盖父类扩展」不是 bug，而是同一个机制的必然结果。两个 describe 之间没有继承关系，只有重载关系；重载在编译期按静态类型选，选完就结束。

对照三：库新增一个成员，行为静默换轨

这是三个里最难防的，因为它不需要你改任何代码。

假设你的项目里长期有一个扩展：

// 下游代码，com.example.app.util
fun Session.invalidate() {   // 清本地缓存、发一条埋点、通知界面
    clearCache()
    track("session_invalidated")
    notifyUi()
}

某天依赖的库升级，Session 这个类型自己新增了一个成员函数 fun invalidate()。你的代码照常编译——扩展还在，调用点还在，签名匹配。但解析顺序变了：成员优先，调用从扩展切到成员。清缓存、埋点、通知界面这三件事，一起消失。

编译不报错，测试未必覆盖到这条路径，日志上看不出异常，因为成员函数本身工作正常。真正丢的是你附加在扩展里的那层副作用。这类切换不会在运行时抛异常，也不会在调用点给提示，只有在事后比对行为时才有可能发现。

这个场景不是假想出来的边缘情况，而是库演进中的常见形态：一个类型早期没有某个能力，下游用扩展补；后来类型自己补上了，下游的扩展就被顶掉。上游认为这是正常的功能增强，下游看到的是行为变化。

什么时候该用扩展

扩展不是坏东西，它只是不适合承担「多态」这个职责。把它放回它擅长的地方，价值很直接。

工具：不改变类型语义的纯函数

字符串截断、集合分块、时间格式化、JSON 字段读取——这类函数的特点是只依赖公开 API，不持有状态，不改对象的语义。写成扩展只是为了调用点读起来顺，text.truncate(80) 比 Strings.truncate(text, 80) 少一层括号。

这类扩展不需要被覆盖，也不指望子类改变行为，所以编译期绑定不但不是缺点，反而让调用点更容易推理：看到 truncate 就知道去哪个文件找，不必在继承体系里翻。

适配：给拿不到源码的类型补一层壳

第三方 SDK 的类型、JDK 的类型、生成代码里的类型，都不能改。想给它加一个领域内顺手的入口，扩展是成本最低的做法。Instant.toReadable()、Response.jsonBody()、Cursor.nextOrNull() 都属于这一类。

关键在命名：这类扩展应该读起来像「转换」或「取值」，而不是像「这个类型本来就该有的行为」。名字一旦起得像成员（save()、refresh()、close()），阅读的人就会默认它能被覆盖、能被替换，误解从命名开始。

边界：扩展碰不到 private 和 protected

扩展不是成员，所以它拿不到接收者的 private 和 protected 成员。它只能站在外部，用公开的 API 组合出行为。

这条限制经常被当成不便，其实它是一道有用的边界：如果一个行为非得访问私有状态才能实现，那它本来就应该属于这个类，而不是外挂上去。硬要把扩展写在「使用方内部」来绕过可见性，得到的是一个位置诡异、依赖隐式接收者的函数，读代码的人要在两个作用域之间来回跳。

什么时候不能用扩展

反过来，有两种诉求一旦出现，扩展就应当立刻退出候选。

想让子类改变行为

只要需求里出现「不同子类做不同的事」「运行时根据实际类型选实现」，答案就是接口或 open 成员，而不是扩展。扩展没有虚方法表槽位，子类写同名函数得到的只是一个更具体的重载，通过父类静态类型调用时仍然命中父类那个版本。

判断方法可以很直接：把调用点的变量类型写成父类，问自己「这里应该走子类的实现吗」。如果答案是「应该」，扩展就是错的工具，不管它写起来多顺手。

想被重写、想被 mock

测试里替换实现、插件式的扩展点、框架留的钩子——这些都需要运行期可替换。扩展做不到：调用目标在编译期就定死了，测试代码 import 另一个同名扩展，改变的是测试模块自己的解析结果，不是被测代码的。

想在测试里替换一个扩展的行为，现实的做法是把它变成接口依赖注入，或者把这个函数作为参数传进去。指望用「同名的测试扩展」覆盖生产扩展，只会在两个模块各自解析到各自的版本时，得到一份看起来很绿的测试。

怎么避免静默旁路

机制本身不会改，能改的是工程上的检查点。下面三条按投入从低到高排。

成员与扩展同名：先查成员再定义

在给一个类型写扩展之前，先确认它没有同名同签名的成员，包括父类继承来的。IDE 的补全会把成员排在前面，但补全列表不是契约，换个版本可能就多一项。

团队里可以加一条约定：扩展的命名带领域前缀或动词短语，避免和类型自身的词汇撞车。toDisplayString() 比 toString() 安全，asJsonBody() 比 body() 安全。撞车的代价不是编译错误，而是「写了没生效」这种最难查的故障。

库升级时的检查点

依赖升级的 PR 里，除了看 changelog 和编译结果，还应该扫一遍「新增的公开成员是否与本地扩展同名」。这一步可以脚本化：列出项目里所有扩展的「接收者类型 + 函数名」，与升级后依赖的公开 API 做交集。交集非空的地方，逐个确认调用点是否依赖了扩展里的副作用。

升级后第一次全量编译时，注意 shadowed by a member 这类警告。它通常不是噪音，而是行为已经换了轨道的信号。把这类警告在 CI 里提升为可见的输出（至少不要被日志淹掉），成本很低。

命名与可见性收口

扩展的可见性决定了它能被谁解析到，也决定了行为变化的半径。只在一个文件里用的扩展，写成 private；只在一个模块里用的，用 internal。可见性收得越紧，被别人的同名扩展干扰、被库的新成员顶掉的概率越小，出问题时也越容易定位。

反过来，把一堆扩展放进一个全局可见的 Extensions.kt 并用通配符 import，等于把解析结果交给命名空间碰撞。这不是风格问题，是行为可预测性的问题。

收束：你写的是静态函数，不是方法

回到开头那个错觉。fun Article.render() 不是在给 Article 加方法，是在当前包里声明一个静态函数，第一个参数是 Article。点号调用只是语法糖，编译器把它翻成 RenderKt.render(article)。

一旦这样看，前面所有结论都不需要额外记忆：

  • 静态函数没有虚表槽位，所以不能被覆盖。
  • 静态函数的调用目标在编译期按签名解析，所以看静态类型，不看实际类型。
  • 静态函数的解析遵守「成员优先」，所以同名成员出现时扩展被旁路。
  • 静态函数的可见性由 import 和作用域决定，所以换个文件就可能换个实现。

需要运行期决定行为时，用接口或 open 成员，把选择权交给实际类型。需要给拿不到源码的类型补一个顺手的入口时，用扩展，并且接受它编译期就定死这个事实。

把这两件事分开，代码里就不会出现「明明写了覆盖，为什么没生效」这种问题——因为从一开始，那里就没有覆盖，只有重载。
