看不见的那部分工作，决定了你以后能跑多快

📅 2026-11-07 20:30:00 ⏱️ 13 min read 👤 张小猛

看不见的那部分工作，决定了你以后能跑多快

改一行文案，真正花时间的往往不是改。是改完之后那段不确定：页面会不会崩、链接会不会断、别的地方会不会跟着变。这段不确定有多长，决定了你一天能改几处，也决定了你敢不敢动那些真正该动的地方。

我们平时说「快」，说的几乎是同一件事：写得快、上线快、迭代快。但这几种快混在一起就没法比较了。我把它们拆成三个，各自量不同的东西。

一、先给三个速度起名字

V1：把想法变成改动

这一段包括想清楚、找到该改的地方、把改动写下去、让它在本机跑起来。它最容易被看见，也最容易被当成全部。编辑器、补全、脚手架、模板，主要都在压这一段。它的上限受两件事限制：你对代码的熟悉程度，和你要跨越的认知距离。

V1 有一个特点：它有进度感。文件在变，屏幕在变，你能感觉到自己在推进。这种手感很容易被误认成工作的全部。

V2：从改完到「我确信它没坏」

这一段里没有产出。你只是在等：等构建、等测试、等 CI、等自己把页面点一遍。它的长度不由你多努力决定，而由链条决定——构建要多久，检查覆盖到哪，失败信息能不能读懂。

「确信」听起来是主观的，但它的成本是客观的。你不知道有没有坏，就只能用时间去换确定性：全量跑一遍、手工点十个页面、或者干脆等第二天看线上有没有人报错。最后这种最贵，因为它在用真实用户做检查。

V3：从发现错了到回到已知良好状态

这一段包括定位、回滚、重做，以及向别人解释。它的成本高度非线性。错误在几分钟内被发现，上下文还在脑子里，撤回近乎免费；错误在几小时后被发现，你得先把自己重新载入那个状态——真正贵的不是回滚命令，是重建上下文。

三个速度不是并列的，是串联的。一次改动的总时长不是三者相加，因为不同改动可以并行；但长期产出受最慢的那一环限制。这一点后面还会回来。

速度 量的是什么 谁在影响它 变慢时的体感
V1 想法到改动 熟练度、工具、代码结构 卡住，但看得见
V2 改动到确知 构建链、检查覆盖、错误信息 等待，像在浪费生命
V3 出错到复原 版本控制、可回滚的粒度、上下文 慌乱，且常在深夜

需要说明一句：V1、V2、V3 是分析框架，不是测量结果。我没有给它们计时，也不打算编一组数字出来。本文后面出现的「几秒」「几小时」都是示意，指量级差异，不是实测值。

二、门禁只碰 V2，但它改的是 V3 的价码

门禁、构建脚本、检查器，这些工作的共同点是：它们不产出任何功能。装上去之后，用户看不到任何变化，页面一个像素都没动。

为什么 V2 是隐藏的瓶颈

V1 有明确的进度感，V2 没有。V2 像编译：你盯着日志，什么也没发生。人对等待的忍耐有限，于是会自发地减少等待——攒一批改动，再统一验证。这个策略是理性的，但它有一个副作用：一次失败时，你可能不知道是哪一处改坏的。

批处理变大，是 V2 变慢的后果。而批处理变大，又让 V3 变贵。这条链条平时没人提，因为它跨了两个阶段，而人习惯在自己的阶段里找原因。

撤回成本决定了你敢下多大的注

这里是最反直觉的一环。门禁并不直接让你写得更快，它是把「错了也能退回来」这件事变便宜。

当撤回便宜，单次改动的最优规模就会变大，试错的最优次数也会变多。反过来，如果每次改错都要花半天收拾，理性策略是只做最有把握的那一个改动——看起来稳，实际上把探索的空间关掉了。你会开始避开那些「改坏了不好收场」的地方，而那些地方往往正是结构问题所在。

被放大的不是速度，是试错次数

可以用一个粗略的关系来描述我现在的理解：长期产出大致等于试错次数乘以单次试错的期望收益。这个式子是示意的，但方向清楚——右边两项里，更容易被工程手段改变的是第一项。

十次尝试里成一次，前提是九次失败都能被便宜地撤回。如果每次失败都要付出一次「事故」的代价，你只会试一次，而那一次未必对。所以门禁真正的产出不是「快」，是「敢」：敢改结构、敢动模板、敢在别人也在改的时候动发布链。

三、五道检查，各自有一个具体的理由

我这套发布链上的检查不是设计出来的，是长出来的。每加一道，前面都有具体的理由：有的是事故，有的是一条迟早会出事的机制。

单测：最早的那一道

最早只有单测，一条 python3 -m unittest discover -s tests 就能跑完。它管的是纯逻辑：解析、渲染、路径拼接。它给了最初的确定感，也给了最早的错觉——单测绿了，就以为没事了。它看不见页面，看不见链接，也看不见仓库里躺着什么。

产物一致性：漏掉一个 rss.xml

有一次我改了某篇文章的 description，忘了把所有产物重新编译并提交。这条链会同时写出文章页、元数据、列表页、首页、RSS、sitemap；我凭记忆列了一份要 add 的名单，漏了 rss.xml。

CI 里那条断言很直接：重新构建一次，git add -A，然后 git diff --cached --exit-code。它当场变红。

这件事教我的不是「要记得」，而是「记得」不可靠。产物是一组由同一份源生成的集合，任何一个成员掉队，仓库就处在一个不会被任何单测发现的不一致状态里——源码是对的，构建也是对的，只有提交进去的那份快照是错的。

内链检查：全站重建之后才敢说没断

内链检查的来历没那么戏剧性。每次全站重建，都会重写所有文章页里的相关文章、上一篇、下一篇；这些链接是生成的，而生成的链接会指向不存在的地址——删文、改 slug、只重建一部分，都会留下这种空洞。

于是有了内链检查：重建完，把所有内部链接抓出来逐个核对。它检查的不是我亲手写的链接，是我没写、由脚本生成的那些链接。这一类东西的共同点是：写的时候不存在，坏的时候也没人盯着。

隐私扫描：密钥进了公开仓库

有一次，一个密钥被写进了仓库里的一个 Markdown 文件，推到了公开仓库。发现的时候，那个文件本身可以直接下载。

事后回看，最刺人的不是「写错了」，是「没有任何一步会拦住它」：单测不管内容，构建不管内容，内链检查只管链接。整条链上没有一个环节的职责包含「这个仓库里不该有这种东西」。

后来补的扫描器带正例和负例自检：一批必须命中的样本，一批必须不命中的样本。这个设计比规则本身更重要——一个规则写错、从不命中的扫描器，和一个干净通过的扫描器，输出完全一样。

提交钩子：把漏 add 挡在 commit 之前

rss.xml 那次之后，加了 pre-commit：提交前自动构建一次，比对「暂存区」和「工作区」，有产物没 add 就阻断，并列出文件名。

它把同一类错误的发现位置从 push 之后挪到了 commit 之前。这个位移的价值不在省时间，在于 V3 变了：东西还没推出去，撤回只是补一个 add；推出去之后再发现，撤回就是一次公开的返工。

四、钩子不是保险箱：它的三个漏口

这道钩子有三处结构性弱点。我知道它们存在，还是留着它——因为承认局限比假装没有更有用。

它住在 .git/hooks 里，不进版本控制

钩子文件跟着工作副本走，不在仓库里。换一台机器、重新克隆一次，它就不在了。

而「我们有 pre-commit」这句话会被继续讲下去。讲的人以为在讲仓库，其实在讲某一台电脑。这种错位不会报错，它只是让保护在某个时刻静默消失。

--no-verify 一行就绕过去了

任何本地钩子都能被一个参数跳过。它不是权限边界，是提醒。设计它的目的是减少疏忽，不是防止故意。所以它挡不住「我赶时间」，而「我赶时间」恰好是最需要它的时候。

找不到 .venv 就降级放行

钩子要跑构建，构建依赖本机的虚拟环境。找不到就降级放行——这是一个明确的 fail-open。

fail-open 在「可用性优先」的场景里是合理选择：不能让一个环境问题把所有人锁死。但它意味着钩子的有效性依赖一台机器的目录状态，而这个状态没有任何检查在看着。三道漏口指向同一件事：这套保护是本地的、自觉的、有条件的。它抬高了平均水平，没有抬高下限。

五、批量操作里的文件名，是另一类看不见的坑

core.quotepath 与八进制转义

git 默认会把非 ASCII 文件名在状态输出里转义成八进制。中文标题的页面文件正好中招。我用 awk 和 cut 从状态输出里拼 add 名单，拿到的是一串转义后的字符串，和真实文件名对不上。

一次漏了 36 个页面。奇怪的不是漏，是漏完之后一切看起来都正常：脚本跑完了，没有报错，我也没有理由去数一遍。

换成 -z 解析，或者按目录 add

两个修法。一是让 git 输出原始字节，按 NUL 切分，路径不经过引号转义；二是干脆按目录整块加，不去逐条拼名单。

git -c core.quotepath=false status --porcelain
git status --porcelain -z | tr '\0' '\n'

这里的原则不是「小心一点」，是让中间格式不需要人肉解码。任何要经过一次转译才能用的输出，迟早会在某次转译里出错，而出错时它通常不声不响。

六、为什么这类工作总被算成额外成本

它不出现在功能清单上

功能清单上的每一项都能被演示：点了有反应，页面上有变化。门禁不能演示。你没法在会上说「我这周加了三个检查」，然后期待和「上线了搜索」一样的反应。

它的收益是「没发生的事」

门禁的产出是负数：没有发生的事故、没有浪费的下午、没有推出去又撤回的提交。负数不可见。你只能通过反事实去感受它——如果没有这道检查，那次会怎样。反事实没法写进周报，也没法在复盘会上被量化。

出事故时它才被想起

平时它是噪音，出事时它是嫌疑人。「为什么又红了」——注意这句话的语气：红的那一下，人先怪检查，而不是先怪改动。

检查的存在感，几乎全部来自它拦人的时刻。这是一个很糟糕的激励结构：它做得越好，越不被注意；它一旦出错，立刻被记住。

七、门禁的三种坏味道

假阳性：狼来了之后，红灯也不看了

一道检查如果偶尔误报，人的反应不是「再确认一下」，是「它又抽风了」。红灯的信用是消耗品，用一次少一次。

误报率高的检查，最后会训练出一群看见红也继续推的人。这比没有检查更糟——没有检查时，人至少知道自己没有保护；有一道总在误报的检查时，人以为自己有。

盲区：只扫改动，存量永远不报错

隐私扫描默认只扫「相对主干的改动」。这是有意的取舍：快、噪音少、和本次提交相关。但它有一个必须说清楚的后果——对存量它永远不报错。

不报错不等于干净，只等于没看。一个只扫 diff 的检查器，最危险的时刻是被当成「全库体检」的时候。要真的看存量，得显式换基线或者跑全量模式，而那通常不在日常路径上。

维护成本转嫁给别人

钩子依赖本机环境，规则住在一个不进版本控制的文件里，坏了只有写它的人知道怎么修。于是维护成本没有消失，它被转给了下一个克隆仓库的人——而那个人通常不知道有这回事。

看不见的工作如果只对作者可见，它就还没有真正完成。它只是从「没做」变成了「某个人在做」。

八、什么不该做成门禁

反过来说，不是所有能自动化的判断都该变成门禁。有几类东西，我倾向于不让它们进提交路径。

需要解释的判断

文案的语气、命名的品味、抽象的层次——这些能被讨论，不能被断言。把它们写成规则，规则会先于判断失效：你要么不断加例外，要么开始写违反直觉的代码去讨好检查。

依赖外部网络的检查

网络抖动会产生假红，假红会消耗红灯的信用。外部依赖适合放进定期巡检，不适合放在每次提交都要过的地方。

几分钟才出结果的检查

本地钩子的耐心窗口只有几十秒。超过这个窗口，人就开始找绕过的方法，而绕过的方法通常是一个参数的事。慢检查应该去 CI，快检查才配留在本地。

一次性迁移的规则

为一次重构写的检查，重构完成后就变成了负担。它会继续拦人，而没人记得它为什么存在。规则也会过期，只是过期时不报警。

九、判断一道门禁值不值得留

四个问题

  1. 它回答的是非题吗？能在几十秒内给出是或否，而不是「你自己看看」。
  2. 它误报的时候，人会不会因此忽略下一次真报？
  3. 它失效的时候，是静默通过还是明确失败？fail-open 必须被写下来，不能靠人猜。
  4. 它坏了谁修？如果答案依赖某台机器上的某个人，它迟早会消失。

它得能证明自己没瞎

正例必须命中，负例必须不命中。没有自检的检查器，你无法区分「规则正确且没有违规」和「规则写错了、永远不命中」。这两者的输出完全一样，而后者更常见，因为它看起来一样绿。

一条可以落地的判据

判据 通过的样子 不通过的样子
反馈速度 几十秒内出结果 要等到推送之后
信号可信 红了就真的有问题 偶尔抽风，大家已经习惯
失效方式 明确报错，或明确标注降级 静默跳过，没人知道
自检 正例命中、负例不命中 从没验证过它会不会响
归属 跟着仓库走，谁都能修 只存在于某台机器上

十、收束：先修跑道，再谈提速

如果只让我改一个地方，我会先改 V3，再改 V2，最后才碰 V1。

原因不复杂：V3 决定你敢不敢试，V2 决定你试完多久知道结果，V1 只是把想法写下来。它几乎从来不是瓶颈，却是唯一看得见的那个——所以绝大多数工具、教程、方法论都在讲它。

看不见的那部分工作，不产出任何功能。它不改变页面上任何一个像素，不进功能清单，也没法在演示里被指出来。但它决定了你以后能以多快的速度安全地改东西：把「确知」从几小时压到几秒，把「撤回」从一次事故压成一次补提交，然后你才敢做那些没门禁时不敢做的改动。

所以真正被放大的不是速度，是试错次数。而试错次数，是长期里唯一会累积的东西。

说回现状：钩子仍然住在 .git/hooks 里，扫描器默认仍然只扫改动。这两个漏口我都还没补。写下来是为了不把它们当成已经解决——看不见的工作最容易的结局，就是被讲成已经做完。
