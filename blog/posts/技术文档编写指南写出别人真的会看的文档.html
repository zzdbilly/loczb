技术文档编写指南写出别人真的会看的文档

📅 2026-09-03 17:30:00 ⏱️ 18 min read 👤 张小猛
技术写作 文档规范 工程实践 Docs-as-Code

先说为什么大部分技术文档是失败的

我读过上千份 README、设计文档和接口说明，得出一个不太客气的结论：大多数技术文档不是"写得不好"，而是根本没打算让人读。它们存在的目的更像是"证明这个功能有文档"，而不是"帮下一个人把事办成"。

失败的技术文档通常死在三件事上：

  1. 没人看——因为读者打开前三秒不知道该不该继续读下去；
  2. 看了找不到答案——因为作者按自己的实现顺序组织内容，而不是按读者的问题顺序；
  3. 找到了，但已经过期——因为文档和代码分开维护，改代码的人不知道要改文档。

这三件事都有对应的工程化解法，这篇文章就是把解法摊开讲清楚：写给谁、分几层、怎么组织结构、措辞红线、代码示例的标准、docs-as-code 工作流、以及一份可以直接抄走的发布前检查清单。

判断一份文档好坏的唯一标准

我给自己定了一个很简单的标准，比任何写作课都管用：

一个不了解背景的工程师，能不能只靠这份文档，在不问任何人的情况下完成他要做的事？

做不到，就是文档的问题，不是读者的问题。"这个很简单，显然应该……"是技术文档里最有害的一句话——对作者显然的东西，对三周后的作者本人都不显然。

动笔前先回答：写给谁看

同一个 Redis 配置项，写给三类人看是三种写法。动笔前必须写下读者画像，不写下不去笔。

三类典型读者

读者 他要完成的事 他讨厌什么 文档该给什么
评估者 决定要不要用这个库 看了一半还不知道能干嘛 第一段讲清"解决什么问题"，给最小可运行示例
使用者 把它跑起来、用起来 环境假设、跳步骤 按顺序可复制执行的步骤，每步有预期输出
排障者 出错了，找原因 找不到错误信息对应的那一节 错误码表、常见报错和解法、FAQ

排障者最容易被忽略，但他往往是打开文档频率最高的人——只在系统挂掉的时候。深夜三点对着报错的人没有耐心读你的架构哲学，他需要 Ctrl+F 能搜到那行错误信息。

写读者画像这件事本身

读者画像不用长篇大论，放在文档开头两三行即可：

## 本文适用对象
- 已部署本服务、需要调整超时参数的 SRE
- 不熟悉：不需要你了解内部调度实现
- 前置条件：能登录部署机器，有 config/ 目录读写权限

这同时是在帮作者自己砍内容：凡是这个读者用不到的段落，删掉，或者拆成链接。

用 Diátaxis 把文档分四层

写文档最常见的结构灾难，是一份文档同时想当教程、手册和架构图。Diátaxis 框架把文档切成四种互斥的类型，每种只服务一种需求，这个划分我用了两年，是真正改变我写作习惯的一条：

  • 教程（Tutorial）：带新手走一条预设路线，"跟我做"。重学习，允许啰嗦，保证每步成功。
  • 操作指南（How-to）：解决一个具体任务，"怎么做 X"。重行动，标题就是任务名。
  • 参考（Reference）：描述工具本身，参数表、错误码、API 签名。重信息，必须完整、无遗漏。
  • 解释（Explanation）：讲设计动机和背景，"为什么这么设计"。重理解，可以有观点。

一篇文档只属于一层

判断方法很粗暴：读者是在学习还是在工作？参考和 how-to 服务工作中的读者，教程和解释服务学习中的读者。混层的典型症状是：how-to 的第 4 步突然插入两页架构史——工作的人只想把第 4 步执行完。

以我自己这个博客为例（这篇也是按这个标准维护的）：

blog/
├── README.md            # 教程：5 分钟从零发一篇文
├── docs/
│   ├── write-post.md    # how-to：改封面图 / 加分类 / 回刷旧文章
│   ├── reference.md     # 参考：frontmatter 字段表、脚本参数、模板占位符
│   └── why-markdown.md  # 解释：为什么弃用 WordPress 自己写生成器

四层各自独立，互相用链接引用，绝不把彼此的内容抄进对方——一抄就开始了复制粘贴漂移的深渊（后面反模式一节细讲）。

单篇文档的结构规范

分层解决了"该写哪几篇"，这一节解决"每一篇内部长什么样"。

标准骨架

一份合格的 how-to / 说明类文档，我建议固定这个骨架：

# 标题：面向动作，一眼知道读完能干嘛
## 你将完成什么（1-2 句 + 结果截图/输出）
## 前置条件（版本、权限、账号，用表格或列表）
## 步骤
### 第 1 步：……
### 第 2 步：……
## 验证成功（怎么确认真的生效了，给出预期输出）
## 常见问题 / 回滚（失败怎么办）
## 延伸阅读（链接到参考或解释，不展开）

每步一节、一节一个观点。验证成功是最常被省掉又最不该省的一节——读者做完十步，你需要告诉他怎么知道这十步都成了，而不是让他猜。

标题层级不许跳级

标题是目录树的原料，跳级会毁掉大纲和可访问性（屏幕阅读器按层级导航）。h1 只允许一个，## 下直接出现 #### 属于 bug 不是风格：

# 配置超时参数            ✅ h1 全篇唯一
## 服务端                  ✅
### Nginx 层               ✅ 逐级递进
#### 单个 location 覆盖     ✅

# 配置超时参数
## 服务端
#### 单个 location 覆盖     ❌ 跳级，大纲会错位

发布前用脚本扫一遍，比人眼可靠：

# 检查 h1 数量与标题跳级（本博客 generate-post.py 内置同款检查）
grep -c "<h1>" blog/posts/*.html | grep -v ":1$" && echo "h1 数量异常"
awk '/^#+ /{n=length($1)} prev && n>prev+1{print FILENAME": 跳级 -> "$0} {prev=n}' docs/*.md

目录和锚点

超过两屏的文档必须有目录。目录要么手写要么从标题生成，永远不要在正文里再手写一遍"第一章……"之类的编号——插入一节就得全部重排，编号漂移是文档腐烂的第一现场。

措辞规范：十条红线

内容对了，措辞不对照样劝退。这是我长期修订文档总结的红线，每条都附 bad / good 对比。

红线 1-5：主动、具体、面向动作

❌ 超时可以在配置中被修改。
✅ 你可以修改配置中的 timeout 值。
# 被动语态藏起了"谁来做"；主动语态逼你写出动作的执行者。

❌ 该功能性能很好。
✅ 单次查询 P99 从 120ms 降到 8ms（v2.3，16C32G，100 并发）。
# 没有数字的性能描述等于没写。

❌ 关于部署的相关信息
✅ 部署到生产环境
# 标题就是任务名。名词短语的标题搜不到、看不懂。

❌ 这里我们采用了一个巧妙的方案，非常简单，显然应该……
✅ 采用 X 方案，代价是 Y（见「为什么不用 Z」）。
# "简单/显然/只需"是对读者的否定：读者卡在这一步时只会觉得自己蠢。

❌ 用户点击保存按钮之后，系统将会把数据写入数据库。
✅ 点「保存」，数据落库。
# 删掉"之后/将会/进行/对所……的"这些水分词。中文技术写作同样适用。

红线 6-10：一致、精确、不卖关子

❌ 先"登录控制台"，后"登陆管理后台"，再"进入 Dashboard"。
✅ 全文统一用一个词："登录管理控制台"。
# 术语一致性：同一事物全文只有一个名字。建术语表，review 时对照。

❌ 较新的 Node 版本即可。
✅ 需要 Node.js ≥ 18.17（v16 已 EOL）。
# 版本、路径、参数名精确到可复制。"较新/大概/一般来说"都是埋雷。

❌ 未来将支持导入功能。
✅ 导入功能在 3.1 提供（未 GA，勿用于生产）。
# 不写没有日期的承诺。要么给版本，要么不写。

❌ 详见相关文档。
✅ 见《限流参数参考》#qps 一节。
# "相关文档"要么给确切链接，要么删掉这句废话。

❌ 这段逻辑很复杂，就不再展开了。
✅ 核心逻辑分四步：A → B → C → D（每步一句话 + 链接到解释文档）。
# 复杂不是省略的理由，是拆分层级的信号。

代码优先于文字

能用一行代码说清的，不要三行中文。比较两种赋值方式，最好的写法是并排放两段代码加一句结论，而不是用文字描述代码行为：

❌ 文字描述："你需要先解构出 head 和 tail，然后对 tail 做 map……"
✅ 直接给：

const [head, ...tail] = list;          // 取第一个和其余
const doubled = tail.map(x => x * 2);  // 其余翻倍

代码示例的规范

技术文档里代码示例是本体，文字是注解。示例不合格，整篇文档作废。

合格示例的四条硬标准

  1. 可运行：复制粘贴能跑通，不省略 import、不假设有魔法变量；
  2. 完整但有边界：展示最小闭环，错误处理可以用注释标明"生产环境需处理"，但不能不写输入输出；
  3. 标注版本：语言、库版本不对，示例就是误导；
  4. 有预期输出：跑完之后 stdout / 返回值长什么样，贴在代码后面。
# Python ≥ 3.9；redis-py 5.0.1
import redis

client = redis.Redis(host="127.0.0.1", port=6379, decode_responses=True)
client.set("session:42", "active", ex=900)   # 900 秒后自动过期
print(client.ttl("session:42"))
# 预期输出：899

参数注释写的是"为什么"

字段名和类型看一眼就知道，注释要给的是看代码看不出来的信息：单位、边界、为什么是这个默认值。

@dataclass
class TimeoutConfig:
    connect_timeout: float = 3.0
    # 单位：秒。拨号阶段超时，不含 TLS 握手。
    # 3s 而非 30s：跨机房建连 P99 为 1.2s，超过 3s 基本等于网络已断，
    # 快速失败让上层的重试逻辑接管（见 docs/retry-policy.md）。

    read_timeout: float = 10.0
    # 单位：秒。建连后两次收包之间的最大间隔，不是整个请求的总耗时。
    # ⚠️ 必须 < 上游 Nginx 的 proxy_read_timeout(15s)，否则超时发生在哪一层不可控，
    #    排障时会互相甩锅。这是踩过的坑，别改小注释不通知 SRE。

反例：坏示例长什么样

❌ 修改配置文件中的相关参数，重启服务即可生效。
❌ // TODO: implement here（教程挖坑让读者自己填核心步骤）
❌ 用伪代码当真实 API 用：db.query("SELECT ...") —— 真实叫法不是这个
❌ 截图里带一个无法从文字复现的配置界面（截图不能代替文字，见反模式一节）

Docs-as-Code：把文档当代码管

文档腐烂的根源是"文档和代码分家"。解法是把文档纳入写代码的那套流程：版本管理、lint、CI、code review。这一步做完，前面所有规范才不是靠自觉。

仓库布局

项目文档的推荐布局（docs/ 与代码同仓、同 PR 演进）：
.
├── README.md              # 教程入口 + 一句话定位 + 指向 docs/
├── docs/
│   ├── how-to/            # 面向任务
│   ├── reference/         # 面向信息（可从代码注释生成）
│   └── explanation/       # 面向理解
├── scripts/
│   ├── generate-post.py   # 文档生成器（本博客就是这个模式）
│   └── check-links.py     # 死链检查
└── .github/workflows/docs.yml

Markdown lint 与 frontmatter

先把风格问题交给机器，别浪费 review 的人力在空格和列表符号上：

# .markdownlint.yml —— 收紧到能防住大半结构病
MD001: true        # 标题层级逐级递进，不许跳级
MD003: { style: atx }
MD004: { style: dash }
MD013: false       # 行宽交给编辑器，不禁
MD022: true        # 标题前后必须空行
MD024: { siblings_only: true }  # 允许不同父节下有同名标题
MD025: { front_matter_title: "^\\s*title\\s*[:=]" }  # h1 唯一，排除 frontmatter
MD028: true        # 块引用不能多空行
MD032: true        # 列表前后空行
MD041: true        # 文件必须以 h1（或 frontmatter title）开头

结构化元数据（标题、日期、分类）放 frontmatter，让生成脚本读，而不是从正文里正则抠——这是我把博客生成器从 v2 升到 v3 学到的最重要一课：

---
title: 技术文档编写指南
description: 一句话摘要，给列表页和 RSS 用
date: 2026-09-03 17:30:00   # 带时间：同一天两篇文靠它排序
category: 开发
tags: [技术写作, 文档规范]
slug: 自定义-url-片段
---

CI 校验：链接、示例、数字

死链检查是最小可行 CI。文档里的 URL 和文件路径全部用 markdown 链接写，机器才能扫：

# .github/workflows/docs.yml
name: docs
on:
  pull_request:
    paths: ["docs/**", "README.md"]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: markdownlint
        uses: DavidAnson/markdownlint-cli2-action@v16
      - name: 检查相对链接死链
        run: python3 scripts/check-links.py docs/ README.md
      - name: 示例代码语法检查（能 parse 才能谈可运行）
        run: |
          pip install "pyright==1.1.*"
          python scripts/extract-code-blocks.py docs/ --lang python > /tmp/snippets/
          pyright /tmp/snippets/

# scripts/check-links.py（简化版）
import re, sys, pathlib

LINK = re.compile(r"\[[^\]]*\]\((?!https?://)([^)]+)\)")  # 只看相对链接
bad = 0
for md in pathlib.Path(sys.argv[1]).rglob("*.md"):
    for target in LINK.findall(md.read_text(encoding="utf-8")):
        path = (md.parent / target.split("#")[0]).resolve()
        if not path.exists():
            print(f"❌ {md}: 链接目标不存在 -> {target}")
            bad += 1
sys.exit(1 if bad else 0)

Review 规则

PR 改了行为、接口或参数，必须同 PR 改文档，否则 review 直接打回。这条规则写进 CONTRIBUTING，由模板强制：

## PR 检查模板（.github/pull_request_template.md）
- [ ] 本 PR 是否改变用户可见行为/接口/配置？
- [ ] 若是：对应文档在哪个文件？（附 diff 链接）
- [ ] 新增错误信息是否已收录 docs/reference/errors.md？

常见反模式与解药

规范讲完了，这一节是真实尸体陈列。每种反模式都配可操作的解药。

反模式一：一次性文档

上线前突击写完，上线后再没人打开过。解药是把文档变更绑定到代码变更的触发条件上：CI 规则（上一节）、错误码表从代码注释生成、CHANGELOG 和文档同 PR。

反模式二：只写是什么，不写为什么

❌ "重试次数设为 3。"（三个月后没人敢动这个数字）
✅ "重试次数 3：覆盖瞬时抖动（占故障 92%）；第 4 次起的成功率增益 <1%，
   但最坏延迟翻倍。数据见 docs/explanation/retry-policy.md。"

"为什么"是文档里保鲜期最长的部分——参数会变，权衡的逻辑能活很久。

反模式三：复制粘贴漂移

同一份安装步骤抄在 README、官网和 wiki 三处，半年后三个版本互相矛盾。解药只有一个：单一事实源 + 引用。内容只存在一处，其他地方用链接或 include 指令引入。本博客的相关文章、索引页全是这么做的——所有列表由 generate-index.js 从文章 HTML 反向生成，绝不手写第二份。

反模式四：用截图代替文字

截图不能搜索、不能复制、界面改版即作废。截图只该用于"无法用文字描述的空间布局"，且必须配文字步骤：

❌ （一张 800px 的控制台设置页截图）"按下图配置"
✅ 1. 打开「设置 → 网络 → 高级」
   2. 「连接超时」填 3s（默认 30s，务必改小，原因见下文）
   ![超时设置](../images/timeout.png)   # 截图降级为辅助，不是主体

反模式五：完美主义瘫痪

"等 API 稳定了再写文档"永远不会写。解药是分层：先交参考层的骨架（哪怕每格只有一行），再补 how-to，解释层最后。一份粗糙但完整的地图，胜于一张永远在画的局部高清。

流图表也当作代码

流程图用 Mermaid 存在 markdown 里，跟着 git diff 演进，别贴白板照片。比如本博客的发文流水线：

flowchart LR
    A[写 article.md] --> B[generate-post.py]
    B --> C{本地校验<br/>h1 死链 体积}
    C -- 通过 --> D[git push]
    C -- 失败 --> A
    D --> E[线上 200 验证]

发布前检查清单

最后把全文压缩成一份可打印的清单。本博客发文的实际流程就是这张清单的具象化——写完文章跑生成脚本、本地 grep 校验、push、线上实测，一步不省。

## 发布前逐项打勾
### 定位
- [ ] 这篇属于教程/how-to/参考/解释中的哪一层？没有混层？
- [ ] 开头两行写清读者画像和前置条件？
### 结构
- [ ] h1 唯一、标题逐级不跳、超两屏有目录？
- [ ] 标题是动作短语（"部署到生产"，不是"关于部署"）？
- [ ] 有"验证成功"一节？
### 措辞
- [ ] 无"简单/显然/只需/将会"？
- [ ] 同一事物全文同一个名字？
- [ ] 所有版本、路径、参数精确可复制？
### 示例
- [ ] 代码块可运行：含 import、标版本、附预期输出？
### 工程
- [ ] markdownlint / 死链检查通过？
- [ ] 改动的接口/参数已同步更新对应文档？
