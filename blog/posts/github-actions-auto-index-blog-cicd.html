GitHub Actions 自动索引：我的静态博客 CI/CD 进化之路

📅 2026-07-04 13:50:50 ⏱️ 5 min read 👤 张小猛

为什么手动更新索引是个坑

我一直维护着一个 68 篇技术文章的静态博客。每写一篇文章，要手动更新至少 6 个文件：首页 index.html、博客列表 blog/index.html、搜索索引 articles-index.json、sitemap.xml、rss.xml、相关文章 related-posts.js。

这不是我的博客独有的问题——所有静态博客都会遇到。区别在于你是否意识到这已经是个自动化任务。

之前我的 generate-post.py 脚本虽然能自动完成这些更新，但问题在于：每次改模板、改样式、改索引逻辑，都要回刷全量文章。而且本地脚本和线上部署状态不一致——你在本地更新了 index.html，但如果之后 CI 又覆盖了一次，就出现冲突。

问题分解

静态博客的索引更新可以分为两类：

类型 内容 依赖 更新时机
文章级 文章 HTML 模板 + 内容 写文章时
站点级 首页/列表/RSS/sitemap/搜索索引 所有文章 文章变更后

文章级更新需要本地 markdown → HTML 转换，因为有模板渲染逻辑。

站点级更新本质上是"把已有的文章列表扫一遍 → 生成对应数据文件"。这完全可以在 CI 里做。

数据流设计

核心思路很简单：

  1. generate-post.py 只生成文章 HTML + 更新 related-posts.js
  2. generate-index.js 接管所有站点级更新——从 blog/posts/*.html 解析出所有文章元数据，全量重建
  3. GitHub Actions 监听 blog/posts/ 的 push，自动跑 generate-index.js，提交结果
本地写文章 → git push → CI 触发:
  1. node scripts/generate-index.js
  2. 生成 articles-index.json (搜索索引 + 标签云 + 归档 + 系列)
  3. 重建 blog/index.html (文章列表 + 分类按钮)
  4. 更新 index.html (首页大卡 + 最新列表 + JS数组)
  5. 生成 sitemap.xml + rss.xml
  6. git commit + push → Pages 自动部署

方案设计

为什么选择全量重建而非增量

增量更新的诱惑很大——只改一行，快。但问题很棘手：

  • 要判断文章是否已存在，需要解析 HTML
  • 排序逻辑变了怎么办？比如某篇文章改了日期
  • 模板结构变了怎么办？比如分类按钮从 <select> 换成了 <button> 列表
  • 删文章怎么办？

全量重建的好处：

  • 原子性：每次 CI 跑完，索引文件一定精确反映当前 blog/posts/ 的状态。没有"删了文章但列表还在"的幽灵问题
  • 幂等性：同样的输入（blog/posts/ 目录），同样的输出（所有索引文件）。不需要"检查是否存在 → 决定 insert/update"的分支逻辑
  • 可恢复性：索引文件坏了？rm index.html sitemap.xml && node generate-index.js 就恢复了
  • 一致性：删文章、改日期、换分类——任何变更都不会产生幽灵数据

增量更新需要维护状态（"这篇文章在 index 的第几行？"），而状态维护本身就是 bug 的来源。全量重建没有状态。

而且 68 篇文章的全量重建在 CI 上只需要 不到 1 秒。完全没有性能压力。

generate-index.js 实现

核心逻辑非常直白：

// Phase 1: 扫描所有文章，解析元数据
const files = fs.readdirSync(POSTS_DIR).filter(f => f.endsWith('.html'));
const posts = files.map(file => {
  const content = fs.readFileSync(path.join(POSTS_DIR, file), 'utf-8');
  const titleMatch = content.match(/<title>([^<]+)<\/title>/);
  // ... 从 HTML 中提取 title/date/tags/category/excerpt
  return { slug, title, date, category, tags, excerpt, readTime, url };
});

// Phase 2-6: 写入各种输出文件
rebuildBlogIndex(posts);   // blog/index.html
rebuildHomePage(posts);    // index.html
generateSitemap(posts);    // sitemap.xml
generateRSS(posts);        // rss.xml
// articles-index.json 在 Phase 1 排序后直接写入

整个脚本不到 250 行，纯 Node.js 无外部依赖。CI 上不需要 npm install。

解析 HTML 的元数据提取

从 HTML 中提取元数据用正则：

// 日期: <span>📅 2026-07-04</span>
const dateMatch = content.match(/<span>📅 (\d{4}-\d{1,2}-\d{1,2})<\/span>/);

// 标签: <span class="tag">Android</span>
const tagMatches = content.match(/<span class="tag">([^<]+)<\/span>/g);

// 分类: <span class="category-tag">前端</span>
const catMatch = content.match(/<span class="category-tag"[^>]*>([^<]+)<\/span>/);

// 描述: <meta name="description" content="...">
const descMatch = content.match(/<meta name="description" content="([^"]+)"/);

这种"数据在 HTML 里"的模式其实很适合静态博客——HTML 就是唯一的真相源。不需要额外的 frontmatter 或数据库。

处理排序的边界情况

排序规则：按日期降序，同日文章按 blog/index.html 原有顺序。

// 先构建"原顺序"映射
const htmlOrder = {};
let orderIdx = 0;
const linkRegex = /href="posts\/([^"']+\.html)"/g;
while ((match = linkRegex.exec(blogIndexContent)) !== null) {
  if (!(match[1] in htmlOrder)) htmlOrder[match[1]] = orderIdx++;
}

// 排序
posts.sort((a, b) => {
  const dateDiff = new Date(b.date) - new Date(a.date);
  if (dateDiff !== 0) return dateDiff;
  return (htmlOrder[a.slug + '.html'] ?? 9999) - (htmlOrder[b.slug + '.html'] ?? 9999);
});

第一次跑的时候 blog/index.html 是旧的，排出来的顺序和旧的一致。第二次跑的时候 blog/index.html 已更新，所以同日的顺序会稳定下来。

RSS 日期格式化的坑

RSS 规范要求 RFC 822 格式：Sat, 04 Jul 2026 00:00:00 +0800。

JavaScript 处理日期的坑不少。我踩了一个：

// ❌ 错误：Date 解析带时区的 ISO 字符串时有偏移
new Date('2026-07-04T00:00:00+08:00').getUTCDay() // → 5 (Fri)
                                                      // 因为 2026-07-04 00:00+08
                                                      // = 2026-07-03 16:00 UTC

// ✅ 正确：用本地时间构造函数
const [y, m, d] = '2026-07-04'.split('-').map(Number);
const localDate = new Date(y, m - 1, d);
localDate.getDay() // → 6 (Sat)

GitHub Actions workflow 配置

name: Update Blog Index & Cache Hash
on:
  push:
    branches: [main]
    paths:
      - 'blog/posts/**'
jobs:
  update-index:
    runs-on: ubuntu-latest
    permissions:
      contents: write    # ← 关键：允许提交回仓库
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - name: Generate blog index
        run: node scripts/generate-index.js
      - name: Update cache-busting hashes
        run: node -e '...'  # 计算 CSS/JS 的 MD5 hash
      - name: Commit and Push
        run: |
          git config user.email "github-actions[bot]@users.noreply.github.com"
          git config user.name "github-actions[bot]"
          git add -A
          git diff --staged --quiet || git commit -m "chore: auto-update blog index & cache hashes"
          git push

关键是 permissions: contents: write——允许 CI 提交回仓库。

另一个要点：GITHUB_TOKEN 的提交不会再次触发 workflow。这避免了"提交 → CI → 提交 → CI → ..."的死循环。

缓存哈希自动更新

CI workflow 还有个重要的副作用：自动更新 CSS/JS 的缓存版本号。

// CI 中的缓存哈希更新逻辑
function updateHtmlFile(htmlPath) {
  let html = fs.readFileSync(htmlPath, 'utf-8');
  html = html.replace(/(assets\/(?:css|js)\/[^"?]+)\?v=[a-f0-9]+/g, (match, assetPath) => {
    const hash = crypto.createHash('md5')
      .update(fs.readFileSync(assetPath))
      .digest('hex').slice(0, 8);
    return assetPath + '?v=' + hash;
  });
  fs.writeFileSync(htmlPath, html);
}

每次 CSS/JS 内容变化，引用它们的 HTML 文件中的 ?v=xxx 会自动更新，确保访客拿到的是最新版本。之前这个也要手动改或靠 Python 脚本处理。

模板与索引的解耦

模板（blog-post-template.html）决定文章的视觉呈现，索引（index.html / sitemap.xml 等）决定文章的发现路径。

这两者原本就是独立的变化维度：

  • 改样式：只影响所有文章的 HTML 生成，索引结构不变
  • 改索引逻辑：只影响站点级文件的生成方式，文章内容不变
  • 发新文章：既需要新文章 HTML，也需要更新索引

在旧的 "generate-post.py 一把梭" 模式下，这三个操作都混在一起。改模板后必须用 refresh-posts.py 回刷所有文章，但 generate-post.py 会再次修改 index.html——产生不必要的 diff。

解耦后：

模板变更: refresh-posts.py (只改文章) → generate-index.js (CI 改索引)
                            └──── 两个步骤，互不干扰 ────┘

流程对比

改前（写一篇文章的完整流程）：

# 1. 生成文章
python3 scripts/generate-post.py "标题" "描述" --tags "标签" --category 分类 --content article.md
# 这一步修改了：文章HTML、首页、列表、sitemap、rss、articles-index.json、related-posts.js

# 2. 手动检查（容易遗漏）
grep "标题" index.html blog/index.html  # 确认首页和列表已更新
grep "标题" sitemap.xml rss.xml         # 确认 sitemap 和 RSS

# 3. git diff 里一堆"自动化改动"
git status
# modified: blog/posts/xxx.html
# modified: index.html
# modified: blog/index.html
# modified: sitemap.xml
# modified: rss.xml
# modified: blog/articles-index.json
# modified: assets/js/related-posts.js

# 4. 提交（commit message 很难写清楚）
git add -A && git commit -m "new post: xxx" && git push

改后：

# 1. 生成文章
python3 scripts/generate-post.py "标题" "描述" --tags "标签" --category 分类 --content article.md
# 只修改：文章HTML、related-posts.js

# 2. 直接提交
git add blog/posts/ assets/js/related-posts.js
git commit -m "new post: xxx"
git push

# 3. CI 自动搞定剩下的，30秒后页面生效

git diff 再也不会超过文章内容本身的长度了。

速度

CI 全量重建耗时 < 5 秒（含 npm install）。实际上 generate-index.js 无外部依赖，去掉 npm install 后 < 2 秒。

本地感知的差异：从 push 到页面生效，前后没有区别（都是等 Pages 部署）。但本地操作简洁了很多——不用在 git diff 里翻找真正的改动。

还解决了什么附带问题

模板变更后的回刷不再冲突

之前改一次模板，需要用 scripts/refresh-posts.py 回刷所有旧文章，再手动执行 generate-index.js 更新索引。步骤多且容易漏。

现在：改模板 → 回刷文章 → node scripts/generate-index.js → push。CI 不会再产生额外冲突，因为它做的和你本地做的一模一样。

幽灵文章问题不复存在

删了 blog/posts/xxx.html 但忘了从列表/filter/sitemap/RSS 里删掉？不会再有了——generate-index.js 扫描的是 blog/posts/ 目录，删了文件就自动消失。

多设备协作的冲突消除

以前在另一台电脑上改了文章，push 回来后本地的 index.html 没更新就出现冲突。现在不会有这个问题——索引文件永远只在 CI 端生成。

本地工作副本里 index.html / blog/index.html / sitemap.xml / rss.xml 完全可以不关心，因为它们在任何设备上都是一样的内容（由 CI 决定）。

调试效率提升

以前想排查"为什么这篇文章没出现在博客列表"，要翻 generate-post.py 里的 update_blog_list 函数，看它是否检测到文章已存在、排序是否正确、是否触发了某个边界条件。代码路径长且散落在 Python 文件中。

现在只要看 generate-index.js 里的排序逻辑——因为它是全量重建，输入确定，输出就确定。出错了直接跑本地 node generate-index.js，看哪一步出了问题。

适用场景

这个方案适合：

  • 静态博客 / SSG（Jekyll / Hugo / Hexo 原理）
  • 文章数 100-1000 篇（全量重建 < 1s）
  • 有 GitHub Pages / Vercel / Netlify 部署

不适合：

  • 文章数 > 10,000 篇（全量重建可能超过 CI 时间限制）
  • 需要即时生效的场景（Pages 部署有 30-60 秒延迟）
  • 多人同时编辑同一篇文章（CI 提交可能冲突）

总结

把站点级索引生成从本地脚本迁移到 CI，是一个"做减法"的优化。每次写文章少改 5 个文件，少看 100 行 git diff，少担心漏了哪个索引。

核心原则：文章 HTML 是唯一真相源，所有索引都是衍生数据。衍生数据的生成应该是确定性的、可重复的、自动的。

代码在 GitHub：https://github.com/zzdbilly/loczb

如果你也在维护静态博客，不妨试试把索引生成放入 CI。这可能是你今年做的性价比最高的自动化。
