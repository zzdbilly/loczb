版本号不该手写：缓存失效应当由内容哈希推导

📅 2026-10-29 17:30:00 ⏱️ 14 min read 👤 张小猛
缓存 构建 静态站点 工程实践

先说结论：版本号是缓存键，不是给人看的注释

我对 ?v=1.2 这类东西有过很长时间的误解。我以为它是给人看的——告诉自己这个文件改到第几版了，出问题的时候好回滚。后来在一个静态站上被它咬了一口，才明白它真正的作用对象不是人，是缓存层：浏览器、CDN 边缘节点、Service Worker 的 Cache Storage，这些地方拿 URL 当键。

键在，命中；键变，穿透。版本号唯一的工作就是在内容变化的那一刻改变这个键，在内容没变的时候保持不变。它有没有语义、能不能读懂、是不是递增的，全都不影响它工作；它有没有跟着内容走，直接决定它工作不工作。

一次没被报错的失效

事故的形态特别安静。改了一个组件的 JS，本地构建通过，产物写进仓库，推送，CI 绿，部署完成。打开页面，看到的是旧样式。

不是构建错了，也不是部署没生效——文件确实换了。是请求根本没到源站：静态托管对静态资源下发的是

GET /assets/widget.js HTTP/1.1
Host: blog.example.com

HTTP/1.1 200 OK
content-type: application/javascript
cache-control: max-age=600

max-age=600 意味着十分钟内，边缘节点会直接用它手里的副本回答，不问源站。我推了新文件，用户拿到的还是十分钟前的那一份。等十分钟当然能好，但我是个急性子，改一次样式等十分钟看结果，这个反馈回路没法用。

缓存键的三条性质

把这件事抽象出来，一个能用的缓存键要满足三条：

性质 含义 违反的后果
确定性 同一份内容，任何机器、任何时间算出的键都相同 同一内容多个 URL，缓存被拆散，命中率归零
敏感性 内容一变，键必变 新代码配旧缓存，用户看到的东西和仓库里的不一致
幂等性 内容不变，键不变 每次部署都让全站缓存集体失效，回源打满

三条里最容易被忽略的是第三条——它不产生错误，只产生成本，所以没人报 bug。而没有版本号的裸引用，等于把这三条全交给 HTTP 头里的 max-age 去猜。

实验设置：只改一个颜色

为了把三种策略的差别摆清楚，我把同一个改动分别放进这三种做法里推演了一遍。控制变量只有一个：assets/theme.css 里一个主色值，从 #2b6cb0 改成 #2c5282。除此之外源码一字不动，只改这一行。

三种策略，分别对应三种给引用挂版本号的方式：

组 引用形态 版本从哪来
A widget.js?v=1.3 人手改数字
B widget.js?v=20261029T1512 构建那一刻的时钟
C widget.js?v=3f2a9c1b0d 文件内容的 sha256 前 10 位

改动面比想象中大

这个实验的麻烦之处在于：要改的 CSS 并不在 HTML 里。它是组件自己在运行时注入的——widget.js 里有一个常量记着样式表路径，脚本加载后 document.createElement('link') 把那个 URL 挂到 head 上。

于是「改一个颜色」这件事，实际上要牵动三处引用：

  • theme.css 自己的 URL（拼在 widget.js 的常量里）
  • widget.js 的 URL（拼在全站每个 HTML 的 <script src> 里）
  • 上面两处之间的依赖关系——第二处的哈希必须在第一处落盘之后才算得出来

这不是我设计的复杂度，是浏览器缓存的粒度决定的：缓存按 URL 走，而 URL 分散在三个层次里。任何策略都得面对这条链，区别只在于由谁来维护它。

判分标准

每组看三个维度：一是这次改动能不能让用户看到新颜色；二是这次改动有没有波及没变的文件；三是这套机制失效时，会不会有东西报错。第三项权重最高，因为前两项我可以手动验，第三项不行。

实验 A：手写递增

最朴素的做法。?v=1.2 改成 ?v=1.3，提交。没有脚本、没有依赖、不需要构建流水线配合，改完就能看。

它解决了什么

它确实解决了冷启动时的问题：只要我改了数字，URL 就变了，缓存就失效。只发生一次改动时，A 组的表现和 C 组没有区别——两者都让用户看到了新颜色。

它还有一个真实的好处：人能读懂。v=1.3 告诉我这是第三次修订，v=1.2 告诉我上一版是什么。排查线上问题时，这个信息有用——虽然它不精确，但足够定位个大概。

它引入了什么

问题出在第二次、第三次、第十次。手写数字的可靠性等于人的记性，而人的记性在重复劳动里衰减得很快。

失效有两种形态。第一种是忘了改：改完 CSS，构建，推送，数字还是 1.3。URL 没变，边缘节点继续吐旧文件。整个过程没有任何一步会失败——构建成功、部署成功、HTTP 200，唯一错误的是用户看到的颜色。这是最难查的一类 bug，因为所有自动化都在告诉你「一切正常」。

第二种更隐蔽，是改漏了。全站一百多个页面，每个页面都有一个 ?v=。手动改的时候，编辑器只会告诉你替换了多少处，它不知道总共该有多少处；漏掉的那些还停在旧 ?v= 上。这时候站内是分裂的：

页面 引用 用户实际拿到
首页 widget.js?v=1.3 新文件
文章页（大部分） widget.js?v=1.3 新文件
文章页（漏改的那些） widget.js?v=1.2 旧文件，十分钟后才新

同一个站，同一个组件，一部分用户看到新颜色，一部分看到旧的。这种状态在监控上完全不可见——它不产生 5xx，不产生慢请求，只产生「我这边看着是好的」这类对话。

漏改的第三副面孔

还有一个我起初没想到的：这行数字是共享的可写状态。版本号常量被复制到了一百多个文件里，于是它成了一个没有单一来源的字段。两个人同时改样式，一个人把 1.3 改成 1.4，另一个人从 1.3 改成 1.5，合并时冲突，解决冲突的人多半会选一个，然后丢掉另一个人的改动。

手写递增的本质问题是：它把一个由内容决定的事实，交给了一个由人决定的状态。事实没有歧义，状态有。

实验 B：时间戳

第二种做法看起来聪明得多。构建时把当前时间写进 URL，?v=20261029T1512。不用人记，不用人改，构建一次变一次。

它解决了什么

它一次性干掉了 A 组的两种失效。忘了改？不存在，脚本生成。改漏了？不存在，全站由同一次构建写同一批文件。从「人会不会记得」这个角度看，B 组是彻底正确的——它把版本号从人工维护变成了自动推导。

如果只考虑「会不会漏」，B 组就是终点。

它引入了什么

它违反的是三条性质里的第三条：幂等性。内容没变，键也变。

想象一个平常的下午，我只改了一篇文章的错别字。构建跑起来，时间戳变了，于是全站每篇文章引用的 widget.js?v=... 都变了。一百多个 HTML 文件的 URL 全部是新键，所有用户的缓存全部失效，边缘节点回源拉一遍——尽管那个 JS 的字节一个都没动。

单次成本不大，一个静态站撑得住。但它把缓存从「复用」变成了「摆设」：反正每次部署都会失效，缓存命中率就只能靠部署频率反比来决定。部署越勤，缓存越没用；而部署越勤，恰恰越需要缓存的保护。

更麻烦的是第二层：同一份源码，两次构建得到不同 URL。这破坏了可复现性。我没法用「构建产物是否逐字节一致」来判断这次部署到底改了什么，因为构建本身就引入了差异。排查线上问题时，我失去了一个有用的信号——「产物一样」本来可以证明「这次改动没影响前端」，现在它永远为假。

还有一个小的：时间戳不单调可靠。CI 跑在不同机器上，时钟有偏移，机器 A 构建的 1512 可能晚于机器 B 构建的 1537。URL 的先后顺序和内容的先后顺序不再对应，回滚时看着一串时间戳，判断不了哪个是「更早的版本」。

它不是错，是维度错了

我想公平地说 B 组：它没有做错任何事，它只是回答了一个不同的问题。

时间戳回答的是「这份文件是什么时候产出的」。这是个有意义的问题，日志、审计、缓存 TTL 估算都要它。但缓存键要回答的是另一个问题——「这份文件的字节和上次是不是同一批」。两个问题在大多数时候答案同步，在「构建了但内容没变」的时候分岔，而分岔的那一侧恰好是缓存最需要正确的场景。

用一个产出的时间当内容的指纹，是把时间维度当成了内容维度。它自动、它可靠、它不漏，但它指向的东西不是缓存关心的东西。

实验 C：内容哈希

第三种做法：URL 里挂文件内容的 sha256，取前 10 位十六进制，40 bit。

它解决了什么

三条性质同时成立，而且不是靠纪律成立的，是靠构造成立的。

内容不变，哈希不变——同一个文件在任何机器、任何时间算出来都一样，所以构建一百次得到同一个 URL，缓存一直有效。内容变一个字节，哈希必变——所以键必然更新，不存在忘记。两者是同一个函数的两面，中间没有人的位置。

这也让「构建产物是否一致」重新变成一个可用的断言：如果两次构建的 HTML 逐字节相同，那就真的什么都没变；如果不同，差异一定来自内容，不来自时钟。

为什么是 10 位而不是更长？这是概率和体积的折中。40 bit 的空间，在一万个文件量级上碰撞概率可以忽略；代价只是 URL 长 10 个字符。站上另一个脚本用的是 8 位——那是够用的，我这里多取 2 位，纯粹是把碰撞概率再压一个量级，因为多两个字符的成本实在可以忽略。反过来说，如果哪天文件数量涨到百万级，10 位就该重新算一遍，别把这个数字当成常量信仰。

它引入了什么

代价有三个，都真实。

第一，哈希不表达顺序。3f2a9c1b0d 和 8e1d4f7a22 谁新？看不出来。想回滚到上一版，不能靠读 URL，得靠 git 或者一份版本清单。这是把可读性换成了正确性——我认为值得，但要承认它是个损失。

第二，哈希对无关改动过度敏感。改一个空格、加一行注释、动一下行尾符，哈希全变，缓存全失效。这个敏感性和 B 组的方向相反：B 组是该变的不变也变，C 组是该不变的一变就变。区别是 C 组的「变」总是对应真实的字节变化，我可以控制字节，控制不了时钟。

第三，也是最要命的一条：哈希有依赖顺序。widget.js 里存着 theme.css 的哈希，所以 widget.js 的哈希取决于 theme.css 的哈希。你不能同时算两个——先算谁？这个问题在 A 组和 B 组都不存在，因为它们不读内容。

三级推导链：先落盘，再算下一级

依赖顺序是这个方案唯一需要设计的地方，也是它唯一会出错的地方。我把整条链写成一个脚本，顺序是死的：

// scripts/sync-version.js —— 先落盘第一步，再算第二步
const crypto = require('crypto');
const fs = require('fs');

const HASH_LEN = 10;
const sha = (file) => crypto
  .createHash('sha256')
  .update(fs.readFileSync(file))
  .digest('hex')
  .slice(0, HASH_LEN);

// 逐字节比对：内容没变就不落盘，这是幂等的来源
function patch(file, re, repl) {
  const before = fs.readFileSync(file, 'utf8');
  const after = before.replace(re, repl);
  if (before === after) return false;
  fs.writeFileSync(file, after);
  return true;
}

// 第 1 步：CSS 的哈希写进组件里的常量
const cssVersion = sha('assets/theme.css');
patch('assets/widget.js',
  /(const CSS_PATH = '\/assets\/theme\.css)(\?v=[0-9a-f]+)?';/,
  `$1?v=${cssVersion}';`);

// 第 2 步：改完再算 JS 的哈希（此时 JS 已经包含新的 CSS 版本）
const jsVersion = sha('assets/widget.js');

// 第 3 步：把新版本写进全站 HTML 的引用
for (const page of htmlFiles()) {
  patch(page, /(widget\.js)(\?v=[0-9a-f]+)?"/, `$1?v=${jsVersion}"`);
}

为什么顺序不能反

假设反过来：先算 widget.js 的哈希写进 HTML，再去改 widget.js 里的 CSS 版本。第一步算出的哈希对应的是「还没更新的 JS」，第二步改完 JS，那个哈希就过期了。结果是 HTML 指向 js?v=A，而 A 这个键下的文件其实是 B 的内容。浏览器按 A 请求，边缘节点按 A 缓存——它缓存的是一份谁都说不清版本的字节。

更糟的是这种状态会稳定下来：再跑一次脚本，第一步重算 JS 哈希（此时已经包含新 CSS 版本），写进 HTML，看起来修好了。但只要顺序不变，下一次改 CSS 又会制造同样的半新状态。它不是偶发 bug，是设计缺陷。

一遍收敛的条件

正确的顺序满足一个性质：每一级的输入在算它之前已经终态。

  1. theme.css 是叶子，没有依赖，直接算。
  2. 把结果写进 widget.js，落盘。此时 widget.js 终态。
  3. 算 widget.js 的哈希，写进 HTML，落盘。

三步走完，全站一致，一次构建收敛。不需要迭代到不动点，因为依赖图是一条链，不是环。这也解释了这套东西能做成脚本：图是线性的，顺序能写死。

如果哪天组件之间互相引用（A 引用 B 的版本，B 又引用 A 的），这个方案就得换成拓扑排序加不动点迭代。我做的时候特意把依赖限制成单向的，就是为了避开那一层。

门禁：把「忘了跑」变成构建失败

脚本写得再对，还是有一步人要做：在部署前跑它。这一步只要存在，就会有人忘——包括我自己。

所以真正的保障不是脚本，是断言。校验脚本里有一条硬检查：

// scripts/verify.js —— 引用版本必须等于当前内容哈希
const expected = sha('assets/widget.js');           // 用当前文件现算
const html = fs.readFileSync('blog/posts/example-post.html', 'utf8');
const m = html.match(/widget\.js\?v=([0-9a-f]{10})/);

if (!m) {
  console.error('页面里没有带版本号的组件引用');
  process.exit(1);
}
if (m[1] !== expected) {
  console.error(`版本号不匹配：HTML=${m[1]} 实际内容=${expected}`);
  console.error('改完组件后忘了跑 scripts/sync-version.js');
  process.exit(1);
}

这里的关键是期望值现算，不是从别处读。如果断言去对比「HTML 里的版本」和「某个 version 文件里的版本」，那两者可以一起过期——两个错的数字相等，断言通过。只有拿当前文件的字节重新算一遍，断言才有意义。

断言写在哪个位置

放在 CI 和本地都要跑的那条路径上，紧挨着构建。我的顺序是：编译 → 同步版本 → 校验。同步在校验之前，所以正常情况下校验总是通过的；它拦的不是「脚本写错了」，是「脚本没跑」。

这个区分很重要。门禁不是用来发现逻辑 bug 的——逻辑 bug 该由测试发现。门禁是用来兜住「流程被跳过」的，它的价值全在于在人偷懒的时候仍然执行。一条永远不会失败的断言没有意义；一条只在我记得跑的时候才跑的断言，和没有断言一样。

不静默跳过

脚本处理异常的方式，决定了它能不能被信任。我给自己定了两条：

  • 找不到锚点常量——比如有人重命名了 CSS_PATH——报错并非零退出，不打印一句警告就继续。
  • 正文之外出现裸引用（有 <script src> 却没带 ?v=），同样报错。因为那意味着有页面逃出了同步范围。

这两条都是「宁可红，不要绿得可疑」。一个默默跳过的脚本会让人产生「已经在保护我」的错觉，而它实际上什么都没做。这类错觉比没有脚本更危险，因为它会让人停止检查。

顺带一个实现细节：匹配引用时必须排除 <pre> 区间。文章里贴的示例代码是转义过的 <script src>，如果正则不剥掉代码块，脚本会去改写正文里的示例——这既污染内容，又让哈希算不准。

一次真实事故：算得对，不等于传得全

这套机制上线一段时间后，我以为它已经闭合了。然后一次改版暴露了另一层问题。

改版完成后，全站重新构建，版本号算得没错，校验也绿。推上去之后，抽查了几篇文章，页面引用的版本号还是旧的。数了一下，36 个页面。

36 个全部是中文文件名的文章页。

根因不在哈希

根因在 git。仓库默认开着 core.quotepath=true，非 ASCII 路径在 git status 的输出里会被转义成八进制转义序列，并且整体加引号：

# 不可靠：core.quotepath=true 时非 ASCII 路径被转义
git status --porcelain | awk '{print $2}'
# "blog/posts/\344\270\255\346\226\207.html"

# 可靠一：-z 用 NUL 分隔，不做路径转义
git status --porcelain -z | tr '\0' '\n'

# 可靠二：直接按目录 add，别拼文件名
git add -- blog/posts

我用 awk '{print $2}' 拼 add 列表，拼出来的是一串带转义的假路径。git add 对不存在的路径只会抱怨一句，然后跳过——它不中断，不返回非零，不阻止提交。于是那 36 个文件压根没进那次提交。

它们没进提交，意味着它们还停在旧版本号上。站上于是同时存在两批页面：一批指向新哈希，一批指向旧哈希。后者因为键没变，边缘节点继续吐旧资产——看起来像缓存没生效，实际是文件没上传。

两条不同的链路

这次事故教会我一件事：这套机制有两个环节，它们失效的方式完全不同。

环节 做什么 失效时的表现 靠什么兜住
推导 算哈希、写引用 键是旧的，内容变了 门禁断言（现算比对）
分发 把改过的文件传上去 一部分文件没传，站内分裂 只能靠「改完核对工作区为空」

第一环我做了门禁，第二环我只做了「应该没问题」的假设。而 git add 的静默跳过恰好落在假设的位置——它不报错，所以我看不到它。

修法是把「add 完工作区为空」变成硬检查：git status --porcelain 的输出行数必须为 0，不为 0 就说明还有产物没进暂存区，先补齐再提交。加上仓库的提交钩子会在提交前重跑一次构建再比对暂存区与工作区，这条漏就堵住了。

这条教训超出了缓存的范畴，但我觉得它是这套方案里最值得记的一条：自动推导的版本号只解决「算得对」，不解决「传得全」。键的正确性由哈希保证，键的覆盖范围由分发链路保证，后者自己也会漏，而且漏得没有声音。

判据：什么时候该把键交给内容

三组实验跑完，我不认为内容哈希是普适答案。它适合的场景有明确的轮廓。

该用的场合

  • 引用是静态的、可枚举的。版本号写在 HTML 里，或者写在某个常量里，构建时能遍历到。如果你的引用是运行时拼出来的（比如从接口拿配置），哈希链就没法闭合成一条固定的链。
  • 内容变化需要立刻生效。样式、交互脚本、Service Worker 这类东西，用户晚十分钟看到新版本，可能就是「改了个 bug 但用户还在踩」。
  • 构建必须可复现。需要靠「产物是否逐字节一致」来判断改动影响的场合，时间戳方案会把这个能力废掉。
  • 缓存命中率有价值。静态站尤其如此——回源成本、首屏时间、边缘节点的带宽，都吃命中率。

不该用的场合

  • 内容几乎不变。给一个三年没动过的图标库做内容哈希，收益接近零，只是多了一层要维护的脚本。
  • 构建时间本身就是需求。有些场合需要知道产物的产出时刻，那就该用时间戳，只是别把它当缓存键用——两个字段可以共存，?v=<hash>&t=<buildtime> 不是不行。
  • 依赖图会成环。互相引用的组件，哈希链要拓扑排序加迭代，成本超出收益，这时候该退回手工维护加门禁，而不是硬套。

一条更朴素的判据

如果只能记一条，我记这个：问自己「这个版本号在内容没变的时候会不会变」。

会变，那它就不是缓存键，是时间戳伪装成缓存键——代价是每次部署全站失效。不会变，但不是因为内容没变、而是因为你忘了改，那它是一份人工维护的谎言——代价是用户拿到旧文件，而且没有任何东西会报错。

只有「内容不变它就不变、内容一变它必变」这一种，才是键该有的行为。这个条件没法靠纪律满足，只能靠函数满足。

收束：让 URL 承担缓存失效的责任

把这件事从头捋一遍，我发现真正的分界线不在「用不用哈希」，而在缓存失效的责任放在哪一层。

放在 max-age 上，等于说「十分钟后自然就好了」——这是一种放弃，接受一段时间的状态不一致，把它当成成本。放在人手上，版本号就成了一份要记住的约定，而约定会过期。放在内容上，URL 自己变成了失效信号：只要内容变，URL 就变，缓存层不需要知道发生了什么，它只要按 URL 工作就行。

第三条路的代价是引入一条推导链、一个同步脚本、一条门禁断言，以及一次因为 git 转义漏了 36 个文件的事故。这些成本是真实的。但它换来的东西是一种不需要记住的正确性——我不再需要在改完样式后提醒自己「记得改版本号」，因为这个动作已经从流程里消失了，变成了构建的一部分。

手写 ?v=1.2 的问题从来不是它不好看，是它把一个客观事实交给了主观状态。事实可以算，状态会忘。凡是能被算出来的东西，就别让它停在人的记性上——缓存键只是这条原则最典型的一个落点，URL 里那 10 个字符，正好是它最便宜的实现。
