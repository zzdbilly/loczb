别人的一次改名，是你的全站停机：外部标识符的耦合半径

📅 2026-10-28 17:20:00 ⏱️ 15 min read 👤 张小猛
配置管理 部署 耦合 工程实践

一个改名的下午：我改的是别人的设置，停的是自己的站

事情的开头跟我自己的服务器没有关系。

我把 Cloudflare 账户的 workers.dev 子域改了个名——从旧账号名换成一个新名字。这个动作在控制台上是一次点击，语义上是一次「账户级设置变更」，影响面是「该账户下所有 Worker 的默认域名」。我当时心里的预期是：评论服务会换地址，我改一下前端就够了，十分钟的事。

十分钟之后，全站评论区坏了。

不是报错，不是 500，不是构建失败。是读者打开任意一篇文章，往下滚到评论区，看到一行「评论加载失败」。而我的构建、我的 CI、我的死链巡检、我的部署检查，全部是绿的。它们没有一个人在看我。

这件事的性质值得先说清楚，因为它决定了后面所有讨论的方向：我改的是别人家的一个设置，停的是我自己的站。 那个子域不是我控制的命名空间里的一个变量，它是 Cloudflare 账户的一个属性；它一变，所有挂在上面的地址同时变，而我的仓库并不知道这件事发生过。

一天下来，我在自己的项目里挖出 9 处需要跟着改的地方。9 处不是一个特别大的数字，但它分布得很有意思——从最前端的运行时请求，一直到我自己写给未来的「待办记忆」。我没有按文件清单去改，而是按离改名的距离去量：以那次改名为圆心，一圈一圈往外，看每一圈的半径有多长，以及每一圈的失效长什么样。

这篇就是那份测量记录。

圈层 漏在哪里 为什么容易被忘 失效时的表现
第一圈 · 运行时 评论组件里硬编码的 API_BASE 它在业务代码里，不像配置 评论区空白，无报错
第二圈 · 策略层 文章模板 CSP 的 script-src / connect-src 同一个值在同一个文件里写了两遍 请求被浏览器拦截
第二圈 · 策略层 18 个页面各自内联的同一份 CSP 不走文章模板，生成链覆盖不到 同上，且是逐个页面
第三圈 · 隐形文件 _headers 里的一份 CSP 对当前托管平台不生效 无表现，但文件公开可读
第四圈 · 衍生标识 同账户另一个 Worker 的项目链接 改名动机与它无关 两个死链
第五圈 · 看板与脚本 日报脚本读的 url 字段 数据在配置里，不在代码里 每天输出旧地址
第六圈 · 文档 源码 OG 标签、README、部署文档、技能文档 文档没人跑，自然没人验 读者与未来的自己走错

表里的顺序不是按修复难度排的，是按离圆心由近到远排的。越往外，越不疼，也越容易被留下来；但恰恰是最外圈的那些，会在半年后变成「为什么文档上写的地址打不开」这类没人认领的问题。

半径第一圈：运行时，前端一声不响地坏掉

一个字符串常量，决定了评论区能不能用

评论组件的初始化代码里，评论服务地址是一个字符串常量。

// 改造前的样子：地址直接写在组件里
const API_BASE = 'https://comments.<account>.workers.dev';

async function loadComments(slug) {
  const res = await fetch(`${API_BASE}/list?slug=${encodeURIComponent(slug)}`);
  if (!res.ok) throw new Error('comments unavailable');
  return res.json();
}

这段代码本身没有错。它错在把「外部标识符」当成了常量——而外部标识符的定义就是「它的值由别人决定」。旧地址在新子域生效的那一刻就不再解析，DNS 层面直接查不到，于是 fetch 抛出网络错误，loadComments 走到异常分支，UI 把错误吞掉，渲染成一句「评论加载失败」。

它坏掉的时候，没有任何一个监控在看

这一圈最值得记的不是「要改」，而是它为什么没有惊动任何监控。

我的构建是静态站点构建，它不执行浏览器里的代码；我的死链巡检扫的是仓库里的内部链接，管不到运行时的 fetch；我的部署检查比对的是线上和本地的文件哈希，两边都是同一个坏文件，自然一致。整条链路上有一个巨大的盲区：从「页面被正确部署」到「页面里的请求能成功」之间，没有任何东西在验证。

三件事确认它是真的活了

改到新地址之后，我做了三件事才算确认它真的活了，而不是「我觉得它活了」：

  1. 直接请求 API，看返回码与响应体，确认服务端在新地址上是通的。
  2. 在真浏览器里打开一篇文章页，看 Network 面板里那条评论请求——实测 436ms 成功返回，列表正常渲染出条目。
  3. 确认数据没丢：评论在 D1 里按文章 slug 存储，跟域名无关，改名只换了入口，没换家。

第三点是我当时最担心的。事后看，它也是这次事故里唯一让人松口气的部分：入口地址和存储键是两套标识符，它们没有耦合在一起。 如果当初我把评论按「完整 URL」当键存，这次改名就等于把全站评论清零，那才是真的停机。

半径第二圈：策略层，一个地址在同一个文件里写了两遍

script-src 与 connect-src，各自记了一遍

修好前端之后，我以为结束了。然后控制台报了 CSP 违规。

内容安全策略是一份白名单：它告诉浏览器「这个页面允许从哪些源加载脚本、允许向哪些源发请求」。评论服务的地址必须同时出现在两个指令里——script-src（加载 SDK）和 connect-src（发起 XHR/fetch）。也就是说，同一个值，在同一个文件里，被写了两遍。

Content-Security-Policy: default-src 'self'; script-src 'self' https://comments.<account>.workers.dev; connect-src 'self' https://comments.<account>.workers.dev; img-src 'self' data:; style-src 'self' 'unsafe-inline'

这一圈的特点是：它不是「忘了改」，而是「改了一遍以为改完了」。 前端改完、页面能加载、SDK 脚本也能下下来，但请求发不出去——因为 connect-src 还是旧的。表现上跟第一圈几乎一样（评论区空白），排查方向却完全不同。这就是副本的代价：两份副本让你有两次机会只改一半。

模板之外的 18 个页面，生成链覆盖不到

更麻烦的是第二圈的下一层。我的文章页由模板生成，模板里的 CSP 改一处，所有文章页跟着变——这部分是可控的。但站上还有一批页面不走文章模板：首页、关于页、项目页、404、离线页，以及从第 2 页到第 13 页的分页列表。这些页面各自内联了同一份 CSP，一共 18 个文件。

它们由索引重建脚本产出，而索引重建脚本不读文章模板。也就是说，生成链覆盖不到它们——不是「脚本有 bug」，是这些页面的 CSP 从一开始就是复制粘贴出来的字面量，从来没被参数化。我最后是逐个页面改的，因为改生成脚本的风险（影响 18 个页面的结构）大于改 18 处字符串的风险。这是一次有意识的妥协，不是最优解。

半径第三圈：隐形文件，不生效但公开可读

一个对当前平台不生效的文件，为什么还要改

仓库里有个 _headers 文件。

它的用途是给 Cloudflare Pages 用的：Pages 支持用一个纯文本文件声明响应头，包括 CSP。而我现在的托管是 GitHub Pages，完全不认这个文件——它不生效，不在任何请求路径上，也不被任何页面引用。

按「生效路径」去排查，它根本不该出现在清单里。但它在仓库里，而仓库是公开的；我用浏览器直接访问那个路径，返回 200，内容明明白白写着旧子域的 CSP。

这一圈暴露的是一个判断错误：我把「不生效」和「不重要」当成了同一件事。

对功能而言它确实不重要——改不改，站点行为一样。但对另外两件事它很重要：

  • 它是给别人看的。任何人（包括未来的我）读这个仓库，会认为这是这个站点的头部策略声明。里面写着旧地址，就是一份错误的现状描述。
  • 它是为迁移准备的。哪天真的迁到 Pages，这个文件会立刻变成生效路径，而那时候没人会记得它里面有个过期域名——它会在迁移当天制造一次「怎么刚迁完评论就坏了」的二次事故。

从「生效路径」换到「仓库视角」

第三圈之后我调整了排查顺序：不再只问「哪些地方在生效路径上」，而是问「哪些地方写着这个值」。前者是运行时视角，后者是仓库视角。改名这类事件，仓库视角才是完整视角。

半径第四圈：衍生标识，你只是想改评论，却打断了另一个项目

你只改了评论，它顺手打断了另一个项目

这一圈是我当时最没有预期到的。

同一个 Cloudflare 账户下，我还跑着另一个 Worker：一个用来临时分享文本的 pastebin。它在我心里的定位是「跟博客无关的独立小工具」。改名之后，它也跟着换了地址——因为 workers.dev 子域是账户级的，不是 Worker 级的。

结果是我博客首页和项目页上的两个项目链接变成了死链。

请注意这里的因果结构：我改名的动机跟 pastebin 毫无关系，但改名顺手把它打断了。 我不是「忘了改 pastebin」，我是「根本不知道 pastebin 在这个半径之内」。它的地址出现在我博客的 HTML 里，这一条引用关系把两个本来独立的项目连成了一条耦合链——而这条链在我做决策时不在我的视野里。

副本与派生：两种性质不同的漏法

第四圈和前三圈的性质不同。前三圈是「同一个值的多份副本」，第四圈是「同一个源派生出的多个值」。前者靠 grep 旧值能全部找出来；后者要靠理解「这个账户级设置还影响了谁」，grep 只能帮你确认影响面，不能帮你发现影响面。

我后来的做法是：改这类账户级设置之前，先列出该账户下的所有服务，再看每个服务的地址在自己的哪些仓库里被引用过。这一次我是反过来的——先改，再发现。顺序错了，代价就是两个死链挂在那儿，直到我自己点了一下。

半径第五圈：看板与脚本，日报每天都在念旧地址

地址集中在一处，漂移还是会发生

我的日报脚本从一份项目清单里读 url 字段，拼成当天要汇报的链接。

# 项目清单：地址集中在一处，脚本不写死链接
projects:
  - name: loczb
    url: https://709527.xyz
    repo: nook/loczb
  - name: pastebin
    url: https://pastebin.<account>.workers.dev
    status: active

这份清单的设计其实是对的：地址集中在一处，脚本不硬编码。问题在于——它集中的是「我关心的那些地址」，不是「所有地址」，而且它没有任何机制保证自己跟现实同步。改名之后，清单里的值没变，脚本照常运行，日报每天输出一个已经打不开的链接，输出得很稳定。

对账要测现实，不是测记忆

这一圈的教训不是「配置要集中」（那部分我早就做了），而是：集中之后还需要一条「与现实对账」的路径。 配置是声明，现实是事实，两者之间的漂移是静默的——声明不会自己发现自己是错的。对账可以很土：定期把那批 URL 全部请求一遍，看返回码。土办法的价值在于它测的是现实，不是我的记忆。

半径第六圈：文档，一份写着不存在的子域的部署文档

三种形态：旧值、新值、以及一个拼错的变体

文档这一圈最不缺，也最不值钱——因为没人跑它。

我盘出来的有：pastebin 源码里的 og:url、它的 README、一份私有部署文档 DEPLOY.md、三个技能文档、工作区 README、还有项目总览的记忆文件。

其中 DEPLOY.md 值得一提：它里面写的地址，是一个根本不存在的子域变体——不是旧值，也不是新值，是某次手抄时拼错的第三种形态。这份文档从来没有被验证过，因为它描述的操作我已经很久没做了。

这说明文档的失效模式跟代码不一样。代码写错了，跑一次就报错；文档写错了，只有在有人照着它做的时候才会暴露，而那时候暴露的形式是「照文档做不通」，责任人会以为是自己的问题。

文档失效只在有人照着做时暴露

我对文档的处理原则因此改了一条：凡是包含外部标识符的文档，标识符必须来自可复制的单一位置，而不是手打。 手打一个域名，出错概率不高，但错了不会有人告诉你。

半径最外圈：记忆与状态，一条差点被写成「现状」的待写入记忆

记忆的语法是陈述句，没有时间戳

最后一圈最阴。

我有一条待写入的记忆，内容是：「旧子域暴露在 143 页里，需要 token 才能改，暂不处理。」

这条记忆写于问题解决之前，描述的是当时的判断。事情在一天之内就解决了——143 页全部换成了新值。如果这条记忆按原样写进去，它会变成一条假事实：一个已经过期的结论，以「现状」的语法被存储下来，然后在未来某次决策里被当成前提引用。

记忆层的危险不在「记错」，而在记忆的语法是陈述句，没有时间戳语义。代码里的注释过期了，你读的时候知道它是注释；记忆过期了，你读的时候以为它是事实。它的失效是无声的，而且它会自我强化——基于它做出的决策，又会变成新的记忆。

把状态改写成事件

我最后没写那条，改写成了「已处理 + 处理方式 + 验证手段」。差别在于：前者是一个悬而未决的状态，后者是一个已关闭的事件。状态会被继承，事件不会。

为什么漏：不是马虎，是同一个值被写了 N 遍

每一份副本，在当时都是合理的决定

把七圈摊开看，我漏的原因只有一个，而且它不在任何单独一圈里。

这个值在我系统里存在 9 份副本，没有一份是「源」。

不是我不小心。恰恰相反，每一份副本在当时都是合理的决定：把地址写在组件里，是因为组件要独立可用；把 CSP 内联在页面里，是因为静态站点没有服务端可以统一注入；在文档里手打地址，是因为写文档的时候地址就在浏览器标签页上。每一个决定单独看都说得通，合起来就是一个改了要改 9 次、且没有任何机制提醒你漏了第 7 次的结构。

副本数与漏的概率不是线性关系，是指数式的心态关系：改完前 5 处，你会产生「差不多都改完了」的确定感，而剩下 4 处正好落在你没在看的圈层里。确定感本身是漏的原因之一。

每份副本都是一次发布权的让渡

还有一层更结构性的话要说：每一份副本，都是一次发布权的让渡。

地址写死在 9 个地方，意味着这个地址的任何变更都要经过 9 次人工操作才能落地——而这 9 次操作的触发条件，是「有人记得」。如果这个值由别人控制（比如账户子域），那么变更的发起权在别人手上，落地的执行权在我手上，两者之间没有任何自动连接。别人按一下，我要跑一天。这就是「别人的一次改名，是你的全站停机」在工程上的准确含义：不是他不该改，是我没有把「他改了」这件事变成「我的系统自动跟上」。

单点来源：把半径收到一个点上

目标：一个定义，其余全是引用

设计上的目标很明确：让这个值在全系统里只有一个定义，其余全部是引用。

构建时注入：把地址从代码里赶出去

静态站点没有服务端，最接近「运行时注入」的手段是构建时注入。地址从配置读，构建产物里写死——注意，产物里写死是没问题的，因为产物是生成物，下次构建会重新生成；有问题的是源文件里写死。

// 构建脚本里：一次读取，多处注入
const fs = require('node:fs');
const cfg = JSON.parse(fs.readFileSync('site.config.json', 'utf8'));
const commentsBase = cfg.services.comments.baseUrl;

const runtime = `window.__SITE__ = ${JSON.stringify({
  commentsApi: commentsBase,
  csp: `script-src 'self' ${commentsBase}; connect-src 'self' ${commentsBase}`,
})};`;
fs.writeFileSync('assets/site-runtime.js', runtime);

这段代码的价值不在技巧，在它把「两份副本」变成了「一次求值」。模板里 CSP 的两个指令都从同一个 commentsBase 拼出来，物理上不可能只改一半。

三种注入手段，按站点形态选

手段 适用场景 代价
构建时变量注入 静态站点、产物可重建 改值要重新构建并发布
CI 环境变量 同一份源码部署到多环境 本地构建与线上可能不一致
模板变量 / 配置中心 有服务端渲染或运行时配置 引入一个额外的可用性依赖

我用的是第一种，因为站点是纯静态的，产物本来就要重建。如果换成有服务端的形态，配置中心更合适——但要注意它会变成新的单点：配置中心挂了，全站起不来。收拢耦合不是消灭依赖，是把散落的依赖换成一个你知情的依赖。

什么该硬编码：少数不该动态化的地方

这里要公平一点，不然容易滑向「一切皆配置」的教条。

有几类值我仍然写死，而且认为写死是对的：

  • 规范里定义的常量。HTTP 方法名、状态码、协议前缀，这些不随部署环境变，抽成配置只是把常量搬到更远的地方。
  • 安全边界上的值。CSP 里 'self' 的有无、'unsafe-inline' 的开关，这类决定的语义是「我允许什么」，它应该被读到、被 review，而不是被一个环境变量在部署时悄悄替换。
  • 一次性脚本里的地址。跑完就删的迁移脚本，为了让它可配置而引入一套机制，是把成本花在了不会重复发生的地方。

判断标准不是「这个值会不会变」，而是「它变的时候，有没有第二个人需要知道」。需要，就单点来源；不需要，写死更诚实。

两个反直觉点

账户级设置的半径，大于你以为的范围

我改名的动机是「评论服务的地址不好看」，而我实际影响的是「该账户下所有 Worker 的默认域名」。

这里有个认知错位值得单独说：我在控制台上操作的对象是一个账户属性，但我脑子里想的是一个服务的地址。对象和心智模型不匹配，半径就会被低估一个数量级。

同样的结构在很多地方存在：改一个组织名，所有仓库的默认 Pages 域名一起变；改一个项目 ID，所有引用它的 webhook 一起失效；改一个数据库实例名，所有连接串一起断。平台把它们设计成全局的，因为它们本来就是全局的；而使用者往往把它们当成局部的，因为操作入口是局部的。 一次点击的界面尺度，跟它的影响半径没有关系。

失效是静默的

这一点比上一点更值得记住。

整个事故里，我没有收到任何一条告警。构建成功、部署成功、死链巡检通过、文件哈希一致。坏掉的东西是「浏览器里一个 fetch 返回了网络错误，而 UI 把它渲染成一句人话」。

静默失效的共同特征是：错误被捕获了，然后被翻译成了正常状态。 评论区的「加载失败」在视觉上跟「这篇文章还没有评论」几乎一样；项目页的死链在视觉上跟「链接有点旧」几乎一样。系统没有报错，系统只是安静地少了一块功能。

对抗静默失效的办法不是加更多日志，是加端到端的断言：不是「文件部署了吗」，而是「页面里的那个请求成功了吗」。前者我一直在测，后者我从来没测过。这次之后我加了一条最朴素的检查——定期把关键外部地址请求一遍，非 2xx 就报警。它拦不住所有问题，但它能拦住「地址已经不存在了而我还以为它在」这一类。

我用来盘副本的也是同一类土办法：

# 1. 旧值还剩几处（改完之后这一条必须是 0）
grep -rn --exclude-dir=.git --exclude-dir=node_modules \
  -e '<old-account>' . | wc -l

# 2. 新值铺开了几处（应与预期页数一致）
grep -rl --exclude-dir=.git -e 'comments.<account>.workers.dev' . | wc -l

# 3. 线上抽查：抓一批真实 URL 逐个看返回码
python3 - <<'PY'
import urllib.request as u, urllib.error as e
urls = ['/', '/blog/', '/about/', '/projects/', '/404.html']
for p in urls:
    req = u.Request('https://709527.xyz' + p, headers={'User-Agent': 'Mozilla/5.0'})
    try:
        print(p, u.urlopen(req, timeout=20).status)
    except e.HTTPError as ex:
        print(p, ex.code)
PY

第 3 条是我这次唯一算得上「验证」的动作：线上抓了 38 个 URL 逐个核对。38 不是全站，但覆盖了每一类模板产出的页面——比「首页能打开」有意义得多。

量半径的六条判据

六条问句，动手前先答一遍

下次遇到「某个外部标识符要变」，我会先回答这六个问题，再动手：

  1. 这个值在我的系统里有几份副本？ 不是「几个文件」，是「几处字面量」——同一个文件里写两遍算两份。
  2. 这些副本里，有几份在生效路径上？ 生效路径之外的（比如给未来用的 _headers）不算功能风险，但算现状描述风险。
  3. 这个标识符是哪个层级的？ 服务级、账户级、组织级——层级越高，半径越大，跟我的改动动机越无关。
  4. 同一个源还派生了哪些值？ 同账户的其它服务、同一项目的其它环境，它们有没有被我的站点引用。
  5. 失效会以什么形式出现？ 如果答案是「静默地少一块功能」，那它必须在改完之后被主动验证一次。
  6. 谁会读到这个值？ 只有构建进程，还是也包括人和未来的自己——后者的副本必须来自可复制的单一位置。

六个问题里，第 3 和第 4 个是我这次答错的。它们不涉及任何技术细节，只涉及「我知道自己在动什么吗」。

收束：这次改名的真正成本不是那 9 处修改

9 处修改加起来不到一小时。真正花掉一天的是发现：我不知道半径有多长，只能一圈一圈往外摸，每摸到一圈就以为到底了，然后被下一圈打回来。

这不是一次配置管理事故，配置管理只是它的表现形式。它的实质是：我的系统里有一批「我以为它是常量、其实是别人的变量」的东西，而它们之间没有任何一致性约束。 只要这个结构不变，下一次改名——不管是我的还是别人的——还会重演一遍，只是漏的那几处换一批。

所以这次之后我做的事很具体，也很无聊：把评论服务地址收进一份配置，让模板从它求值；把 18 个页面的 CSP 改成由生成脚本统一产出；把 _headers 和文档里的地址改成引用同一份配置；把「关键外部地址可达性」加进定期检查。

没做的是「建一套配置管理体系」。那需要我先证明自己有第二个消费方，而我现在只有一个。

如果要把这次的收获压成一句话：耦合半径不是由代码量决定的，是由这个值被写了几遍决定的。 写一遍，半径是一；写九遍，半径就是九，而且你只会记得前五遍。别人改一次名，你就要跑九趟——这不是他给你添麻烦，是你把发布权分九次交了出去。
