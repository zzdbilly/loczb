不会让流水线变红的检查，只是注释

📅 2026-11-17 15:01:00 ⏱️ 14 min read 👤 张小猛
CI 代码质量 自动化 工程实践

不会让流水线变红的检查，只是注释

最近一次全库隐私扫描的输出是 0 errors, warnings only，退出码 0——告警全部是绝对路径这类提示，没有一条是凭据。

那几条告警，从出现到现在，一条都没有被处理。不是它们不重要，也不是没人看见——它们就躺在每次构建的日志里，谁跑一次都能看见。问题是看见之后什么也不会发生：流水线照常变绿，提交照常通过，第二天的终端缓冲区里早就没有那几行字了。

这件事让我重新想了一遍「我们有检查」这句话。同一个词，在不同的实现里含义差得很远。有的检查会让一次提交被拒绝，有的检查只让日志多一行，还有的检查只活在文档的某一段里。它们都被叫做检查，但它们对现实的影响不在一个量级上。

我的结论是：检查的价值不在它写了什么断言，而在失败时会发生什么。 一行打印在日志里、退出码仍为 0 的告警，与一行注释在效果上没有区别——它把判断推给了「下次」，而「下次」不是一个时间点，是一个不会到来的日子。

一根滑杆，四个刻度

我把见过的检查按「失败时会发生什么」排成一根滑杆，从最弱到最强四档。需要说清楚：这是一根用来定档的分析尺子，不是实验数据，也不是什么行业标准。它的用处只有一个——把「检查」这个词拆开，逼自己回答「这条东西到底能拦住谁」。

每一档我都问三个问题：失败时发生什么、写出来的代价是多少、它能拦住哪一类错误。

档位 失败时的表现 谁能绕过 典型位置
第四档 约定 什么也不发生 任何人，不需要动作 文档、评审清单
第三档 告警 打印一行字，退出码仍为 0 任何人，不需要动作 只读扫描脚本
第二档 阻断 任务变红，动作停在本地 知道参数的人，一条命令 本地钩子、必过任务
第一档 不可绕过 请求被拒绝，本地状态无效 需要改共享配置或权限 服务端校验、共享流水线

这张表最容易被误读的地方是「强度」两个字。它不代表检查的质量，也不代表写它的人有多认真。第四档的文档可能写得比第一档的脚本更用心，但它仍然是第四档，因为它没有执行点。

下面从最强的一档往回走。倒着讲是有意的：先看清最强的那一档到底强在哪里，再回头看弱档缺的是什么。

第一档：绕不过去的失败

失败时发生什么

第一档的检查不在你的机器上执行。它执行在别人控制的机器上，或者执行在接收请求的那一侧。失败的表现不是「提示」，是「这个动作没有被接受」：合并按钮在检查通过之前不可用，推送在服务端被拒绝，构建根本没有开始。

这一档的关键不是「检查更严格」，而是执行点不在你的工作区。你本地删掉钩子、改掉脚本、加一个跳过参数，对这个检查没有任何影响，因为它读的不是你的本地状态。

它长什么样

两种形态最常见。

第一种是共享流水线上的必过任务。检查写在流水线配置里，分支保护把它设成必需项，红灯的时候合并入口是关的。它的执行环境是干净的容器，从远端拉代码，装依赖，跑脚本，退出码决定这一步的结论。

# pipeline.yml（示意，不是某个真实仓库的配置）
stages:
  - verify
  - build
  - publish

verify:
  script:
    - ./verify.sh              # 产物与源是否一致，不一致直接非 0
    - python3 scan.py --all    # 凭据与真实邮箱，命中即非 0
  allow_failure: false         # 这一行才是「阻断」和「告警」的分界

allow_failure: false 这个字段比上面所有脚本都重要。同一批脚本，把它改成 true，整段检查立刻从第一档掉到第三档——脚本没变，断言没变，只有失败之后会发生什么变了。

第二种是接收端的校验。推送被服务端拒绝，通常是因为历史里含了不该有的东西，或者权限不够，或者目标分支受保护。这种拒绝有一个特点：它不跟你商量，也不给你「继续」的选项。你在本地怎么折腾都没用，因为拒绝发生在你看不见的那一侧。

它适合拦什么

只装一类东西：漏过去就不可逆的错误。

凭据和真实个人信息是第一类。密钥进了公开历史，删文件不等于收回——旧的对象在托管方仍然可以被访问，正确的第一动作是轮换，而不是改写历史。数据写错是第二类，尤其是覆盖式的写：旧值没有副本，回滚脚本也拼不回来。产物与源不一致是第三类，它不会立刻造成损失，但它让「线上跑的是什么」这个问题失去答案，而这类问题往往在出事之后才被追问。

判断标准可以压成一句话：这个错误发生之后，我能不能用一条命令回到发生之前？不能，就归第一档。

它的代价

第一档的代价不是运行时间，是所有人的等待。每加一条，你就多了一个让整个团队停下来的理由。误报的代价不是「某人看一眼」，而是「所有人等某人看一眼」。所以这一档的规则必须少、必须确定、必须可复现——同一个输入跑两次结论一致，换一台机器结论一致。

一旦第一档开始误报，它就会被降级或者被绕过，而绕过第一档通常意味着改共享配置，那是比写检查大得多的动作。也就是说，第一档的误报会消耗掉这一档本身的信用。

第二档：会让流水线变红，但可以绕

一个钩子的三个逃生口

本地提交钩子是第二档的典型代表。它真的会阻断：检查不通过，git commit 直接失败，你得先处理才能继续。这个体验和第一档很像，直到你发现它有三个逃生口。

第一个是参数。--no-verify 一行就能跳过全部钩子，而这个参数在每个人的肌肉记忆里。

第二个是安装状态。钩子住在 .git/hooks/ 里，那个目录不会被提交，也不随克隆分发。换一台机器、重新克隆一次、换一个工作树，钩子就不存在了。除非有人专门写了安装脚本并且在文档里提醒，否则新环境默认是没有这道检查的。

第三个是路径。钩子只拦本地提交。如果流程允许直接推送到目标分支，那么本地一切检查都可以被整体跳过，服务端不会替你补跑。

git commit --no-verify -m "wip"    # 逃生口一：参数
ls .git/hooks/pre-commit           # 逃生口二：换机器后这里可能是空的
git push origin main               # 逃生口三：本地没装钩子时，没人拦

三个逃生口都不需要权限，也不需要理由。这就是第二档和第一档的真实差距：不是严格程度，是绕过的成本。第二档的绕过成本是一条命令，第一档的绕过成本是一次权限变更。

它真正的价值是反馈速度

第二档容易被低估成「弱一点的第一档」，但它解决的是另一个问题：把失败提前到你还记得自己改了什么的时候。

等第一档告诉你产物没同步，你已经在做别的事了，得重新把上下文捡回来。第二档在提交那一刻就告诉你，那时候改动还在脑子里，修起来是几分钟的事。同一类错误，被第二档拦住的成本远低于被第一档拦住，尽管第一档更可靠。

所以第二档不是第一档的替代品，是它的前置分流。

它适合拦什么

适合装「挡错了代价很小、挡漏了还有兜底」的规则：格式、构建产物与源是否同步、内链是否有死链、单元测试。

这些规则的共同点是修法明确。产物没同步，重跑一次构建；内链死了，改链接或者删链接；测试红了，看断言。挡错了重跑一次就好，不会有人因为被挡而损失什么。挡漏了也不要紧，因为合并前的共享流水线还会再跑一遍——那一遍才是第一档。

它最怕的不是绕过，是没人装

一个只有本地钩子的检查，实际覆盖率等于「装了钩子的人」的比例。而这个比例没有任何地方会告诉你。你以为有一道闸，其实是一张自愿签署的承诺书。

要让它变成真正稳定的第二档，安装动作得自动化：克隆之后跑一次初始化脚本，或者干脆把它写进项目的标准开发流程里。不然它的强度会随着人员流动和时间推移单调下降。

第三档：打印告警，退出码 0

五条告警的去向

回到开头那组数字。我的扫描器分两档：错误（凭据、真实邮箱）返回非 0 退出码，告警（例如源码里出现本机绝对路径）只打印一行，进程正常结束。

$ python3 scan.py --all
[ERROR] credentials / real mailbox : 0
[WARN ] absolute path in source    : 5
exit status: 0

最近一次全库跑下来是 0 个错误、5 条告警。这 5 条一条都没被处理，而且我能说清楚为什么：没有任何一个时刻需要有人处理它们。构建不会因此失败，提交不会因此被拒，报告不会因此变红。它们只是存在。

这不是纪律问题。即使我当天认真读完了 5 条，第二天新加的文件还会产生新的告警，而没有机制保证有人再看一遍。一条不影响任何流程的告警，它的读者是随机的。

告警的成本被记在了别人账上

第三档有一种奇怪的账目结构：写检查的人付出了实现成本，读告警的成本却摊给了未来每一个看日志的人，而且每个人看到的都只是一小段。

真正的问题不是噪音多，是噪音没有归属。错误有归属——流水线红了，必须有人修，修完才能继续。告警没有归属，它默认属于「以后」。而「以后」没有负责人。

为什么它和注释等价

一行打印在日志里、退出码仍为 0 的告警，与一行注释的差别只有一个：它消耗了一点运行时间。两者都不改变任何后续行为，都不阻止任何东西通过，都不产生必须回应的信号。

区别在于心理效果。注释看起来像备忘，告警看起来像检查。这种「看起来像」很贵：它让人相信这件事已经被管住了，从而不去做真正能管住它的事。安慰剂的价格从来不是药费，是延误。

第四档：写在文档里的约定

它为什么看起来像检查

评审清单、贡献指南、「提交前请确保……」。它有文件名，有段落编号，甚至有人在评审时逐条打勾。它看起来比脚本更权威，因为它带着人的判断。

但它没有执行点。违反它不会产生任何自动后果，只会产生一个可能发生的对话。而对话会不会发生，取决于当时有没有人记得这一条。

它真正的作用

第四档不是检查，是记录意图。它回答的是「我们当初为什么在意这件事」，这个信息有独立价值：新来的人靠它理解边界，争论的时候靠它对齐口径，写自动化的时候靠它推导规则。

把文档当检查用，是把「记录」错当成「执行」。文档能说明一条规则的来历，说明不了这条规则今天还在不在生效。

什么时候可以接受

当违反的代价足够小、且判断必须由人来做的时候。比如命名风格里那些没有明确边界的选择、评审时该不该要求补一段说明、某个改动的动机是否成立。这些事写成脚本要么误报率高到没人看，要么把判断压扁成一条正则。

可以接受的前提是不假装它在执行。写「评审时请留意」，不要写「已检查」。

为什么人会往下滑

新检查默认从告警开始

加一条阻断，第一个被挡住的人往往是自己。写完检查的当天，你正在改一处无关的代码，它红了，你得先处理它才能继续。这个体验会让人本能地选一个更温和的档位：先打印吧，观察一段时间再说。

「观察一段时间」听起来很稳妥，实际上是把定档的决定推给了一个没有议程的未来。

告警没有升级的机制

阻断会自动升级——它红了，有人必须处理，处理不了就讨论，讨论的结果可能是修规则或者降档。告警不会。告警的数量只会增加，因为加告警没有阻力，删告警需要有人负责。

于是系统的默认演化方向是：规则越来越多，硬约束越来越少。每一条新规则都以最弱的形态进入系统，而没有任何力量把它们往上推。

越晚升越难升

一条告警放得越久，背后积累的历史命中就越多。这时候把它升成阻断，第一次跑就会让流水线红一片，而其中大部分是历史遗留。于是升级动作被推迟，推迟又继续积累。

这也是为什么定档要在写检查的当天做完，而不是「等稳定了再说」。稳定期不会自动结束。

升级的两个判据

判据一：漏过去会不会造成不可逆损失

不可逆是关键词。凭据泄露、真实个人信息进入公开历史、覆盖式写入错误数据、产物与源长期不一致——这些错误的共同点是回滚不等于撤销。历史可以被改写，但已经被读走的东西收不回来。

可逆的错误不该占用第一档。格式错了、链接死了、测试红了，修一次就回去了，把它们放在第二档甚至第三档都合理。

判据二：有没有确定的修法

确定的修法指两种：能自动修，或者修法唯一。产物与源不一致，重跑构建就能修；缺少文件头，脚本可以补；真实邮箱出现在源码里，换成保留域下的占位地址就行。

反例是「这段代码是否应该存在」「这个抽象是否合理」。这类判断没有唯一答案，写成硬失败只会把讨论变成对抗。

两项都否，就删掉它

如果一条检查既拦不住不可逆的损失，又没有确定的修法，正确的动作不是降级，是删除。

留着的成本比想象中高：它占着一条规则的名额，让「我们已经有检查了」这句话成立，从而阻止真正的检查被讨论；它还在每次构建里制造一行需要被忽略的输出，训练所有人对日志失去注意力。一个被训练成「日志里的黄字不用看」的团队，也会错过真正的黄字。

删掉一条没用的检查，和加一条有用的检查，价值是一样的。

两档共存的正确分工

硬档只装必须停的规则

第一档的清单应该短到能背下来。我的版本是四条：凭据与真实个人信息不进历史；产物必须与源一致；发布前的构建不能失败；推送不能覆盖别人的提交。

四条之外的规则，一律不进第一档。这个约束不是为了宽松，是为了保住第一档的信用——第一档每次变红都必须意味着「真的有事」，一旦它开始为风格问题变红，人们就会开始找绕过的方法，而绕过第一档的方法通常影响面很大。

软档必须有人清账

软档（第二档和第三档）的存续条件不是「能打印」，是「有人定期看并且关掉几条」。

清账不需要很复杂。每周花十分钟，把告警按文件归堆，能自动修的写进脚本，判断不了的降级成第四档的说明，重复出现的考虑升成第二档。关键是这个动作有固定的人和固定的节奏，不然软档就是一个持续变大的垃圾堆。

还有一个更硬的约束可以加：给软档设一个总数上限，超过就当作失败。这样软档的膨胀至少会在某个点上被迫处理，而不是无限期地积累。（这条我还没落地，先记在这里。）

一张分工表

规则 档位 为什么
凭据、真实个人信息 第一档 泄露不可逆，修法明确（轮换 + 换占位）
产物与源一致 第一档 不一致意味着线上状态不可解释
构建必须通过 第一档 失败即不可发布，没有讨论空间
单元测试 第二档 挡错代价小，合并前还有共享流水线兜底
内链死链 第二档 修法明确，影响可逆
绝对路径告警 第三档 不影响运行，但值得人看一眼
命名风格偏好 第四档 判断依赖上下文，写成规则误报率高

这张表不是标准答案，它只是把「为什么是这个档」写出来了。写不出理由的档位，通常就是定错了。

把滑杆用在下一个检查上

三个问题

下次要加检查的时候，先回答三个问题，再动手写脚本。

第一，这条错误漏过去，最坏的结果能不能撤回？不能，从第一档开始考虑。

第二，修法是不是唯一的、能不能自动化？不能，就别指望它变成阻断，它会变成无休止的争论。

第三，执行点在哪，谁能改它？如果执行点在你的工作区，那它最多是第二档，别按第一档的强度去设计它的文案和流程。

三个问题的答案会直接把规则推到某一档，剩下的工作只是实现。反过来，先写脚本再想档位，结果几乎总是第三档——因为打印最不脏手。

升级是一次改动，不是一次倡议

把一条检查从第三档升到第二档，改动量通常小得让人意外：让退出码说话。

# 示例：把「只打印」改成「命中即失败」
# 现在的形态（第三档）
python3 scan.py --all                    # 无论命中多少，退出码 0
# 升档后的形态（第二档）
python3 scan.py --all --fail-on=warn     # 命中告警即非 0（示例参数）

真正难的不是这个改动，是改完之后第一次跑红时，有没有人愿意处理它。所以升档要选在清单还短的时候做——那时候红的成本最低。

收束：检查器在失败时替你按下停止

检查器不是在日志里说话。它是在你不在场的时候，替你把某件事停下来。

这个定义很窄，窄到会排除掉很多东西：写在文档里的约定不是检查，只打印不失败的告警不是检查，需要每个人自己记得安装的钩子只是半个检查。它们都有价值，但价值不在「拦住」，在「记录」或者「提示」。把这两件事混着叫，代价是以为自己有一道闸，实际上只有一张纸条。

那 5 条告警还在。我还没处理它们，也没把它们升成阻断——这篇文章写的是我怎么给检查定档，不是我完成了一次改造。下一步很具体：先把 5 条按文件归堆，能自动修的写进脚本，剩下的逐条决定是升档还是删掉。在那之前，它们仍然是注释。

一根滑杆的意义不在于把东西排个高低，而在于让你在写下一行 echo "warning: ..." 之前停一下，问自己：这条东西失败的时候，会让谁停下来？如果答案是「没有人」，那它现在就是一行注释，只是穿了件检查的衣服。
