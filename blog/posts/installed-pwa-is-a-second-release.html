装到主屏的那份，是你召回不了的版本

📅 2026-11-04 17:10:00 ⏱️ 15 min read 👤 张小猛
PWA Service Worker 缓存 发布

同一份代码，两次发布

一次绿了的流水线，和一个没人问的问题

我对「发布完成」的判据长期只有三条：流水线绿了，线上页面能打开，页面上的字是新写的。三条都满足，这事就从待办里划掉。

这套判据在浏览器里成立。用户下次刷新拿到的就是新东西，刷新的成本接近零，他也不觉得这算「等了一次发布」。

装到主屏的那份不成立。它是 display: "standalone" 的独立窗口，没有地址栏，也没有刷新按钮。它下次启动时读哪份缓存、由哪个版本的 Service Worker 接管、窗口里跑的是哪一次构建的 JS，这些都不由我决定。我能决定的只有一件事：我把什么推到了服务器上。至于这份东西什么时候落进某个具体设备，取决于那个设备的用户什么时候打开它、系统什么时候把它冻结、又什么时候让它恢复。

所以同一份代码有两次发布。第一次由我做，第二次由每个已安装的客户端各自做。我做不了第二次，只能让它更容易发生，并且在它没发生时知道自己不知道。

把「发布」拆成两条轨道

拆开之后有些词立刻变形。比如「验收」——在两条轨道上根本不是同一件事：轨道 A 的验收是比对，可以写进脚本，跑一次两秒钟；轨道 B 的验收是制造一个场景再观察，只能写进清单，而且每次都要有人真的去做。

再比如「回滚」。轨道 A 回滚是把上一个提交重新推一遍，几分钟后线上就是旧的。轨道 B 里没有回滚这个动作：已经装到主屏上的那份不会因为我退回一版就跟着退回去，它可能还停在更早的版本上，而我连它在哪个版本都不知道。

下面两张清单，是同一个提交在两条轨道上的两套生命周期。

轨道 A：部署，判据在你自己手里

触发条件：一次 push

轨道 A 的触发完全确定：我推了，托管方收到，构建开始。没有用户参与，没有设备状态参与。这也是它容易被当成「发布」的全部的原因——它是唯一一次有明确起点的发布。

完成判据：线上字节与本地逐字节一致

我不再拿「页面能打开」「标题对得上」当判据。标题对得上只证明 HTML 里有那串字，证明不了这份 HTML 就是你刚提交的那份——中间隔着 CDN 缓存、构建缓存、分支没同步。可以用的判据是哈希：把线上取回来的响应体和本地工作树里的文件算 sha256，两个值相等，这次部署才算完成。

这个判据的好处是它可重复、可脚本化、不依赖我的眼睛。坏处是它只覆盖服务器上那一侧。服务器上对，不代表任何人手里对。

失败形态：会吵的那几种

轨道 A 的失败几乎都会主动来找我：构建报错、502/500、CDN 还发着上一个副本、分支落后被拒推。它们的共同点是在我盯着的时候发生，所以最迟几分钟内就会暴露。

项 轨道 A（部署）
触发条件 一次 push，确定发生
完成判据 线上响应体与本地 HEAD 逐字节一致
失败形态 构建失败 / 5xx / 旧副本 / 推不上去
可观测性 高，可脚本轮询
等待时长 分钟级，且可预期
谁承担等待 我
回滚 重推上一个提交，分钟级生效

轨道 B：安装态召回，判据不在你手里

触发条件：由用户的手和设备的状态共同决定

一台设备上已经装好的应用，要换到新版本，需要三件事同时成立：用户再次打开它、浏览器在某个时机去检查 /sw.js 有没有变、检查到的结果被允许生效。这三件事里没有一件是我能调的。我能做的是把新版本放上去，然后等。

「等」在这里不是个修辞。它意味着发布这件事从一次动作变成了一段没有终点的状态：有些设备很快就换了，有些可能很久都停在旧版，而我收不到任何回执。

完成判据：没有一个你能直接读到的信号

轨道 A 有 curl 和哈希。轨道 B 没有对应的东西。我无法向「所有已安装客户端」发一次查询，也拿不到它们的版本号。能看到的只有日志里零散的请求，而有日志的只是打开过的那部分设备。

这意味着完成判据只能退化成一句很难受的话：我不知道它完成没有。 严谨一点的说法是，我知道它「可能」完成了，因为我做了能让它完成的事；但我没有任何证据。

失败形态：静默停留

轨道 B 的失败不报错、不掉线、不发通知。用户打开应用，看到的是上一次发布的首页，标题、卡片、甚至那篇刚发的文章都不在。他不会认为「这个站发布了但我收到了旧版」，他会认为「这个站没更新」，或者根本不认为有问题——他不知道自己错过了什么。

这是两条轨道最本质的差别：轨道 A 失败会让你知道，轨道 B 失败只会让用户看到一个自洽的旧世界。

项 轨道 B（安装态召回）
触发条件 用户下次打开 + SW 更新检查 + 允许生效，三者同时
完成判据 无法直接观测，只能间接推断
失败形态 静默停留在旧版，无报错
可观测性 低，只能靠真机逐个看
等待时长 不确定，可能以天计
谁承担等待 用户，且他不知道自己在等
回滚 没有对应动作，旧版本可能仍在某些设备上活着

两张清单逐行对照

同一行，两种答案

把两张表叠起来看，差异集中在四行：触发、判据、失败形态、回滚。这四行恰好是「发布」这个词在工程语境里的全部内涵。四行里有三行在轨道 B 上是空的或者不可观测的，那这次发布就只能算完成了一半。

哪些是「你以为完成了其实没有」

  • 「CI 绿了」：只说明产物可复现，不说明有人拿到。
  • 「线上打开是新版」：说明我这条路通了，说明不了别人那条。
  • 「用户没反馈问题」：安装态的失败本来就不会被当成问题反馈，它是「这站最近没更新」。
  • 「缓存版本号变了」：说明新缓存名已经被写进 sw.js，不说明任何设备已经激活了它。

这四条我都在不同时期当成过完成信号。它们共同的问题是把服务端的状态当成了客户端的状态。

更新链路：install → waiting → activate

版本常量由内容哈希推导

站上的 sw.js 开头是这么写的：版本常量不是人填的，是构建时用文章索引、搜索脚本、样式表三个文件的内容算出来的哈希前 8 位，缓存名再拼上这个版本。内容一变，缓存名就变；缓存名一变，activate 阶段就会把名字不等于当前值的整份缓存删掉。

// 版本由构建管线算出，不是手写的
const SW_VERSION = 'c-1f3a9d2e';         // sha256(索引 + 搜索脚本 + 样式表)[:8]
const CACHE_NAME = 'site-' + SW_VERSION; // 前缀随意，名字里带着版本才是关键

这段设计解决的是「缓存不该混着用」：新旧两份内容不会被塞进同一个缓存桶，旧桶会被清掉。它解决不了的是「谁先加载哪一份」——那是下面三个阶段的事。

install：新脚本先落盘，旧页面照跑

浏览器发现 /sw.js 的字节变了，会把新脚本装进一个新的 worker。这个 worker 在 install 事件里做预热：把核心页面和静态资源抓一遍塞进当前版本的缓存。抓取失败，整个安装失败，旧 worker 继续服役——这是好事，它保证你不会因为一次网络抖动而失去离线能力。

站上的 install 里还调了 self.skipWaiting()：

self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => cache.addAll(CORE_URLS))
  );
  self.skipWaiting();   // 不等所有页面关闭，直接进入激活
});

self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((names) =>
      Promise.all(
        names
          .filter((name) => name !== CACHE_NAME)  // 删掉所有旧版本缓存
          .map((name) => caches.delete(name))
      )
    )
  );
  self.clients.claim();  // 接管已经打开的页面
});

不加 skipWaiting() 的话，新 worker 装完会停在 waiting 状态，一直等到所有受控页面都关闭才 activate。加了它，新 worker 立刻上位。站上两者都用了：skipWaiting() 让它别等，clients.claim() 让它把手头已经开着的页面也接过来。

waiting：等的是「没有页面在用它」

waiting 这个状态存在的理由很朴素：一个正在运行的页面，它的 JS 已经在内存里了。如果新 worker 在页面还开着的时候就把缓存换掉，这个页面后续的懒加载请求会拿到新版本的文件，配上旧版本的运行时——这是最难受的一种错配，报错信息会指向一个你没改过的地方。

所以规范的选择是等。等所有受控客户端都关闭，旧的 worker 自然退场，新的接手。这个策略在普通网页上成立，因为「关掉标签页」是用户的日常动作。

activate：换缓存名，删掉旧的那份

activate 干两件事：把名字不等于当前 CACHE_NAME 的缓存全部删掉，然后 clients.claim() 接管现存页面。第一件事有个副作用值得留意——它是按名字删的。如果有别的代码往同一个 origin 下写过缓存，名字不匹配就会被一起清掉。这是命名前缀要带项目标识的原因。

clients.claim() 之后，页面发出的下一个请求会走新 worker。注意这句话的主语是「下一个请求」。

skipWaiting 换的是控制权，不是页面

这是最容易混淆的一点，也是我在写这套东西时想了很久的地方：

skipWaiting() + clients.claim() 解决的是「谁在处理网络请求」，不解决「页面里已经跑起来的 JavaScript 是哪个版本」。窗口里那份文档、已经执行过的脚本、已经应用过的样式，都在内存里。换掉网络层不会让它们重新加载。

结果是一种很别扭的中间态：网络层已经是新的，页面看上去还是旧的。用户点一个链接，新页面是新版本；用户留在原地，看到的是旧版本，而且不知道差别在哪。要越过这道坎，仍然需要一次导航或一次 location.reload()——而 standalone 窗口里没有那个刷新按钮。

有些实现会在 controllerchange 时自动刷一次页面。站上没有这么做，我也倾向于不做：在用户正在读文章的时候把页面重载掉，代价比「他看到的是稍早的版本」大。

为什么安装态里，那个等待条件难以自然满足

「关闭所有标签页」在安装态里没有对应动作

轨道 B 的整个假设是「用户会关掉它」。可主屏应用的使用方式和标签页不一样：它不是一堆并列的页签中的一个，它是一个图标，点开、用完、按 home 键离开。离开不等于关闭，进程可能还挂着，页面可能还在内存里。

没有 skipWaiting() 的时候，这个差异是致命的：waiting 的 worker 等的条件在安装态里可能要很久才成立一次。站上用了 skipWaiting()，所以这一条被绕过了——但绕过的是激活，不是用户看到的画面。

冻结与 resume：平台相关，需要真机验证

移动系统对后台应用普遍有冻结机制：一段时间不活跃就挂起，下次打开时尝试恢复而不是重新冷启动。这类行为的细节随平台和版本不同，我按「可能恢复」来设计，不按「一定冷启动」。

具体到某个平台会不会保留独立的存储容器、resume 时会不会重新检查 sw.js、主屏应用的存储是否与浏览器标签页共享，这些行为随系统版本变化，也和安装方式有关。这一条我给不出通用结论，只能写成平台相关、需要真机验证。 我能确定的只有推论方向：越接近「恢复」而不是「冷启动」，页面里旧代码存活的时间就越长。

sw.js 自己也要过 HTTP 缓存这一关

还有一层容易被忽略：Service Worker 脚本的更新检查本身是一个网络请求，而这个请求也受 HTTP 缓存约束。站上的静态资源响应头长这样：

GET /sw.js HTTP/1.1
Host: blog.example.com

HTTP/1.1 200 OK
content-type: application/javascript
cache-control: max-age=600
etag: "6f1c9a7e2b"

max-age=600 是十分钟。浏览器在导航时会去要一次 /sw.js，但在这十分钟内它可能直接用手里的副本回答自己，于是「检查更新」这一步看到的还是旧脚本。十分钟不算长，但它的存在说明：连「浏览器什么时候知道有新版本」这个最上游的环节，都有缓存参与。

这条对发布的含义是：推完之后立刻验收，看到的可能是缓存，不是部署结果。 所以要带 cache-bust 参数、要看哈希，而不是看「我刷新了一下，好像还是旧的」。

验收拆成两条路径

路径一：浏览器里，可重复地制造旧版本

浏览器这条路径的好处是可以反复折腾。DevTools 里能清缓存、能注销 Service Worker、能模拟离线，能把「旧版本」这个状态随手造出来再消掉。这条路径要测的是三件事：

  1. 新版本能不能被检测到（/sw.js 的字节确实变了）。
  2. 检测到之后能不能激活（缓存名换了，旧缓存被删）。
  3. 激活之后页面拿到的是不是新内容（导航一次，比对标题或哈希）。

这三步任何一步失败，问题都在我的代码或构建里，与用户无关。这是唯一一条我能独立闭环的路径。

路径二：安装态，只能制造一次现场

安装态这条路径不能反复折腾，因为它模拟的正是「用户不会配合」的那个场景。要做的是把应用装到主屏，正常用一次，然后推一个新版本，不做任何清理，再打开它，看它给你哪个版本。

关键在「不做任何清理」：不清缓存、不注销 worker、不在 DevTools 里点 Update。任何一次清理都会把你要观察的那个状态抹掉，测出来的东西就变成了路径一。

要在没有地址栏的窗口里看状态，只能靠远程调试：

// 安装态窗口连上调试器后，在 Console 里跑
const reg = await navigator.serviceWorker.getRegistration();
console.log({
  active: reg?.active?.scriptURL,
  waiting: reg?.waiting?.scriptURL ?? null,
  controlled: navigator.serviceWorker.controller?.scriptURL ?? null,
  caches: await caches.keys()
});

waiting 非空说明新 worker 卡在等待；caches 里有不止一个名字说明旧缓存还在；active 和 controlled 不一致说明页面还没被新 worker 接管。这三个值合起来，能回答「这台设备现在到底在哪个版本上」——这是轨道 B 唯一能拿到的直接证据，而且只对眼前这一台有效。

各自测什么

维度 路径一（浏览器） 路径二（安装态）
目的 证明新版本本身可用 证明新版本能落到已安装的客户端
可重复性 高，随时清随时造 低，一次现场只能用一次
主要手段 清缓存、注销 worker、离线模拟 装到主屏、正常使用、不清理、观察
能发现的问题 构建错、缓存键错、资源 404 激活条件不成立、旧页面存活、检查被 HTTP 缓存挡住
结论强度 强，可脚本化 弱，只能代表这一台设备

判据：什么算两条路径都过

一张可执行的验收表

我把验收写成两张必须都勾的表，任何一张没勾就不写「已发布」：

# 检查项 轨道 通过标准
1 线上响应体与本地 HEAD 哈希一致 A 两个 sha256 相等
2 首页/列表/索引都含新内容 A 三处都能查到
3 /sw.js 里的版本常量已变 A 与上一个版本不同
4 浏览器路径能检出并激活新版本 B 缓存名切换、旧缓存消失
5 安装态冷启动后内容是新的 B 无清理情况下看到新内容
6 安装态里页面能完成一次导航 B 导航后内容与线上一致

前三条是脚本，后三条是人。这个分工不是懒，是承认后三条没有可靠的自动化方式。

出问题时先看失败形态

两条路径的失败长得不一样，从现象就能反推在哪一段：

  • 浏览器里也是旧的：问题在部署或缓存键，先查轨道 A。
  • 浏览器新、安装态旧：缓存键没问题，问题在召回——检查是不是卡在 waiting、是不是页面没被接管、是不是 /sw.js 的检查被 HTTP 缓存挡住。
  • 安装态新、但页面里有一段行为还是旧的：skipWaiting 生效了、控制权换了，但页面没重新加载。这是「控制权 ≠ 已渲染页面」那一节说的情况。

第二种是最容易被漏掉的一种，因为它只在一个不给地址栏的窗口里出现。

收束：把第二次发布写进清单

我现在对「发布」的定义改成了两个句子：

部署完成 = 线上字节与我提交的字节一致。 召回完成 = 至少一台已安装的客户端在没有人工清理的情况下拿到了新版本。

第二句永远只能给出「至少一台」这种强度的结论。这不是方法不够好，是这件事本身的结构：安装态的版本分布没有中央视图，你手上没有那份名单。承认这一点，比假装有一条命令能查全体设备要诚实得多。

落到动作上，我给自己加了三条，都还没写进自动化：

  1. 发布汇报里分两栏：轨道 A 写实测哈希，轨道 B 写「跑了几台、什么平台、观察结果」。B 栏空着就写「未验证」，不写「已发布」。
  2. 打算每篇新文章发布后，至少在一台真机上装一次主屏应用，不做清理，看它给哪个版本。这一条是为了保住「知道自己在不知道」的状态，不是为了收集数据。
  3. 把 sw.js 的检查路径单独当一件事看：它有自己的 HTTP 缓存，max-age=600 意味着「推完之后的最初十分钟」里，连「有没有新版本」这个判断都可能是旧的。验收要么等过这个窗口，要么带 cache-bust。

这三条做完，第二次发布仍然不在我手里。但至少它从我视野之外，挪到了清单上——一件知道自己没做完的事，和一件以为自己做完的事，后果差得很远。
