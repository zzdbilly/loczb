MySQL 索引优化实战：从慢查询到最佳实践

📅 2026-07-05 13:07:10 ⏱️ 5 min read 👤 张小猛

你有没有遇到过这种情况：一个数据库查询在本地跑得飞快，部署到生产环境后突然变慢几十倍？或者同一个查询，同样的数据量，有时候几毫秒就返回，有时候几秒钟还没结果？

这种"玄学"问题，十有八九跟 索引 有关——更准确地说，跟查询有没有用上索引、用对了索引有关。今天我们就用 MySQL 8 来实战，从一条慢 SQL 开始，一步步推到索引设计的最佳实践。

先复现一个慢查询问题

为什么要先复现？因为优化一定要有基准，没有基线就不知道改了有没有效果。

建表和造数据

CREATE TABLE orders (
  id INT PRIMARY KEY AUTO_INCREMENT,
  user_id INT NOT NULL,
  product_id INT NOT NULL,
  amount DECIMAL(10,2) NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'pending',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  category VARCHAR(50),
  INDEX idx_user (user_id)
);

-- 插入 50 万条模拟数据
-- 用存储过程批量插入，跳过具体代码，重点是后面的查询

有了数据以后，我们执行一个看起来很正常的查询：

SELECT * FROM orders
WHERE status = 'completed'
  AND amount > 100
  AND created_at >= '2025-01-01'
ORDER BY created_at DESC
LIMIT 20;

这个查询没有建复合索引，MySQL 只能走全表扫描或者选其中一个索引。我们来 EXPLAIN 一下：

EXPLAIN SELECT ... -- 同上

结果会看到 type: ALL 或者 type: index，rows 接近 50 万，Extra 里有 Using where; Using filesort。filesort 意味着排序没有走索引，效率极差。

什么是 filesort

filesort 不是真的写到磁盘文件了（小数据量是在内存里），但它意味着 MySQL 不得不把数据拿出来自己排序，而不是从索引顺序直接读取。当排序列上没有索引、或者排序和查询条件不在同一个索引上时，就会触发 filesort。

单列索引的局限性

大多数人第一反应是：在 created_at 上加个索引。

CREATE INDEX idx_created_at ON orders (created_at);

再来 EXPLAIN，发现 type: ref 或者 range 了，rows 减少到了几万行——但是 Extra 里依然是 Using where; Using filesort。

这就是单列索引的第一个问题：条件用了一个索引，排序又没用到。MySQL 只能选一个索引来用，选了 idx_created_at 可以在时间范围上快速定位，但排序仍然是 filesort。

单列索引的第二个问题是：多个单列索引之间，MySQL 只会选其中一个，不是组合使用。MySQL 有 Index Merge 优化，但那是特例且性能不可预测。

复合索引的黄金法则

解决上面的问题，最直接的方法就是建复合索引：

CREATE INDEX idx_status_amount_date ON orders (status, amount, created_at DESC);

再 EXPLAIN，结果变成了 type: ref，rows 只有几千，Extra 里终于没了 Using filesort，变成了 Using index condition。

最左前缀法则

复合索引的核心规则是最左前缀：索引 (a, b, c) 可以匹配： - WHERE a = ? ✅ - WHERE a = ? AND b = ? ✅ - WHERE a = ? AND b = ? AND c = ? ✅ - WHERE b = ? ❌ — 跳过了 a，用不上索引 - WHERE a = ? AND c = ? ⚠️ — 能用 a，但 c 用不上（被 b 隔断）

这就是为什么我们把 status 放在最左边——等值查询最左边是最常见的模式。

排序字段放中间还是最后

很多人纠结排序字段放在复合索引的什么位置。记住一条原则：

如果排序字段是范围查询，放中间；如果是排序且没有范围，放最后。

例子中 amount > 100 是范围条件，范围条件之后的索引字段对排序无效。所以我们把 created_at 放在 amount 之后，让排序走索引。

实践中避不开的 Covering Index

什么是覆盖索引

覆盖索引（Covering Index）是指查询需要的所有列都在索引里，不需要回表查询。Extra 里会出现 Using index。

-- 覆盖索引查询
SELECT user_id, amount, status FROM orders
WHERE status = 'completed'
  AND amount > 100;

如果索引 (status, amount, user_id) 包含了所有查询列，MySQL 就可以在索引 B+ 树上完成查询，完全不碰数据行。这在数据量大时能带来数量级的性能提升。

覆盖索引的设计方法

设计覆盖索引时，先把 SELECT 列和 WHERE 列罗列出来，然后尝试建一个包含所有这些列的复合索引。但不要把所有列都塞进索引，因为：

  1. 索引占用空间
  2. 写入性能变差（索引越多，插入越慢）
  3. 如果列太多，不如回表

建议把高频查询做覆盖索引优化，低频的不管。

MySQL 索引失效的 7 个经典场景

场景 1：索引列参与计算

-- 失效
WHERE YEAR(created_at) = 2025

-- 生效
WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01'

场景 2：隐式类型转换

-- user_id 是 VARCHAR
-- 失效（字符串 vs 数字）
WHERE user_id = 12345

-- 生效
WHERE user_id = '12345'

场景 3：LIKE 通配符在开头

-- 失效
WHERE name LIKE '%keyword%'

-- 生效（如果 name 有索引）
WHERE name LIKE 'keyword%'

场景 4：OR 条件中有非索引列

-- 失效（如果 status 有索引但 memo 没有）
WHERE status = 'completed' OR memo LIKE '%refund%'

-- 改写为 UNION
SELECT * FROM orders WHERE status = 'completed'
UNION
SELECT * FROM orders WHERE memo LIKE '%refund%'

场景 5：NOT IN 和 <>

-- IN 可以用索引
WHERE status IN ('pending', 'processing')

-- NOT IN 通常不会用
WHERE status NOT IN ('cancelled', 'refunded')

场景 6：索引列使用了函数

-- 失效
WHERE UPPER(email) = 'USER@EXAMPLE.COM'

-- MySQL 8.0.13+ 可以建函数索引
CREATE INDEX idx_upper_email ON users ((UPPER(email)));

场景 7：数据分布导致优化器放弃索引

这可能是最"冤"的一种情况：索引明明建了，查询也符合最左前缀，但 MySQL 发现你要查的数据占比太大了（超过 20-30%），全表扫描比走索引 + 回表更快，于是自动放弃了索引。

实测对比：从 2 秒到 10 毫秒

我们来做一个完整的对照实验。以 50 万行 orders 表为基础：

索引类型 查询内容 耗时 Extra
无索引 按状态 + 金额 + 时间排序 2.1s Using where; Using filesort
单列 (status) 同上 1.8s Using where; Using filesort
复合 (status, amount, created_at) 同上 12ms Using index condition
覆盖索引 只查索引内列 3ms Using index

从 2 秒到 12 毫秒，同一个查询，同一个数据量，差距 167 倍。

如何分析你的索引是否有效

用好 EXPLAIN

EXPLAIN FORMAT=JSON SELECT ... ;

JSON 格式会给出更详细的信息，包括： - cost_info — 优化器估算的成本 - attached_condition — 索引附加条件 - used_key_parts — 实际用到的索引列 - access_type — ref/range/ALL

开启慢查询日志

SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;  -- 超过 500ms 记录

定期检查慢查询日志，找出最慢的几条 SQL，逐一 EXPLAIN + 优化。

pt-query-digest 工具

Percona Toolkit 中的 pt-query-digest 可以分析慢查询日志，按总耗时、平均耗时、出现频率排序，帮你找到最值得优化的查询。

表结构层面的索引设计

除了单条 SQL 的索引优化，整体表结构层面的设计同样重要。

区分 OLTP 和 OLAP

OLTP 表（订单、用户、支付）索引不宜太多，一般控制在 5-8 个以内，每次 INSERT 索引更新开销不可忽略。

OLAP / 报表类查询，可以多建覆盖索引，甚至建专门的汇总表。

前缀索引

对于长字符串字段，可以用前缀索引来节省空间：

CREATE INDEX idx_email_prefix ON users (email(10));

但注意：前缀索引无法用于 ORDER BY 和 GROUP BY。

索引排序与 ORDER BY

MySQL 8 支持在索引定义时指定排序方向：

CREATE INDEX idx_user_date ON orders (user_id, created_at DESC);

这样做了以后，ORDER BY created_at DESC 就可以直接走索引，不需要 filesort。

写多读少的场景如何妥协

不是所有场景都适合疯狂建索引。对于写多读少的表（如日志表、事件流）：

  • 控制索引数量：写密集型表超过 5 个索引后，写入性能下降明显
  • 考虑分表：按时间分表，每个新表重新维护索引
  • 使用 NoSQL：如果写请求远大于读请求，MySQL 可能不是最好的选择

监控索引使用情况

-- 查看索引使用统计
SELECT * FROM sys.schema_unused_indexes;

-- 查看索引使用频率
SELECT * FROM performance_schema.table_io_waits_summary_by_index_usage;

定期用这两个查询清理从未使用的索引，释放写入性能。

总结一下

索引优化的核心就是这几件事：

  1. 总有 EXPLAIN：任何慢查询，先 EXPLAIN，看 type、rows、Extra
  2. 复合索引取代单列索引：根据查询模式建 (等值列, 范围列, 排序列)
  3. 覆盖索引是杀手锏：高频查询直接覆盖，避免回表
  4. 警惕索引失效：7 种经典场景牢记在心
  5. 写多读少别建太多索引：索引不是越多越好
  6. 定期监测：用 pt-query-digest + sys.schema_unused_indexes 保持索引健康

数据库索引不是什么玄学。理解了 B+ 树的存储结构，明白了最左前缀、覆盖索引、索引下推这些概念，再遇到慢查询就能按部就班推理了——而不是靠猜和碰运气。
