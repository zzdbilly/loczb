幂等与可复现：为什么你的构建总在产生无意义的 diff

📅 2026-09-27 15:56:42 ⏱️ 14 min read 👤 张小猛
构建 幂等 可复现 工程实践

这篇文章写给正在维护静态站点、代码生成器或任何「跑脚本产出文件」流水线的工程师。你大概见过这种场面：明明没有人改内容，git status 却列出一屏变更；review 的 diff 里 90% 是行序变化；CI 上的产物和本地对不上，谁也说不出哪边是对的。

前置条件：Node 18+、Python 3.9+、git 2.30+，以及一个能跑构建脚本的仓库。文中所有命令都在 Linux 或 macOS 上执行，所有代码片段都可以直接复制运行并复现输出。

下文用一个真实维护了两百多天的静态博客仓库作为样本（111 篇文章、286 个标签、单次构建产出十几个文件），把三类构建噪声逐个拆开，再补上元数据真相源和可执行门禁的落地写法。

一、把「空转构建」的症状固定下来

先别急着改代码。构建噪声最麻烦的地方在于它是间歇的：今天复现，明天就没了，于是所有人都当它不存在。把它固定成一条可以反复执行的命令，后面每一步修复才有裁判。

用两连跑把噪声量出来

连续跑两次全量构建，中间不做任何内容改动，然后看工作区有没有变化：

# 记录基线指纹
md5sum blog/articles-index.json blog/index.html index.html sitemap.xml rss.xml > /tmp/before.md5

# 第一遍
node scripts/generate-index.js > /tmp/run1.log

# 第二遍
node scripts/generate-index.js > /tmp/run2.log

# 工作区是否出现「无内容变化」的改动
git status --porcelain

在一个已经收敛的仓库里，这三条命令的输出是这样的：

$ git status --porcelain
（没有任何输出）

$ diff /tmp/run1.log /tmp/run2.log
（没有差异）

如果 git status --porcelain 打印了文件名，说明第二次构建写了一些字节不同的东西。注意这里是「字节不同」而不是「内容语义不同」——排序换了、空白多了一个换行、时间戳字段被刷新，都算。

把 diff 分成三类噪声

把 git diff 的内容按性质归类，后面每一类都有独立的成因和对策：

  • 顺序漂移：同一批条目、同样的字段，只是排列不同。典型是列表页、索引 JSON、sitemap 的条目顺序在两次构建之间互换。
  • mtime 漂移：文件内容逐字节相同，但文件的修改时间被无条件刷新。这类噪声在 git status 里看不见，却会污染所有依赖 mtime 的下游逻辑。
  • 不收敛（一遍不平）：第一遍构建留下的产物，第二遍构建还会改一次；第二遍的结果才是稳定态。这种「洗噪」现象说明写入逻辑不是自映射的。

三类噪声的修法完全不同，混在一起改会互相掩盖。判断顺序建议是：先修顺序漂移（最容易量出规模），再修不收敛（因为它会制造假的顺序漂移），最后修 mtime 漂移（它对 git 不可见，最容易漏掉）。

量出噪声的规模再动手

在样本仓库里统计一次就发现，问题不是边角料。111 篇文章里有 27 篇的发布时间戳完全并列：

python3 - <<'PY'
import json, collections
posts = json.load(open('blog/articles-index.json'))['posts']
groups = {k: v for k, v in collections.Counter(p['dateTime'] for p in posts).items() if v > 1}
print(f"并列时间戳分组: {len(groups)} 组, 覆盖 {sum(groups.values())} 篇 / 共 {len(posts)} 篇")
PY

输出：

并列时间戳分组: 9 组, 覆盖 27 篇 / 共 111 篇

27 篇、接近四分之一，全部落在同一个排序分支上。这意味着只要这个分支的裁决依据不稳定，四分之一的文章在每次构建里都可能换位置——而它们恰恰是列表页第一屏和 sitemap 前段的常客。

二、把四个被混用的词分开

「幂等」「可复现」「确定性」「字节比对写盘」经常被当成同义词用。它们描述的是四个不同层次的保证，混用会导致你修错地方。

幂等：同一份输入跑两次，第二次不改变任何东西

幂等（idempotent）关心的是重复执行：把构建跑第二遍，产物一个字都不应该变。它不要求跨机器一致，也不要求产物本身有什么特性，只要求「再跑一次 = 什么都没发生」。

判断幂等有一个副作用可见的判据：跑完第二遍之后，git status --porcelain 必须为空，且所有产物的 mtime 保持不变。

可复现：换一台机器、换一次检出，结果仍然一致

可复现（reproducible）关心的是环境无关：开发机、CI runner、三年后重新 clone 出来的工作区，跑同一份源码得到逐字节相同的产物。

幂等是可复现的必要条件，不是充分条件。一个脚本可以在同一台机器上稳定收敛，却在全新检出上产出完全不同的顺序——因为它的输入里混进了「这台机器恰好如此」的事实，比如文件 mtime、目录遍历顺序、环境变量、本地时区。

确定性：同一个输入永远给同一个输出

确定性（deterministic）关心的是函数纯度：同样的参数调用两次，返回同样的值。读时钟、读随机数、读文件系统顺序，都会破坏确定性。

构建脚本里最常见的非确定性来源有四个：Date.now()（生成时间戳字段）、Math.random()（临时文件名、哈希盐）、readdirSync 的返回顺序（依赖文件系统而非排序）、statSync().mtime（依赖检出与写入历史）。

字节比对写盘：把「内容未变」翻译成「不落盘」

字节比对写盘（write-if-changed）是一条写入纪律，不是排序技巧：写文件之前先读出旧内容，逐字节比对，相同就直接返回，不调用写盘系统调用。

它的价值有两层。第一层是消除 mtime 漂移——内容没变就不写，文件的修改时间自然不动。第二层是让「幂等」这件事变成可观测的：产物没有 mtime 变化，说明写入路径确实没有空转。

概念 关心的问题 典型失败现象 主要对策
幂等 再跑一次会不会改变产物 第二遍构建仍有 diff 字节比对写盘、写入前归一化
可复现 换机器会不会得出不同产物 CI 与本地不一致、全新检出顺序翻转 去掉 mtime/readdir 依赖、固定排序裁决
确定性 同输入是否恒定输出 时间戳字段每次不同、顺序随机 输入显式化、排序键完备
字节比对写盘 内容未变时是否还落盘 mtime 被刷新、下游缓存失效 读写前比对、相同则跳过

三、拿文件 mtime 当并列裁决，换机器就翻脸

排序里总会遇到「主键相同」的情况。这时需要第二个键来决定先后，也就是并列裁决（tiebreaker）。用文件 mtime 作裁决依据是最常见的错误选择，因为它在开发机上看起来很合理。

问题代码长什么样

下面这段比较器在本地跑一个月都不会出问题：

// ❌ 用文件 mtime 作并列裁决
posts.sort((a, b) => {
  if (a.timestamp !== b.timestamp) return b.timestamp - a.timestamp;
  return fs.statSync(a.file).mtimeMs - fs.statSync(b.file).mtimeMs;
});

在开发机上，你写完一篇文章就构建一次，文件的 mtime 大致反映了写作先后，所以顺序满足直觉。这个正反馈会掩盖一个事实：mtime 描述的是「文件被写入的时刻」，而你想表达的是「条目的发布时间」。

mtime 在全新检出上为什么必然失效

git 不保存 mtime。检出时所有文件被一次性写下，它们的 mtime 等于检出时刻。用一个三点小实验验证这一点：

mkdir work && cd work && git init -q .
for n in 1 2 3; do printf 'post %s\n' $n > "post-$n.html"; done
git add -A && git -c user.name=t -c user.email=t@t commit -qm init
cd .. && git clone -q work clone
find clone -maxdepth 1 -name '*.html' -printf '%T@ %p\n' | sort

输出（三行 mtime 精确到纳秒完全相同）：

1790495702.3200957370 clone/post-1.html
1790495702.3200957370 clone/post-2.html
1790495702.3200957370 clone/post-3.html

三个文件的 mtime 一模一样。回到上面的比较器：并列裁决返回 0，排序退化为「引擎稳定性未知」的状态——V8 现在会保持原顺序，但原顺序来自 readdirSync，而目录遍历顺序由文件系统决定，不在你的控制范围内。于是：

  • 开发机上 27 篇并列文章有一个顺序；
  • CI 新 clone 的工作区有另一个顺序；
  • 三年后别人 clone 出来，又是第三个顺序。

按照第二节的分类，这同时破坏了确定性和可复现。

换成既有索引位次做裁决

稳定的做法是把裁决依据放进版本控制。读上一次已提交的索引，记录每个条目的既有位次，并列时按位次升序——位次是仓库里的数据，跨机器一致：

// ✅ 用已提交索引中的既有位次作并列裁决
const prevOrder = {};
try {
  const prevIndex = JSON.parse(fs.readFileSync(OUTPUT_FILE, 'utf-8'));
  prevIndex.posts.forEach((p, i) => { prevOrder[p.slug] = i; });
} catch (e) { /* 首次构建时无锚点，退化为 slug 字典序 */ }

posts.sort((a, b) => {
  if (a._ts !== b._ts) return b._ts - a._ts;          // 主键：发布时间降序
  const ra = prevOrder[a.slug], rb = prevOrder[b.slug];
  if (ra !== undefined && rb !== undefined && ra !== rb) return ra - rb;
  if (ra === undefined && rb !== undefined) return 1;  // 新条目排在同刻旧条目之后
  if (rb === undefined && ra !== undefined) return -1;
  return a.slug < b.slug ? -1 : a.slug > b.slug ? 1 : 0; // 兜底：slug 字典序
});

这个比较器有三个值得注意的性质：

  1. 自映射：用产物自己作为下一次构建的锚点。内容不变时位次不变，位次不变时顺序不变，顺序不变时产物字节不变——闭环一遍收敛。
  2. 新条目有确定落点：不在索引里的条目统一排在同刻旧条目之后，落点不取决于目录遍历顺序。
  3. 兜底键完备：最后一个分支用 slug 字典序，保证任意两个条目都能比较出确定结果，比较器不会返回 0。

顺带一句维护提醒：这段逻辑迁移完成后，文件头部的注释里还留着一句「同日无精确时间时，用文件 mtime 作 tiebreaker」的旧描述，而实现已经不再读 mtime。注释漂移本身不产生 bug，但它会让下一个读到这段代码的人按旧注释推理。迁移完排序依据后，同步改掉注释是流程的一部分。

验证并列裁决稳定

node scripts/generate-index.js
md5sum blog/articles-index.json
node scripts/generate-index.js
md5sum blog/articles-index.json
git status --porcelain

两行 md5 必须相同，git status --porcelain 必须为空。如果第一次 md5 不同、第二次才相同，说明顺序还在依赖某个未被锚定的输入。

四、生成物无条件写盘，把 mtime 刷成噪声

顺序修好之后，git status 干净了，但事情只走完一半。还有一类噪声对 git 不可见：文件内容一字未改，写入操作却照常发生，于是 mtime 被刷新。

观察一次「什么都没变」的写盘

用一段最小脚本观察 mtime 是否被刷新：

const fs = require('fs');

function writeIfChanged(filePath, content) {
  let old = null;
  try { old = fs.readFileSync(filePath, 'utf-8'); } catch (e) { /* 文件不存在则直接写 */ }
  if (old === content) return false;
  fs.writeFileSync(filePath, content, 'utf-8');
  return true;
}

const target = 'out.txt';
console.log(`首次写入: ${writeIfChanged(target, 'same bytes\n')}`);
console.log(`内容相同: ${writeIfChanged(target, 'same bytes\n')}`);

连续跑两次并观察 mtime：

rm -f out.txt
node wic.js && stat -c '%Y %n' out.txt
sleep 1.1
node wic.js && stat -c '%Y %n' out.txt

输出：

首次写入: true
内容相同: false
1790495675 out.txt
首次写入: false
内容相同: false
1790495675 out.txt

两次输出的时间戳完全相同（1790495675），说明第二次调用虽然跑完了 writeIfChanged，但没有落盘，mtime 原地不动。这就是字节比对写盘的全部机制，二十行不到。

谁在依赖 mtime

mtime 漂移之所以危险，是因为依赖它的逻辑通常不在同一个文件里，甚至不在同一个仓库里。

在样本仓库里有过一次真实的连锁事故：早期的专栏注入脚本每次运行都重写全部文章页，把 mtime 刷成「脚本运行日」。而 sitemap 的 lastmod 字段当时取自文件 mtime，结果是 106 篇文章的 lastmod 全部挤在同一天，第二天再构建又集体跳到新的一天。搜索引擎看到的信号是「这个站每天全量更新」，lastmod 的可信度被彻底稀释，而仓库里没有任何一条 diff 能反映这件事。

改法有两条，两条都要做：

  1. 写入端：所有产物写盘走字节比对，内容未变不写。
  2. 读取端：lastmod 从元数据的发布日期取值，不再取文件系统 mtime。
// sitemap 的 lastmod 使用文章发布日期（来自元数据），不再取 fs mtime
posts.forEach(p => {
  lines.push('  <url>');
  lines.push(`    <loc>${BASE_URL}/blog/posts/${p.slug}.html</loc>`);
  lines.push(`    <lastmod>${p.date}</lastmod>`);   // 发布日期，YYYY-MM-DD
  lines.push('    <changefreq>monthly</changefreq>');
  lines.push('    <priority>0.6</priority>');
  lines.push('  </url>');
});
writeIfChanged(SITEMAP_XML, lines.join('\n') + '\n');

除了 sitemap，还有一批常见依赖方需要检查：

  • make、gradle、webpack 等工具的增量判断；
  • rsync --update、部署工具的「只传更新的文件」逻辑；
  • 编辑器与语言服务器的索引重建；
  • 备份与冷存归档的「变更文件」筛选；
  • 缓存失效策略里的「文件比缓存新」比较。

这些依赖方都不看内容，只看时间。内容未变却刷了 mtime，等于给它们发了一次假事件。

写一份 Python 版本

同一份纪律在 Python 侧需要显式处理编码与原子性：

import os
import tempfile


def write_if_changed(file_path: str, content: str, encoding: str = 'utf-8') -> bool:
    """内容逐字节相同时跳过写盘，返回本次是否真的写入。"""
    try:
        with open(file_path, 'r', encoding=encoding) as f:
            if f.read() == content:
                return False
    except FileNotFoundError:
        pass

    # 原子写：先写同目录临时文件，再 rename 覆盖，避免半截文件被读到
    directory = os.path.dirname(os.path.abspath(file_path))
    fd, tmp_path = tempfile.mkstemp(dir=directory, suffix='.tmp')
    try:
        with os.fdopen(fd, 'w', encoding=encoding) as f:
            f.write(content)
        os.replace(tmp_path, file_path)
    except BaseException:
        try:
            os.unlink(tmp_path)
        except OSError:
            pass
        raise
    return True

原子写这一步在构建脚本里容易被省掉，代价是：当构建被别人在写入中途读到产物时，会读到半截文件。注意 os.replace 会改变 mtime——这是对的，因为这次确实写入了新内容。

五、注入与移除正则不对称，一遍就不收敛

顺序锚定了、写盘也加了比对，还是可能剩下「第一遍洗噪、第二遍才稳」。这类问题的根源通常在注入与移除的一对正则上。

「第一遍洗噪、第二遍才稳」是怎么来的

考虑一个构建期注入的组件块，它的更新方式是「先删旧的、再写新的」：

// ❌ 移除端吃掉块两侧的空白，写入端只写回单侧 —— 两端不对称
let out = orig.replace(/\s*<!-- Widget -->[\s\S]*?<!-- \/Widget -->\s*/g, '');
out = out.replace(/(<div class="post-tags">[\s\S]*?<\/div>)/,
  `$1\n<!-- Widget -->\n<span>w</span>\n<!-- /Widget -->`);

移除端用 \s* 吃掉了块前后的空白，写入端却不负责把这些空白补回去。跑三次的实际输出：

run1: len=121
run2: len=119
run3: len=119

第一遍和第二遍的长度不同，第二遍之后才稳定。原因很直白：第一遍是「删除什么都不做、只做注入」，此时块后面的空白还是文件原有的；第二遍先把块连同两侧空白一起吃掉，再写回一份不带尾部空白的版本，长度因此短了 2 个字符。

这种模式下，git status 会出现一次「无意义的空白 diff」，reviewer 会以为有人手改过文件；而如果构建产物被部署，第一遍的产物和稳定态产物是两个不同版本。

让吃掉的空白等于写回的空白

对称规则可以用一句话表达：移除端吃掉的空白，必须与写入端写回的空白逐字节相同。实现上，让两端只处理「锚点之后到块结尾」这一段，不碰块之外属于文件自身的分离空白：

// ✅ 两端严格对称：移除吃掉锚点后的空白，注入写回同量的空白
let out = orig.replace(/\n*[ \t]*<!-- Widget -->[\s\S]*?<!-- \/Widget -->/g, '');
out = out.replace(/(<div class="post-tags">[\s\S]*?<\/div>)/,
  `$1\n\n        <!-- Widget -->\n        <span>w</span>\n        <!-- /Widget -->`);

同样的三次连跑：

run1: len=146 md5=8da03c4d1fec879e21413ebb8485b23a
run2: len=146 md5=8da03c4d1fec879e21413ebb8485b23a
run3: len=146 md5=8da03c4d1fec879e21413ebb8485b23a

三次结果的长度和 md5 完全一致，第一遍就是不动点。样本仓库的专栏注入脚本里，这条规则是以注释的形式写下来的：「缩进与移除正则严格对称：吃掉的空白 == 写回的空白」。

用两连跑断言收敛

改成对称之后，把「一遍收敛」变成可以自动判定的条件：

node scripts/generate-index.js
FINGERPRINT_1=$(md5sum blog/index.html index.html sitemap.xml | md5sum)
node scripts/generate-index.js
FINGERPRINT_2=$(md5sum blog/index.html index.html sitemap.xml | md5sum)
[ "$FINGERPRINT_1" = "$FINGERPRINT_2" ] && echo "PASS: 一遍收敛" || echo "FAIL: 需要第二次构建才稳定"

输出的期望结果是 PASS: 一遍收敛。这条断言比「看 git diff」更严格，因为它在同一次会话里排除了「git 忽略了某个产物」的可能性。

六、把元数据抽成 sidecar，让真相源唯一

前五节解决的是「相同的输入产生相同的输出」。这一节解决另一个方向的问题：输入本身从哪来。如果元数据是靠正则从生成物里反解的，那么构建的正确性依赖于模板的 HTML 细节，模板一改，元数据解读就集体漂移。

正则反解 HTML 的三种失败方式

从文章 HTML 里正则提取标题、描述、日期，在仓库规模小的时候看不出问题，规模上来后有三种必然失败：

  • 正文撞车：文章正文里恰好出现 <span class="tag"> 或一段形如日期的文本，正则抓到了正文里的字符串，而不是元数据区。
  • 模板改动静默失效：模板调整属性顺序、换标签、加一层 div，正则匹配失败后返回空串，而空串会被当成「这篇文章没有描述」静默接受。
  • 回刷后语义漂移：回刷脚本从 HTML 提元数据、再套模板重渲染，一次成功的回刷会把「上一版生成物的解读结果」固化成新的元数据，误差被逐次放大。

样本仓库的回刷脚本在自己的文档字符串里就写下了这个隐患的结论：元数据从 HTML 正则提取，如需增强，「可考虑在文章 HTML 中嵌入元数据块」。这句话指的就是把元数据从生成物里剥离出来。

让 sidecar 成为唯一真相源

做法是每篇文章配一份独立的元数据文件，与文章 HTML 同步落盘，索引重建优先读它：

{
  "slug": "idempotent-reproducible-builds",
  "title": "幂等与可复现：为什么你的构建总在产生无意义的 diff",
  "description": "从 mtime 并列裁决、无条件写盘到不对称正则，拆开构建噪声的三个真实来源……",
  "date": "2026-09-27",
  "dateTime": "2026-09-27 15:52:00",
  "category": "开发",
  "tags": ["构建", "幂等", "可复现", "工程实践"],
  "readTime": 14
}

放在 blog/meta/<slug>.json，与 blog/posts/<slug>.html 一一对应。读取端按「sidecar 优先、正则回退」的顺序取字段，而且回退粒度是字段级而不是文件级——这样部分字段缺失时仍然可以工作：

// 元数据 sidecar 优先：字段取 sidecar，缺失字段回退正则
function readSidecar(slug) {
  const p = path.join(META_DIR, slug + '.json');
  if (!fs.existsSync(p)) return null;
  try {
    return JSON.parse(fs.readFileSync(p, 'utf-8'));
  } catch (e) {
    console.warn(`⚠️ blog/meta/${slug}.json 解析失败，回退正则: ${e.message}`);
    return null;
  }
}

const sidecar = readSidecar(slug);
const title = (sidecar && sidecar.title) || regexTitle(html);
const date  = (sidecar && sidecar.date)  || regexDate(html);

配套要做两件事：存量回填（给已有文章批量生成 sidecar，并逐字段核对与正则结果一致）和门禁断言（见下节 b 组），否则 sidecar 会慢慢变成一份没人维护的平行数据。

回填之后用门禁守住一致性

回填一次脚本就能完成，难的是此后不再漂移。门禁里至少要断言三件事：sidecar 与文章文件一一对应（不能多、不能少）、slug 字段与文件名一致、dateTime 可以被解析成合法时间。

node scripts/verify.js

✅ verify.js 全部通过（posts/index/meta 各 111 条对齐，静态相关与静态分页门禁通过，主页面版本一致）

这条输出里的「各 111 条对齐」就是集合对账的结论：blog/posts/*.html 的文件名集合、索引 JSON 里的 slug 集合、blog/meta/*.json 的 slug 集合，两两双向相等。

七、把「零改动」写成可执行的门禁

前面所有修法都有一个共同弱点：它们靠人记得。人一忙，绕过校验直接 push 的路径就会出现。把纪律变成退出码，才算落地。

门禁要断言的五件事

按「能自动判定就不要靠人眼」的原则，门禁脚本应该覆盖这些断言，任一条失败即以非零码退出：

  1. 集合对账：文章文件、索引 JSON、元数据 sidecar 三处集合双向相等，缺一篇、多一条都要报错并列出名字。
  2. 元数据可解析：每份 sidecar 的 slug 匹配文件名，dateTime 能解析成合法时间；解析不出来的直接失败，不进入排序。
  3. 并列裁决有锚：索引里同刻条目的相对顺序与上一次已提交索引一致——也就是跑一遍构建后 git status --porcelain 为空。
  4. 体积线：索引 JSON 超过预警线只提示、超过阻断线直接失败。索引膨胀到某个规模说明架构该换了，让门禁替你做这个判断。
  5. 静态分页自洽：页数等于「总数除以每页条数向上取整」，每页卡片数在合理区间，跨页无重复，合计等于总数，每页有自指 canonical 与可达的上一页/下一页链接。

第 3 条的本质就是本文第一节那条两连跑命令，只是被固化成了门禁的一部分。样本仓库的门禁把这份清单实现成了七组断言（a 至 g），任何一组不一致都会打印具体到条目的错误信息，然后以 exit 1 阻断发布。

用 md5 做一遍收敛断言

门禁脚本之外，再加一条幂等断言，成本极低：

#!/usr/bin/env bash
set -euo pipefail

ARTIFACTS="blog/articles-index.json blog/index.html index.html sitemap.xml rss.xml"

node scripts/generate-index.js > /dev/null
md5sum $ARTIFACTS > /tmp/idem-1.md5
node scripts/generate-index.js > /dev/null
md5sum $ARTIFACTS > /tmp/idem-2.md5

diff /tmp/idem-1.md5 /tmp/idem-2.md5 && echo "PASS: 两连跑产物一致"
test -z "$(git status --porcelain)" && echo "PASS: 无内容变化时零 git 改动"

在样本仓库上跑出来的完整结果：

✅ 静态相关文章: 111 篇处理，0 篇写入，每篇 top 5（<3 条的 0 篇）
✅ sitemap.xml: 111 articles
✅ sw.js: cache version unchanged (c-8aecd35c), skip write
PASS: 两连跑产物一致
PASS: 无内容变化时零 git 改动

两行关键证据：0 篇写入 说明相关文章内联步骤在内容不变时没有任何落盘动作；cache version unchanged, skip write 说明 Service Worker 的缓存版本号是按内容哈希算的，哈希不变就不写文件。这两条加上前面 md5 的比对，构成完整的幂等证据链。

把门禁接进发文链

门禁不能是「可选的一步」。把它挂在构建脚本的末尾，让发布流程无法跳过：

# 索引重建成功后跑门禁，不通过则以同码退出（阻断发布）
vresult = subprocess.run(['node', 'scripts/verify.js'], capture_output=True, text=True, cwd=proj_root)
for line in (vresult.stdout + vresult.stderr).strip().split('\n'):
    if line.strip():
        print(f"  {line}")
if vresult.returncode != 0:
    print("❌ 一致性校验未通过，请修复后重新运行")
    sys.exit(vresult.returncode)

同一份构建脚本里还有一条值得抄的纪律：目标文件已存在时拒绝覆盖，必须显式传 --force 才允许，否则以 exit 2 退出。这条保护挡住的是最昂贵的一类事故——同名覆盖让一篇已发布文章整篇消失，而 git 历史里只剩一次「内容替换」。

八、带状态的任务必须成功后才推进

前面讨论的都是「无状态构建」：输入是仓库内容，输出是产物，跑多少次都一样。还有一类任务天生带状态——增量抓取、增量日报、断点续传的同步。这类任务里最常见的顺序错误，就是先推进状态、再执行动作。

先推进状态再执行，失败就丢事件

# ❌ 先写水位线，再处理数据：中途失败就永久丢掉一段事件
def run_daily():
    last_seen = read_watermark('watermark.txt')
    new_events = fetch_events(since=last_seen)
    write_watermark('watermark.txt', latest_ts(new_events))   # 水位线先推进
    for event in new_events:
        render_and_send(event)                                  # 这里抛异常…

如果第 7 行的发送因为网络抖动抛了异常，水位线已经写到了最新时间戳。下一次运行会从新的水位线开始拉取，那些没发出去的事件不会重来——数据静默丢失，而且没有任何日志会显示丢失，因为「拉到过、也推进过」。

用状态锚点做幂等重放

正确顺序是把水位线的推进放在成功之后，并且锚点本身要能表达「处理到哪」，而不是一个单调的时间水位：

# ✅ 成功后才推进水位线；锚点写入走字节比对，重放安全
def run_daily():
    anchor = read_anchor('anchor.json')          # {"last_id": "...", "date": "2026-09-27"}
    events = fetch_events(after_id=anchor['last_id'])

    processed = []
    for event in events:
        render_and_send(event)                    # 先完成副作用
        processed.append(event['id'])             # 全部成功才记录

    if processed:
        write_if_changed('anchor.json', json.dumps({
            'last_id': processed[-1],
            'date': today(),
        }, ensure_ascii=False, indent=2))

三个设计要点：

  1. 锚点用稳定 ID 而非时间戳。时间戳会并列（和第三节的排序问题同源），并列就会漏事件或重复事件；单调递增的 ID 没有这个问题。
  2. 锚点写入走字节比对。重放时锚点内容相同就不落盘，避免「每次重放都刷一次 mtime」，也避免锚点文件本身成为噪声来源。
  3. 失败时锚点不动，下一次运行重放未完成的那一段。副作用端的接口要能容忍重复（发送前查重、或按 ID 幂等写入），这就是幂等在这里的落点。

补一条可观测的校验

顺序改对之后，加一条能断言的校验，避免回归：

python3 - <<'PY'
import json, datetime
anchor = json.load(open('anchor.json'))
# 锚点时间不得晚于当前时间，且必须早于或等于最后一次产物的覆盖时间
assert anchor['date'] <= datetime.date.today().isoformat(), "锚点跑到未来了"
print(f"PASS: 锚点 date={anchor['date']} last_id={anchor['last_id']}")
PY

这条断言检查的是锚点语义而不是语法：锚点一旦跑到未来，说明某次推进写入了不该写入的时间，后续拉取会长期空转。

九、发布前照这份清单逐条打勾

把上面九节的结论压成一份可以直接照做的清单。每一条都对应一条命令或一个可判定的结果。

构建层：产物是否收敛

  • 两连跑构建，产物 md5 逐字节相同。
  • git status --porcelain 为空——没有内容变化时不产生任何 git 改动。
  • 排序比较器没有任何来自文件系统的输入（mtime、遍历顺序都不算合法输入）。
  • 并列裁决的依据存在于版本控制中，而不是存在于某台机器的文件系统里。
  • 所有写入路径都经过字节比对；写盘的数量等于「内容真正变化」的数量。

内容层：真的变了吗

  • 日志里的写入计数能被解释：0 篇写入 是可接受的结果，111 篇全部写入 在内容未变时就是噪声。
  • 注入与移除的正则逐字节对称，注释与实现描述同一套行为。
  • 元数据只从 sidecar 读取，正则只作字段级回退。
  • 门禁脚本以退出码表达结论，且挂在发布链的末尾，无法被绕过。

发布层：线上是否可达

  • 门禁以 exit 0 通过，非零时不推送。
  • 提交身份、作者邮箱与仓库约定一致，提交后用一条只读命令复核。
  • 推送后实测线上地址返回 200，且页面包含本次标题。
  • 首页、列表页、索引 JSON、sitemap、RSS 五处都能查到本次发布的标识。
  • 若线上持续 404，先看首页响应头的 last-modified：它若不包含本次构建时间，说明站点构建没有被触发，用一次空提交触发重建，而不是归因于内容错误。
git -c user.name=zzdbilly -c user.email=billycust716@gmail.com commit -m "新增文章：示例标题（example-slug）"
git log -1 --format='%ae'
curl -sS -o /dev/null -w '%{http_code}\n' -A 'Mozilla/5.0' https://example.com/blog/posts/example-slug.html

预期的两条输出依次是约定的作者邮箱与 200。

回到开头那个问题：构建为什么总在产生无意义的 diff。答案不是「工具不行」，而是构建的输入里混进了三样不属于内容的东西——文件的修改时间、目录的遍历顺序、以及「上一版产物被反解出来的字段」。把这三样逐一换成版本控制里的事实，diff 就会回到它本来的含义：只显示有人真的改了内容。
