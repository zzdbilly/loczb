软删除买的是后悔药，付的是每条查询的利息

📅 2026-10-26 15:30:00 ⏱️ 16 min read 👤 张小猛
数据库设计 软删除 数据建模 PostgreSQL

一笔看起来划算的买卖

上个项目的运营同学在群里发了一份「近期活跃用户」名单，说准备做一轮召回。名单发出去十分钟，有人回了一句：这里面有好几个是上个月自己注销的账号。

查下去不复杂。导出脚本是两周前新加的，写脚本的同学不知道 users 表上有一个 deleted_at 字段——这个字段从来没进过文档，它的全部存在感就是散落在几十处 where 里的一个条件。新脚本没带这个条件，于是把「逻辑上已经不存在的人」原样交了出去。

这件事之后我重新算了一遍软删除的账。当初加那个字段花了十几分钟：一个 nullable 时间戳、一个 @updatedAt 风格的赋值、把 delete 换成 update。买到的能力是「误删能救回来」，价格看起来只有十几分钟。

但账单不是一次性的。它是一个按查询计息的负债：每一条读路径、每一个 JOIN、每一次 schema 演进、每一个新入职的同事，都要再付一次。这篇文章就是把这笔账逐笔摊开——不是要证明软删除一无是处，而是想说清它到底在为什么收费。

出事的那条查询

值得说明的是，那份名单的 SQL 单看没有任何毛病：字段选对了、时间范围对、索引命中、执行时间也在可接受范围内。它错的地方在语义层——它回答的是「哪些行还在表里」，而运营问的是「哪些人还是用户」。

这两件事在加了软删除之后就不再等价，而数据库没有任何机制会提醒你它们不等价。

后悔药的定价方式

我把这笔账拆成六笔利息：过滤税、唯一索引冲突、级联失效、表与索引膨胀、语义混淆、合规落差。每一笔都能指出钱花在哪一行代码、哪一个约束上。先记账，再说什么时候这笔账是划算的。

第一笔：过滤税

WHERE deleted_at IS NULL 本身不值钱，值钱的是它必须出现在所有地方。

具体到位置：列表查询的 where、详情查询的 where、include 里每个关联表的 where、JOIN 的 on 子句、聚合的 count／sum、原生 SQL、报表导出、定时同步任务、后台运维脚本、BI 工具直连。这不是一个「记得加一次」的条件，而是一个必须沿着所有读路径复制的不变式。

这条谓词要出现的所有地方

翻过一个中等规模的模块：读路径几十处，绝大多数是散在各处的 where，只有少数收在 ORM 的统一入口里。加上这个条件之后，数据库层面的正确性被降级成了代码层面的约定——而约定是靠人执行的。

// 每个读入口都得挂一次 scope，漏一个就是一次静默的数据事故
export async function listOrders(userId: string) {
  return prisma.order.findMany({
    where: { userId, deleted_at: null },
    include: {
      items: { where: { deleted_at: null } }, // 关联表也得再来一次
    },
  });
}

注意上面这段的形状：一个函数里出现两次同样的条件，而它们之间没有任何约束关系。下一次有人加一个 comments 关联，第三个条件会不会写上，取决于他当天有没有看到这段代码。

漏掉的代价是静默的

这是它跟大部分 bug 的区别。忘记加事务，并发下会报错；忘记加索引，慢查询会被监控抓到；忘记加 deleted_at IS NULL，什么都不会发生——直到某个把已删数据当真的人做了决定。

没有异常、没有日志、没有告警。系统在「看起来一切正常」的状态下把错误的数据交出去，而你发现它的时机，往往是有人拿着这份数据来问你为什么。

第二笔：唯一索引跟软删除打架

用户注销账号，半年后想回来，用同一个邮箱重新注册——unique constraint violation。因为旧的那一行还在，还占着 email 的唯一键。

这是软删除最典型的翻车点，也是最难在代码评审里看出来的：注册失败的错误信息指向「邮箱已被使用」，而用户明明已经注销了，客服查后台也查不到这个邮箱对应的有效账号。

被软删的行仍然占着键

唯一约束是数据库层面的、无条件的。它不知道 deleted_at 这回事，也不会因为你业务上认为那一行「不存在」就放行。你想让「已删的邮箱可以再次注册」，就必须把唯一性从「全表」缩小到「仍然有效的行」。

model User {
  id         String    @id @default(cuid())
  email      String    @unique   // 对被软删的行同样生效
  deleted_at DateTime?
}

部分索引能救，但要离开 schema

PostgreSQL 支持带条件的唯一索引，问题能解：

CREATE UNIQUE INDEX users_email_active_key
  ON users (lower(email))
  WHERE deleted_at IS NULL;

代价在工具链。Prisma schema 里没有语法能表达「带 WHERE 的唯一索引」，这条 DDL 只能手写进 migration：先 prisma migrate dev --create-only 生成空壳，再手工编辑 SQL。从此这份索引定义脱离 schema 这个单一真相源，谁跑一次 prisma db push，它就可能被静默抹掉。

顺带一提，MySQL 没有部分索引，同等问题要靠生成列（已删时置 NULL、有效时置邮箱）加唯一键绕过去，绕法本身又要写进文档，否则下一个人看不懂那列是干什么的。

一个为了「恢复能力」加的字段，最终换来了一个 schema 表达不了的索引、一份手工维护的 migration、一段需要口头传承的 MySQL 绕行方案。这些都是利息。

第三笔：外键与级联失效

ON DELETE CASCADE 的触发条件是「行被删除」。软删除执行的是 UPDATE，外键约束一动不动，级联一次都不会发生。

于是订单「删」了，order_items 还在；用户注销了，他的收货地址、登录 token、上传文件的元数据、消息记录全都留在原地。这些关联数据本来由数据库在一条语句里原子清掉，现在要在应用层重写一遍。

CASCADE 只听 DELETE 的话

重写不是把清理逻辑挪个位置那么轻。数据库的级联在一个事务内完成，顺序由约束定义；应用层的「级联」是若干条语句，你得自己规定顺序（先删子还是先删父）、自己包事务、自己保证幂等（重跑一次不能报错，也不能把数据删两遍）。

应用层的级联要自己保证原子

更现实的问题是覆盖率：任何一张新加的、引用 users 的子表，都要回到那段清理代码里补一行。漏掉的那张表不会报错，它只会安静地把已注销用户的数据留在库里，直到某次数据核对或者合规审查把它翻出来。

数据库把这件事做对是一次性的，应用层把它做对是持续性的——每加一张表，就重新赌一次。

第四笔：表里的幽灵与索引膨胀

已删的行还在数据页里，还在每一个索引里，还参与顺序扫描，还会被 ANALYZE 采样进统计信息。

B-tree 索引不会因为你逻辑上不再查它而收缩。行还在，索引项就在；顺序扫描读的页数不变；优化器估算的行数包含了这些永远不会被返回的行——估算偏离到一定程度，执行计划就可能走错，而这类问题从慢查询日志里看不出原因，因为 SQL 本身写得没问题。

索引不知道你逻辑上删了

部分索引（WHERE deleted_at IS NULL）可以缓解这一点：索引里只放有效行，体积跟着有效数据走。但它要求每一条查询都带上同样的谓词，优化器才会用这个索引——于是「过滤税」这一笔，在性能层面又收了一次。

删得越多，口径越分裂

当「删掉的比活着的多」，问题从「浪费一点磁盘」变成「口径分裂」：count(*) 是错的，分页的 total 是错的，导出要加条件，报表和埋点对不上，数据仓库同步过去的宽表里混着两种语义的行。

每一处都要单独判断「这里该不该过滤」，而判断依据不在数据库里，在那个人脑子里。

第五笔：一个字段长出四个字段

deleted_at 是技术二值：有值或者没值。而业务上真正需要区分的状态，往往不止两种。

用户自己注销、被风控停用、订阅到期归档、临时冻结——对外表现都是「不能登录」，但恢复路径、通知策略、数据保留期限、是否允许重新注册，每一项都不同。用一个 nullable 时间戳去近似这台状态机，信息必然丢失。

二值表达不了状态机

丢失的信息会被补回来，方式通常是加字段：deleted_by（谁删的）、delete_reason（为什么）、restored_at（恢复过没有）、is_system_deleted（是用户操作还是系统清理）。半年之后，那张表上有五个字段共同描述「这个账号现在算什么状态」，而没有一个字段能单独回答。

字段长成表

这就是「一个字段长成一张表」的过程：不是因为设计时想复杂，而是因为用技术标记去近似业务状态，必然要不断打补丁。补丁之间没有互斥关系，于是出现了 deleted_at 有值但 restored_at 也有值、is_system_deleted 为真而 delete_reason 为空的组合——每一种组合在代码里对应一个 if，没人能穷举完。

CREATE TYPE account_status AS ENUM ('active', 'suspended', 'archived', 'closed');

ALTER TABLE accounts
  ADD COLUMN status account_status NOT NULL DEFAULT 'active',
  ADD COLUMN status_changed_at timestamptz NOT NULL DEFAULT now();

枚举把「互斥且完备」写进了类型里。archived 和 closed 的区别写在类型定义旁边，而不是藏在三个布尔字段的组合里。读代码的人不需要还原状态机，他直接看得见。

第六笔：合规上的反讽

这一笔不谈法律，只核对工程事实。

如果隐私政策里写了「你可以要求我们删除你的数据」，而实现是 UPDATE users SET deleted_at = now()，那么对外承诺的删除和实际执行的删除是两件事。数据还在主表里、还在从库上、还在备份里、还在数据仓库的宽表里、还在某个没人记得的导出文件里。

承诺删除和打了标记不是一回事

用户按下「删除账号」时理解的是数据消失。系统做的是给一行打个标记，然后继续在每一条查询里把它过滤掉。这两者之间的差距，不会因为前端提示写得温和就变小。

要留痕就建留痕的表

反过来看，确实存在必须保留历史的场景：财务凭证、审计要求、争议处理。这类诉求是合理的，问题在于把它塞进主表。

正确的位置是单独的 history／audit 表：写时复制一份旧行，记下操作人、时间、原因、来源。主表保持窄，保持「删了就是删了」。这样审计轨迹是完整的（因为它是为审计而设计的），主表也不会变成一个既存当前状态又存历史状态的混合体。

把两件事压进一张表，两边都做不好：主表变胖、查询变慢、语义变糊，而审计轨迹依然缺字段——因为 deleted_at 记不下「谁」和「为什么」。

这笔账什么时候是划算的

写到这里必须公平一点：软删除不是一无是处，它在三种场景下确实成立。但要看清它成立的原因，以及那个原因是否真的需要一个主表字段。

三种它确实成立的场景

  • 短窗口撤销：误点删除后十五分钟内能恢复。这个需求是真的，但它要的是「一份临时副本」，不是「主表上的永久标记」。回收站表加 TTL 清理能做得更好：主表删除就是删除，撤销是从回收站搬回来，过期由定时任务物理清理。
  • 法规或审计要求保留历史：需求是真的，位置错了。history／audit 表按写时复制保存旧版本，主表只承载当前状态，职责单一。
  • 业务状态本身就有「已取消／已归档」语义：那就用 status 枚举，值叫 cancelled、archived，不要叫 deleted。名字对了，过滤条件自然变成「哪些状态参与业务」，而不是「哪些行被逻辑删了」——前者是业务规则，写在领域层是合理的；后者是技术补丁，散在每一处 where 里。

分界线在哪

一句话能分开：这个标记是为了让数据消失，还是为了让数据进入另一种状态？

前者属于生命周期管理和备份层，不该出现在表结构里；后者属于状态机，应该是一个有语义的枚举。软删除的问题在于它把这两件事混成了一个字段——于是两种诉求都得到了一个勉强的近似。

怎么把账做平

如果认同上面的记账，落地动作是四个，按投入产出排序。

恢复能力挪到备份层

这是整个主张的核心。误删要能救回来，靠的不是表上的标记，是备份加恢复演练：

  • PITR：WAL 归档加基础备份，能恢复到任意时间点。误删发生在 14:32，就恢复到 14:31:59。
  • 定期逻辑备份：pg_dump 出来的东西用于跨版本迁移、单表恢复、以及「只想捞回一张表」的场景。
  • 定期恢复演练：这一项最容易被跳过，也是唯一能证明前两项有效的动作。没演过的备份不叫备份，叫「我以为是备份的文件」。

演练要落到可验证的数字上：恢复到某个时间点需要多久、能接受丢多少数据（RPO／RTO），每季度真跑一次，把耗时记下来。这笔投入是一次性的，而且不随查询数量增长——这正是它跟软删除在成本结构上的根本区别。

状态交给枚举，历史交给副本，撤销交给回收站

三条各自对应一种真实需求，互不重叠：

  1. 主表的业务状态用 status 枚举表达，名字用业务语言。
  2. 要留历史，写时复制进 history 表，主表保持窄。
  3. 要撤销窗口，用回收站表加 TTL，主表删除就是删除。

第三条的表结构大致是这样：

CREATE TABLE deleted_orders (
  id          uuid PRIMARY KEY,
  payload     jsonb NOT NULL,          -- 删除瞬间的整行快照
  deleted_by  uuid NOT NULL,
  deleted_at  timestamptz NOT NULL DEFAULT now(),
  purge_after timestamptz NOT NULL     -- 过期由定时任务物理删除
);

CREATE INDEX deleted_orders_purge_idx ON deleted_orders (purge_after);

它的好处不只是「主表干净」。回收站表的行有明确的生命周期（到期就物理删），所以磁盘增长是有界的；而主表上的软删除行没有终点，删了就是永久占位。

判据

三条问句。任何一条答不上来，就先别加那个字段：

  1. 这个字段是为了让数据消失，还是让数据换状态？ 如果是前者，它属于备份层和生命周期管理，不属于 schema。
  2. 明天新增一条读路径（报表、导出、BI 直连、数据同步），谁会记得加这个谓词？ 如果答案是「靠 code review」，那这个不变式其实没有保障，只是在赌评审的人当天状态好。
  3. 如果用户现在要求删除，我能诚实地说「删了」吗？ 如果不能，那么「删除」这个功能要么改承诺，要么改实现，不能靠一个 nullable 时间戳把差距盖住。

收束

软删除真正卖的不是「恢复能力」，是「暂时不用想恢复这件事」——十分钟加一个字段，把问题往后推。

代价是把数据库的一次性正确性，换成了代码里的持续约定。过滤条件要复制到每条读路径，唯一约束要让位给手写 migration，级联要在应用层重写，索引里躺着永远不会返回的行，一个技术二值被迫承担一台状态机，对外承诺的删除变成一个标记。这些都不是 bug，是设计选择的正常账单，只是它按月寄、按查询寄。

备份层的投入形状正好相反：配一次 PITR，写一次演练脚本，每季度跑一次，成本固定，不随读路径数量增长。

所以我的判断是：删除语义应该只有一种，就是删除。可恢复性属于运维，不属于 schema。
