读副本的延迟不是毫秒问题，是因果问题

📅 2026-11-13 15:27:00 ⏱️ 14 min read 👤 张小猛
复制 一致性 分布式 读写分离

延迟是一个时长，因果是一条顺序

监控面板上的复制延迟是一条以毫秒为单位的曲线。它偶尔抬头，然后回到零，告警解除，值班结束。但如果在这条曲线抬头的几百毫秒里，正好有用户下了单又跳去详情页，他看到的东西不是「慢」，是「不存在」。

这是两个不同的度量，常被混成一个：

  • 延迟回答的是「副本落后了多久」。它是一个时长，连续、可平均、可画分位数。
  • 因果回答的是「这一次读，有没有看到它本该看到的那次写」。它是一个顺序判断，只有成立与不成立。

把前者压到很小，不等于后者成立。一条 1ms 的延迟曲线下面，依然可以藏着一次「读到的副本还没回放到我上一次提交」；而一条 200ms 的曲线，如果用户写完之后隔了半分钟才读，可能一次违反都没有。

问题的源头在读写分离的路由层。写请求进主库，读请求按负载分给任意副本，每一次请求独立选节点。这个设计里没有任何地方保存「这个用户刚刚写到了哪个位置」，所以顺序信息在路由层就丢了。丢的不是精度，是事实。

t=0ms    客户端   POST /orders              -> 主库
t=1ms    主库     提交完成，返回 201        -> 客户端
t=2ms    客户端   GET /orders/123           -> 副本 A
t=2ms    副本 A   回放位置还停在上一次事务  -> 404 Not Found
t=40ms   副本 A   追上，这一行才可见

（上图是示意，用于说明请求的先后，不代表任何产品的实测时序。）

注意失败发生的位置：写成功了，读也成功了，两个请求各自的日志都是 200，慢查询里没有记录，错误率没有变化。故障不在任何一个请求内部，而在两个请求之间。

四条承诺：把「一致性」拆成可验收的句子

笼统地说「最终一致」没有可操作性，因为它不告诉你哪一次读可以旧、旧到什么程度。分布式系统文献里常把这方面的约束拆成四条会话保证（session guarantees），单位不是单次请求，而是同一个用户的连续请求构成的那个会话。

拆开之后，每条都可以单独验收：它承诺什么、谁在破坏它、破坏了用户看到什么、守住它要付什么代价。下面四条各写这四件事。

承诺 一句话 被破坏时用户看到 守法的主要成本
读己之写 自己刚提交的写，自己一定读得到 「我刚存的东西不见了」 写后的一段时间读主库，或校验副本位点
单调读 同一个会话不会先看到新值、再看到旧值 「刚才明明有，刷新又没了」 会话固定到同一个副本
单调写 同一个会话的写按提交顺序生效 「我后改的那次被前一次盖了」 按用户或实体收束写入点
读后写 基于某次读做的写，排在那次读之后 「别人的修改被我的保存覆盖了」 带上读到的版本做条件更新

四条之间是正交的，不是一条比一条强。会话粘住一个副本能守住单调读，但如果那个副本一直落后于你自己刚提交的写，读己之写照样破。给写后读加位点校验能守住读己之写，但如果两次读分别打到不同副本，单调读仍然会破。把它们当成一张清单逐条问，比记成「一致性等级」更接近实际。

第一条：读己之写

它承诺什么

同一个会话里，一次写成功返回之后发起的读，必须能看到这次写，或者看到比它更新的状态。范围限定在「自己」：别人什么时候看到不在承诺之内，那是另一条线。

谁在破坏它

读写分离加上「每个请求独立选节点」。写落在主库，读落在任意副本，副本的回放位置落后于主库的提交位置，读就落在了一个还没有这次写的快照上。破坏者不是「延迟数值大」，而是「读的路由没有携带刚刚那次写的位置」。

异步复制是最常见的场景，但半同步并不自动解决问题。多数产品的半同步只保证副本收到了日志、或者把日志写进了本地的 relay log，并不保证已经回放完成、对查询可见。PostgreSQL 的 synchronous_commit 有多个等级，其中 remote_apply 才等到副本回放完成，remote_write 只等到写入副本的操作系统；MySQL 一类产品的半同步语义也以「收到并落盘」为主，具体参数名与行为按各自版本文档确认。选错等级，会得到「写变慢了，但读仍然看不到」的结果。

破坏了，用户看到什么

  • 下单接口返回成功，跳转到详情页显示「订单不存在」，用户返回再点一次，产生重复下单。
  • 保存个人资料后页面刷新，头像和昵称还是旧的，用户以为没保存成功，再存一遍。
  • 评论提交成功，但列表里没有自己的评论，于是再发一条，出现两条一样的。
  • 改完密码立刻重新登录，认证服务读到旧密码，提示密码错误。

这几类的共同点是：页面全是 200，业务没有抛错，监控里只有一条平平的延迟曲线。

守住它要付什么代价

有两种守法，代价差别很大。

第一种是时间窗口：写成功之后的若干秒内，这个会话的读走主库。做法便宜，不需要改协议，但窗口长度是猜的。猜短了，尾部延迟一大就漏；猜长了，主库白扛一批本来可以给副本的读。窗口本质上是用一个常数去覆盖一个没有上界的分布。

第二种是位点：写完成时取回这次提交在日志里的位置，跟着会话走；读的时候先问副本「你回放到这个位置了吗」，没有就改读主库或者等它追上。位置由数据库比较，不能拿字符串比大小。

-- PostgreSQL 示意：提交之后取位点，再让副本自己回答「追上没有」
INSERT INTO orders (id, user_id, status) VALUES ($1, $2, 'created');
COMMIT;

SELECT pg_current_wal_lsn() AS commit_lsn;

-- 读之前，在候选副本上执行（函数名随版本变过，以所用版本文档为准）
SELECT
  pg_is_in_recovery()                    AS is_replica,
  pg_last_wal_replay_lsn() >= $1::pg_lsn AS caught_up;

// 读路径：位点不够就读主库。注意比较交给数据库，不在应用层比字符串
async function readYourWrites<T>(
  session: Session,
  run: (db: Db) => Promise<T>,
): Promise<T> {
  const replica = pickReplica(session.userId);
  if (session.minLsn) {
    const { rows } = await replica.query(
      "SELECT pg_last_wal_replay_lsn() >= $1::pg_lsn AS ok",
      [session.minLsn],
    );
    if (!rows[0].ok) return run(primary);
  }
  return run(replica);
}

代价落在三处：多一次位点查询；副本落后时要么等（读的尾延迟变长），要么回主库（主库多承担一部分读）；必须显式定义超时后的行为。超时后回主库，是牺牲容量守住承诺；超时后读副本，是牺牲承诺换取延迟。两种都可以选，但不能选了后者还在文档里写「已保证读己之写」。

位点的形式随产品不同：PostgreSQL 是 LSN，MySQL 一类是 GTID 或 binlog 文件名加偏移。语义是同一个——这个副本有没有应用到我需要的那个位置。

第二条：单调读

它承诺什么

同一个会话不会先看到新值、再看到旧值。用户眼里的时间不会倒流，哪怕数据本身还在追赶。

谁在破坏它

每次读都用轮询或随机的方式选副本。两个副本的回放进度不同，第一次读打到已经追上的那个，看到新值；第二次读打到落后的那个，看到旧值。破坏者不是延迟，是「选节点的策略没有记忆」。

这一条和读己之写经常一起出现，但成因不同：读己之写破在「自己写的还没到」，单调读破在「两次读落在了不同进度的节点上」。后者甚至不需要有写发生——只要副本之间的进度有差异，重复读同一个对象就可能倒退。

破坏了，用户看到什么

发帖成功，回到列表看到了自己的帖子，下拉刷新，帖子没了，再刷新，又出现了。计数从 15 变成 12 再变回 15。两个标签页打开同一个账户，余额显示不同的数字。

这类现象对信任的伤害比「慢」大得多。慢是等一会儿就好，倒退是用户无法判断哪个数字是真的，于是每次操作都要刷新确认一遍。

守住它要付什么代价

会话固定到同一个副本：按会话标识做哈希，落在一个副本上，整个会话期间不换。代价是负载均衡变差——长会话会集中在少数节点；副本故障时必须换，而且只能换到不更旧的节点，随便挑一个可能把倒流放大成一次明显的回退。

一致性哈希能把这个代价压小：故障时只重映射一部分会话，而不是把全部会话重新洗牌。

// 单调读：会话固定副本；换节点时只能往上换，不能往下换
const ring = new ConsistentHash(replicas, 128);

function replicaFor(session: Session): Replica {
  return ring.get(session.id) ?? primary;
}

function onReplicaFailure(session: Session, failed: Replica): Replica {
  const next = ring.nextAfter(failed);
  // 新节点的回放位置不得低于旧节点，否则宁可读主库
  return next.replayedAtLeast(session.lastSeenLsn) ? next : primary;
}

守住单调读还要在会话里记住「上次读到的最低位点」，换节点时用它做下限。这个字段很小，但它把「随机选一个」变成了「选一个不更旧的」。

需要说明的是，粘住副本不解决读己之写：副本可能一直落后于你刚提交的写，粘得再稳也只是稳定地看到旧值。两条承诺要分别守。

第三条：单调写

它承诺什么

同一个会话发出的写，按提交顺序被应用。后提交的不会先落地，先提交的不会覆盖后提交的。

谁在破坏它

单主复制的场景里，这一条通常是白送的：主库的提交顺序就是日志顺序，副本按顺序回放。破坏一般来自三个地方：

  • 写被路由到多个接受写入的节点（多主、双写、按分片打散），两个节点之间没有全序。
  • 客户端并发提交，服务端没有按用户串行化，两个写在不同连接上竞争。
  • 重试。第一次请求超时但实际成功了，客户端重发，于是同一个逻辑写变成了两次物理写，中间还可能插进别的写。

破坏了，用户看到什么

改了两次昵称，最后显示的是第一次的。先把任务标记完成、再撤回，过一会儿又变回完成。更隐蔽的是「我的修改被覆盖了」，而两次保存都提示成功——用户只能归因于系统不可靠。

守住它要付什么代价

按用户或实体维度收束写入点：同一个用户的写永远进同一个主库、同一条连接池队列，需要串行化的部分显式串行。代价是写入扩展性——你放弃了一部分「把写打散到多台」的自由。

如果业务确实要多写入点，那就只能把「顺序」降级成「可检测的冲突」：给每行带版本号或逻辑时钟，写入时校验版本，冲突就拒绝并让上层处理。代价是写路径要能接受失败、界面要能展示冲突，而不是静默地 last-write-wins。

幂等键是成本更低的一半：它不保证顺序，但保证重试不会变成第二次写。很多「顺序错了」的案例，实际是「重试多写了一次」。

第四条：读后写

它承诺什么

基于某次读的结果做出的写，在因果上排在那次读之后。用户读到 v3，基于 v3 改，这次写就应该作用在「已经包含了 v3 的状态」上，而不是作用在一个 v3 已经被别人改过的状态上。

谁在破坏它

读到旧值，基于旧值写，写到主库。主库此时可能已经是新值，写入把旧前提带了回来，覆盖掉中间那次修改。另一类是同一个人在两个标签页里各读一次、各写一次，后写的那次基于更旧的前提。

这一条常被误认为「读主库就没事」。读主库只保证你读到的是最新的，不保证你读完之后别人不写。它要的是「我读到的前提在写的时候仍然成立」，那是并发控制，不是路由。

破坏了，用户看到什么

「我只改了一个字段，别人的改动没了。」库存读到 1，两个人同时扣减，最后是 -1。回复了一条已经被删除的评论，页面上留下一个指向空白的引用。

这类事故最难受的地方在于它不可复现：两次操作都合法，只是顺序不对，日志里找不到异常。

守住它要付什么代价

把读到的版本带回写路径，用条件更新让主库拒绝过期前提：

// 读后写：版本一起带回来，主库只在前提仍成立时才写
const { rows } = await primary.query(
  `UPDATE documents
      SET body = $1, version = version + 1, updated_at = now()
    WHERE id = $2 AND version = $3
  RETURNING version`,
  [body, id, readVersion],
);

if (rows.length === 0) {
  throw new ConflictError("这份内容已被修改，请重新加载");
}

代价是引入版本列、写可能失败、界面要能处理冲突。把冲突显示出来，比让它静默地丢一次修改更接近正确。另一种守法是悲观锁：读的时候加锁，写到提交为止。它把冲突变成等待，代价是锁持有时间直接换算成并发上限。

两种修法的性质不同：一个赌概率，一个消除条件

看到「读到了旧数据」，第一反应通常是让复制更快：加带宽、换同步提交、多挂几个副本、把大事务拆小。这些都对，但它们改变的是概率，不是条件。

只要「提交」和「副本可见」之间存在非零窗口，就存在读落在窗口里的可能。窗口越小，撞上的机会越少，但撞上的那一次并不会因为窗口小就变得无害——用户看到的仍然是「我刚写的东西不见了」。而且窗口的尾部不由你控制：网络抖动、一个大事务、副本上一次全表扫描，都会把某一次窗口拉长。

改路由是另一种性质的修法：写后的一段时间读主库、位点校验、会话粘副本、按用户收束写入点。它不降低延迟，它让「这条路径上不存在能违反承诺的节点」。违反的条件被移除，不是被压缩。

副本延迟（示例） 读己之写被破坏的条件 是否可能被破坏
1ms 读在回放完成之前到达 可能
50ms 读在回放完成之前到达 可能
0（读主库或同步回放） 不存在这个回放窗口 不可能

表里的毫秒只是示意，用于对照三种情形，不是实测数据，也不对应任何概率。重点在前两行的结论完全一样：数值变了，条件没变。

两种修法不是二选一，而是分层。降低延迟的收益是全站所有读，代价摊在复制链路上；改路由的收益是特定会话的确定性，代价摊在主库容量和实现复杂度上。合理的组合是：用前者把整体概率压下去，用后者给「违反了就会被认为丢数据」的那部分读兜底。

判断标准可以很具体：如果这次读看到旧值，用户会不会认为自己的操作没生效或者数据丢了？会，就走路由；只是「稍旧但结论不变」，就让副本承担。

指标的盲区：延迟 p99 不会报因果断裂

延迟指标度量的对象是时间，违反度量的对象是顺序。两者之间没有换算关系。

设想一次写提交后 2ms 就读副本，而那个副本此刻落后 3ms。这次读违反了读己之写，但当时的复制延迟只有 3ms，任何以毫秒为阈值的分位数都看不到异常。反过来，一次 200ms 的延迟可能一次违反都没造成，因为那段时间里没有人写完之后立刻读。

（上面两个数字是示意的量级，用来说明「小延迟也能违反、大延迟未必违反」，不是测量结果。）

这解释了一个常见的误判：故障复盘时看延迟曲线，发现「当时延迟很低」，于是排除了复制的嫌疑，转去查缓存和代码。曲线没错，是它测的东西回答不了这个问题。

Seconds_Behind_Source 一类指标还有额外的局限：它是粗粒度的时间估计，空闲时可能显示 0，复制断开时可能是 NULL，它回答的是「落后大概多久」，不是「我这一次写是否已经可见」。具体语义按所用产品的文档确认。

能报出违反的指标是另一类东西，都需要在应用层埋：

  • 写成功之后立刻读回自己写的那条记录，统计读不到的比例。
  • 同一个会话连续两次读同一个对象，统计版本倒退的次数。
  • 条件更新返回 0 行的比例——它同时是「读后写被破坏」和「正常并发冲突」的信号，要配合业务语义看。
  • 会话被路由到主库的比例。这个数突然升高，往往说明副本在落后，而延迟曲线还没反应过来。

复制延迟告警和一致性告警是两条独立的线。只有前者，等于只监控了「慢」，没有监控「错」。

什么时候不必守

把四条承诺当成全站默认，会把主库压垮，也会把系统做成一个没有读扩展性的单点。它们只在特定读上必要。

可以放心读副本的场景：

  • 报表与分析。读的是分钟级聚合，落后几秒不改变结论。给页面标一句「数据截至某时刻」，比强行读主库更有用。
  • 内容分发。文章正文、商品描述、图片元数据，读到旧版本不会让用户认为自己的操作丢了。
  • 明确允许最终一致的写后读。异步任务的状态页、导入进度、通知列表，用户本来就预期它会变。
  • 可以重试且无副作用的后台任务。失败重跑一次即可，不值得为它加一条主库读路径。

必须守的场景：

  • 认证与会话。改密码、改权限之后读到旧值，是安全问题，不是体验问题。
  • 余额、库存、额度。读到旧值会直接导致超卖或透支。
  • 订单状态与支付结果。用户刚付完钱，看到「待支付」，接下来就是重复支付。
  • 任何「写完之后立刻展示结果」的页面。

判据不是「这张表重不重要」，而是「这一次读如果看到旧值，用户会不会认为自己的操作没生效」。前者是表级判断，后者是读级判断。同一张 orders 表，后台报表扫描可以落后几分钟，下单后的详情页一次都不能落后。

把问题从「副本多快」换成「这一个读需要哪条承诺」

设计评审时，与其问「复制延迟多少、能不能接受」，不如对每条读路径问四个问题：

  1. 这个读会不会紧跟在同一个用户的写之后？是，就需要读己之写。
  2. 同一个用户会不会在短时间内重复读同一个对象？是，就需要单调读。
  3. 这个用户的写会不会落到多个写入点，或者可能被重试？是，就需要单调写。
  4. 这次写是否基于刚刚读到的内容？是，就需要读后写。

四个都是「否」，就让它读副本，接受最终一致，并把这个决定写进代码注释——写清楚「这里允许旧数据，因为……」，比默默依赖默认路由可靠。

有一个是「是」，就为这条路径选路由策略：粘主库、位点校验、固定副本、条件更新。而不是回头去调复制参数，指望把窗口压到不会撞上。

复制延迟是一条可以优化的曲线，因果是一条必须成立的顺序。前者用毫秒衡量，可以画图、可以定阈值、可以在周报里变小；后者只能用一个「是/否」验收，而它出事的时候，指标上看不出任何异常。

把「副本多快」换成「这一个读需要哪条承诺」，第一个问题会变得容易，第二个问题才有机会消失。
