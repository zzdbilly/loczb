写在前面

2026 年年中，我做了一个拖延了很久的决定：把跑了大半年的 AI Agent 工作区，从 OpenClaw 整体迁移到 Hermes Agent。

这篇文章是这次迁移的完整记录。我尽量把每个环节——为什么迁、迁了什么、踩了什么坑、最终怎么验证——都写清楚，希望能给同样在纠结"要不要换平台"的朋友一些参考。

说明：本文是个人技术复盘，不涉及具体账号、密钥、项目名等敏感信息；涉及内部细节的位置均已脱敏，只保留迁移方向和方法论。

为什么迁移：告别 OpenClaw

背景：我的 AI Agent 工作区

过去大半年，我一直靠一个"常驻式"AI Agent 帮我干活：写代码、写博客、做部署、做定期任务。它跑在一台 Linux 服务器上，有自己的身份设定、长期记忆、一套技能（skills）和几个独立 git 仓库。

这套体系运转得一直不错，我把它称为我的"第二大脑+第三只手"。但它的底座 OpenClaw 渐渐让我不安：

  • 维护节奏放缓：上游更新越来越少，社区讨论冷清，感觉像是项目被半放弃了
  • 功能天花板明显：我想要的多模型路由、更细的工具权限、更好的会话记忆，它都给不了
  • 核心机制依赖：它的一些"魔法"（比如心跳、自动任务）依赖老旧的进程模型，出问题很难排查

Hermes 进入视野

接触到 Hermes Agent 之后，几个点立刻打动了我：

  • 多 Profile 设计：一个实例可以跑多个"人格"（profile），各自有独立的记忆、技能、工作目录——这正好匹配我"一个开发助手+一个系统助手"的分工需求
  • 原生记忆系统：记忆作为一等公民，长期记忆自动注入每一轮对话，而不是靠人肉维护 markdown 文件
  • 技能体系更规范：SKILL.md 有标准的前端格式（frontmatter + 正文），还能挂载脚本和模板
  • 工具集丰富且现代：浏览器自动化、cron 定时任务、子代理委派（subagent）、图像生成，全都在同一个框架里

程序员的本能告诉我：长期看，迁移到活跃维护、架构更现代的底座，比抱着快停更的旧平台死磕更划算。于是决定搬家。

迁移前的资产盘点

先搞清楚自己有多少家当

迁移第一步不是动手，而是盘点。我拿一张表列了所有"不可再生资源"：

资产类别 具体内容 迁移优先级
身份与人格 各助手的性格设定、沟通规范 P0，不可再生
长期记忆 几年来的用户偏好、项目经验、踩坑教训 P0，不可再生
技能 沉淀下来的各类工作流（博客生成、部署、体检） P0，可转换
项目仓库 好几个独立 git 仓库 P1，本质不用迁移
配置文件 Git / SSH / 包管理器 / 部署相关配置 P1，环境重配
历史日志 每日记忆、会话记录 P2，只读参考

用一句话总结盘点结论：项目代码不用"迁移"，因为它们本来就在独立的 git 仓库里；真正要迁移的是 Agent 的"灵魂"——身份、记忆、技能。

迁移策略：增量还是推倒？

我考虑过两种策略：

方案 A：推倒重来——在新平台重新写身份、记忆、技能，从零开始。 方案 B：数据搬家——把旧平台的标记文件（身份、记忆、日志）备份出来，分析、提炼、再导入新平台。

方案 A 干净但丢失巨大，方案 B 复杂但保留了沉淀。我最终选了 B 为主、A 为辅：

  • 身份和规范类文件：基本保留，只做格式适配
  • 记忆：全部备份，但只把"高价值条目"导入新记忆系统，垃圾信息趁机清理
  • 技能：保留 SKILL.md，按新平台规范检查一遍，过时的直接改

这其实是一次借迁移的机会做的减负——不是把所有历史都搬过去，而是把有价值的搬过去。

目录结构的变化：从 workspace 到 profile

迁移前：单工作区

OpenClaw 时代，一切业务文件都堆在一个大工作区里：

~/.openclaw/
├── workspace-xiaoma/          # 主工作区
│   ├── SOUL.md                # 助手人格
│   ├── MEMORY.md              # 长期记忆
│   ├── IDENTITY.md            # 身份定位
│   ├── TOOLS.md               # 工具配置说明
│   ├── skills/                # 技能目录
│   ├── memory/                # 按日期的记忆归档
│   └── nook/                  # 项目仓库集合
│       ├── project-a/         # 项目 A（独立 git）
│       ├── project-b/         # 项目 B（独立 git）
│       └── project-c/         # 项目 C（独立 git）
├── config.yaml                # 全局配置
└── logs/                      # 运行日志

问题显而易见：一个工作区塞了所有东西——人格、记忆、技能、项目、配置混在一起。想开第二个助手？几乎只能复制整个目录。

迁移后：多 Profile 结构

Hermes 用 Profile（配置文件）隔离一切：

~/.hermes/
├── workspaces/                # 所有工作区
│   ├── dev/                   # 开发助手工作区
│   │   ├── project-a/         # 项目 A
│   │   ├── project-b/         # 项目 B
│   │   └── project-c/         # 项目 C
│   └── ops/                   # 系统助手工作区（全新）
├── profiles/
│   ├── dev/                   # 开发助手 profile
│   │   ├── SOUL.md            # 人格
│   │   ├── skills/            # 该 profile 的技能
│   │   └── memories/          # 该 profile 的记忆
│   └── ops/                   # 系统助手 profile
└── config.yaml                # 全局配置

变化的核心是关注点分离：

  • 工作区（workspaces）只管"业务文件"：项目代码、草稿、产物
  • Profile 只管"人格状态"：身份、记忆、技能、配置
  • 一个实例可以同时挂多个 Profile，各跑各的，互不干扰

这带来的直接好处是：我不用再为第二个助手复制一份工作区，新建 Profile 就行，工作区可以共享（代码仓库只存在一份）。

身份文件的迁移：换格式，不换灵魂

人格文件怎么处理

旧的助手人格文件长这样（简化版）：

## 身份
- 名字：小马
- 角色：开发与写作助手

## 核心原则
- 先理解需求再动手
- 重要决策先确认

新平台对"人格"的承载方式不太一样——它主要读 Profile 里的 SOUL.md，而且支持在每轮对话中注入记忆。迁移时我做的是：

  1. 保留核心：名字、角色、沟通风格、价值观，原样保留
  2. 适配格式：按新平台的 frontmatter / 分节习惯重新组织
  3. 补充运行规范：把过去在实践中积累的"硬性规范"（比如：长任务一口气干完、临时服务用完必须清理）写进去

一个很重要的感悟：人格文件不是给人看的简历，是给 AI 看的运行手册。迁移时不要只顾着"忠实还原原文"，要把这一年多"怎么跟它协作最顺"的经验也沉淀进去。

用户档案的处理

用户档案也一样。旧平台里有一份用户的长期观察记录（技术背景、偏好、工作风格），这属于最不该丢的资产。迁移后直接进入新平台的 user 记忆，保证新底座启动的第一天，AI 就知道我是谁、我喜欢怎么干活。

记忆系统的迁移：从文件到原生

旧模式：人肉维护 markdown

以前我的记忆是这么管的：

## 2026-08-15
- 用户要求：部署改完验证通过后直接 push
- 教训：临时服务用完必须清理
- 项目进展：zest 优化完成

每天一个文件，靠约定维护。问题：

  • 靠人肉记得"今天该归档了"，经常忘
  • 检索靠 grep，想查半年前的决策效率很低
  • 信息过载：流水账记了很多，真正重要的反而淹没

新模式：原生记忆系统

新平台的记忆机制完全不同：

  • 记忆分 user（用户画像）和 memory（我的笔记）两类
  • 每次对话开始，相关记忆自动注入上下文，不用手动翻文件
  • 记忆有容量上限，逼着你"记高价值的，忘低价值的"

迁移时我做了一次"记忆断舍离"：

迁移前记忆资产（粗略统计）
├── 每日记忆文件 约 200 个
├── 长期记忆文件 1 个（很长）
└── 项目进展记录 1 个

迁移后（提炼之后）
├── 用户画像     1 条（精简版）
├── 环境与规范   5 条（配置、Git、部署要点）
├── 项目记忆     4 条（每个项目一行踩坑重点）
└── 关键教训     4 条（协作方式、回合完整性等）

数量从几百条压到十几条，但每条都是"高信号"的。 这其实是一次很好的记忆卫生——旧文件一个没删，全部备份着，随时可查；但注入到新系统的，只有真正影响未来协作的核心事实。

体会：记忆系统迁移的价值不在于"原样搬走"，而在于借机提炼。AI 的记忆容量是稀缺资源，装进低价值流水账才是浪费。

技能系统的迁移：SKILL.md 标准化

旧技能长什么样

旧平台的技能是一堆 markdown 文档，命名看心情：

skills/
├── 写博客的规范.md
├── 服务器体检.md
├── deploy-checks.md
└── backup-steps.txt

有的有结构，有的没有；有的过时了，有的还引用着已经不存在的目录。迁移时检查了一圈，发现状态漂移相当严重——很多技能描述的东西跟现实已经对不上了。

新标准：统一的 SKILL.md

迁移后，所有技能统一成标准格式：

---
name: blog-post-generator
description: 博客文章生成规范，确保模板结构正确
---

# 技能说明

## 正确生成方式
（具体命令）

## 参数说明
（参数表）

## 生成后验证
（验证命令）

## 发布流程
（发布命令）

## 常见错误
（避坑清单）

统一的格式带来几个好处：

  • 触发条件明确：description 里写清楚"什么时候用"，系统能自动匹配
  • 流程可执行：步骤、命令、验证闭环，照着做就不会漏
  • 可维护：每次用到发现过时，当场就能用工具更新

尤其是状态漂移的问题，我在迁移时顺手做了一轮清理：

  1. 删掉引用已不存在目录的技能
  2. 更新版本号、路径、命令
  3. 把"旧经验教训"融进相关技能，而不是单独开一篇

配置层迁移：Git 与 SSH

Git 配置重配

项目仓库本身不用迁移，但机器上的 Git 配置是要重配的。包括：

  • 全局用户名/邮箱
  • SSH 密钥的加载方式（以前是托管在旧平台的密钥管理里）
  • 推送走哪个通道（普通 22 端口还是 443 端口的 SSH over HTTPS）
# 迁移后的 Git 全局配置示例
git config --global user.name "my-name"
git config --global user.email "my@example.com"

# 让 git 走 443 端口 SSH（某些网络环境必需）
git config --global url."ssh://git@ssh.github.com:443/".insteadOf "git@github.com:"

这里有个细节值得说：公网服务器上，22 端口经常被墙/被限速，SSH over 443 是更稳的选择。这一步配置错了，后面 push 会非常痛苦。

包管理器版本差异

迁移后环境里的包管理器版本也变了（pnpm 从旧版本升到了 11.x），这直接引发了后面最大的一个坑——下一节细说。

大坑：pnpm 11 的 build scripts 审批机制

现象：莫名其妙的报错

迁移后第一次跑测试，报了个之前从没见过的错：

ERR_PNPM_IGNORED_BUILDS] Ignored build scripts:
@prisma/client@6.x.x, @prisma/engines@6.x.x,
esbuild@0.x.x, prisma@6.x.x, sharp@0.x.x, unrs-resolver@1.x.x

Run "pnpm approve-builds" to pick which dependencies
should be allowed to run scripts.

更诡异的是，工作区里隔三差五冒出一个 pnpm-workspace.yaml，内容还是占位符：

allowBuilds:
  '@prisma/client': set this to true or false
  '@prisma/engines': set this to true or false
  esbuild: set this to true or false

根因分析

排查之后搞清楚了机制：

  1. pnpm 10/11 引入了依赖构建脚本审批：出于供应链安全考虑，依赖包的 postinstall 脚本默认不执行，必须显式批准
  2. 有未批准构建脚本时，pnpm 执行任何命令都会报错退出（退出码 1），而不是静默跳过
  3. 非交互环境下，pnpm 会生成一个占位 pnpm-workspace.yaml 模板，把待批准列表写进去，内容就是 "set this to true or false"，等你手动填

这个占位文件是"回魂怪"：删了它，下次跑 pnpm 又生成。我一开始的思路是"干脆 gitignore 掉"，但很快发现这治标不治本——pnpm 每次还是会报错。

正确解法：真实配置 allowBuilds

正确的解法是把模板变成真实配置，明确批准这些构建脚本（它们本来就是需要的）：

# pnpm-workspace.yaml
allowBuilds:
  '@prisma/client': true    # prisma client 生成需要 postinstall
  '@prisma/engines': true   # prisma 引擎库
  esbuild: true             # esbuild 二进制
  prisma: true              # prisma CLI
  sharp: true               # 图片处理库
  unrs-resolver: true       # 模块解析

配完之后一切正常：

.../esbuild@0.28.1/node_modules/esbuild postinstall: Done
.../node_modules/@prisma/client postinstall:
  ✔ Generated Prisma Client (v6.19.3) in 97ms
.../node_modules/@prisma/client postinstall: Done
Done in 8.3s using pnpm v11.21.0

 RUN  v4.1.10
 Test Files  4 passed (4)
      Tests  50 passed (50)

这个坑值得单独写出来：如果你在 pnpm 11 项目里看到 ERR_PNPM_IGNORED_BUILDS，先找 pnpm-workspace.yaml 检查 allowBuilds，而不是瞎删文件。安全策略本身是合理的——postinstall 任意执行确实危险——只是新手上路容易懵。

测试兼容性修复：环境变严了

现象：老测试过不去

迁移后跑测试套件，有几个文件报类型错误，报错信息大致是：

Property 'updatedAt' is missing in type
'{ id: string; name: string; ... }'
but required in type 'Habit'

原因很直接：新环境的 TypeScript / Prisma 类型更严格，mock 数据少字段直接编译不过，而且 vitest 的版本也变了，一些旧的写法不被推荐了。

修复：三个典型修改

我总结了三类典型修复：

1. mock 数据补全字段：

// 迁移前：缺字段，类型编译不过
const mock = { id: "habit-1", name: "Test", emoji: "🎯" };

// 迁移后：补全必填字段
const mock = {
  id: "habit-1",
  name: "Test",
  emoji: "🎯",
  createdAt: "2026-01-01T00:00:00.000Z",
  updatedAt: "2026-01-01T00:00:00.000Z",
  description: null,
} as any;

2. 环境变量操作换规范写法：

// 迁移前：直接改 process.env（容易污染其他用例）
delete process.env.API_TOKEN;
process.env.NODE_ENV = "production";

// 迁移后：用 vi.stubEnv（自动清理）
vi.stubEnv("API_TOKEN", "secret-token");
vi.stubEnv("NODE_ENV", "production");

3. 类型断言补强：

// 迁移前：find 返回类型不匹配
Promise.resolve(mockList.find((b) => b.id === args.where.id)!);

// 迁移后：显式断言
Promise.resolve(mockList.find((b) => b.id === args.where.id)! as any);

这些修复本身没有业务逻辑变化，纯粹是适配新环境的类型系统。但从这件事我也得到一个经验：换环境之后，先跑一遍全量测试再谈其他——测试是最诚实的"环境变化报告"。

定时任务的迁移：从心跳到 cron

旧机制：心跳（Heartbeat）

旧平台有个心跳机制：Agent 每隔一段时间自己醒一次，检查有没有该做的事（比如"该提醒用户喝水了""该做每日健康提醒了"）。

这在设计上很优雅，但问题在于它强依赖平台的进程模型——一旦 Agent 进程不稳，心跳就断，还没法知道断在哪。

新机制：显式 cron

新平台用标准的 cron 定时任务，语义更清晰：

# 定时任务示例
- 每天早上 9:00 发日报            -> 0 9 * * *
- 每 30 分钟检查一次价格变化      -> */30 * * * *
- 每周一早上清理临时文件          -> 0 8 * * 1
- 一次性任务：明天 18:00 提醒     -> 2026-08-19T18:00:00

迁移策略很简单：把旧的"心跳该做的事"全部转成显式 cron，能定义的都定义出来，不再依赖隐式的"自己醒"。

这其实是个更工程化的思路：隐式机制靠猜，显式机制靠看。出问题的时候，cron list 一眼就知道有没有任务、上次跑没跑。

文档的迁移与修订

沿用的文档体系

迁移后并不是所有东西都数字化了。我把几类核心文档保留在新的工作区里：

文档 作用 迁移方式
用户资料 用户技术背景、偏好 内容保留，导入记忆系统
长期记忆 历史经验教训 备份 + 提炼，精简版入新系统
身份定位 助手人格说明 适配新格式
工具配置 Git/SSH 配置说明 全量重写（环境变了）
项目清单 各项目状态一览 全量修订（路径全变）
健康习惯 定时提醒的依据 原样保留

路径漂移的修复

迁移最烦的一类问题是文档里的路径全失效了：

- 分析范围：/root/.openclaw/workspace-xiaoma/nook/project-a/
+ 分析范围：/root/.hermes/workspaces/dev/project-a/

这种改动本身一行字，但如果文档多、引用深，就是个体力活。我的做法是：改完一个目录，立刻全局搜索旧路径前缀，批量替换：

# 示例：批量替换路径前缀（注意先备份）
grep -rl "\.openclaw/workspace-xiaoma" docs/ | xargs -I{} sed -i \
  's|\.openclaw/workspace-xiaoma|.hermes/workspaces/dev|g' {}

改完必须验证：打开文档抽查、跑一遍文档里提到的命令，确认没引到不存在的文件。

验证与收尾

迁移完成 checklist

我给自己列了一个迁移验收清单，全部打勾才算完成：

  • [ ] 新平台能正常对话，人格正确（身份文件生效）
  • [ ] 记忆注入正常——问"我讨厌什么"，AI 答得上来（记忆系统生效）
  • [ ] 技能能触发——按技能描述执行一遍流程（技能系统生效）
  • [ ] 所有项目仓库能 clone/push（Git/SSH 生效）
  • [ ] 全量测试通过（依赖与类型适配完成）
  • [ ] 定时任务上线，首次触发成功（cron 生效）
  • [ ] 旧平台数据完整备份，且新平台有恢复路径

迭代式的迁移

还有一点很重要：迁移不是一天完成的，别追求一步到位。

我的实际节奏是：

  1. 第一周：新平台跑通开发助手，日常编码任务切过去
  2. 第二周：系统助手 + 定时任务迁移
  3. 第三周：博客发布流程切换，验证新技能链
  4. 全程：旧平台保持可回滚，随时能切回去

双跑（dual-run）期很关键：在两个平台都能干活的日子里，你会自然发现哪个更好用、哪些流程该保留、哪些该改。

复盘：哪些值得，哪些后悔

值得做的事

  • 借机做记忆减负——这是最大的意外收获，几百条流水账变成几十条高信号记忆
  • 技能标准化——借迁移把技能全部格式统一，找起来、用起来都顺了
  • 定时任务显式化——从"靠心跳猜"变成"看 cron 清单"，心智负担大降
  • 文档路径大扫除——虽然累，但做完整理感极强

踩过的坑（如果再迁一次）

  1. 别急着删旧平台的占位文件——先搞明白它为什么出现（pnpm 的坑），治本而不是治标
  2. 先跑测试再改代码——环境变了，测试会告诉你所有差异
  3. 密钥和配置走"重配"而不是"搬运"——旧配置里可能有过期、有坑，重配一遍反而干净
  4. 文档路径替换要全局搜——随手改一个，剩下的会在三个月后咬你

结语：迁移的本质是升级

回头看，这次"OpenClaw 迁移 Hermes"名义上是搬家，实质上是一次彻底的、被逼着做的架构升级：

  • 单工作区 → 多 Profile 隔离
  • 人肉记忆 → 原生记忆系统
  • 散装技能文档 → 标准化 SKILL.md
  • 隐式心跳 → 显式 cron
  • 旧包管理器行为 → 新安全机制（并学会与它共处）

整个过程最大的感触是：平台迁移最大的敌人不是技术，是"以为搬完就完了"的侥幸心理。真正的迁移，是从验收清单全部打勾那一刻才开始的——之后每一次使用，都在检验迁移的质量。

如果你也在考虑给 AI Agent 换底座，我的建议是：列清单、做备份、放双跑、留回滚，然后果断开始。迁移本身没有想象中那么可怕，可怕的是带着一屋子旧家具，永远不搬家。
