引言：为什么并发编程这么难又这么重要

在移动端和服务器端开发里，并发几乎是绕不开的话题。网络请求、数据库读写、图片加载、复杂的计算任务……只要涉及异步，就必然要和并发打交道。而并发之所以难，是因为它把"顺序执行"这个我们大脑最习惯的模型打破了——你不再能确定哪一行代码先跑、哪一行后跑，数据共享时的竞争条件、死锁、资源泄漏等问题也随之而来。

Java 时代我们靠线程池 + 回调处理异步，代码很快会陷入"回调地狱"；RxJava 用响应式流解决了回调嵌套，但学习曲线陡峭，且容易过度设计。而 Kotlin 推出的 Coroutines（协程） 则给出了一套更轻量、更贴近顺序代码心智模型的并发方案——你几乎可以像写同步代码一样写异步代码，同时性能和可读性兼得。

这篇文章会从零开始，带你系统掌握 Kotlin Coroutines：先讲清楚协程到底是什么、和线程有什么区别；然后深入核心概念（CoroutineScope、Job、Dispatcher、结构化并发）；接着通过真实场景教你如何优雅地处理并发、并行、取消与异常；最后给出工程实践中的最佳实践和常见陷阱。读完你会有能力在自己的项目里写出简洁、健壮、可维护的并发代码。

理解协程：轻量级线程到底轻在哪

很多教程把协程称为"轻量级线程"，这个说法对了一半。说它"轻量"是对的，但把它理解为"更小的线程"就错了——协程和线程是两个层级的抽象，理解这一点是掌握协程的前提。

线程是操作系统调度的单位

线程是由操作系统内核管理的，每个线程都有自己独立的栈空间（默认通常 1MB 左右），线程的创建、销毁、上下文切换都涉及内核态的系统调用，成本不低。一台普通服务器上，同时运行几千个线程就会明显吃力；移动端虽然主线程很轻，但任何耗时操作放到主线程都会导致 UI 卡顿甚至 ANR。

// 线程的创建与启动
val thread = Thread {
    println("在子线程中执行: ${Thread.currentThread().name}")
}
thread.start()
thread.join()

上面的代码创建并启动了一个线程。注意 thread.join() 会阻塞当前线程直到子线程结束——这就是线程的一个特点：同步等待必须阻塞。

协程是代码层面的调度单元

协程则完全处于用户态，由 Kotlin 运行时（或者说协程调度器）管理。协程不绑定某个固定的线程，它可以被调度器挂起（suspend）和恢复（resume）。一个协程挂起时，它占用的线程会被释放出来给别的协程用，所以一个线程上可以同时运行成千上万个协程而没有任何压力。

// 协程的创建与启动
import kotlinx.coroutines.*

fun main() = runBlocking {
    launch {
        println("在协程中执行: ${Thread.currentThread().name}")
    }
}

对比上面两段代码，协程的写法更简洁，而且 launch 不会阻塞当前线程。

挂起与恢复：协程的核心机制

协程最神奇的一点是 suspend 函数。一个用 suspend 修饰的函数可以被"挂起"——挂起时它让出线程，等到异步操作完成后再"恢复"继续执行，而这一切对调用方看起来就像同步代码一样自然。

suspend fun fetchData(): String {
    // delay 是挂起函数，会让出当前线程而不阻塞
    delay(1000L)
    return "数据"
}

fun main() = runBlocking {
    println("开始: ${Thread.currentThread().name}")
    val data = fetchData() // 看起来像同步调用
    println("拿到结果: $data")
}

delay(1000L) 会挂起当前协程，但不会阻塞线程——线程在这 1 秒里可以去执行别的协程。这就是协程轻量的本质：挂起几乎零成本，恢复也只是在调度器里排个队。

为什么协程在 Android / 服务端这么受欢迎

协程能成为现代 Kotlin 并发的事实标准，原因是多方面的：

  • 消除回调地狱：顺序代码风格，逻辑清晰
  • 轻量：百万级协程无压力，适合高并发 I/O 场景
  • 结构化并发：简化取消、生命周期管理，避免内存泄漏
  • 与语言深度集成：suspend 是语言级关键字，编译器做了大量优化
  • 生态完善：Ktor、Spring WebFlux、Room、Retrofit 等都有官方协程支持

协程构建器：launch、async 与 runBlocking

协程不会凭空出现，需要通过构建器（Builder）来创建。Kotlin 提供了几个核心构建器，各自用途不同，选错会导致行为不符合预期。

runBlocking：桥接阻塞世界

runBlocking 会阻塞当前线程，直到块内的所有协程执行完毕。它主要用于 main 函数测试、或者从同步代码桥接到协程世界。在 Android 主线程或真实业务代码里，绝不建议使用 runBlocking，因为它会阻塞调用线程。

fun main() {
    // 阻塞 main 线程，等待内部协程完成
    runBlocking {
        launch { println("A") }
        launch { println("B") }
    }
    println("全部完成")
}

输出顺序：A、B 可能交错，但"全部完成"一定在最后。

launch：启动一个"即发即忘"的协程

launch 启动一个协程并立刻返回一个 Job，它不返回结果。适合做"触发后不关心返回值"的任务，比如写入日志、刷新缓存、发送埋点等。

fun main() = runBlocking {
    val job: Job = launch {
        delay(100L)
        println("任务执行中")
    }
    println("launch 返回了，job 还没完成")
    job.join() // 等待 job 完成
}

async：返回结果的并发协程

async 和 launch 类似，但它返回一个 Deferred（可理解为带结果的 Job），通过 await() 拿到结果。这是实现并发的核心工具——多个独立任务可以同时开始，最后统一取结果。

fun main() = runBlocking {
    val deferred1 = async { fetchUser() }
    val deferred2 = async { fetchSettings() }

    // 两个任务已经并发执行，这里只是等待结果
    val user = deferred1.await()
    val settings = deferred2.await()
    println("用户: $user, 设置: $settings")
}

三个构建器的选择

构建器 返回值 是否阻塞 用途
runBlocking Unit 是 测试、main 函数、同步桥接
launch Job 否 即发即忘的并发任务
async Deferred 否 需要结果的并发任务

一个关键原则：能不用 runBlocking 就不用。业务代码里应该始终通过 CoroutineScope 来创建协程，让协程的生命周期与组件生命周期绑定（后面详细讲）。

CoroutineScope：协程的容器与生命周期

协程必须在某个 Scope（作用域） 内启动。Scope 决定了协程的生命周期、以及它们如何被取消。理解 Scope 是掌握"结构化并发"的第一步。

什么是结构化并发

结构化并发意味着：每个协程都有明确的父协程和生命周期，父协程会等待所有子协程完成，父协程被取消时所有子协程一并取消。这套机制避免了"协程泄漏"——协程不会在没人管理的情况下偷偷运行。

fun main() = runBlocking {
    coroutineScope {
        launch { delay(1000); println("子任务1完成") }
        launch { delay(500); println("子任务2完成") }
        println("coroutineScope 会等待所有子协程")
    }
    println("作用域内全部完成")
}

coroutineScope 会挂起直到其内部所有子协程完成，但它不阻塞线程。

全局作用域是个陷阱

GlobalScope 是全局单例作用域，它的协程生命周期和整个应用一样长，且不受任何调用方控制。滥用它会导致协程泄漏、难以测试。除非你非常清楚后果，否则不要用 GlobalScope。

// ❌ 不好的实践：GlobalScope 长生命周期，容易泄漏
GlobalScope.launch {
    while (true) {
        delay(1000)
        println("后台循环")
    }
}

自定义 Scope：让生命周期可控

在生产代码里，你应该创建自己的 Scope 并显式管理它的取消时机，让协程和业务组件同生共死。

class DataRepository {
    // 每个实例持有自己的 Scope
    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.IO)

    fun loadData() {
        scope.launch {
            val data = fetchFromNetwork()
            println("拿到数据: $data")
        }
    }

    fun onCleared() {
        scope.cancel() // 组件销毁时取消所有协程
    }
}

在 Android 中绑定生命周期

Android 的 Activity / Fragment / ViewModel 都有生命周期。ViewModel 是协程最自然的宿主——viewModelScope 已经内置，在 ViewModel 被 clear 时自动取消。

class MainViewModel : ViewModel() {
    // viewModelScope 随 ViewModel 销毁而自动取消
    fun fetchData() {
        viewModelScope.launch {
            val data = repository.getData()
            _uiState.value = data
        }
    }
}

如果你用 Activity/Fragment 而非 ViewModel，可以在 onStart 创建 scope、onStop 取消，或者用 LifecycleScope。

Dispatcher：协程跑在哪个线程

协程本身不干活，它最终还是要调度到某个线程上执行。Dispatcher 就是决定"协程在哪个线程池上跑"的组件。选择正确的 Dispatcher 是高性能协程的关键。

内置的四种 Dispatcher

Dispatcher 用途
Dispatchers.Main Android 主线程，UI 操作只能用这个
Dispatchers.Default CPU 密集型任务（默认调度器，线程数 ≈ CPU 核数）
Dispatchers.IO I/O 密集型任务（网络、磁盘、数据库）
Dispatchers.Unconfined 不限定线程，挂起恢复后可能在任意线程（极少用） 
// 默认调度器：CPU 密集型
runBlocking {
    launch(Dispatchers.Default) {
        // 大数据计算
        val result = heavyComputation()
        println(result)
    }

    launch(Dispatchers.IO) {
        // 网络请求
        val data = api.fetchPosts()
        println(data)
    }
}

Main 与 IO/Default 的无缝切换

协程最优雅的地方之一是 withContext：在协程内部，你可以随时切换线程上下文，而且切换后代码看起来依然是顺序的。这在 Android 里尤其常用——在 IO 线程请求，回到主线程更新 UI。

viewModelScope.launch {
    // 默认在 Main 线程启动
    val result = withContext(Dispatchers.IO) {
        // 切到 IO 线程做网络请求
        api.fetchData()
    }
    // withContext 返回后自动回到 Main 线程
    textView.text = result
}

withContext 会挂起并等待内部代码执行完，然后带着返回值切回原来的上下文。它不代表"并发"，而是"切换执行位置"。

为什么不要自己 new 线程池

很多初学者会自己 Executors.newFixedThreadPool(...)，然后再包一层 Dispatcher。这通常是多余的——Kotlin 的 Dispatchers.IO/Default 已经基于共享线程池做了充分优化，并且在协程挂起时能高效复用线程。

// ❌ 过度设计：自己建线程池再转 Dispatcher
val myPool = Executors.newFixedThreadPool(4).asCoroutineDispatcher()

// ✅ 直接用内置调度器
launch(Dispatchers.IO) { ... }

除非你有明确的线程隔离需求（比如必须独占一组线程），否则优先使用内置 Dispatcher。

IO 与 Default 的自动共享优化

从 Kotlin 1.6 起，Dispatchers.IO 和 Dispatchers.Default 共享同一个底层线程池，可以自动进行负载均衡。这意味着你可以放心地混合使用它们，而不用担心各自创建独立线程池造成资源浪费。

Job 与 Deferred：协程的状态机

每个协程都对应一个 Job，它代表了协程的生命周期状态。理解 Job 的状态机，是掌握取消和结构化并发的基础。

Job 的生命周期状态

New → Active → Completing → Completed
        ↓ 取消
      Cancelling → Cancelled
  • New：刚创建，还没开始
  • Active：运行中（默认状态）
  • Completing：等待子协程完成
  • Completed：正常结束
  • Cancelling：正在取消（执行 finally 清理）
  • Cancelled：已取消
fun main() = runBlocking {
    val job = launch { delay(1000) }
    println("isActive: ${job.isActive}")    // true
    println("isCompleted: ${job.isCompleted}") // false

    job.join()
    println("isCompleted: ${job.isCompleted}") // true
}

Job 的父子关系

一个 Job 可以有子 Job。父子关系的关键规则：

  • 父 Job 取消 → 所有子 Job 取消
  • 父 Job 等待所有子 Job 完成
  • 子 Job 抛异常 → 父 Job 取消（除非是 SupervisorJob）
fun main() = runBlocking {
    val parent = launch {
        launch { delay(1000); println("子1") }
        launch { delay(500); println("子2") }
    }
    parent.join()
    println("父协程等所有子协程完成")
}

Deferred：带结果的 Job

async 返回的 Deferred 就是一个携带结果值的 Job。除了 Job 的全部特性（取消、父子关系），它还有 await() 来取结果。

fun main() = runBlocking {
    val deferred = async(Dispatchers.IO) {
        // 模拟耗时计算
        delay(500)
        42
    }
    println("结果: ${deferred.await()}") // 42

    // Deferred 也是 Job
    println("isCompleted: ${deferred.isCompleted}")
}

结构化并发实战：并行请求、集合并发与并发限制

掌握了基础概念，现在看真实场景中协程如何优雅地处理并发。

场景一：多个请求并行，全部结果一起用

最常见的场景：首页需要同时请求用户信息、推荐列表、消息数，三个接口互不依赖，可以并发执行。

suspend fun loadHomePage() {
    coroutineScope {
        val user = async { api.getUser() }        // 并行
        val posts = async { api.getRecommend() }  // 并行
        val msgCount = async { api.getUnreadCount() } // 并行

        val homeData = HomeData(
            user = user.await(),
            posts = posts.await(),
            unread = msgCount.await()
        )
        renderHomePage(homeData)
    }
}

三个请求同时发出，等待最慢的一个完成后统一渲染，总耗时 ≈ 最慢接口的耗时，而不是三者之和。

场景二：并发处理集合元素

kotlinx.coroutines 提供了 map、filter 等集合操作的挂起版本，可以轻松把集合处理并行化。

suspend fun processAll(ids: List<Int>): List<String> {
    // map 的挂起版本，所有元素并发处理
    return ids.map { id ->
        async(Dispatchers.IO) { fetchDetail(id) }
    }.awaitAll() // 等待全部完成，返回结果列表
}

awaitAll() 是处理 List<Deferred> 的利器，它会等待所有 Deferred 完成并返回结果列表；如果有任何一个失败则抛出异常。

场景三：限制并发数量（信号量思路）

当任务很多但不想一次性全部并发（怕打爆服务器或耗光资源）时，需要限制并发度。可以用一个共享的 Mutex 或限制线程池实现。一个常见做法是使用 Semaphore（Kotlin 1.8+ 提供了协程版）。

import kotlinx.coroutines.sync.Semaphore
import kotlinx.coroutines.sync.withPermit

suspend fun downloadAll(urls: List<String>) {
    // 最多同时 3 个下载
    val semaphore = Semaphore(3)
    coroutineScope {
        urls.forEach { url ->
            launch(Dispatchers.IO) {
                semaphore.withPermit {
                    download(url)
                }
            }
        }
    }
}

Semaphore(3) 保证同时最多 3 个协程拿到"许可"执行 download，其余排队等待。这是控制并发度、保护下游资源的优雅方案。

场景四：超时控制

真实网络请求绝不能无限等待。用 withTimeout 给操作加一个截止时间。

suspend fun fetchDataWithTimeout() {
    try {
        withTimeout(3000) { // 3 秒超时
            api.fetchData()
        }
    } catch (e: TimeoutCancellationException) {
        println("请求超时，做降级处理")
    }
}

超时后会抛出 TimeoutCancellationException（它是 CancellationException 的子类），通常需要捕获它做降级或重试。

协程的取消与协作：优雅地停下来

取消是协程里最容易踩坑的地方。很多人以为调用了 cancel() 协程就会立刻消失，实际上协程的取消是协作式的——协程必须主动配合才能被取消。

取消协作机制

协程默认在挂起点（如 delay、withContext、挂起的 I/O）检查取消。如果一个协程是纯 CPU 计算、从不挂起，那么调用 cancel() 后它其实还会继续跑完。

fun main() = runBlocking {
    val job = launch {
        repeat(1000) {
            Thread.sleep(100) // 阻塞操作，不响应取消!
            println("计算中: $it")
        }
    }
    delay(300)
    job.cancelAndJoin()
    println("已取消，但上面的循环仍在跑?")
}

上面用 Thread.sleep 阻塞，协程不会响应取消，会一直跑完。这就是"非协作"代码的典型问题。

让计算任务支持取消

要让 CPU 密集型任务响应取消，需要定期检查 isActive 或调用 ensureActive()。

fun main() = runBlocking {
    val job = launch(Dispatchers.Default) {
        var i = 0
        while (isActive) { // 每次循环检查取消状态
            i++
            if (i % 100_000 == 0) println("进度: $i")
        }
        println("协作式取消: 循环停止了")
    }
    delay(50)
    job.cancelAndJoin()
}

isActive 是 CoroutineScope 的扩展属性，在循环体里检查它，被取消时返回 false，循环自然退出。

挂起函数自动协作

挂起函数（如 delay、挂起的 I/O、suspendCancellableCoroutine 转换的 API）默认支持取消。在取消的协程里调用它们，会立刻抛出 CancellationException。

fun main() = runBlocking {
    val job = launch {
        try {
            repeat(10) {
                delay(100) // 挂起函数，取消时抛 CancellationException
                println("第 $it 次")
            }
        } finally {
            // finally 里的清理代码会执行
            println("清理资源")
        }
    }
    delay(300)
    job.cancelAndJoin()
    println("主协程结束")
}

注意：要捕获取消时抛出的 CancellationException，记得在 finally 中做资源清理，但不要在 finally 里做挂起操作（否则需要 withContext(NonCancellable)）。

非取消上下文里的清理

如果在取消后的 finally 里仍需挂起（比如关闭数据库连接需要异步），要用 withContext(NonCancellable)，否则取消状态会让挂起直接失败。

fun main() = runBlocking {
    val job = launch {
        try {
            repeat(10) { delay(100) }
        } finally {
            withContext(NonCancellable) {
                // 即使协程已取消，这里也能正常挂起
                closeResource()
            }
        }
    }
    delay(300)
    job.cancelAndJoin()
}

协程异常处理：让错误可控

异常处理是协程生产级应用的重头戏。协程的异常传播机制和普通代码不太一样，理解它才能写出不会"悄悄失败"或"意外崩溃"的程序。

异常传播：launch 与 async 的区别

  • launch 的异常会直接抛出给未捕获异常处理器，可能导致全局崩溃
  • async 的异常会被保存在 Deferred 里，直到 await() 时再抛出
fun main() = runBlocking {
    // launch：异常直接抛到顶层
    val job = launch {
        throw RuntimeException("launch 里的异常")
    }
    job.join() // 这里异常已经冒泡，程序会崩溃

    // async：异常延迟到 await 才抛
    val deferred = async {
        throw RuntimeException("async 里的异常")
    }
    // 不 await 就不会暴露
    try {
        deferred.await()
    } catch (e: RuntimeException) {
        println("捕获到 async 的异常: ${e.message}")
    }
}

让 async 也获得异常处理能力

如果想用 async 但又不想让异常延迟传播，SupervisorJob + 让 async 自己处理错误是常见组合。更直接的做法是：在 async 内部 try-catch 或使用 runCatching。

fun main() = runBlocking {
    val deferred = async {
        runCatching { riskyOperation() }
            .getOrElse { defaultValue() } // 出错时返回兜底值
    }
    val result = deferred.await()
    println("结果: $result")
}

CoroutineExceptionHandler：全局兜底

对于 launch 的未捕获异常，可以设置 CoroutineExceptionHandler 作为兜底处理（比如上报日志）。

val handler = CoroutineExceptionHandler { _, throwable ->
    println("捕获到未处理异常: ${throwable.message}")
}

fun main() = runBlocking {
    // handler 需在顶层协程设置才生效（作为 context 传入）
    val scope = CoroutineScope(Dispatchers.Default + handler)
    scope.launch {
        throw RuntimeException("boom")
    }
    // 睡一会让异常抛出来
    delay(500)
}

注意：CoroutineExceptionHandler 只对 launch 创建的根协程（没有父协程的协程）生效，对子协程或 async 不生效。

SupervisorJob：隔离子协程的失败

默认情况下，子协程抛异常会连带取消父协程和其他兄弟协程。如果你希望"一个任务失败不影响其他任务"，用 SupervisorJob() 替代普通 Job。

fun main() = runBlocking {
    val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)

    scope.launch {
        delay(100)
        throw RuntimeException("任务1失败")
    }
    scope.launch {
        delay(200)
        println("任务2不受影响，正常完成")
    }
    delay(500)
}

有了 SupervisorJob，并行任务中单个失败不会拖垮全部——这在"多任务互不影响"的场景（比如并行上传多个文件）非常有用。

supervisorScope：局部隔离

如果你不想创建独立的 scope，只想在某个代码块内隔离异常，可以用 supervisorScope，它提供父级作用域但子任务之间互相隔离。

fun main() = runBlocking {
    supervisorScope {
        launch {
            throw RuntimeException("子任务1失败")
        }
        launch {
            delay(100)
            println("子任务2完成")
        }
    }
    println("父协程继续执行")
}

常见陷阱与最佳实践

掌握基础后，还需要了解工程实践中的坑，避免写出"看起来对但运行就炸"的代码。

陷阱一：在主线程做耗时操作

协程默认继承启动它的上下文。如果你在 Dispatchers.Main 里直接做耗时计算，即使用了协程也会卡 UI。

// ❌ 错误：async 没指定 Dispatcher，跑在 Main
viewModelScope.launch {
    val result = async { heavyComputation() }.await() // 卡主线程!
}

// ✅ 正确：显式用 Dispatchers.Default
viewModelScope.launch {
    val result = withContext(Dispatchers.Default) { heavyComputation() }
}

陷阱二：忘记处理取消异常导致误判

捕获异常时如果把 CancellationException 也 catch 了，会破坏协程的取消机制。

// ❌ 错误：catch 所有异常会把取消也吞掉
try {
    delay(1000)
} catch (e: Exception) {
    println("异常") // 取消时也会进这里，掩盖了取消
}

// ✅ 正确：CancellationException 需要重新抛出
try {
    delay(1000)
} catch (e: CancellationException) {
    throw e // 重新抛出，保持取消语义
} catch (e: Exception) {
    println("真正的异常")
}

陷阱三：GlobalScope 泄漏

如前所述，GlobalScope 的协程生命周期与应用一致，滥用会泄漏资源。始终使用生命周期可控的 Scope。

陷阱四：在非 suspend 函数里调用 suspend 函数

suspend 函数只能在 suspend 函数或协程里调用。如果非协程代码需要调用，可以通过 runBlocking（同步）或把逻辑包进协程。

// ❌ 编译错误：suspend 函数不能在普通函数调用
fun normalFunction() {
    delay(1000) // 编译不过
}

// ✅ 正确：包进协程或用 runBlocking（谨慎）
fun normalFunction() = runBlocking {
    delay(1000)
}

最佳实践清单

  • 业务代码用 viewModelScope / 自定义 Scope，禁止 GlobalScope
  • 显式指定 Dispatcher，主线程只做 UI
  • 用 withContext 做线程切换，而非手动 new Thread
  • 需要结果用 async + awaitAll，即发即忘用 launch
  • 互不影响的任务用 SupervisorJob / supervisorScope
  • 网络请求全程加超时 withTimeout
  • 捕获异常时重新抛出 CancellationException
  • 集合并发用挂起版本的 map/filter + awaitAll

实战：构建一个带并发控制的网络请求模块

最后，把前面所有知识点整合成一个实战示例：一个支持并发上限、超时、取消、异常隔离的网络请求模块。

import kotlinx.coroutines.*
import kotlinx.coroutines.sync.Semaphore
import kotlinx.coroutines.sync.withPermit

class ApiClient(private val scope: CoroutineScope) {
    // 限制并发请求数，保护后端
    private val semaphore = Semaphore(5)

    // SupervisorJob 隔离：单个失败不影响其他请求
    private val requestScope = CoroutineScope(
        SupervisorJob() + Dispatchers.IO
    )

    suspend fun <T> request(block: suspend () -> T): T {
        return withTimeout(10_000) { // 全局 10 秒超时
            semaphore.withPermit { // 并发限制
                block()
            }
        }
    }

    // 并发拉取多个资源，失败独立处理
    fun loadBatch(ids: List<String>) {
        scope.launch {
            ids.map { id ->
                async {
                    runCatching { request { fetchResource(id) } }
                }
            }.awaitAll().forEach { result ->
                result.onSuccess { println("成功: $it") }
                      .onFailure { println("失败: ${it.message}") }
            }
        }
    }

    fun onDestroy() {
        requestScope.cancel() // 清理
    }
}

这个模块集合了：结构化并发、显式 Dispatcher、SupervisorJob 异常隔离、Semaphore 并发限制、withTimeout 超时、runCatching 独立失败处理——是一个可直接套用的生产级骨架。

总结

Kotlin Coroutines 通过语言级的 suspend 机制，把复杂的并发编程简化成了接近顺序代码的心智模型，同时保留了高性能与强可控性。回顾本文核心要点：

  • 协程是轻量级用户态调度单元，挂起/恢复几乎零成本，优于线程
  • 用 launch / async / runBlocking 三种构建器创建协程，按需选择
  • CoroutineScope 决定了协程生命周期，务必结构化、避免 GlobalScope
  • Dispatcher 决定线程，主线程只做 UI，IO/CPU 任务显式指定
  • Job/Deferred 是协程状态机，父子关系是取消的基础
  • 取消是协作式的，CPU 任务要检查 isActive 配合
  • 异常处理区分 launch 与 async，用 SupervisorJob 隔离失败
  • 并发限制用 Semaphore，超时用 withTimeout，集合并发用 awaitAll

进阶方向：如果你已经熟练掌握了这些基础，可以继续探索 Flow（响应式数据流）、Channel（协程间通信）、以及 kotlinx.coroutines 的协程调试工具（CoroutineName、-Dkotlinx.coroutines.debug）。并发编程是一座值得深耕的大山，而协程给了你最顺手的登山杖。希望这篇文章能帮你迈出坚实的一步。
