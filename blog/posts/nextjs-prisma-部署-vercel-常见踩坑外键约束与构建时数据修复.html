Next.js + Prisma 部署 Vercel 常见踩坑：外键约束与构建时数据修复

📅 2026-08-01 15:12:09 ⏱️ 5 min read 👤 张小猛
Next.js Prisma Vercel 部署 DevOps

将 Next.js + Prisma 项目部署到 Vercel 时，构建阶段的数据库操作常常踩坑。本文记录了一次真实的外键约束失败案例，从问题定位到根因分析再到解决方案，完整复盘整个过程。

问题背景

项目 Zest 是一个基于 Next.js 15 + Prisma 6 + PostgreSQL 的习惯追踪应用，部署在 Vercel 上。build 脚本中包含 prisma db push 来同步 schema：

{
  "scripts": {
    "build": "if [ \"$DATABASE_URL\" ]; then prisma db push; fi && next build"
  }
}

某次修改了 Badge 模型（添加 nullable 的 habitId 字段）后推送代码，Vercel 构建失败，报错信息：

Error: insert or update on table "streaks" violates
foreign key constraint "streaks_habit_id_fkey"

streaks 表的外键约束在 prisma db push 同步 schema 时失败了。

根因分析

数据库里的"幽灵外键"

查看 Prisma schema，发现 Streak、Reward、DiaryEntry 三个模型都有 habitId 字段引用 Habit 模型：

model Streak {
  // ...
  habitId    String    @default("default") @map("habit_id")
  habit      Habit     @relation(fields: [habitId], references: [id])
  // ...
}

model Reward {
  // ...
  habitId     String    @default("default") @map("habit_id")
  habit       Habit     @relation(fields: [habitId], references: [id])
  // ...
}

model DiaryEntry {
  // ...
  habitId   String   @default("default") @map("habit_id")
  habit     Habit    @relation(fields: [habitId], references: [id])
  // ...
}

问题在于这三个表的 habitId 默认值是 "default"，但 habits 表里从未创建过 id = "default" 的记录。

为什么之前没有报错

这个项目最初是单习惯追踪器，habitId 只是占位字段，没有真正的外键约束。prisma db push 在早期版本中可能没有严格执行外键检查，或者数据量小的时候恰好没触发。

当我修改 Badge 模型添加 habitId 字段后，prisma db push 重新计算了整个 schema 的约束，这时 streaks 表中 habit_id = "default" 的记录找不到对应的 habits 记录，外键约束就炸了。

问题链路

修改 Badge schema（添加 nullable habitId）
  → prisma db push 重新同步全部 schema
  → 重新创建所有外键约束
  → 检查 streaks 表的 habit_id 外键
  → 发现 habit_id='default' 在 habits 表中不存在
  → 外键约束失败 → 构建中断

解决方案

方案对比

方案 描述 优点 缺点
A. 插入 default habit 确保 habits 表有 id='default' 的记录 最简单、向后兼容 default 记录是垃圾数据
B. 迁移现有数据 将 streaks/rewards/diary 的 habit_id 更新为真实 habit id 数据干净 需要知道真实 habit id
C. 移除外键约束 将 habitId 改为不引用 habits 无依赖问题 失去数据完整性
D. 使用 nullable habitId 所有模型都改为 nullable 灵活 需要大量代码适配

考虑到这是紧急修复，且向后兼容性最重要，选择了 方案 A：在构建前自动插入 default habit 记录。

修复 SQL

创建 prisma/fix-data.sql 文件：

-- 修复外键约束问题：确保 habits 表有 id='default' 的记录
-- streaks/rewards/diary_entries 中有 habit_id='default' 的记录引用它
INSERT INTO "habits" (
  "id", "name", "emoji", "color",
  "description", "active", "order",
  "created_at", "updated_at"
)
SELECT
  'default', '默认习惯', '🎯', '#8b5cf6',
  '', true, 0, NOW(), NOW()
WHERE NOT EXISTS (
  SELECT 1 FROM "habits" WHERE "id" = 'default'
);

这个 SQL 的关键点：

  1. 幂等性：WHERE NOT EXISTS 确保多次执行不会重复插入
  2. 向后兼容：只在不存在时插入，不影响已有数据
  3. 完整字段：覆盖 habits 表所有非 null 字段

修改 build 脚本

{
  "scripts": {
    "build": "if [ \"$DATABASE_URL\" ]; then prisma db execute --file prisma/fix-data.sql --schema prisma/schema.prisma && prisma db push; fi && next build"
  }
}

执行顺序：

有 DATABASE_URL?
  → 是 → prisma db execute（修复数据） → prisma db push（同步 schema） → next build
  → 否 → next build（本地无数据库跳过）

第一次踩坑：缺少 --schema 参数

推送后 Vercel 再次失败：

Error: Either --url or --schema must be provided.

prisma db execute 命令需要显式指定 --url 或 --schema 参数，不像 prisma db push 会自动读取 schema 文件。修复后加上 --schema prisma/schema.prisma 即可。

这个坑值得记住：Prisma CLI 的不同子命令对参数的要求不一致。db push 自动找 schema，db execute 必须手动指定。

Prisma CLI 参数一致性问题的根因

这种不一致源于 Prisma 的设计哲学。db push 和 migrate 是高频操作，CLI 做了自动发现优化；而 db execute 是低频工具命令，设计上要求显式参数以避免误操作。理解这个设计逻辑后，就不会再踩这个坑了。

查看 Prisma 源码可以看到，db push 内部调用了 getSchema() 辅助函数自动搜索 schema.prisma 文件，而 db execute 没有调用这个函数，直接要求用户提供 --url 或 --schema。这是一个有意识的 API 设计选择，不是 bug。

最终验证

修复后的构建流程：

1. prisma db execute → 插入 default habit 记录 → ✅
2. prisma db push → 同步 schema，外键约束通过 → ✅
3. next build → 编译成功 → ✅
4. Vercel 部署 → HTTP 200 → ✅

经验总结

Prisma db push vs Migrate

prisma db push 和 prisma migrate dev 是两种不同的 schema 同步方式：

特性 db push migrate
生成 migration 文件 ❌ ✅
数据迁移 ❌ ✅
适用场景 原型开发 生产环境
外键约束 重算所有约束 按计划执行

db push 每次都会重算所有约束，这意味着任何 schema 变动都可能暴露之前隐藏的数据不一致问题。而 migrate 是增量式的，只在 migration 文件中定义的步骤执行。

构建时数据修复的最佳实践

在 CI/CD 构建阶段执行数据库操作是一种常见模式，但需要注意：

1. 幂等性

所有 SQL 必须可以重复执行。使用 INSERT ... WHERE NOT EXISTS、CREATE TABLE IF NOT EXISTS 等模式：

-- ✅ 幂等
INSERT INTO "habits" (...) SELECT ... WHERE NOT EXISTS (...);

-- ❌ 非幂等，第二次执行会报主键冲突
INSERT INTO "habits" (id, ...) VALUES ('default', ...);

2. 顺序依赖

确保修复 SQL 在 schema 同步之前执行：

"build": "prisma db execute --file fix.sql --schema p.schema && prisma db push && next build"

如果反过来，db push 会先因为外键约束失败，修复 SQL 就没机会执行了。

3. 注释和文档

修复 SQL 应该清晰说明为什么存在、何时可以移除：

-- 临时数据修复：确保 habits 表有 default 记录
-- 当所有 streaks/rewards/diary_entries 的 habit_id='default'
-- 都迁移到真实 habit id 后，可以移除本文件和 build 脚本中的引用
INSERT INTO "habits" (...) SELECT ... WHERE NOT EXISTS (...);

Vercel 构建的特殊性

Vercel 的 build 环境有几个值得注意的特性：

环境变量

Vercel 的 Environment Variables 需要在项目设置中手动配置。DATABASE_URL 如果没有配置，build 脚本中的 if [ "$DATABASE_URL" ] 判断会跳过数据库操作，这既是保护（不会在无数据库环境跑 db push）也是隐患（可能悄悄跳过必要的初始化）。

构建日志

Vercel 的构建日志只能通过 Dashboard 查看，如果 prisma db push 失败，日志会显示完整的 Prisma 错误信息（包括 Rust 源码的 stack trace），这对定位问题很有帮助。

部署目标

Vercel 部署的 URL 不是固定的。zest.vercel.app 是 production URL，但每次构建后的 preview URL 不同。验证生产环境时用 zest.vercel.app 而不是 preview URL。

更深层的问题

虽然外键约束问题解决了，但 habitId = "default" 本身是一个技术债。理想情况应该：

1. 数据迁移

将所有 habit_id = "default" 的记录更新为真实的 habit id：

-- 假设用户只有一个习惯，用第一个真实习惯替代 default
UPDATE streaks SET habit_id = (
  SELECT id FROM habits WHERE id != 'default' LIMIT 1
) WHERE habit_id = 'default';

-- 同样处理 rewards 和 diary_entries
-- 然后删除 default habit
DELETE FROM habits WHERE id = 'default';

2. Schema 改为 nullable

将 Streak、Reward、DiaryEntry 的 habitId 也改为 String?（nullable），null 表示全局/未关联。这和 Badge 的设计一致。

3. 移除修复 SQL

数据迁移完成后，从 build 脚本中移除 prisma db execute 步骤，保持构建流程干净。

常见 Vercel + Prisma 构建问题速查

错误信息 根因 解决方案
Environment variable not found: DATABASE_URL Vercel 未配置数据库 URL 项目设置添加环境变量
foreign key constraint violated 外键数据不一致 构建前修复数据
Either --url or --schema must be provided prisma db execute 缺参数 加 --schema prisma/schema.prisma
PrismaClientInitializationError 构建时静态页面生成连接数据库失败 配置 DATABASE_URL 或改为动态渲染
Migration failed migration 文件有冲突 检查 migration 历史或用 db push 替代

总结与最佳实践清单

部署前检查清单

在每次修改 Prisma schema 并部署前，过一遍以下检查项：

  • [ ] 确认所有外键引用的记录存在
  • [ ] 确认 build 脚本中的数据库操作顺序正确
  • [ ] 确认 Vercel 环境变量已配置
  • [ ] 确认 prisma db execute 带了 --schema 参数
  • [ ] 确认修复 SQL 是幂等的
  • [ ] 本地跑一遍 pnpm build 验证

核心教训

这次踩坑的核心教训是：Prisma 的外键约束在 schema 变动时会全局重算。你以为只改了 Badge 模型，实际上 db push 会重新验证所有模型的外键完整性。

解决方案的关键思想是 构建时数据修复：在 CI/CD 的 build 阶段，schema 同步之前，先执行幂等的修复 SQL 确保数据一致性。这是一种通用的 CI/CD 模式，不限于 Prisma 或 Vercel。

更长期的解决方案是做好数据迁移，将占位符数据（如 habit_id = "default"）替换为真实的数据关系，然后移除修复 SQL，保持构建流程的简洁。
