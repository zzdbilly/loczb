## 先把尺子摆出来：直觉说慢，实测说一点八秒

「每次改一篇文章，都要把 149 篇全部重编一遍」——这句话我听了很久，也自己说过很久。它听起来就是个该被优化掉的毛病：明明只动了一篇，为什么要付 149 篇的代价。

直到我真的按下秒表。

同一个仓库，同一台机器，连着跑三次全量重编，不做任何缓存预热也不清 page cache，也就是我平时发文时机器所处的那个状态：

| 第几次 | 全量重编耗时 |
|:--|--:|
| 第一次 | 1.783 s |
| 第二次 | 1.801 s |
| 第三次 | 1.769 s |
| 三次均值 | 1.78 s |

149 篇，一点八秒。折到单篇大约 12 毫秒——比我按下回车到松开手指的时间还短。

我没有做任何优化。这三个数字就是现有构建脚本原样跑出来的，脚本里没有 mtime 判断、没有变更集、没有「跳过未修改文件」的分支，每一次都是从 149 个 Markdown 源文件重新渲染到最后一个字节。这一点我专门翻过源码确认：整个构建过程没有任何基于文件修改时间或变更集合的逻辑。

所以这篇文章不是一篇优化记。它是一篇测量记，外加一个我认为更值得讨论的问题：**当你要优化的那一段本来就只有一点八秒，你优化的是什么。**

## 四段时间：一次发文到底花在哪

把一次发文拆开，本地脚本能计时的部分其实只有三段。

### 第一段：全量重编，1.78 秒

这一段做的事比「渲染 149 个页面」多：读 149 个源文件、解析 frontmatter、渲染正文、写出 149 个 HTML 与 149 个元数据 sidecar，然后重建列表首页与全部分页、重建首页的最新文章区、重算搜索索引、重写 RSS 与 sitemap、更新 Service Worker 的缓存版本号。

也就是说，它本来就不是「149 次单篇渲染」，而是「149 次单篇渲染 + 一整套聚合视图」。聚合视图的代价和篇数是弱相关的：分类计数、标签云、分页边界这些都要遍历全量，但遍历本身几乎不花钱，花钱的是渲染与写盘。

一点八秒里，真正跟篇数成正比的部分大约就是那 12 毫秒乘以 149。

### 第二段：产物一致性校验，0.21 秒

编译完不是就完了，还要对账：文章集合、索引集合、相关文章集合、元数据集合，四处必须能互相对上，主页面上写的篇数版本也要和实际产物一致。

| 第几次 | 产物校验耗时 |
|:--|--:|
| 第一次 | 0.214 s |
| 第二次 | 0.205 s |
| 第三次 | 0.205 s |

三次均值 0.21 秒。它比构建快一个数量级，因为它只读不写，做的是集合比对而不是模板渲染。

### 第三段：内链巡检，0.15 秒

站内一共 5202 条内链，分布在 173 个 HTML 页面里，平均每页 30 条左右。巡检要把这些链接全部解析出来，逐条确认目标文件存在。

| 第几次 | 内链巡检耗时 |
|:--|--:|
| 第一次 | 0.157 s |
| 第二次 | 0.148 s |
| 第三次 | 0.141 s |

三次均值 0.15 秒。按 5202 条算，每千条链接大约 29 毫秒。

### 第四段：提交、推送、上线与人眼核验

前三段加起来：

```text
全量重编   1.78 s   83.2%
产物校验   0.21 s    9.8%
内链巡检   0.15 s    7.0%
----------------------------
合计       2.14 s  100.0%
```

2.14 秒。

然后是第四段：暂存改动、写提交、推送到远端、等托管侧构建完成、打开线上页面核对标题与首屏、确认列表页与首页都出现了新文章、确认 RSS 与 sitemap 里有它。

**这一段我没有装计时器。** 我不想在这里编一个「总共 47 秒」之类的数字，因为我确实没测。我能确定的是它的构成：一次网络往返、一次远端构建、若干次人工点击与肉眼比对。它的最小粒度不是毫秒，是「一次推送往返」和「一次人工核对」。

所以「前三段 2.14 秒占一次发文总耗时的一个零头」这个判断，依据不是我把总时长量出来了，而是第四段的计量单位本来就在秒与分钟这一侧——把前三段全部优化到零，你也省不掉第四段里的任何一次往返。

## 三个体积：唯一跟着规模长的那条线

如果耗时不是瓶颈，那什么在随规模增长？体积。

### 产物 37M

不含版本库的站点产物一共 37M。其中 3242 个受控文件、173 个 HTML 页面、149 篇文章。平均下来每篇贡献约 254KB 的产物。

### blog 目录 9.8M，占产物的四分之一

文章正文、列表页、分页、索引 JSON 全在这一个目录里，9.8M，占 37M 的 26.5%。折到每篇约 67KB——这里面大部分不是正文，是每篇文章页面里嵌的那份导航、相关文章卡片与站点框架。

### .git 39M：历史比产物还重

| 对象 | 体积 | 说明 |
|:--|--:|:--|
| 站点产物（不含版本库） | 37M | 3242 个文件、173 个 HTML |
| 其中 blog 目录 | 9.8M | 149 篇正文与聚合页 |
| 版本库 .git | 39M | 全部历史版本 |
| 两者合计 | 76M | .git 占 51.3% |

版本库比当前产物还大，是产物的 1.05 倍。折到每篇，产物贡献 254KB，历史贡献 268KB，而且历史那一份是**不可逆**的：只要提交过，它就在那里，除非重写历史。

### 体积与耗时朝相反的方向走

把两个维度放在一起看：

| 维度 | 每增加一篇的增量 | 是否可逆 | 是否与篇数同步 |
|:--|--:|:--|:--|
| 全量重编耗时 | 约 12 ms | 可逆（随时能删缓存重来） | 线性，系数很小 |
| 站点产物 | 约 254 KB | 可逆（重新构建即可） | 线性 |
| 版本库历史 | 约 268 KB | 不可逆 | 线性，且只增不减 |

每发一篇文章，你多付 12 毫秒的构建时间、254KB 的产物、268KB 且永不消失的历史。前者是零头，后两者才是会咬人的那一侧。

这也解释了我为什么对「增量化」这个方向一直提不起兴趣：它优化的是表里系数最小的那一行。

## 增量化真正卖的是什么，收的是什么

增量化不是没有价值，它只是有价格。价格不在实现复杂度上——那部分是一次性的——而在它把「结果」换成了「历史」。

### 产物漂移：磁盘不再等于全量重跑

全量构建有一个性质：`site/` 目录的内容，恒等于「拿当前源码从零跑一遍」的输出。这个等式是发布正确性的定义。

增量构建打破的正是这个等式。磁盘上的产物变成了「一系列增量操作的累积结果」，而它是否等于全量重跑的结果，取决于每一条失效规则都写对了。想验证这件事，你只有一条路：

```bash
# 在一个干净副本里做，不要动正在发布的目录
rm -rf site/
python3 build.py --all
git diff --stat -- site/
```

如果 diff 为空，说明你的增量是可信的；如果不为空，说明过去某次增量漏了依赖。而这个检查本身，就是一次全量重编——你已经把省下来的时间花回去了，只是花在了更晚、更被动的时间点。

### 缓存失效面：一篇文章牵动的不止三个文件

我对着产物清单过了一遍。它远不止「新增一个 HTML、一个 JSON、改一个索引」：

- 文章本身的页面与元数据 sidecar
- 列表首页（新文章要进第一页）
- 分页边界（第一页挤出去的那篇要落到第二页，第二页同理往后推）
- 站点首页的最新文章区与内嵌的文章数组
- 搜索索引
- RSS 与 sitemap
- Service Worker 的缓存版本号（内容哈希变了）
- 若干篇相邻文章的「相关文章」卡片
- 篇数锚点所在的几个静态页面

一份可靠的增量实现，必须为上面每一条写出「什么输入变化会触发它重建」的规则。规则的数量与产物的耦合面成正比，而不是与「改了几个文件」成正比。这就是失效面：你省下的每一毫秒，都要用一条规则去换。

### 构建行为随环境变

增量依赖上一次构建留下的状态。状态在，结果是一种；状态被清掉、换了机器、在 CI 的干净克隆里跑，结果是另一种。

全量构建没有这个问题：同样的输入，在任何机器上都是同样的输出。CI 里那条「重新全量编译一遍，再和提交的产物逐字节比对」之所以能成立，靠的就是这个性质。如果构建本身是增量的，这条断言就退化成了「再增量一遍，看看和上次增量像不像」。

### 门禁从「比对全量」退化成「相信上次」

这是我认为最贵的一项。

现在这套门禁能拦住东西，是因为它手里有一份独立算出来的基准：源文件重跑一遍的结果。产物和基准不一致，就红。

引入增量之后，门禁能比对的就只剩下「这次增量产出的东西」和「上次增量留下的东西」。两者如果一起错——比如某次失效规则漏了，产物和缓存一起偏——门禁会安静地通过。它不再是一个校验器，而是一个记录员。

**所以全量重建不是性能开销，它是发布正确性的定义。** 一点八秒买的不是「重新生成一遍文件」，买的是「我知道磁盘上这份东西，等于源码此刻应该生成的东西」。这笔交易在 149 篇的规模上，价格低到没有必要还价。

## 什么情况下增量化才值得

我不是在说增量化永远不该做。它有三个成立条件，我的这套构建一个都不满足。

### 条件一：规模到了另一个量级

耗时如果与篇数近似线性，那么从 1.78 秒推到 10 秒，需要八百多篇——这是按每篇 12 毫秒线性外推的**推演**，不是实测，真实曲线会在某个点上因为内存与 IO 变陡。

八百多篇之前，你省下的是几十毫秒到一两秒；八百多篇之后，全量重编才开始和「一次推送往返」处在同一个量级，那时它才真的值得被优化。

### 条件二：构建里有编译型步骤

类型检查、打包、代码分割、压缩、图片转码——这些步骤的单次成本是常数级的大开销，而且它们本身就是增量的（编译器自带依赖图）。在这种构建里，增量省的不是「渲染 149 个模板」，是「重新类型检查整个项目」。

我这套构建里没有这些步骤。它是纯文本渲染：读 Markdown、套模板、写文件。没有依赖图可算，也就没有增量可做。

### 条件三：全量已经超过十秒

十秒是我给自己定的讨论阈值，**经验值，不是实测**。它的含义是：低于十秒，优化收益落在人的感知阈值以下，你省下的时间会被一次手动刷新抵消；高于十秒，等待开始打断工作节奏，优化才有体验上的回报。

三个条件放在一起：

| 条件 | 我的现状 | 是否满足 |
|:--|:--|:--|
| 规模到另一个量级 | 149 篇，全量 1.78 s | 否 |
| 含编译型步骤 | 纯 Markdown 渲染，无类型检查与打包 | 否 |
| 全量超过十秒 | 1.78 s | 否 |

三条全否。这就是我不动它的原因——不是因为增量难写，是因为在这里它买不到东西。

## 该优化的是另外三处

把「构建太慢」这个假设去掉之后，真正值得看的地方浮出来了。每一处我都给了可观测量，因为不可观测的优化等于许愿。

### 仓库体积：39M 的历史

可观测量：`.git` 目录体积、历史中最大的若干个 blob、单次克隆耗时。

39M 对一个 149 篇的文本站来说偏重。文本的压缩率很高，这个体积大概率来自历史里的大二进制——图片、字体、某次误提交的构建产物。处理手段是清理历史中的大对象、把图片转成更省的格式、确认构建产物与依赖目录没有被提交进去。这些都不影响发布正确性，是可以放心做的减法。

### 门禁覆盖：5202 条内链之外还剩什么

可观测量：检查项数量、覆盖的页面数、被拦住的次数。

内链已经全覆盖了：5202 条，173 个页面。没覆盖的是另外几类——外链是否可达、产物体积是否出现异常膨胀、可访问性有没有退化、页面的首字节与关键资源数量。这些检查加进去会增加门禁耗时，但增加的是「能拦住错误」的时间，而不是「重新生成一遍已经正确的文件」的时间。两者的性价比不在一个量级。

### 人工核验：第四段才是真瓶颈

可观测量：从推送完成到线上可访问的间隔、人工核验需要点击的次数、核验项的数量。

这是唯一一段我明确知道它比 1.78 秒大的环节，也是唯一一段没有自动化兜底的环节。把「打开页面、核对标题、确认列表页、确认 RSS」这四步压成一条命令一次输出，收益比把构建从 1.78 秒压到 1.5 秒高一个数量级。

## 判据：先量，再决定哪一秒值得省

我现在给自己三条判据，按顺序过。

### 第一条：有没有数字

没有测过的「慢」不是问题，是感觉。我这次测完才知道，那个听起来该被优化的全量重编，实际是一点八秒。在此之前，我对它没有任何数字，只有一个形容词——而形容词是没法拿来做取舍的。

### 第二条：要省的那部分，是否大于测量噪声

三次连跑，最快 1.769 秒，最慢 1.801 秒，抖动 32 毫秒。这意味着任何小于三十毫秒的优化，在这台机器上你根本测不出它是否生效。如果你的优化目标是「省 200 毫秒」，那它就在噪声边缘，你需要跑几十次才能把信号从抖动里捞出来——而那些跑几十次的时间，早就超过你省下的时间了。

### 第三条：省下来的时间，是否以可验证性为代价

前两条是性价比，第三条是底线。任何让「磁盘上的产物不再等于全量重跑结果」的优化，都必须先回答一个问题：出问题的时候，我用什么独立基准去发现它。如果答案是「再全量跑一遍」，那这次优化只是把成本挪到了故障时刻。

三条判据合起来，结论很朴素：**优化之前先量，量完再决定哪一秒值得省。** 在这套构建上，值得省的那一秒不在构建里。
