## 一个公式，三个数字

服务变慢的时候，第一眼往往落在连接池上：池里在排队，那就把池调大。这个动作背后有一个隐含前提——池是吞吐的瓶颈。前提成立时它有效，前提不成立时它让问题更难看清，因为改完以后指标会朝两个方向同时动。

把这件事写成一行：

```text
吞吐 ≈ min(N, C) / R

N = 池允许同时持有的连接数（应用侧的上限）
C = 数据库实际能并行服务的请求数
    （受 CPU 核数、IO 带宽与延迟、锁争用共同约束）
R = 一次请求从取到连接、到归还连接的平均时长
```

这行式子里只有 N 是配置项。C 由机器和工作负载决定，R 由代码结构决定。池能改的只有一个字母，而吞吐取决于三个字母的比值。

### 直觉成立的那一半

当 N < C 时，应用侧确实卡住了数据库：数据库还有余力，但只有 N 个请求能同时进去。这时把 N 往上调，吞吐沿着 N/R 这条线上升，一直升到 N 追上 C 为止。这一段是线性的，也是「调大池有用」这个经验的全部来源。

注意这个区间的位置：N < C 意味着数据库是闲着的，CPU 没打满，锁等待不高。这是可以从外部观测到的状态，不需要猜。

### 直觉反过来的那一半

一旦 N > C，`min(N, C)` 取的是 C。再往上加连接，式子的分子不动，分母 R 反而会因为争用变长。于是吞吐不升，延迟上升，而观测到的现象是「池还是不够用」——因为请求在池外的等待时间没变短，在池内的执行时间变长了。

这就是那个动作失效的地方：它在 N < C 时是对的，在 N > C 时是反向的，而两种状态在监控面板上都表现为「慢」。

### 三个数字各管什么

| 数字 | 由谁决定 | 改池配置能不能动它 | 动它的直接后果 |
|:-----|:---------|:------------------|:---------------|
| N | 应用配置 | 能 | 改变同时持有连接的数量 |
| C | CPU、IO、锁、数据分布 | 不能 | 由硬件与工作负载决定 |
| R | 事务边界、查询、外部调用 | 不能 | 只能改代码，不能改配置 |

这张表是整篇文章的骨架：唯一能靠改配置移动的，是那个在 N > C 之后就不起作用的字母。

## N：池限住的是「同时持有」，不是「并发」

### 池里没有并发，只有占位

一个连接是一份被租出去的资源，不是一个线程。池的计数器记的是「此刻有几个连接被借出还没归还」，不是「有几个请求在处理」。这两者在 R 很长的时候会严重脱节：一百个请求在途，池里可能只有八个连接被持有，另外九十二个在池的等待队列里排着。

所以「并发」这个词在讨论池的时候要先拆开：

- **在途请求数**：从进入应用到返回响应，包括排队的那部分。
- **持有连接数**：真正握住一份数据库会话的数量，上限是 N。

池限制的是后者。用前者去调后者，就会得出「并发上不去所以要加池」这种把两个量混在一起的结论。

### 排队的人也算并发

从客户端看，一个在池队列里等待的请求和在数据库里执行的请求没有区别——它都还没返回，都占着内存、占着上游的连接、占着用户的时间。区别在服务端：排队的那部分不消耗数据库的 CPU，也不持有任何锁。

这一点决定了后面所有的判断：**排队发生在哪一层，决定了它有多贵**。在应用内存里排队，代价是一个协程或一个线程的栈；在数据库的锁队列里排队，代价是一个后端进程、一份内存基线，以及持锁期间阻塞别人。

### N 是一个被装饰过的常量

生产配置里的池从来不只是「最大连接数」一个数字，它通常是一组联动参数：

| 参数 | 作用 | 配置失当时的典型现象 |
|:-----|:-----|:--------------------|
| 最大连接数 | 上限 N | 撞数据库硬上限，新请求连不上 |
| 最小空闲数 | 预热与抖动缓冲 | 冷启动时集中建连，出现尖刺 |
| 取连接超时 | 排队多久就放弃 | 排队时间被截断，看起来「很快失败」 |
| 空闲回收 | 释放长期不用的连接 | 低频时段池被抽干，突发时排队 |
| 最大存活时长 | 定期换掉旧连接 | 长于负载均衡的摘除周期，连到已下线的节点 |

其中「最大存活时长」最容易被忽略：连接是有年龄的，而它对面的数据库节点可能在某次发布后就不在了。池里留着一批比节点还老的连接，表现出来不是错误，是间歇性的超时。

## C：数据库真正能同时干活的份数

### C 从哪来

数据库的并行服务能力不是抽象的，它由几件具体的东西卡住：

- **CPU 核数**：同一时刻真正在跑的查询数不会超过可用的执行线程数。超出的部分在操作系统的运行队列里等，不在做计算。
- **IO 带宽与延迟**：数据页不在内存里的时候，一次查询的进度取决于磁盘。并发上去以后，IO 队列深度增加，单次读的延迟上升。
- **锁**：写同一行、同一张表的请求只能串行。热点行的更新，其并行度在那一行上等于 1，无论你开多少连接。
- **连接自身的成本**：以 PostgreSQL 为例，每个连接对应一个独立的操作系统进程，有固定的内存基线，切换要付上下文切换的代价。连接数不是免费的并发度，它本身就是要花钱的。

### 为什么 C 不随 N 增长

并发度是「同时被服务的请求数」，它需要资源来支撑。N 增加的是「同时被允许进入的请求数」，进入以后要抢的还是那几份资源。抢的人多了，单位时间内完成的量不会变多，只会让每个人的等待变长。

一个常被引用的起步估计是「C 在 CPU 核数的量级」，而不是几十上百。这个说法的价值在于给出数量级，不在于给出答案：真实的 C 取决于查询是 CPU 密集型还是 IO 等待型、有多少写冲突、缓存命中率有多高。它需要测，不能照抄。

### C 不是常数

C 会随负载移动，而且是往下移动：

- 一批大查询同时进来，每个都吃掉一个核的一段时间，可服务的并发数下降。
- 热点行被频繁更新，那条记录上的并行度接近 1，整张表的有效 C 被拉低。
- 长事务持锁不放，后来的请求在锁队列里等，看起来是「数据库卡住了」，实际是 C 被一个事务占住了。

这一点解释了为什么按峰值调好的 N，在另一个峰值的形状下就不合适：不是 N 变了，是 C 变了。而 N 是写死在配置里的，C 是随流量实时变化的。

## R：被忽略的那个变量

### R 里装了什么

R 是连接从被借出到被归还的整段时间。它不等于查询的执行时间，通常比执行时间长得多：

```text
R = 取连接等待
  + BEGIN 到 COMMIT 之间的全部时间
      ├─ 语句执行
      ├─ 锁等待
      └─ 应用代码（ORM 懒加载、外部 HTTP 调用、日志、序列化）
  + COMMIT 之后、归还之前的清理
```

第二项里的「应用代码」是最常见的隐性成本。在事务里调一次外部接口，那条连接在整个网络往返期间都被占着，而数据库什么也没干。这段时间会计入 R，也就会计入「池不够用」的观感，但它跟数据库的容量没有关系。

### 事务边界决定 R 的下限

R 有一个由代码结构决定的下限：事务开得越早、提交得越晚，R 就越长。常见的几种拉长方式：

- 在事务开始之后才做参数校验、权限查询、远程调用。
- 用 ORM 的懒加载，在事务里触发一串本来可以预取的查询。
- 把「读一批、算一会儿、写一批」放进同一个事务，中间的计算时间也算持有时长。
- 事务里等待用户交互或消息队列的响应。

这些做法在功能上都对，在容量上都贵：它们让一份连接在大部分时间里处于「占着但不干活」的状态。

### 降 R 的杠杆比加 N 长

Little's Law 给出的是同一个式子的另一种写法：并发数 L 等于吞吐 λ 乘以停留时间 W。反过来读，吞吐等于并发除以停留时间。

```text
λ = L / W

W 减半，在 C 允许的范围内，λ 翻倍      ← 改代码
L 翻倍，在 L > C 之后，λ 不变          ← 改配置
```

两条路的区别不在幅度，在方向：一条是把同样的资源用得更紧凑，另一条是把更多的请求塞进同一个瓶颈。前者没有上限（只要 R 里还有可压缩的部分），后者在 N 追上 C 的那一刻就结束了。

## N 超过 C 之后

### 排队搬家

池调大最直接的后果不是变快，是把等待的位置换了。原来在应用内存里排队的请求，现在进了数据库，变成了锁等待、CPU 时间片竞争和运行队列里的等待。

这个搬家在指标上的样子很有特征：

| 观测项 | 搬家前 | 搬家后 |
|:-------|:-------|:-------|
| 池等待时间 p99 | 高 | 下降 |
| 数据库活跃会话数 | 接近 N | 接近新 N |
| 数据库 CPU | 有余量 | 打满或接近打满 |
| 锁等待 | 低 | 上升 |
| 端到端延迟 | 高 | 不变或更高 |

（表中数值方向为示意，不是实测。）

只看第一行会得出「池调大有效」的结论，因为等待确实从池里消失了。它没有消失，只是换了地方，而且换到了一个更贵的地方——在那里等待的连接还占着后端进程和内存。

### 反馈环

把上面几行连起来，会得到一个自我强化的循环：

1. N 调大，池等待下降。
2. 更多请求同时进入数据库，争用上升。
3. 争用上升拉长了每条语句的执行时间，R 变长。
4. R 变长意味着单位连接的服务速率下降，池再次显得不够。
5. 回到第 1 步。

这个环的可怕之处在于每一轮都有「证据」支持下一步：池等待时间确实高，活跃连接数确实贴着上限。指标没说谎，是读数的人把「结果」当成了「原因」。R 变长本来就是 N 变大的产物，用它去论证 N 还要再大，逻辑上是自证。

### 故障形态从「慢」变成「连不上」

在 N 还远小于数据库上限的时候，调大的代价是延迟。当 N 乘以实例数逼近数据库的硬上限时，代价换了一种形式：新的连接建立请求被拒绝。

这时候的现象不是变慢，是直接失败——而且失败的位置很分散：应用启动时连不上、健康检查超时、迁移脚本和备份任务拿不到连接、运维想上去看一眼也连不上。以 PostgreSQL 为例，`max_connections` 是硬上限，`superuser_reserved_connections` 会预留几个位置给超级用户，但那是最后的安全垫，不是容量规划的一部分。

「慢」是可以降级的，「连不上」不能。这就是为什么池的上限要留余量：留的不是性能余量，是故障时的操作余量。

### 多实例把 N 乘起来

单机讨论池大小是安全的，多实例讨论池大小是危险的，因为连接数是相乘的：

```text
总连接数 ≈ 实例数 × 每实例池大小 + 迁移/备份/运维连接
```

横向扩容的直觉是「加机器分担压力」，对连接数来说恰恰相反：每加一个实例，就从数据库的同一个上限里再切走一份。自动扩缩容把这件事放大——流量高峰触发扩容，扩容触发连接数翻倍，连接数翻倍触发数据库拒绝连接，拒绝连接触发健康检查失败，健康检查失败触发重启。整条链上没有任何一步是错的，合起来是一次雪崩。

托管方案通常在中间放一个外部池化层来解决这个乘法：应用连池化层，池化层用少量后端连接服务大量前端连接。按事务级池化的话，一个后端连接在不同事务之间被不同客户端复用。代价是会话语义被削弱——会话级的预处理语句、会话级临时表、咨询锁、`LISTEN/NOTIFY` 这类依赖「同一个会话」的特性会受影响。具体产品的行为差异很大，选型时要按自己用到的特性逐条核对，不能按「兼容 PostgreSQL」一句话带过。

### 超时链路要对齐

池的等待超时、语句超时、上游网关超时，三者构成一条链。这条链的每一环都要满足两个条件：外层比内层长，内层真的会取消工作。

```text
网关 / 上游超时        10s   ← 最外层，决定用户等多久
语句超时                5s   ← 服务端执行上限
取连接等待超时          2s   ← 池队列上限
```

如果顺序反了——网关 3 秒、语句 30 秒——用户在 3 秒时收到超时，应用放弃了等待，但数据库里那条语句还在跑。它继续占着 CPU、继续持锁、继续消耗连接。这类「客户端已经走了、服务端还在干」的请求叫幽灵负载，它的直接效果是拉长 R，而拉长 R 又会让更多人排队，于是又有更多人超时。

语句超时必须是**服务端**的超时（例如 PostgreSQL 的 `statement_timeout`），只在客户端放弃等待不算取消。这一条经常被写错：客户端设了超时，以为工作停了，其实只是自己不再听了。

## 观测：先有指标，再动参数

调池之前要能回答一个问题：现在的瓶颈是 N、C 还是 R。三个答案对应三种完全不同的动作，而它们在「服务变慢」这个描述下长得一模一样。

### 池侧看什么

- **取连接等待时间的 p50 与 p99**：平均值会把少数长等待抹平，而队列的痛感全在尾部。
- **活跃连接数 / 空闲连接数 / 总数**：三者一起看，能区分「池满了」和「池空着但请求慢」。
- **取连接超时次数**：这是队列溢出到失败的直接计数。
- **连接创建速率**：持续建连说明连接寿命太短，或者池在频繁回收，本身就是一个成本项。

### 数据库侧看什么

- **CPU 使用率与运行队列长度**：判断 C 是否已经被吃满。
- **活跃会话数与上限的比例**：判断离「连不上」还有多远。
- **锁等待**：按等待事件分类，而不是只看总数。等锁和等 IO 是两种病。
- **按持有时长分桶的语句分布**：不只看最慢的那条，要看「有多少条落在中间那段」——那才是 R 的主体。

### 一条判据

把两侧的读数交叉，能得到一个不需要猜的判断：

| 池等待 p99 | 数据库 CPU / 锁等待 | 结论 | 动作 |
|:-----------|:-------------------|:-----|:-----|
| 高 | 低 | N 是瓶颈 | 加 N，加到 C 的量级为止 |
| 高 | 高 | C 是瓶颈 | 降 R，不要动 N |
| 低 | 高 | C 是瓶颈，池不是 | 降 R 或扩数据库 |
| 低 | 低 | 瓶颈不在数据库 | 去查上游、网络、应用代码 |

（此表为判断逻辑示意，不含实测数据。）

四种组合里只有第一种支持「调大池」。另外三种情况下调大池，最好的结果是没效果，常见的结果是让下一轮的读数更难解释。

## 调整顺序：先 R，后 N，最后中间层

### 第一步：把 R 拆开

先量，不改。目标是找出 R 里占比最大的那一段，以及那段是不是「占着连接但不干活」。

```sql
-- 示例：按事务已持续时长排序，看谁把连接占住了
SELECT pid,
       now() - xact_start       AS xact_age,
       state,
       wait_event_type,
       wait_event,
       left(query, 80)          AS query_head
FROM pg_stat_activity
WHERE backend_type = 'client backend'
  AND xact_start IS NOT NULL
ORDER BY xact_age DESC
LIMIT 20;
```

读这张表的方法：`state = active` 且 `wait_event_type = Lock` 的，是锁争用；`state = idle in transaction` 的，是应用拿着事务在等别的东西——这一类是纯浪费，它占着连接、可能持着锁，而数据库没有为它做任何事。`idle in transaction` 的时长分布，往往就是「加池没用」的根因。

对应的动作按收益排序：

1. 把外部调用挪出事务边界。这一步通常是单项收益最大的。
2. 给长事务加语句超时，让跑飞的查询自己结束。
3. 补索引、改查询，压掉执行时间——这是执行计划那一层的事，和池无关。
4. 收敛事务范围，只包住必须原子的写。

### 第二步：按 C 定 N

N 的目标不是「尽可能大」，是「刚好喂满 C，并留出运维余量」。推导方式：

- 估计 C 的量级（核数级别起步，用压测校正）。
- 观察 R 里「数据库真正在干活」的比例。比例高，N 接近 C 就够；比例低，说明大量时间花在等外部系统上，这时调大 N 确实能提高吞吐，但那是在为一段本不该存在的持有时长买单。
- 从数据库硬上限里扣掉迁移、备份、监控、运维要用的连接，剩下的才是应用可用的总额度。
- 把总额度除以最大实例数（不是当前实例数），得到每实例的 N。

最后一条是关键：N 要按**最大**实例数算，因为扩缩容的时候没人会记得回来改池大小。

### 第三步：才轮到池化层

如果做完前两步，连接数仍然被实例数乘爆，那才需要考虑在中间放池化层。它是一个正确的工具，但它解决的是「连接数」问题，不是「慢」问题——把池化层加到一条 R 很长的链路上，只会让排队的位置再换一次。

```ts
// 示例：三个超时成链，且最内层是服务端超时
const pool = new Pool({
  max: 8,                          // N：按 C 与最大实例数推导，不按峰值 QPS 拍
  connectionTimeoutMillis: 2_000,  // 取连接等待上限
  idleTimeoutMillis: 30_000,
  maxLifetimeSeconds: 1_800,       // 短于负载均衡摘除周期
  options: '-c statement_timeout=5000', // 服务端取消，客户端放弃不算
});
```

配置本身不复杂，复杂的是每个数字背后的依据。`max: 8` 这个值如果没有推导过程，它和 `max: 80` 一样是猜的。

## 判据

把上面的推演收成几条可以在评审里直接用的判断：

- **加 N 之前，先说出 C 的估计值和 R 的构成。** 说不出来就还没到调参的阶段。
- **池等待高 + 数据库 CPU 低**，才是加 N 的许可。缺一半条件就不成立。
- **端到端慢但池等待低**，说明瓶颈不在池，动它只会制造新的变量。
- **任何一次 N 的调整都要能预测哪条指标会变。** 预测不了，就是没想清楚机制。
- **池大小必须和实例数一起算。** 单机上的合理值，乘上二十个实例就是事故。
- **三个超时要有明确的大小关系，且最内层真的会取消工作。** 否则超时只是让客户端先走，活还留在数据库里。
- **上限要留出非应用连接。** 留的是故障时还能登进去看的余地。

回到开头那行式子：`吞吐 ≈ min(N, C) / R`。池改的是 N，而 N 在追上 C 之后就不再出现在分子里。真正决定这条线高度的是 R，也就是一段请求要占着连接多久；而 R 由事务边界、查询形状、外部调用位置决定，全都在代码里，不在配置里。

所以池大小这个参数的性质要说清楚：它不生产吞吐，它决定队列有多长、等待发生在哪一层。队列长度可以调，服务速率不能靠调队列长度获得。把这两件事分开，`max_connections` 那一栏就不再是一个可以随手加个零的数字。
