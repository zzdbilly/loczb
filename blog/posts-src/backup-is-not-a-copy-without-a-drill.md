## 备份不是副本：没做过恢复演练的那份，只是一堆还在的字节

凌晨的定时器跑完，脚本退出码是 0，`snapshots/2026-11-11/` 里多出一个约 125MB 的归档，体积和昨天那份差不多，日志最后一行写着完成。这三条我盯了很久，也一直把它们当成「备份正常」的证据。

它们都是真的。但它们证明的事情比我以为的小：证明字节写进去了，没有证明字节拿得出来。

副本和备份的差别就在这里。副本是「还有一份」，备份是「这一份能顶上去」。前者是一种存储状态，后者是一种能力，而能力只能通过使用来证明。这两件事我混着说了很久，直到需要真的往回退的时候，才发现自己手里只有前一种。

### 我验收的一直是生产过程，不是恢复结果

回头看，我检查的每一项都发生在写入侧：进程有没有报错、目录里有没有文件、体积对不对。没有一项发生在读取侧。写入侧检查得再密，也只覆盖写入这一段链路；读取那一段没人走过，就等于没被验证过。

这不是态度问题，是判据选错了。用一个容易观测的指标替代了一个难以观测的目标，然后慢慢把前者当成了后者。exit 0 是前者，能不能恢复是后者。两者之间隔着一整套没被执行过的动作。

## 两个数字：RPO 与 RTO

备份这件事其实可以压缩成两个数字。它们不是术语秀，是两句承诺：一句对数据说，一句对停机说。

### RPO 是我对数据说「最多丢这么多」

RPO 是最坏情况下会丢多少数据。我的备份每天凌晨跑一次，所以这个数字接近一天。不是精确的二十四小时，因为写入是连续发生的，崩溃点落在哪个时刻是随机的；但量级上就是「一天」。

关键在于：这个数字不是我算出来的，是我默认接受的。我没有在某个时刻说过「最坏丢一天可以接受」，只是把备份频率设成每天一次，然后就没有再想过它。设定频率和承诺上限，看起来是同义词，其实是两件事。前者是配置，后者是判断。

### RTO 是我对停机说「最多停这么久」

RTO 是最坏情况下要停多久才能恢复服务。这个数字我没有。不是很大，是空的。

空着的 RTO 会让 RPO 也失去意义。一次恢复如果要花三天，丢一天数据这件事就不重要了——业务早在那之前换了别的路。反过来，如果恢复只要二十分钟，丢一天仍然可能很痛，但至少那是一个可以拿去和别人商量的数字。

所以这两个数字必须成对出现。单独一个，都是半句话。

## 供给侧有三个量，前两个能查，第三个没人测

把承诺翻译成操作，会落到三个量上。它们的关系不复杂，麻烦在于可观测性完全不同。

| 供给侧的量 | 决定什么 | 我这里的现状 | 能不能直接查到 |
|:---|:---|:---|:---|
| 备份频率 | RPO | 每天凌晨一次 | 能，看定时器和日志 |
| 保留层数 | 能回溯多远 | 每天 / 每周一 / 每月，三层 | 能，看目录结构 |
| 恢复耗时 | RTO | 未知 | 不能，因为没有记录 |

### 频率决定 RPO，而且它是被配置固定住的

每天一次意味着最坏丢一天。这个量可以改，改起来也不贵——频率翻倍，代价是空间和打包时占用的 IO。但它改的是「丢多少」，不是「能不能回来」。频率再高，也不产生任何关于恢复的信息。

### 保留层数决定能回溯多远，而它会被空间挤掉

留存按三层控制：每天一份、每周一那份多留一段时间、每月那份留得更久。这个结构本身是对的，它让「退回到上周」和「退回到上个月」都还有路。

问题是这层结构会被磁盘推着走。有一次空间吃紧，我从 550MB 清到 254MB，顺手把策略从一个更宽松的值收紧了。清的时候我没觉得这是风险，因为服务是好的、备份也是好的。但收紧这个动作动的恰好是「能回溯多远」这个量：层还在，每层覆盖的时间窗窄了。当时省下的是磁盘，提前花掉的是历史。

这件事的教训不是「不要清理」，而是：**保留策略是一个安全参数，不是存储参数。** 它应该和 RPO 一起被写下来，而不是在磁盘报警的夜里被临时改掉。

### 恢复耗时决定 RTO，而这一栏我是空的

单份快照约 125MB，其中 96% 是四个 SQLite 数据库的 gzip，配置、记忆、技能、文档加起来不到 5MB。这个构成说明恢复的瓶颈大概率在那四个库上，配置部分可以忽略——但这是推断，不是测量。

我从来没有把那些库解压回去、让服务真的跑起来，也没有记过表。所以这一栏不是「大约十分钟」，是「没有数据」。没有数据的栏位，在事故里会被现场的情绪填满，通常填进去的是乐观。

## 四种失败形态

下面的四类是我按恢复链路的环节分出来的，是分类，不是统计。我没有做过足够多次恢复，给不出比例，也不打算编一个。

### 第一种：文件在，但解不开

归档被截断、介质损坏、权限不对、解压时才发现 gzip 尾部校验过不去。这类问题的共同点是：写入的时候一切正常，`tar` 没报错，退出码是 0，体积也在合理区间。损坏发生在写完之后，或者在写入时被缓冲掩盖了。

写入侧的检查抓不到它，因为写入侧根本不读。只有真的解一次，才会撞上。

### 第二种：解开了，但拼不回去

文件都在，解压也成功，服务起不来。原因可能有很多：数据库文件是旧版本格式，运行时的依赖已经换过，配置里指向的某个东西当时不在备份范围内。

第二种比第一种更难受，因为它会给人一种「备份是好的」的错觉——数据确实完好，缺的是数据之外的那部分上下文。而「数据之外的那部分」恰恰最容易在划备份范围时被漏掉，因为它看起来不像数据。

### 第三种：恢复得回来，但太慢

恢复成功了，耗时超过了能承受的窗口。这时候备份在技术上是可用的，在业务上等同于没有。

慢的原因往往不是单个动作慢，而是动作太多：找到正确的快照、校验、解压、放到正确的位置、改回正确的属主和权限、起服务、等它自检、验证数据。每一个动作单独看都是分钟级，串起来就是小时级，而且中间任何一步卡住都会重来。

### 第四种：恢复回来，但不是你要的那份

时间点选错。每天一份，往回退一格就是一天。事故发生在两份快照之间时，你只能选「丢掉这一天」或者「丢掉这一天加前一天的写入」。

这一种最容易被忽略，因为它不算失败——系统起来了，数据也在，只是比你预期旧。而「比预期旧多少」这个量，如果平时没算过，现场就只能估。

## 一次演练：唯一真做过的那次，和从没做过的那份

我有过一份被真正验证过的备份，也有过一份从没被验证过的。它们躺在同一台机器上，看起来一样。

### 演练过的那份：镜像加 bundle，然后 clone 回来

有一次要改写一个 git 仓库的历史。这类操作不可逆，所以动手前我做了两份备份：一份镜像，一份 bundle。做完之后我没有停在「备份完成」，而是把 bundle clone 回一个新的目录，确认它确实能被读出来、内容对得上。

那次演练通过了。它让我在改历史的时候心里有底，因为我知道退路是通的——不是相信它通，是刚刚走过一遍。

值得注意的是这次演练的规模：它验证的是一个仓库，不是一台机器。它证明的是「这份备份能被读出来，且读出来的东西和原件对得上」，这个证明方式是对的，但覆盖面很窄。

### 从没演练的那份：125MB 的整机状态

那份 125MB 的整机状态备份，从来没有做过完整恢复。我没有把四个数据库解压回去让服务真正跑起来，也没有量过要花多久。它每天准时生成，体积稳定，退出码一直是 0。

两份备份的差别不在质量，在证据。一份有「读出来过一次」的记录，另一份只有「写进去过很多次」的记录。前者可以叫保险，后者只能叫信心。

而「唯一一次」这个事实本身就是个信号：演练在我这里是例外，不是例行。例外的东西不会在需要的时候恰好存在。

## 演练会撞见什么

演练的价值不只是确认「能恢复」，还在于它会把你平时不会去看的地方照亮。下面三类是我在推演里预期会撞见的，不是已经撞到的清单。

### 早已该清理的凭据

备份里可能躺着早就该作废的凭据。平时没人会去翻归档内部，所以它们一直安静地待在那里，既不报错也不占多少空间。只有在恢复的时候，这些文件会被解压到工作目录、被服务读进内存、被日志打出来。

换句话说，**备份是历史凭据的保险箱，而恢复是开箱动作。** 清理凭据时如果只清了在用的那份，归档里那份就一直在。这件事在演练之前不会有人发现，因为没人打开过。

### 已经下线的外部依赖

已经删掉的账号、迁走的对象存储、停掉的内网地址，在备份生成的那天都是有效的。恢复的时候它们会被重新读出来，然后连接失败。

这类失败不会让解压报错，只会让服务在启动后某个时刻卡住或者反复重试。它属于第二种形态：解开了，拼不回去。

### 脚本里写死的路径、用户、时区

备份脚本和恢复脚本里通常有几个写死的值：归档放在哪、解压到哪、用哪个用户跑、按哪个时区算日期。这些值在原来的机器上是对的，换一台机器、换一个目录、换一个时区就未必。

时区这一项尤其隐蔽：按日期命名的目录，在跨时区的机器上会算出不同的名字，恢复脚本去找「今天那份」时可能找到空目录。

## 把判据换掉

我不打算再问「备份成功了吗」。这个问题太好回答，也太容易答错。换三个问题。

### 第一个：从「进程 exit 0」换成「恢复成功过一次」

判据从写入侧移到读取侧。不是「脚本跑完了」，是「从这份备份里恢复出过一个能用的系统，并且验证过数据对得上」。没有这条记录，备份的状态就是「未验证」，不是「正常」。

### 第二个：两个数字写成数字，不写形容词

「大概一天」「应该挺快」「几分钟吧」都不是数字。RPO 写成「最坏 24 小时」，RTO 写成「从决定恢复到服务可用，不超过 N 分钟」——N 可以是估的，但必须是量过的估，而不是感觉出来的估。

写不下来的时候，说明这件事还没被想过，而不是说明它不重要。

### 第三个：最近一次演练在 N 天以内

备份会腐坏，依赖会漂移，脚本会过期。所以「恢复成功过一次」还不够，得加一个时间窗：最近一次演练在 N 天以内，超过就当作未验证。

这个 N 不需要很小。一个季度跑一次，比一年跑零次强得多。重要的是它进入日历，而不是停留在「有空的时候」。

## 一份可以照着跑的演练骨架

下面是我打算照着跑的东西，是示例，不是实测记录。它把「恢复」拆成几个能分别判定成败的步骤，每一步失败都能定位到环节，而不是笼统地报一个「恢复失败」。

第一步，先看清楚现在的备份脚本到底保证了什么。它保证的是「写完了」，不是「读得出来」——这两件事在顺利的时候看起来是同一件，在出问题的时候会分开。

```bash
#!/usr/bin/env bash
set -euo pipefail

STAMP="$(date +%F)"
DEST="/home/user/backups/snapshots/${STAMP}"

mkdir -p "$DEST"
tar -czf "${DEST}/state.tar.gz" /home/user/app/state
echo "backup finished: ${DEST}/state.tar.gz"
```

这套写法能保证的只有一件事：打包过程没报错。它没有回答「这个归档能不能还原成一台能用的机器」，也没有记录任何和耗时有关的信息。

第二步，还原到临时目录，用备用端口起一份，验完就拆。不要在原机上原地恢复——演练的第一原则是不能把演练变成事故。

```bash
#!/usr/bin/env bash
# 演练：还原到临时目录，用备用端口起一份，验完就拆
set -euo pipefail

SNAP="/home/user/backups/snapshots/2026-01-01"
WORK="/home/user/restore-drill/$(date +%s)"
PORT=18080

mkdir -p "$WORK"
START=$(date +%s)

gzip -t "${SNAP}/state.tar.gz"                    # 归档完整性
tar -xzf "${SNAP}/state.tar.gz" -C "$WORK"        # 能不能解开
sqlite3 "${WORK}/state.db" 'PRAGMA integrity_check;'   # 库能不能读

HOME="$WORK" ./bin/service --port "$PORT" &
PID=$!
trap 'kill "$PID" 2>/dev/null || true' EXIT

for _ in $(seq 1 60); do
    curl -fsS "http://127.0.0.1:${PORT}/health" > /dev/null && break
    sleep 1
done

curl -fsS "http://127.0.0.1:${PORT}/health"
echo "restore took $(( $(date +%s) - START ))s"
```

第三步，把结果写成一行记录。没有记录，演练就退化成一次「我觉得没问题」。

```text
演练记录
日期:        2026-01-01
快照:        snapshots/2026-01-01/state.tar.gz
归档校验:    通过 / 失败
解压:        通过 / 失败
库完整性:    通过 / 失败
服务启动:    通过 / 失败
耗时:        __ 秒
结论:        可用 / 不可用
撞见的问题:  __
```

这份骨架我还没有跑过。写在这里的意义，是把它从「想法」变成「待办」——前者不会发生，后者至少会在某天被翻出来。

## 备份的价值不在它存在

一份备份有三种状态：写进去了、读出来过、在需要的时候顶上去过。大多数人（包括我）停在了第一种，然后用第一种的语言去描述第三种。

exit 0 是个好信号，但它只覆盖了链路的前半段。后半段没有捷径：解一次、起一次、量一次，把两个数字写下来，把演练排进日历。做完这些，备份才是保险；不做，它就只是一堆还在的字节——体积对，日期新，看起来很像退路。

我现在能诚实说的只有一句：那份 125MB 的备份，我还没用它拿回过任何东西。这句话不好听，但它比「备份正常」准确。
