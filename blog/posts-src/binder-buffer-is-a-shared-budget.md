## 1MB 不是建议值，是同一个进程里所有 Binder 事务共享的顶

先看一段能编译、能跑、在单页调试时也没有任何异常的代码：

```kotlin
// 示例：一个看起来没有任何问题的详情页入口
fun openDetail(context: Context, article: Article) {
    val intent = Intent(context, DetailActivity::class.java).apply {
        putExtra("article", article)                 // 整个实体
        putExtra("paragraphs", article.paragraphs)   // 长列表
        putExtra("cover", article.coverBitmap)       // 位图
    }
    context.startActivity(intent)
}
```

这段代码在冷启动、只点一次、列表只有十条的时候，通常看不出问题。它失效的时刻往往很具体：用户一边在同步离线包，一边点开了详情页；或者后台正在批量上报埋点，前台刚好推了一个新页面；又或者上一次打开详情页的操作还没走完，第二次点击紧跟上来。

异常的名字很容易把人带偏。`TransactionTooLargeException` 读起来像是在说「你这次传的东西太大了」，于是第一反应是压缩那个对象、删几个字段、把位图换成缩略图。这些动作有时有效，但经常无效——因为真正被撑满的，不是这一次调用的额度，而是整个进程共用的那一块。

把这句话先摆在前面：**Binder 的事务缓冲记在进程头上，不记在调用头上。** 你发出的每一个跨进程请求，都在从同一口池子里舀水。理解这一点之后，很多「明明只传了几十 KB 却崩了」的现象才有解释。

## 先把 1MB 这个词拆开：它属于进程，不属于调用

Android SDK 对 `TransactionTooLargeException` 的说明里有一句关键描述：Binder 事务缓冲的大小是固定的，业界常引的量级约为 1MB，并且由该进程所有在途的事务共享。这是文档事实，不是某一台设备上的实测值。不同系统版本、不同厂商的实现细节可能不同，但这个「按进程共享」的结构是理解问题的起点。

初学时的直觉是把它当成一条管道的直径：一次请求不能超过这个直径，超了就被拒绝。真实的模型更像一个共用的中转仓：所有人的包裹都先放进同一个仓里，仓满了，最后来的人被拦在门口。

### 池是按进程分的，不是按调用分的

一个进程里可以有几十个 Binder 代理对象，指向不同的服务；可以有多个线程同时发起调用；也可以有 Service、ContentProvider、Messenger 各种入口。这些差异都不会让额度变多。池只有那一个，谁来都从里面取。

这件事的直接推论是：**换一个 Binder 对象、换一个目标服务、换一个线程，都不改变预算的归属。** 你在 A 通道上超了，不会因为改走 B 通道就变宽；B 通道和 A 通道花的是同一笔钱。

### 在途事务共享同一个池

「在途」指的是从数据被写进 Binder 驱动，到接收侧把它读出去、缓冲被释放之间的这段时间。它不是一个瞬间，而是一个区间。区间里的事务都要占地方。

于是「单次请求多大」这个问题，必须补上另外两个维度才有意义：同一时刻有几个请求在途，以及每个请求会在途多久。前一个由并发度决定，后一个由接收侧的处理速度决定。只盯着单次体积，等于只看三个变量里的一个。

### 报错现场总是指向最后一次

这是这套机制里最容易误导人的地方。

当池子被占满、新事务写不进去时，异常会落在触发失败的那一次调用上，可能抛在发送侧，也可能抛在接收侧。异常信息里带的字节数，描述的往往是「当时那一次写入」的数据量，而不是池里已经躺着多少。也就是说，报错指向的是最后一个受害者，不是主要原因。

如果前面几个事务各自都只有一两百 KB，最后一个只有几十 KB，异常照样会出现在最后一个身上。日志里看到的是「几十 KB 的请求导致了 TransactionTooLargeException」，看起来荒谬，实际上是账本被记错了人。

用一个纯示意的表把这件事摊开（数字只为说明叠加关系，不代表任何真实设备或真实应用）：

```text
示例：同一进程内的在途事务，数字仅作示意
时刻   事务                          单次大小    池占用
t0    预取图片列表                  约 380 KB   约 380 KB
t1    同步日志批量上报              约 300 KB   约 680 KB
t2    打开详情页（整个实体）        约 260 KB   约 940 KB
t3    设置页读取配置                约 40 KB    约 980 KB
t4    埋点批量写入                  约 60 KB    超出，异常落在 t4
```

单看每一行，没有一条接近 1MB。四行叠在一起，池就满了。最后那 60 KB 的埋点请求没有任何设计错误，它只是来得最晚。

## 误判一：我的 Bundle 只有几十 KB，不可能超

这个判断的问题不在于数字算错，而在于用「单次」去回答一个「累计」的问题。

### 单次体积的直觉从哪里来

大多数接口文档、大多数示例代码、大多数同事之间的经验传递，说的都是「一次别传太大」。这句话本身没错，但它省略了主语：别传太大，是相对于什么而言。相对于单次事务的上限，几十 KB 确实很小；相对于一个同时跑着预取、上报、配置同步的进程，几十 KB 乘以在途数量之后就不再小。

更麻烦的是，单次体积的直觉会让人形成一种错误的安心感：既然我只有几十 KB，那么任何 `TransactionTooLargeException` 都一定不是我的问题。这种安心感会拖长排查时间，因为你会去怀疑系统、怀疑 ROM、怀疑别的模块，而真正该看的是自己这个进程的并发结构。

### 序列化后的体积和内存里的体积不是一回事

Bundle 里放一个对象，写进 Parcel 时要按 Parcel 的格式重新编码：字符串带长度前缀，容器带元素个数，字段按顺序写入，还有对齐和类型标记。最终字节数和你用内存分析工具看到的对象大小不是同一个量。

一个经验上「看起来只有几十 KB」的实体，序列化之后可能明显更大；一个包含大量短字符串的列表，开销尤其容易超预期，因为每个元素都有头部。这里不给具体倍数，因为倍数取决于字段类型和内容分布，任何固定比例都是编出来的。可执行的做法是量一次，而不是估一次。

### 并发让每次都很小失效

十个各自 80 KB 的请求，单独看都在安全区，同时在路上就是 800 KB 的量级。这个加法是示意性的，实际占用还要算上每次事务的固定开销，但方向是确定的：**小请求不会互相礼让。**

这也是为什么问题常常出现在「用了某个 SDK 之后」「加了预取之后」「埋点改成批量之后」。你没有改那个传参的函数，你只是给池子增加了同时取水的人。

## 误判二：之前一直好的，今天突然坏了

「一直好的」通常意味着：在你能观察到的使用路径上，池子从来没有同时被占满过。它不意味着代码是正确的。

### 变化往往不在你改的那一行

新增一个前台服务、把某个同步从串行改成并行、给列表加了预加载、把日志从本地文件改成实时上报、接了一个会在启动时拉配置的 SDK——这些改动都不会碰 `putExtra`，但都会改变在途事务的数量和持续时间。

排查时如果只 diff 传参那一处，很容易得出「这行没动，所以不是它」的结论。有效的做法是反过来问：这个进程在崩溃前的一段时间里，一共发起了哪些跨进程调用，它们分别有多大，接收侧处理得有多快。

### 前一次事务没释放，会占着池

这是最隐蔽的一种。缓冲不是在发送完成时释放的，而是在接收侧读完、事务结束之后才释放。如果接收侧卡住了——主线程在做重计算、在等一把锁、在等数据库、在等网络——那块内存就一直被占着。

于是会出现这样的序列：第一个请求很大，接收侧处理慢；第二个请求很小，但池里还留着第一个的账；第二个请求失败，日志里只有它。从日志看，是一个小请求崩了；从时间线看，是前一个大请求没有及时退场。

推演到这里可以得到一个可操作的判断：**当异常信息里的体积和你的实际数据对不上时，先去看同一时间段内还有哪些事务在途，而不是继续压缩当前这个对象。** 这不是文档给出的结论，是从共享池模型推出来的排查方向。

### onSaveInstanceState 走的是同一条路

Activity 的状态保存也通过 Binder 传递。`onSaveInstanceState` 收到的 Bundle，以及 `SavedStateHandle` 里存的东西，最终都要序列化后交给系统进程。它和普通的跨进程调用共享同一类约束。

社区里常提到一个约 500 KB 量级的经验值，但具体行为与系统版本、厂商实现相关，不能当成契约来依赖。可靠的写法是把它当预算来管：状态里只放恢复界面所必需的最小信息，列表数据、正文、图片一律不放，需要时按 id 重新取。`SavedStateHandle` 里塞一大块 JSON 是同一类错误的另一种写法——名字叫 Handle，不代表它适合装行李。

## 误判三：改成在后台线程发就不会超

这个想法很自然：主线程上的调用容易卡顿，那就挪到后台。挪完之后卡顿确实少了，于是认为问题解决了。

### 线程换的是执行位置，不是额度

池是按进程计的，线程只是取水的人。主线程取水和后台线程取水，舀的是同一口池。把调用挪到工作线程，改变的只是「谁在等结果」，不改变「有多少水」。

更常见的情况是反过来的：挪到后台之后，原本串行的几次调用变成了并发，池的占用反而上升。表面上看主线程不卡了，实际上失败的概率变高了，只是失败发生在一个没有人处理异常的地方。

### 异步只是把失败挪到别的时间点

同步调用失败，异常沿着调用栈往上走，容易被看见。异步调用失败，异常落在线程池的任务里，如果没有兜底，表现就是「偶现崩溃」或者「功能静默不生效」。这就是为什么有些团队在改成异步之后，问题看起来消失了，实际上只是从必现变成了难复现。

### 串行化能缓解，但它不是预算

把同一类请求串起来发，确实能降低并发占用，这是一种有效的止血手段。但它有两个局限：一是只能约束自己发起的请求，管不了同进程里其他模块；二是串行会拉长总耗时，接收侧一旦变慢，队列会堆积，池的占用时间反而变长。

止血清创可以，把它当成长期方案不行。真正的解法还是回到预算：每一次传参都足够小，任何时候在途都不会把池占满。

## 传的到底是什么：一次序列化拷贝

跨进程传参不是把对象的引用递过去，而是把对象写成一串字节，交给内核搬运，再由接收侧读出来、重新构造一个对象。发送侧一份，接收侧一份，中间还有一份在池里。

### 写入侧：把对象变成字节

写入的过程要遍历对象图：基本类型直接写，字符串转成 Parcel 的字符串格式，集合先写长度再逐个写元素，可序列化的类按字段顺序写。每一步都有开销，也都有可能踩到「这个字段不该被传」的问题。

一个容易被忽略的点是：**你在发送侧持有的那个对象，和接收侧拿到的不是同一个实例。** 接收侧修改它，不会影响发送侧；发送侧在发送后修改它，也不会影响已经写进 Parcel 的那份拷贝。把跨进程传参当成「把对象交出去」来设计，会自然地写出「传整个实体、让对方直接用」的代码，而这正是体积失控的来源。

### 读取侧：再变成一个新对象

接收侧读 Parcel 时，要为这些字节重新分配内存、重新构造对象。数据越大，分配越多，GC 压力越大，读取耗时越长。读取耗时又直接决定了缓冲被占用的时间——这是一个闭环：传得越大，读得越慢，池被占得越久，后面的请求越容易失败。

所以在讨论「能不能传」的时候，真正要评估的是三件事：发送侧写多久、接收侧读多久、这块内存在池里躺多久。只算第一项，会低估风险。

### 拷贝的代价会叠加在池上

同一份数据，在内存里出现两次，在池里还占一次，写入和读取各消耗一次 CPU。这个结构决定了「传大对象」在任何维度上都不划算：内存、时间、失败概率，三项同时变差。

如果只是想知道自己有没有超标，可以在发送前量一次：

```kotlin
// 示例：发送前给 extras 做一次序列化体积体检
fun Bundle.parcelSizeBytes(): Int {
    val parcel = Parcel.obtain()
    return try {
        writeToParcel(parcel, 0)
        parcel.dataSize()
    } finally {
        parcel.recycle()
    }
}

fun Intent.assertExtrasBudget(limitBytes: Int = 64 * 1024) {
    val size = extras?.parcelSizeBytes() ?: 0
    check(size <= limitBytes) {
        "extras 序列化后 $size 字节，超过单次预算 $limitBytes"
    }
}
```

这段代码量的是「这一次要写进去多少」，不是池里已经占了多少。它不能替代并发分析，但它能把「几十 KB」从感觉变成数字。量出来超过预期的时候，通常会发现列表、位图或者一整段 JSON 藏在某个不起眼的字段里。

## 把跨进程传参当成网络请求来做预算

如果两个模块之间要走 HTTP，几乎没有人会把整个数据库实体塞进请求体，然后指望对端直接使用。大家会定义 DTO、只传必要字段、给请求体设上限、大文件走对象存储、列表接口分页。跨进程传参是同一类问题，只是链路更短、延迟更低，让人误以为约束也更少。

### 先定字段白名单

不要从「这个对象有什么」出发，而要从「对方需要什么」出发。接收侧真正用到的字段通常只有几个：一个 id、一个来源标记、一个可选的定位参数。其余的字段要么接收侧自己能查，要么根本不该由发送侧决定。

白名单还有一个附带好处：它让接口的演化变得可控。字段是显式列出来的，增加一个字段就要改两边的定义，不会出现「发送侧悄悄多带了一个大字段，接收侧根本没用」这种情况。

### 只传标识符，让对方自己取

这是收益最大的一条改动。把实体换成一个 id 或一个 URI，传输的体积从「和内容成正比」变成「常数」。接收侧拿到 id 之后，从数据库、ContentProvider、文件或者内存缓存里取。取不到就显示空态或重试，而不是让整个页面打不开。

代价是接收侧要多一次查询。这次查询是本地的，耗时可控，而且可以按需只取当前屏幕需要的部分。相比之下，把整篇正文和所有图片先塞过 Binder，再在接收侧解析，通常是更贵的那条路。

### 大载荷换通道

大文件不该走 Parcel。可以写进应用私有目录，传一个 `file://` 或 `content://` URI；跨应用共享时用 `FileProvider` 加读权限授予，让接收方按 URI 自己去读。需要在进程间共享大块内存时，用文件描述符或共享内存类的机制，而不是把字节数组塞进 Bundle。

判断标准很直接：如果这个数据在接收侧本来就要落盘或者本来就在盘上，那就没有必要先读进内存再序列化一次。传地址，不传内容。

### 能分批就分批

批量接口要支持分页或游标。一次传一百条和一次传十条，除了体积差异，更重要的是失败代价：整批失败要整批重试，分批失败就只重试那一段。分页还天然给了你一个背压点——上一批没处理完，下一批不发，池的占用就可控。

### 给预算留余量

不要拿 1MB 当上限来设计。那个数字是整个进程共享的总量，不是你一个模块的配额。给自己定一个远低于它的数，比如几十 KB，把剩下的留给同进程里其他不可控的调用。这个数字不需要精确，重要的是它存在，并且在代码里被检查。

把几种形态放在一起对比：

| 传参形态 | 单次体积 | 谁负责读取 | 失败形态 | 适用场景 |
|:---------|:---------|:-----------|:---------|:---------|
| 传整个实体 | 与内容成正比 | 接收侧直接用 | 偶发超限，难复现 | 不建议 |
| 传 id | 常数级 | 接收侧查库 | 查不到，可显示空态 | 绝大多数页面跳转 |
| 传 URI | 常数级 | 接收侧按权限读 | 权限或文件缺失 | 图片、文档、导出文件 |
| 传文件描述符 | 常数级 | 接收侧直接读写 | 句柄失效 | 大块数据、流式处理 |
| 分批传列表 | 每批可控 | 接收侧逐批处理 | 单批失败可重试 | 同步、导入、批量操作 |

## 检查清单：把应该不会超变成可执行动作

下面这几条适合放在发版前的自查里，也适合在排查偶发崩溃时逐条过一遍：

1. extras、arguments、SavedStateHandle 里有没有列表、位图、整段 JSON、整个实体？有的话先列出来，逐项判断能不能换成 id。
2. 每个传过去的字段，接收侧是否真的用到了？没用到就删掉，不要因为「以后可能要用」而保留。
3. 发送前有没有对序列化体积做过一次断言？上限是不是设在几十 KB，而不是贴着 1MB？
4. 这个进程在同一时刻还可能有哪些在途调用？预取、日志上报、配置同步、埋点批量写入是否会和页面跳转撞在一起？
5. 接收侧有没有可能长时间不读？主线程重计算、等锁、等数据库、等网络，都会延长缓冲的占用时间。
6. `onSaveInstanceState` 和 `SavedStateHandle` 里放的是状态还是数据？超过几十 KB 就该考虑换存储，只留恢复所需的最小信息。
7. 大文件是否走了 URI 权限或文件描述符？有没有把文件读成 `ByteArray` 再塞进 Parcel 的写法？
8. 批量接口是否支持分页或游标？失败之后能不能只重试某一段，而不是整批重来？

这八条里，第一条和第四条最能暴露问题。第一条决定单次体积，第四条决定同时有多少次。两者相乘，才是池真正承受的压力。

## 收束：预算是共享的，账记在最后一个身上

跨进程传的不是对象，是拷贝。这句话有两层含义：一是接收侧拿到的是副本，不要指望共享状态；二是这次拷贝要占内存、占时间、占一块全进程共用的缓冲。

预算是共享的，账却总记在最后一个身上。异常指向最后那次调用，日志里只有最后那次的数据量，于是人很容易去修那个最晚到的、体积最小的请求。真正该做的，是回头看这个进程在同一段时间里一共舀了多少水。

把跨进程传参当成网络请求来设计，是一个能落地的起点：定字段白名单、只传标识符、给体积设上限、大载荷换通道、批量接口分页。这些做法不依赖任何具体版本的阈值，也不会因为系统实现变化而失效。它们做的事情只有一件——让每一次传输都足够小，让任何时候的在途都不会把池占满。
