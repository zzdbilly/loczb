## 两个平台给「进程能活多久」的默认答案，是相反的

写安卓久了会形成一种直觉：屏幕上的一切随时可能消失。用户按了 Home、切到另一个应用、系统内存吃紧，进程就可能被回收；回来时 Activity 会被重建，`onDestroy` 不保证被调用，静态变量和单例全部回到初始值。这套直觉不是悲观，是平台文档写明的运行模型（文档事实）。

这种直觉会渗进代码的每个角落。数据先写数据库再更新界面，后台任务交给可持久化的调度器，页面恢复时从 `SavedStateHandle` 里取回游标和选中项，而不是指望某个字段还在。写久了之后，开发者对"内存不可信"这件事不再讨论，它变成了默认前提。

写服务端久了会形成另一种直觉：进程会一直在。请求进来、处理、返回，内存里的缓存越攒越热，启动时把配置和字典加载进单例，定时器里挂几个清理任务——这些写法在开发机上跑几个月都不会出事，因为开发机上那个进程确实一直在（文档事实：这是对开发机的观察，不是生产环境的保证）。

两种直觉各自都对，放在一起就矛盾。同一段业务逻辑，移动端版本假设"执行随时会被打断、内存随时会清空、启动会发生很多次"，服务端版本假设"进程长活、内存可信、启动只发生一次"。这个差异很少被写进注释，也很少出现在接口文档里。它藏在 `object`、`companion object`、`@Singleton`、`static`、进程内定时器这些语法糖后面，编译器不会提示，代码评审也通常不会问。

于是跨栈迁移时，塌的往往不是语法。协程能编译，定时器能跑，单例注入能过评审，类型全对、测试全绿。等到滚动发布、容器重调度、OOM kill、扩缩容这些"正常事件"发生时，问题才出来——而那时候，出错的位置离当初写下假设的那行代码已经很远了。

后面这份对照表，是把这些没写下来的假设摊开。表里的"意外"一列，指的是两边各自都会遇到、但很少被写进测试的事件。

（本文两类句子分开写：Android 平台行为与通用服务端事实标为「文档事实」；从默认写法推到后果的部分标为「推演」，具体是否触发取决于进程回收时机与部署方式。）

## 一张存活假设对照表

| 同一件事 | 安卓的默认假设 | 服务端的默认假设 | 两边都会遇到的意外 |
|:---|:---|:---|:---|
| 内存里的数据 | 随时会没，不能当真源 | 进程活着就在，可以当真源 | 进程被杀或实例被替换，内存归零 |
| 定时任务 | 不能依赖进程内计时器，要用可持久化调度 | 进程内定时器够用，反正进程不关 | 发布、缩容、崩溃时任务消失，或每个实例各跑一遍 |
| 初始化 | 每次冷启动都要重来，必须便宜且可重入 | 启动时算一次，之后全局复用 | 多实例各算一次；配置改了不刷新 |
| 锁与标志位 | 进程死了，标志位也该跟着失效 | 一个布尔字段表示"正在处理"就够了 | 持锁进程死掉，标志位永久卡住 |
| 未完成的写 | 不能假设能做完，要可恢复、可续 | 请求处理完再返回，客户端会等 | 进程在写到一半时被杀，留下半条记录 |

这张表不是在评判谁对谁错。两边的假设都是各自约束下的局部最优：安卓的假设来自资源约束（手机内存有限、系统有权回收进程），服务端的假设来自部署形态的历史（单机、长驻、手工发布）。约束变了，假设没跟着变，问题才出现。

值得逐行读一遍的是第三列。"进程被杀"在安卓上是被写进文档的常态，在服务端上则被当成故障；但滚动发布和容器重调度让"进程被杀"变成了服务端的常态。同一件事，一边写进了设计，一边留在了意外里。

下面三行是真正会塌的。它们共同的特征是：错误不在编译期暴露，也不在单实例的测试里暴露。

## 第一个塌的东西：把进程内缓存当成数据源

### 服务端在哪些时刻失去进程

滚动发布时，新版本逐批替换旧实例，旧实例上的内存缓存随着进程一起消失。容器编排重调度时，节点下线或健康检查失败都会让容器换个地方重建，本地状态不带过去。内存超限时，内核直接杀掉进程，没有优雅退出的机会。低峰缩容时，被移除的实例带着自己那份缓存一起消失。无服务器形态下，请求结束之后运行环境可能被冻结或回收，下一次冷启动从零开始。

（文档事实：这些是容器与编排系统的常规行为；推演：具体到某个服务在哪个时刻触发，取决于部署方式、资源限制和回收策略。）

这些事件没有一个是"故障"。它们每天都在发生，监控面板上通常是绿的，因为系统整体可用——单个实例的消失被负载均衡和副本数掩盖了。

### 进程没了之后，错误行为长什么样

一条典型路径：请求 A 更新数据库，同时把新值写进进程内的 Map；请求 B 读取时先查 Map，命中就返回。进程重启后 Map 空了，请求 B 回落到数据库，读到正确值——这时候看起来没问题。

真正的问题在两种情况下暴露。

第一种，缓存里存的是数据库里还没有的状态：预写标记、聚合中间值、去重集合、已发送消息的 id。这些东西没有持久副本，进程一死就凭空消失。业务表现是"少了一块"——少发一条通知、少做一次对账、同一个事件被处理两遍。它不会报错，只会让某个数字慢慢偏。

第二种，多实例。请求 B 打到另一个实例，那个实例的缓存里是旧值，于是读到旧数据。更麻烦的是这个旧值会一直存在，直到那个实例也重启。代码里没有任何一行声明"这份内存是权威的"，但读取路径事实上把它当成了权威。

还有一种更隐蔽的：缓存为空时的行为没有被设计过。进程刚启动，缓存是冷的，所有请求同时回落到数据库，数据库瞬时压力上升；如果此时还有降级开关或者熔断逻辑，系统可能直接进入降级状态，而原因只是"进程重启了"。这属于缓存击穿，但根因仍然是同一个：代码默认缓存应该一直在。

### 正确形态：缓存只是加速层

把内存缓存降级成"可丢失的加速层"：任何写操作先落持久层，缓存只做读加速；缓存里允许放派生值，不允许放唯一副本；进程启动时缓存为空是合法状态，不能因此报错或进入特殊分支。

判断标准很朴素：把缓存整个清空、重启进程，业务结果应当不变，只是变慢。如果结果会变，那这份内存就不是缓存，是没落盘的数据。

```kotlin
// 状态分层：可丢失的、需要恢复的、必须持久化的，分开放
class OrderRepository(
    private val dao: OrderDao,                                     // 持久层：唯一真相
    private val cache: MutableMap<String, Order> = mutableMapOf()  // 加速层：可丢
) {
    suspend fun get(id: String): Order =
        cache[id] ?: dao.find(id).also { cache[id] = it }

    suspend fun save(order: Order) {
        dao.upsert(order)      // 先落盘
        cache[order.id] = order
    }
}
```

这段代码只表达顺序：先持久化，再更新缓存。反过来写，进程在两步之间被杀，缓存里就会留下一条数据库没有的记录——下一次读命中它，等于读了一条不存在的订单。

## 第二个塌的东西：进程内定时器

### 发布窗口里丢掉的执行

进程内的定时器绑在进程上。滚动发布时旧实例被替换，计时器跟着消失；缩容时被移除的实例同样带走自己的计时器。如果这个定时器负责的是"每分钟扫一次超时订单""每小时对一次账"，那么发布窗口内的那次执行就没了。

丢一次通常没人发现，丢几次之后数据开始漂移。漂移是静默的：没有报错，没有告警，只有某天对账时数字对不上，然后往回翻日志，发现那几段时间里任务确实没跑。而日志本身也可能随着实例一起没了。

还有一类是"补跑"缺失。进程内定时器通常只触发"当前这一次"，不会关心上次执行到哪。实例重启后，它从下一个周期开始，中间空掉的窗口没有人补。如果业务语义是"每小时的增量必须处理"，这个空洞就是永久的数据缺口。

### 多实例下的重复执行

更隐蔽的是反方向。为了保证"不丢"，把定时器留在每个实例里，于是 N 个实例各跑一遍。清理任务重复执行通常无害（删两次同样的记录），但对账、发券、发通知、计费这类带副作用的操作，重复就是事故。

代码里常见的补丁是一个布尔标志位或者一行数据库记录锁。问题是标志位的生命周期又回到了进程：持锁的实例被 OOM kill，锁没人释放，任务从此卡死。有些实现会加一个"超时清理"，但清理逻辑本身又跑在进程内定时器里——用同一个假设去修同一个假设，只是把故障推迟了。

### 正确形态：调度外置，执行幂等

把"什么时候跑"和"跑什么"分开：调度交给外部系统（编排平台的定时任务、独立调度服务、带持久化的任务队列），执行端只保证"同一件事做多次和做一次结果相同"。

执行端还需要一个租约式的互斥：拿锁时带上过期时间，处理过程中续期，进程死了锁自动过期，下一个实例能接手。这比布尔标志位多写几行，但它是唯一不依赖"进程会活着"的写法。

```text
进程内定时器                     外置调度 + 幂等执行
─────────────────────────────    ─────────────────────────────
绑在进程生命周期上                绑在调度系统上
发布、缩容即丢失                  调度记录持久化，重启后补跑
多实例各跑一遍                    由调度器决定谁跑，或租约互斥
失败无记录                        失败进重试队列，可观测
补跑窗口无人负责                  按业务键去重，重复投递无害
```

表里最后一行是关键。外置调度只解决"什么时候跑"，不解决"跑两次会怎样"。两件事都做到，任务才算真正从进程里搬出去了。

## 第三个塌的东西：启动时算一次的单例

### 单例的生命周期其实等于进程

`@Singleton`、`object`、`static final` 这些写法给人一种"全局唯一、只初始化一次"的印象。准确的说法是：在一个进程内唯一，在一个进程内初始化一次。进程换了，单例就是新的；实例多了，单例就是多份。

这个区别在单实例、长驻的服务上几乎不可见，因为"进程"和"服务"是一对一的。一旦上了多副本，一对一就断了：服务还在，进程已经换了好几茬；同一时刻，服务对应着好几个进程，每个进程各有一份"全局唯一"。

### 多实例各算一次，配置变更后不刷新

滚动发布期间，新旧实例同时在线，各自持有一份启动时算出来的规则表。如果这期间配置中心改了规则，新实例读到新值，旧实例还是旧值，同一时刻的请求会得到两种结果。

这不是缓存过期的问题，是"启动时算一次"这个动作把时间点焊死在了进程启动的那一刻。缩容扩容、蓝绿切换、灰度发布都会放大这个窗口：灰度期间两套规则并存，从外部看就是随机行为，而排查的人往往会先怀疑负载均衡或者网络。

还有一类后果是启动成本。规则表越大，冷启动越慢；副本越多，冷启动越频繁；自动扩缩容时，新实例还没加载完就被健康检查判死，然后又起一个，循环几轮才稳定。根因不是加载慢，是把"必须常驻内存"当成了前提。

### 正确形态：要么每次读，要么带版本可刷新

两条路都行，但不能停在中间。

第一条：规则表足够小、读取足够便宜，就每次用时读，或者按短周期刷新，让"过期"有上界。代价是每次读多一次查表或一次远程调用，换来的是不需要关心进程活多久。

第二条：确实需要常驻内存，就带上版本号，订阅变更事件，收到新版本时整体替换引用，让读取方看到一致的快照。替换而不是原地修改，读方就不会看到半张表。

最差的是第三种：启动时算一次，之后既不刷新也不带版本，靠"反正不会变"撑着。

```kotlin
// 带版本的可刷新快照：替换引用是原子的，读方永远看到完整的一份
class RuleSnapshot(val version: Long, val rules: Map<String, Rule>)

class RuleHolder(private val load: (Long) -> RuleSnapshot) {
    @Volatile private var current: RuleSnapshot? = null

    fun get(): RuleSnapshot =
        current ?: synchronized(this) {
            current ?: load(0L).also { current = it }
        }

    fun onConfigChanged(newVersion: Long) {
        current = load(newVersion)   // 整体替换，不做原地修改
    }
}
```

版本号从哪里来取决于配置系统；关键点是替换而非原地改。原地 `putAll` 在并发读下会露出中间状态，而中间状态往往就是最难复现的那类 bug。

## 为什么两边都没提前发现

因为两边的测试各自都跑得绿。

安卓侧的测试通常在 JVM 上跑（Robolectric 或纯单元测试），进程从头到尾活着；instrumentation 测试跑在设备上，也很少主动杀进程。`ViewModel` 的测试验证的是配置变更后状态还在，这确实成立——但配置变更不是进程死亡。真正该测的场景是系统回收进程后恢复，而它在常规测试里几乎不出现，因为需要专门模拟 process death，成本比写一个断言高。

服务端侧的测试更彻底地绕开了问题：单元测试不起进程，集成测试起一个进程然后跑完所有用例，端到端测试在单实例上验证主流程。三类测试都不会在"处理到一半时杀掉进程"，也不会在"两个实例同时在线"的拓扑下跑。滚动发布和多实例是部署阶段的事实，不是测试阶段的输入。

预发环境也补不上。预发通常是单实例、短生命周期、人工触发，恰好是最不容易暴露存活假设的拓扑。真正能暴露问题的是"发布过程中持续有流量"和"实例数在 1 和 N 之间来回变"，而这两种状态在预发里很难长期维持。

评审同样补不上。评审看的是这段代码对不对，而不是这段代码假设了什么在运行。一行 `private val cache = mutableMapOf()` 在评审里再正常不过；要看出问题，得先问"这个进程会不会死、这个类会不会有多个实例"，而这两个问题不在 diff 里。

（推演：这不是某一边的疏忽，而是测试环境的拓扑与生产拓扑不一致——测试里进程的存活时间被固定住了，生产里它是变量。）

## 迁移清单：五件可以马上做的事

### 状态分层

把状态按"可丢失 / 需恢复 / 必须持久"分三层。可丢失的放内存，需恢复的放 `SavedStateHandle` 或等价的序列化通道，必须持久化的落数据库或对象存储。

分层之后，"进程死了会怎样"对每一层都有明确答案，而不是笼统地希望它别死。分层还顺带解决了另一个问题：哪一层该加锁、哪一层该做事务、哪一层可以随便重建，边界清楚了，评审时也容易看出越界。

```kotlin
// 三层各有归宿：内存态、可恢复的 UI 态、持久态
class EditorViewModel(
    private val saved: SavedStateHandle,   // 跨进程死亡，仅限小且可序列化
    private val draftStore: DraftStore     // 跨进程死亡，落盘
) : ViewModel() {
    var cursor: Int
        get() = saved["cursor"] ?: 0
        set(value) { saved["cursor"] = value }

    fun onTextChanged(text: String) {
        draftStore.save(text)   // 正文落盘，不指望内存
    }
}
```

`SavedStateHandle` 适合游标、选中项、草稿 id 这类小状态；正文本身走磁盘。把它当数据库用，序列化体积和事务语义都会出问题。

### 启动幂等

冷启动不是"第一次启动"，而是"又一次启动"。启动时做的事要能在任意次重复执行后得到同一结果：建表用 `IF NOT EXISTS`，迁移带版本号且可重入，初始化写库用 upsert 而不是 insert。

这条纪律在安卓上是刚需（进程随时重启），在服务端上同样成立（实例随时上下）。区别只在于安卓开发者被平台逼着养成，服务端开发者没有这个压力。

### 优雅退出

收到终止信号后停止接新请求、等待在途请求到上限、把队列里的任务放回可重试的位置、释放租约。

"优雅"有上限：OOM kill 和 `SIGKILL` 不给机会，所以优雅退出是减少损失，不是保证完成。这也是为什么关键收尾工作不能只放在关闭钩子里——钩子会跑，但不是每次都跑得到。

```bash
# 终止信号处理的三步：停接入、等在途、交还未完成的工作
trap 'app.stop_accepting; app.drain --timeout=20s; app.release_leases' TERM INT
```

### 租约代替标志位

任何表示"我正在处理"的状态都带过期时间，并且由持有者续期。读方判断的是"租约是否仍有效"，而不是"标志位是否为真"。这样持锁进程死掉之后，系统能自行恢复，不需要人工清标志。

租约还需要一个单调时钟或数据库时间来兜底，否则各实例的本地时钟偏差会让过期判断不一致。这一条在容器环境里尤其容易踩到。

### 任务外置且幂等

把"必须被执行"的工作从进程内存搬到持久化队列或调度系统。执行端按业务键去重（订单号、消息 id、日期分区），保证重复投递不产生重复副作用。

判断标准只有一条：同一条任务投递两次，结果与一次相同。做不到这一点，任务搬到哪里都不安全。

## 反向借用：安卓该从服务端学的四件事

前面说的都是服务端向安卓借纪律。反过来的借用同样成立，而且更少被提起——安卓代码习惯了自己是"随时会死"的一方，反而容易忽略"死之前和死之后"的工程质量。

### 幂等

安卓侧的重复执行很常见：后台任务在约束满足后重试、广播接收器收到重复广播、页面恢复时重新拉取。把写操作设计成按业务键幂等，比在客户端加"只执行一次"的标志可靠——标志本身也在内存里，进程一死就没了。

### 超时

移动网络的特点是"没有响应"多于"明确失败"。每个跨网络调用都该有超时，包括 DNS、连接、读取，以及整体预算。没有超时，协程会挂在挂起态，用户看到的是转圈，代码看到的是"还在进行"。

超时还要能传导：上游给了 2 秒预算，下游的三次重试加起来就不能超过 2 秒，否则超时形同虚设。

### 重试

重试要有边界：指数退避、最大次数、可重试错误与不可重试错误分开。对 4xx 里的语义错误重试没有意义，对超时和 5xx 才值得。重试还需要幂等配合，否则一次超时可能变成两次扣款。

### 可观测

服务端习惯把关键路径的埋点、日志、指标一起上，安卓侧常常只留 `Log.d`。进程被回收之后，日志是唯一能还原"死之前发生了什么"的东西。至少要把关键状态转换、失败原因、重试次数落到可上传的地方，而不是只打在 logcat 里。

可观测还有一层作用：它让"进程死过"这件事变得可见。没有这件事的记录，所有存活假设的问题都会被归因成"偶现"，而偶现的问题通常没人修。

## 判据：怎么判断一段代码在依赖存活假设

不需要读完全部代码，问五个问题就够：

1. 把进程杀掉再启动，这段逻辑的结果会变吗？会变的部分，是不是被当成了真相？
2. 这段代码同时跑在两个实例上，会不会做出两份副作用？
3. 这里的初始化，假设了"只会执行一次"吗？如果不是，重复执行会怎样？
4. 这个"正在处理"的标志，持有者死掉之后谁来清？
5. 这个定时任务，进程不在的那段时间里，谁来补？

五个问题里只要有一个答不上来，那段代码就在依赖一个没写下来的假设。

答不上来不等于写错了。很多场景下这个假设成立，代价也可以接受：一个只在单实例上跑的内部工具，进程内定时器就是合理选择；一个纯展示用的内存缓存，丢了重新拉一次也不贵。关键是这个假设要被知道，而不是被默认。知道之后，才能在部署形态变化时想起它。

## 收束：把假设写下来

两个平台没有谁更先进。安卓的假设来自资源约束：手机内存有限，系统有权随时回收进程，所以代码必须假设内存不可信、执行会中断、启动会重来。服务端的假设来自部署形态的历史：单机、长驻、手工发布，所以代码可以假设进程长活、内存可信、启动只发生一次。

问题出在两种形态开始混合的时候。移动端开始接服务端逻辑（离线队列、同步、后台任务编排），服务端开始跑在多实例和编排系统上，两边的默认假设都还在，但约束已经变了。这时候塌的不是语法，是那些从来没被当成假设的假设。

写下来是最便宜的一步。在类的注释里写一句"这份缓存可丢失，进程重启后为空是正常状态"，在定时任务旁边写一句"调度由外部系统负责，本方法必须幂等"，在单例上写一句"每个实例各有一份，不要假设全局唯一"。这些话不会让代码变快，但会让下一个改这段代码的人知道：他接手的不是一段逻辑，是一组关于进程能活多久的赌注。
