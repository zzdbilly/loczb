## 模型说「今天」的时候，它只是在复述上下文

「今天」是个很小的词，小到写进正文时不会有人停顿。我因为这个词返工过。

一次写发布说明，frontmatter 的日期我直接用了对话里出现的「今天」。稿子写完，编译通过，门禁全绿，推上去。第二天翻列表才发现它排在前一天的位置上，差了一天。还有一次更别扭：我写了一个比真实时间更晚的时刻，新文章于是排在列表首位，看上去像「今天已经发过一篇」。两次都不是谁算错了日期。是我把「日期」当成了一个可以从句子里读出来的东西。

后来规则改成从机器读时间，并且把时区写死：

```bash
TZ=Asia/Shanghai date '+%Y-%m-%d %H:%M:%S %A'
```

这条命令打印出来的才是日期。对话里那个「今天」，只是某次采样时上下文里恰好出现的两个字。

把这件小事放大，会得到一个不太舒服的结论：**模型的输出不是数据源**。凡是要写进外部世界、会被别人当成事实使用的值——日期、计数、版本、路径、耗时——都应当从权威源现取，而不是从上下文或记忆里生成。模型没有时钟，也没有查询能力。它给的「今天」是采样时刻的快照，它给的计数是从语言分布里浮现出来的数字。这不是幻觉，是职责错位：把一个生成器当成了数据库。

## 先给一个能当场执行的程序：三道问

下面的做法不依赖任何工具，也不需要额外配置。任何准备写进正文的值，落笔之前先过三道问。

```text
1. 它从哪来？
   上下文 / 记忆                       还是   命令输出 / 文档 / 数据库？

2. 什么时候取的？
   取的时间与写的时间隔了多久，这中间世界变了吗？

3. 能不能重取？
   有没有一条命令，能把同样的值再跑一遍？
```

三道都答不上来的值，要么删掉，要么明写它的时效。没有第四种处理方式。

### 第一问：它从哪来

「从哪来」问的不是谁说的，而是这个值第一次进入世界时附着在什么上面。

「今天是十一月二十号」——如果它来自我上一轮自己写的话，那它只是上下文。如果它来自 `date` 的输出，它就是时钟。同样一句话，两种来源，可靠性差着一个数量级。

工程上更要命的是中间层。一个数从数据库查出来，写进日志，被贴进对话，再被我抄进正文——到正文这一步，它已经是「上下文里的一个字符串」了。它可能仍然正确，但它的正确性不再由它自身保证，而是由那条链上每一环都没出错来保证。链越长，越该重取。

### 第二问：什么时候取的

值本身没有错，错的是它和现在之间的距离。

计数类的东西最典型。今天跑出来是五条，三周前跑出来是十五条，两个数在当时都是真的。写进正文时如果不带时间，读者只能默认它是当下的。这就是一条会过期的断言，只是它看起来不像。

第二问还管另一件事：取值的口径。同一个「篇数」，算不算草稿，算不算被撤下的，算不算另一个目录里的，结果可以差出十几。取的时候用的是哪个口径，写的时候就得是哪个口径，中间不能换。

### 第三问：能不能重取

这是三道问里最有操作性的一道，也是唯一能自动化的一道。

有命令能重跑的，就是可验证的。没有命令能重跑的，就是记忆。记忆不是罪，但记忆必须以记忆的身份出现——写成「我印象里」「上一次看到」，而不是写成事实。

一个值如果既重要、又重取不出来、又没有时效标注，那它不该出现在正文里。它可以在草稿里待着，等到能取的那天再进来。

| 三道问的结果 | 处理方式 |
|:---|:---|
| 有权威源，能重取，刚取过 | 直接写，必要时附命令 |
| 有权威源，能重取，但取的时间较久 | 重取一次再写；取不了就标时点 |
| 只有记忆，无法重取 | 删掉，或降级成不带数字的表述 |
| 说不清从哪来 | 删掉，不讨论 |

## 五类高危值：时间

### 权威源是时钟，不是句子

日期、时刻、时区，这三样东西有一个共同点：它们每秒都在变，而且变化与文本无关。任何从上下文继承来的时间都自带一个隐式的「截至采样时刻」。

我已经在这上面栽过两次：一次差了一天，一次写到了未来。两次的共同点不是粗心，是我把「今天」当成了一个名词，而它其实是一个指针。

### 写法：绝对时间加时区

时间类值的处理规则可以压成三句话：

- 取，用 `date`，并且显式带时区，不依赖机器默认值。
- 写，写绝对时间，不写「昨天」「上周」「最近」。
- 标，如果非要写相对时间，就在同一句里给出锚点，例如「截至某月某日」。

相对时间在发布场景里是个陷阱。稿子写于周四，发布在周五，「昨天」就错了；如果还被定时任务延后一天，错得更远。绝对时间不会。

时区同样。机器跑在哪个时区、读者在哪个时区、站点按哪个时区排序，是三件不同的事。发布链如果按日期字符串排序，时区差八小时就能让一篇文章插到另一篇前面。这个坑不需要谁犯错，缺一个时区标注就够了。

## 五类高危值：计数

### 计数每天都在漂

文章篇数、告警条数、内链数、文件数——这类值的特点是：**它们在一个健康的项目里一定会变**。不变才说明没人干活。

有一次我在正文里写「0 错误、15 条告警」。发布当天把全库重跑了一遍，真实输出是「0 错误、5 条告警」。命令没变，仓库也没坏，我引的是几周前的结果。这中间文件加了、规则调了、历史告警被清掉了，数字早就不是那个数字。

这类错误的隐蔽之处在于：它看起来有出处。确实跑过，确实有输出，只是那次跑的不是今天。

### 取法：重跑那条命令，而不是引用上次输出

计数类值只有一个可靠来源：现在跑一遍，把输出贴进正文。

```bash
# 篇数：数源文件，不数产物
ls blog/posts-src/*.md | wc -l

# 某一类问题的条数：重跑同一条命令，并把口径写进正文
grep -rn "TODO" src/ | wc -l

# 需要排除某些目录时，把排除条件一起写出来
grep -rn --exclude-dir=node_modules --exclude-dir=.git "TODO" . | wc -l
```

三条命令里，第三条比前两条更值得学：**口径要跟数字一起写**。同一个仓库，「TODO 有多少条」可以有三个答案，取决于排不排依赖目录、算不算测试、算不算文档。只给数字不给口径，等于给了一个无法复核的断言。

还有一条经验：能用「若干」「十几」说清的量级，不要强行精确到个位。读者不会因为「十几条告警」而少获得什么，但会因为你写「十五条」而实际只有五条，对整篇文章打折扣。

## 五类高危值：版本与行为

### 「我记得它改成了报错」不算证据

版本类断言有个特殊风险：它描述的不是一个数，而是一个行为。行为错了，读者照着做会直接失败。

我遇到过一次：某个语言的新版本把一类检查从警告提升为编译错误。这句话在正文里只占半行，但它决定了读者升级之后构建会不会红。我当时的第一反应是「我记得是这样」，第二反应才是去翻变更说明。两个反应之间隔着一次可能的返工。

版本行为是最不该靠印象的一类值，因为它的可信度与记忆的新鲜度强相关，而记忆的新鲜度没有任何外部标志。你无法从「我很确定」里读出「我上次查是两年前」。

### 取法：查变更说明，再在本机验一次

处理版本类断言，两步都要走：

```bash
# 第一步：查发布说明与变更日志，确认这个行为发生在哪个版本
grep -n -i "breaking\|deprecat\|warning\|error" CHANGELOG.md | head -40

# 第二步：在本机用目标版本复现一次，确认现象与文档一致
node --version
```

只做第一步，可能读到一条被后续版本又改回去的记录；只做第二步，可能只验证了一个版本，却写成了「所有版本都这样」。两步都做，才能把断言收缩到「某版本起，某行为如此」这种可以复核的形态。

写的时候也要收缩。不写「新版本会报错」，写「从某个版本起，这类检查从警告变成错误」。前者是一句情绪，后者是一条可查的事实。

## 五类高危值：路径与标识符

### 路径会被移动，标识符会被重命名

路径与标识符的问题不在真假，在时效。一个路径在写下的那一刻是真的，在下一次重构之后就不是了。而正文里的路径通常以「你可以在这里找到」的口气出现，读者会当成导航。

标识符同理。函数名、配置键、环境变量、接口字段，任何一处重命名都会让示例代码失效，而失效的方式往往不报错——配置键写错了，程序读不到，走了默认值，行为变了但没声音。

### 取法：写之前确认存在，写的时候给出处

路径类值的检查成本极低，低到没有理由不做：

```bash
# 确认路径存在，并且是期望的类型
test -f path/to/config.yaml && echo "file ok"
test -d path/to/dir && echo "dir ok"

# 确认某个标识符在当前代码里还有定义
grep -rn "SOME_CONFIG_KEY" src/ | head
```

这两条命令的价值不在输出，而在它们会失败。一个不存在的路径，`test -f` 立刻返回非零；一个被重命名的键，`grep` 立刻返回空。失败得越早，返工越少。

如果某个路径或标识符属于外部系统、本机无法确认，那就别把它写成确定的事实。写成「以实际部署为准」，比写一个曾经正确过的值更负责。

## 五类高危值：量测

### 耗时与体积依赖机器

耗时、内存占用、产物体积、构建时间——这类值有个共同前提：它们是在某台机器、某个负载、某个版本下测出来的。换一台机器，数字可以差一倍；机器空着和机器忙时，数字也可以差一倍。

所以量测类值的正文写法，重点不是精确，而是**可复现**。只写「构建耗时 42 秒」，读者无法判断这是冷启动还是热缓存，是笔记本还是共享构建机。写「在同一台机器、清空缓存后，构建耗时约四十秒」，读者至少知道该在什么条件下对照。

### 取法：同机、同口径、写清环境

量测的取法没有捷径，只有三条约束：

- 同一台机器。跨机器的数字不可比，放在一起会误导。
- 同一口径。冷启动与热缓存、单线程与多线程、含不含依赖安装，都要说明。
- 写清环境。至少给出运行环境与版本，让读者知道偏差可能来自哪里。

三条都做到，数字才有意义。做不到，就把数字降级成量级。量级不精确，但它不会撒谎。

## 为什么模型特别容易在这里出错

### 没有时钟

模型不持有时间。它对「现在」的全部信息，来自上下文里出现过的字符串。上下文里写了「今天」，它就按那个今天说话；上下文里没写，它也可能顺着语感补一个日期出来。补出来的日期通常格式正确、语气自然，唯一的缺点是它不对应任何一个真实时刻。

这不是能力问题，是接口问题。没有时钟的进程，问它几点，只能得到一段文本。

### 没有查询能力

模型不连接你的仓库、数据库、监控。它没有被问「现在有多少条告警」时去执行一条命令的通道。它能做的只有两件事：复述上下文里已有的值，或者根据语言分布生成一个看起来合理的值。

第二件事尤其危险，因为它和第一件事在文本上无法区分。「十五条告警」和「五条告警」都是合法的中文，都可能是模型写的，也都不带出处。

### 上下文是采样时刻的快照

即使上下文里的值全是真的，它们也是某个时刻的真。对话越长，这个时刻离现在越远。上下文不会自己过期，它只会越来越旧——没有任何机制会在值失效时把它标红。

这就是为什么「从上下文继承一个数」和「从数据库读一个数」看起来一样，实际完全不同。后者有事务和时效，前者只有一段文本。

### 语言分布里的数字看起来很像真的

帮忙写稿的模型给过一些个位级的数字：「四十七处」「八十七处」「四十个技术债」。这些数字读起来极有说服力，因为它们精确、具体、有零有整，符合人对「实测」的想象。

但我问出处的时候，答不上来。它们不是从任何一次统计里来的，是从「这类文章里通常会有这种数字」的分布里来的。后来这些位置全部改成了「几十处」，或者干脆去掉数字，只留判断。

精确不等于真实。一个编出来的四十七，比一句诚实的「几十」更糟，因为它多了一层假装。

## 为什么门禁拦不住

发布链上的机械门禁能保证三件事：产物与源一致、没有死链、没有凭据。这三件事都很重要，而且都能自动化。

它保证不了第四件事：源里的这句话是不是真的。

这不是门禁的失职。门禁校验的是形式关系——源文件编译出的 HTML 与提交的 HTML 是否逐字节相同，链接指向的目标是否存在，文本里有没有不该出现的密钥。这些都可以用程序判定。「十五条告警」这句话对不对，程序判不了，除非程序知道该去问谁。

于是真实的兜底方式变得很朴素：发出去，被读者或者被自己发现，然后提交一次修正。我的发布记录里就有若干次这样的提交，标题是「修正某处表述」。它们不是流程的失败，而是流程唯一能提供的那层保护——在机械检查之后，用人再看一遍。

承认这一点比假装门禁万能更有用。知道门禁拦不住什么，才知道自己该在哪一步停一下。

| 检查项 | 能否自动化 | 拦得住什么 |
|:---|:---:|:---|
| 产物与源一致 | 能 | 手改产物、漏编译 |
| 死链 | 能 | 指向不存在页面的链接 |
| 凭据与隐私串 | 能 | 误提交的密钥、真实路径 |
| 日期是否正确 | 部分 | 格式错、未来时间；语义对不对仍要人看 |
| 计数是否当下 | 不能 | 只能靠发布前重跑 |
| 版本行为是否属实 | 不能 | 只能靠查文档与实测 |

## 可执行的纪律：能取则取，不能取则标，只能靠记忆则删

三道问和五类值最后要落到三句话上。这三句话不是原则，是动作。

### 能取则取

凡是有一条命令能跑出来的值，就去跑。日期用 `date`，计数用 `grep` 加 `wc`，路径用 `test -e`，版本用 `--version` 加变更说明，量测用同一台机器重测一次。

取的动作要留在稿子附近。命令和输出一起记下来，下次有人问「这个数哪来的」，能直接贴。没有命令的值，默认按记忆处理。

### 不能取则标

有些值取不到：外部系统的当前状态、别人的机器、已经过去的一次运行。这类值不是不能写，但必须带着时点和口径写。

「截至某月某日」「按某个口径」「在某个版本上」——这些限定词看起来啰嗦，它们的作用是把一句话从「事实」降级成「某时某地的事实」。降级不是示弱，是准确。

### 只能靠记忆则删

最后一类值最麻烦：它重要、取不到、也没有明确的时点。这种值在正文里没有合法位置。

删掉它，论点通常还在。真正支撑论点的往往不是那个数字，而是数字背后的判断。删掉「四十七处」，还剩「这类问题在代码里分布得很散」——后者才是想让读者记住的东西。

发布前我会按这三句话过一遍稿子，重点看三类位置：所有日期、所有数字、所有「最近」「目前」「现在」。这三类位置占了事实性错误的大多数。

## 收束：模型可以说「今天」，但只有时钟知道今天是几号

回到开头那个词。

模型说「今天」的时候，它没有说谎，也没有出错。它只是把上下文里的一次采样，用自然的语气复述了一遍。问题出在我这边：我把一句复述当成了查询结果，又把它写进了会被别人当成事实的地方。

职责错位的修法不是让模型更小心，而是把取值的动作放回它该在的位置。日期问时钟，计数问仓库，版本问文档，路径问文件系统，耗时问同一台机器。模型负责把这些值组织成能读的句子，不负责发明它们。

三道问可以背下来：它从哪来，什么时候取的，能不能重取。五类值可以贴在显示器边上：时间、计数、版本、路径、量测。

模型可以说「今天」。但只有时钟知道今天是几号。
