## 锁文件不跟着进程走：进程崩溃后留下的那把锁，没人会来解开

一个定时任务、一个部署脚本、一个备份进程，启动时都要先抢一把锁，确保同一时刻只有一个实例在跑。实现方式通常只有几行：检查某个文件在不在，不在就创建它，跑完再删掉。正常路径上它工作得很好，好到很多人写完就不再想这件事。

问题出在「跑完再删掉」这个前提上。进程不一定跑完。它可能被 OOM killer 挑中，可能被 `kill -9` 打断，可能所在的机器直接掉电，也可能在容器滚动更新时被替换掉——这些路径上都没有代码去执行那行删除。于是锁留在那里，下一次启动被自己上一次的残留挡在门外。

后面的分析只围绕一个属性：**这把锁记在谁的名下**。原子性、阻塞策略、超时、可重入这些细节都重要，但异常退出后锁还在不在，基本由所有权决定。我倾向于在评审任何一把锁之前先问这一句，因为它比「用 `flock` 还是用锁文件」这种问法更能暴露问题。

> 约定：文中把能直接指到手册页、内核文档或协议规范的结论标为「文档事实」；由这些语义推出、没有逐条实测的结论标为「推演」。本文没有在 NFS 与容器编排的组合上做过实测，相关段落一律写成条件句。

## 一、先把问题问对：这把锁挂在谁身上

讨论文件锁时，容易一上来就比「谁更快」「谁更可靠」。这两个问题都排得太早。先要问的是：锁这个状态，存在哪个内核对象里，由谁负责销毁。

答案是三种，对应三类实现：

- 锁记在**文件系统的一个名字**上。名字存在即为上锁，删除即为解锁。`O_EXCL` 创建、`mkdir` 建目录都是这一类。
- 锁记在**打开的文件描述**（open file description）上。`flock` 属于这一类。
- 锁记在**进程**上。POSIX 记录锁（`fcntl` 的 `F_SETLK` / `F_SETLKW`）属于这一类。

三者在正常退出时的行为几乎一样：锁没了，下一个实例能进。差别全部集中在「没人执行解锁代码」的那条路径上。

### 三种持有者，三种死亡方式

文件系统那一档，严格说没有持有者。持锁的进程和这把锁之间没有内核层面的引用关系，唯一的联系是「它知道这个路径代表锁」。进程死了，这个知识消失，路径还在。这就是 stale lock 的来源。

fd 那一档，持有者是内核里的一个打开文件描述结构。进程终止时，内核关闭它所有的 fd；最后一个指向该描述的 fd 关闭时，锁释放。整个过程不需要进程配合。

进程那一档，持有者是进程本身。进程退出，内核清理该进程持有的全部记录锁。同样不需要用户态代码参与。

### 一个判据：持有者死了，锁会不会跟着消失

判断一把锁能不能自愈，可以只问一句：**这把锁的引用，存在哪个会随进程销毁而销毁的结构里？**

存在文件系统的目录项里，答案是不会——目录项的生命周期和进程无关。存在打开文件描述里，答案是会。存在进程的锁表里，答案也是会。

这个判据不需要读源码，也不需要知道具体系统调用怎么实现，只要判断「锁的状态是不是一个活着的内核对象的一部分」。空文件不是活物，目录也不是。

## 二、第一档：锁属于文件系统

### 常见写法：O_EXCL 与 mkdir

最省事的一种互斥，是用「路径能不能被创建」当原子操作。`mkdir` 在本地文件系统上是原子的：两个进程同时建同一个目录，只有一个成功（文档事实：`mkdir(2)` 的创建是原子操作，失败返回 `EEXIST`）。`open` 加 `O_CREAT | O_EXCL` 同理，创建和检查在一步里完成，不存在「先 stat 再 create」那个窗口。

```bash
# 存在即上锁：拿不到就退出，不等待
if mkdir /var/lib/app/lock.d 2>/dev/null; then
    trap 'rmdir /var/lib/app/lock.d' EXIT INT TERM
    ./sync.sh
else
    echo "another instance holds the lock" >&2
    exit 0
fi
```

这段脚本在正常路径上没有问题：拿到目录，注册 `trap`，跑完或者收到 `INT`/`TERM` 时删掉目录。它甚至处理了 Ctrl-C。

### 崩溃时会发生什么

`trap` 是用户态代码，只有进程还能执行指令时才会跑。`SIGKILL` 不能被捕获，`trap` 不会执行；段错误、OOM killer、宿主机掉电，也都轮不到它执行。

于是 `/var/lib/app/lock.d` 留在磁盘上。下一次启动，`mkdir` 返回 `EEXIST`，脚本打印一行「另一个实例在跑」，退出码 0，什么也没做。从外部看，定时任务按时触发了、日志里也没有报错，只是备份已经连续几天没有真正跑过。这类故障最难被发现，因为它的表现是「安静」。

### 谁能清理，代价是什么

清理者只有两种：人，或者另一段专门写来清理的逻辑。

人工清理的问题是它依赖有人注意到。一个退出码 0、日志一行提示的任务，很难让人注意到。清理逻辑的问题是它必须判断「这个锁是不是真的陈旧」，而这个判断本身要面对竞态：清理进程读到锁、决定删掉、在删之前真正的持有者刚好启动并重新创建了锁——清理进程删掉的是新锁。

还有一个更隐蔽的代价：删除操作会暂时制造出「无锁」状态。两个等待者同时看到锁被删，同时尝试创建，谁先谁后取决于调度。文件的删除和创建不是一个原子事务（推演，依据 `unlink` 与 `mkdir` 各自的原子性不能组合成跨操作原子性）。

## 三、第二档：锁属于打开的文件描述

### flock 的持有者不是进程，是 open file description

`flock(2)` 的锁关联到打开的文件描述，不是关联到进程，也不是关联到路径（文档事实：`flock(2)` 手册明确锁与 open file description 关联）。这个区别有几个直接后果：

- 同一个进程里两次 `open` 同一个路径，得到两个描述，第二次 `flock` 会被第一次挡住。
- `fork` 之后子进程继承同一个 fd，父子共用同一把锁；任何一方显式解锁，另一方也就没有了（文档事实：锁随 fd 继承，指向同一个描述）。
- `dup` 出来的 fd 指向同一个描述，关掉其中一个不会释放锁，要等最后一个关闭。

这解释了为什么 `flock` 比「文件存在」更接近自愈：它的寿命被绑定在一个内核对象上，而不是一个磁盘上的名字。

### 拿一个 fd，一直持有到结束

下面这段是 Python 里的常见形态。要点不在语法，在于 fd 必须活到临界区结束，中间不能被别的代码关掉。

```python
import fcntl
import os
import time

lock_fd = os.open("/var/lib/app/sync.lock", os.O_CREAT | os.O_RDWR, 0o644)

deadline = time.monotonic() + 30
delay = 0.1
while True:
    try:
        fcntl.flock(lock_fd, fcntl.LOCK_EX | fcntl.LOCK_NB)
        break
    except BlockingIOError:
        if time.monotonic() > deadline:
            raise SystemExit("lock timeout")
        time.sleep(delay)
        delay = min(delay * 2, 2.0)

try:
    run_sync()          # 临界区
finally:
    os.close(lock_fd)   # 关掉 fd，锁由内核释放
```

`LOCK_NB` 让加锁失败立刻返回而不是睡眠，退避和总超时由调用方控制。这段代码的失败模式是明确的：要么拿到锁，要么在 30 秒后带着错误退出，不会无限排队。

### 进程退出、kill -9 与断电

`flock` 的锁在最后一个引用该描述的 fd 关闭时释放（文档事实）。进程终止时，内核关闭该进程的全部 fd，因此锁释放。`kill -9` 只是让进程没有机会执行用户态代码，内核的清理路径照常走。

断电是另一回事：锁表在内存里，重启后不存在。磁盘上那个 `/var/lib/app/sync.lock` 还在，但 `flock` 不把「文件存在」当作锁的状态，它只看有没有人持有指向该文件的描述（文档事实：`flock` 不依据文件内容判断锁的归属）。所以断电留下的空文件是无害的，下一次 `open` 之后照样能加锁——前提是没有人把它删掉重建。

这是它和第一档最关键的差别：**残留物相同，语义不同。** 同样是磁盘上多了一个文件，对 `flock` 来说它只是锁的载体，对 `O_EXCL` 来说它就是锁本身。

### 边界：fd 泄漏、fork 继承、以及「锁文件不能删」

`flock` 不是没有坑，只是坑的位置不同。

其一，如果持有 fd 的进程 fork 出子进程然后自己退出，子进程仍然持有那个描述，锁不会释放。daemon 化的脚本容易出现这种形态：父进程拿锁、fork、父进程退出，子进程继承了 fd 却没人记得它带着锁。排查时看 `ls -l /proc/*/fd` 里谁还指着那个文件，比读代码快。

其二，锁文件被删掉再重建，互斥会失效。锁绑在打开的文件描述上，而描述指向某个 inode；`rm` 之后新建的文件是另一个 inode，两组进程各持一把锁，谁都挡不住谁（推演，依据 `flock` 与 inode/描述的关联）。所以清理脚本里顺手 `rm` 锁文件是一个危险动作，锁文件应当允许长期存在，内容为空也无所谓。

其三，`flock` 不是 POSIX 标准的一部分，是 BSD 传统（文档事实）。Linux 有，多数 Unix 有，但语义细节和可移植性不能假定与 `fcntl` 一致。

## 四、第三档：锁属于进程

### fcntl 记录锁跟着进程走

POSIX 记录锁由 `fcntl` 的 `F_SETLK`（非阻塞）或 `F_SETLKW`（阻塞）设置，锁记录在内核的 inode 上，但所有者是进程（文档事实）。进程退出时，它持有的全部记录锁释放。锁不随 `fork` 继承（文档事实），这一点和 `flock` 正好相反。

记录锁的名字里带「记录」，是因为它可以只锁文件的某个字节区间。这一点在数据库和日志文件里有用，在「整个文件当一把锁」的场景里，锁住 `0` 到文件末尾就够。Python 的 `fcntl.lockf` 走的就是这套接口。

### 那个比直觉更宽的释放规则

这里有一条容易记错的规则：**进程关闭该文件的任意一个 fd，就会释放这个进程在该文件上的全部记录锁**（文档事实：POSIX 与 Linux 的 `fcntl(2)` 手册都这么写）。不是关掉加锁的那一个 fd，是任意一个。

这条规则的破坏力在于它把「打开文件读一下」变成了「解锁」。

```python
import fcntl
import os

lock_fd = os.open("/var/lib/app/sync.lock", os.O_CREAT | os.O_RDWR, 0o644)
fcntl.lockf(lock_fd, fcntl.LOCK_EX | fcntl.LOCK_NB)

with open("/var/lib/app/sync.lock") as f:   # 又开了一个 fd
    previous = f.read()

# with 结束，f 被关闭 —— 上面那把锁在这里就没了（文档事实）
run_sync()
os.close(lock_fd)
```

这段代码在单实例下跑起来一切正常，日志也不会有异常。问题只在有并发时出现：锁已经释放，第二个实例可以进来，两个进程同时改同一批文件。而报错的地方通常在数据层，离真正的原因隔着几层调用栈。

规避方式不是「记得别乱开文件」，而是把规则变成结构：加锁之后不要在同一个进程里再打开这个路径，配置读完之后再加锁，或者干脆换一种锁——Linux 3.15 起提供 `F_OFD_SETLK`，锁的所有者变成打开的文件描述，关掉别的 fd 不再影响它（文档事实：Linux 内核 3.15 引入 OFD 锁；用户态是否方便调用取决于 libc 与语言绑定）。它同时保留了字节区间的粒度，是「想要记录锁语义又不想被进程级释放规则坑」时的一个选项。

### 记录锁真正的优势与代价

优势是它对「锁文件被删」不敏感：锁记录在 inode 上，只要还有进程持有，另一个进程即使重新创建了同名文件也不会共享同一把锁——这既是优点也是缺点，取决于你是否把「路径」当成身份。

代价是它的释放语义和文件描述符的生命周期耦合得太松。任何一段打开同一文件的代码都能影响锁的状态，而这种影响在代码里不可见。

## 五、四种结局：三种锁放进同一张表

把三种锁放进同一组异常路径，差别会变得很清楚。下表是推演，依据是前面标为文档事实的释放规则；具体到某个系统，还要看内核版本与挂载参数。

| 结局 | 文件系统锁（`O_EXCL` / `mkdir`） | `flock`（fd 级） | `fcntl` 记录锁（进程级） |
|:-----|:--------------------------------|:-----------------|:-------------------------|
| 正常退出 | `trap` 或收尾代码执行则清除；漏写就残留 | 最后一个 fd 关闭即释放 | 进程退出即释放 |
| `kill -9` | 必然残留，没有代码执行清理 | 内核关闭 fd，锁释放 | 内核清理进程锁表，锁释放 |
| 断电 / 主机重启 | 残留在持久化目录上，下次启动被挡住 | 内存锁表消失；磁盘上的空文件无害 | 内存锁表消失；文件残留无影响 |
| 容器重启（卷保留） | 锁文件或目录留在卷上，新容器被旧锁挡住 | 容器内进程全部消失，锁释放；卷上的文件不影响 | 同左 |

### 怎么读这张表

先看行：四行里只有第一行是「所有人都能对付」的。三种锁在正常退出时表现一致，这就是它们在代码评审里看起来差不多的原因。

再看列：三列的差别不在锁的强度，而在锁的寿命由谁决定。第一列的寿命等于文件寿命，可能是无限的；第二列等于 fd 寿命；第三列等于进程寿命。异常路径考验的不是「锁得牢不牢」，而是「谁来宣布它结束」。

最后看容器那一行：它同时暴露两个维度。锁文件在卷上，寿命跨容器；PID 在命名空间里，寿命只在本容器。两者拼在一起，就会出现「锁还在，但锁里写的那个 PID 在读取它的命名空间里指向另一个进程」这种状态——比单纯的陈旧锁更难判断，因为所有基于 PID 的检查都成功。

## 六、为什么人还是会选最差的那一档

如果第一档明知会留下陈旧锁，为什么它仍然是最常见的写法？把原因摊开看，会发现每一条都成立，只是它们成立的范围仅限于正常路径。

### 它需要的前置条件最少

`mkdir` 一条命令，任何语言的标准库都能调；`O_EXCL` 在 C、Python、Go、shell 里都是一行。不需要理解 fd 的生命周期，不需要知道 `flock` 和 `fcntl` 的区别，也不需要关心进程结构——脚本里加一行判断就行。

`flock` 需要「拿一个 fd 并一直持有」，这句话在 shell 里意味着要控制文件描述符的分配（`exec 9>...`），在 Python 里意味着不能让中间层关掉它，在有的语言里意味着要绕过运行时对文件对象的封装。这些都要求写代码的人对进程和 fd 有明确的心智模型。

### 它跨语言、跨工具、跨人

互斥的双方经常不是同一段代码：一个 shell 脚本和一个 Java 服务，一个 cron 任务和一个 CI step，一个 Python 采集器和一个运维手动执行的命令。让它们共享同一把 `flock` 需要每个参与者都正确使用同一套 API；让它们共享一个目录名，只要大家都同意这个路径。

跨平台也是同样的道理。`flock` 在 Windows 上没有直接对应物，POSIX 记录锁在不同系统上的边界行为不完全一致，而「文件在不在」在所有平台上都成立。选择第一档，很多时候不是因为它更好，而是因为它是唯一一个所有参与者都能实现的协议（推演）。

### 代价被推迟到异常路径

正常路径上它的成本确实低：一次 `mkdir`，一次 `rmdir`，没有额外的 fd，没有阻塞语义要设计。这笔成本不会在写代码的时候付出，而是在「进程被 OOM killer 杀掉的那天」付出。付账的人往往不是写它的人，甚至不在同一个时区。

这就是它的经济学：收益即时且可见，成本延迟且分散。任何按单次任务评估的决策，都会得出「用它就行」的结论。

## 七、陈旧锁怎么判定：PID 不够，时间也不一定够

如果已经用了文件存在性做锁，下一个问题就是「怎么知道这把锁是死的」。常见做法是往锁文件里写 PID，下次启动读出来，看那个进程还在不在。这个做法比「什么都不判」好，但我不会把它当成足够的判据——它有三个漏洞。

### 只看 PID 存在与否

第一个漏洞是 PID 复用。进程退出后，编号会被系统回收再分配（文档事实：PID 在 `pid_max` 范围内循环分配）。原来持锁的进程死了，编号被一个完全无关的进程拿到，`kill -0` 返回成功，判定结果是「锁还被持有」——于是本该清理的陈旧锁被保留，任务继续不跑。

第二个漏洞是命名空间。容器里的 PID 编号只在该 PID 命名空间内有效，锁文件如果放在共享卷上，写入者记录的可能是容器内的 `1`，读取者在另一个容器里 `kill -0 1` 命中的是它自己的 init 进程。

第三个漏洞是锁文件里的内容可能非常旧。一个被复制、被快照、被误写入的锁文件，里面的 PID 与当前系统毫无关系。

### PID + 启动时间

更可靠的判据是把「进程身份」定义成（boot id，PID，启动时间）三元组。PID 会复用，但同一台机器同一次启动内，「PID + 启动时间」不会撞。

```python
import os


def boot_id() -> str:
    with open("/proc/sys/kernel/random/boot_id") as f:
        return f.read().strip()


def starttime(pid: int) -> str | None:
    """返回进程的启动时间（内核 tick 数），进程不存在时返回 None。"""
    try:
        with open(f"/proc/{pid}/stat") as f:
            raw = f.read()
    except (FileNotFoundError, ProcessLookupError):
        return None
    # comm 字段可能包含空格和括号，从最后一个 ')' 之后开始切分
    fields = raw[raw.rfind(")") + 2:].split()
    return fields[19]   # 总第 22 个字段 starttime，切分后下标 19
```

启动时间的单位是内核 tick，不是秒，跨机器不可比，但在同一台机器同一次启动内足够做身份判定（文档事实：`/proc/<pid>/stat` 第 22 个字段为 `starttime`）。判定逻辑是：boot id 相同、PID 存活、且 starttime 与锁文件里记录的一致，才算「仍被持有」；任何一项不符，按陈旧处理（推演）。

### 时间戳与租约

另一种思路是不判身份，判时间：锁文件里写过期时间，超过就认为陈旧。这就是租约。

租约把问题从「进程还在不在」换成了「它有没有按时续期」，好处是不依赖 PID、不依赖命名空间、跨机器也能用。代价是两个前提：临界区必须短于租期，且时钟不能漂得太多。

第一个前提经常不成立。备份、全量重建索引、大批量同步，这些任务的耗时取决于数据量，写代码的人往往按「正常情况下几分钟」设定租期，遇到数据翻倍就超时。锁一过期，第二个实例进来，两个进程同时写同一批文件。

第二个前提也经常不成立。机器挂起、虚拟机迁移、NTP 校正，都会让「现在几点」跳变。用单调时钟计算经过时间可以避开系统时间调整，但跨机器比较仍然依赖双方时钟大致同步（推演）。

所以租约的正确用法是「可续期」：持有者定期把过期时间往后推，续期失败就主动停止工作。这样锁的有效期由「最后一次成功续期」决定，而不是由最初设定的时长决定。

### 主机名 + boot id：跨机器共享目录

当锁文件放在共享存储上、多个主机都可能抢时，PID 单独使用没有意义——每台机器都有自己的 PID 空间。

此时锁文件至少要写四元组：主机名、boot id、PID、starttime。主机名用于路由到正确的机器去查进程，boot id 用于判断那台机器有没有重启过（重启后 `starttime` 的参照系变了），PID 与 starttime 用于在机器内部确认身份。

容器环境里主机名通常就是容器 ID，容器重建后主机名改变，这反而提供了一个天然的「实例身份」——名字变了，旧锁一定是陈旧的（推演）。但如果容器使用固定的 hostname，这个信号就消失了，需要改用编排系统提供的实例 ID。

### 谁来判断，以及判断本身的竞态

即使判据都对，清理动作仍然要小心。两个进程同时发现锁陈旧、同时删除、同时创建，其中一个会覆盖另一个。稳妥的做法是把「判定 + 删除」做成可检测的原子步骤：先把锁路径原子地改名到一个唯一名字（`rename` 在同一文件系统内是原子的），再检查改名后的内容是不是自己刚才看到的那份；如果是，才真正删除并重建（推演，依据 `rename(2)` 的原子性）。

这段逻辑不长，但它是并发代码，需要测试。很多「陈旧锁清理」的实现只测了单进程路径，上线后在两台机器同时启动时才暴露。

## 八、可执行的规则

把上面的分析收成几条能落地的规则。它们不解决所有问题，但能把「锁会不会自己消失」这件事变成设计时就要回答的问题。这几条是我给自己定下的默认值，不是行业规范。

### 规则一：让内核持有锁，而不是让文件持有锁

只要锁的持有者是一个会随进程销毁的内核对象，异常退出就有默认答案。

```bash
#!/bin/sh
# 拿不到锁就退出；退出码 0 表示「已有实例在跑」，不是错误
exec 9>/var/lib/app/sync.lock
if ! flock -n 9; then
    echo "another instance is running" >&2
    exit 0
fi

./sync.sh
# 脚本退出时 fd 9 关闭，锁由内核回收，不需要任何清理代码
```

`flock(1)` 用 shell 的 fd 重定向持有锁，锁的生命周期与脚本进程绑定（文档事实）。这段代码里没有 `trap`，也没有 `rm`，异常路径不需要额外处理。

### 规则二：等待要有上限，退避要有节奏

非阻塞加锁 + 指数退避 + 总超时。不要无限阻塞：一个卡住的实例会让后来者全部排队，等它被清理时，排队的进程一起涌进来，形成一次尖峰。

超时时间要按任务的正常耗时设定，并且在日志里明确写出「等锁超时」和「任务失败」是两件事。前者通常意味着需要人工看一眼锁的持有者，后者意味着任务本身有问题。混在一起会让排查从第一步就走错方向。

### 规则三：如果必须用文件存在性，就必须带陈旧判定

两条路选一条：

- 写（主机名，boot id，PID，starttime），启动时严格校验，任何一项不符就按陈旧处理。
- 写过期时间，并且实现续期；临界区超过租期时主动停止，而不是继续跑。

两条都不做，等于把清理工作外包给「某天有人发现备份没跑」。这个外包合同没有 SLA。

### 规则四：NFS 上先确认行为，再决定能不能依赖

这是全文最需要写成条件句的一段。NFS 上的锁行为与本地文件系统不同，而且不同版本、不同挂载参数的差别很大：

- NFSv4 把锁纳入协议本身，服务端参与锁的管理（文档事实）。
- NFSv3 使用单独的 NLM（Network Lock Manager）协议，依赖客户端与服务端的 `lockd` / `statd` 正常工作和互通（文档事实）。
- Linux 客户端在部分配置下会把 `flock` 模拟成 `fcntl` 锁，也可能在挂载参数要求下退化成纯本地锁（文档事实：Linux NFS 客户端有 `local_lock` 挂载选项，取值影响 `flock` 与 POSIX 锁的处理方式）。

所以「`flock` 在 NFS 上能不能用」没有统一答案，取决于内核版本、NFS 版本、挂载参数、服务端实现，以及是否所有客户端都同意同一套语义。上线前用 `mount` 看清版本和选项，在目标环境里做一次双客户端互斥测试，再决定是否依赖它（推演：跨环境行为不可假定一致）。

`O_EXCL` 在 NFS 上同样要看版本：NFSv3 及以后支持原子性的独占创建，更老的实现存在已知缺陷（文档事实：`open(2)` 手册对 NFS 上的 `O_EXCL` 有专门说明）。这类细节不能靠记忆，查当前内核与协议版本的文档。

### 规则五：锁文件不要删，锁目录不要手动清

`flock` 的锁绑在打开的文件描述与 inode 上，删除再创建会得到一把全新的、与旧锁无关的锁（推演）。清理脚本里顺手 `rm -f /var/lib/app/sync.lock` 看起来无害，实际会让互斥失效：老进程还持着旧 inode 上的锁，新进程在新 inode 上又拿到一把。

锁文件允许永久存在，大小为 0 也无所谓。需要清理的从来不是文件，而是「谁持有它」这个状态。

## 九、收束：能自愈的锁，必须有人替它收尸

回到最初那个问题：这把锁挂在谁身上。

挂在文件系统上，它的寿命等于文件寿命，进程的死活与它无关。挂在打开的文件描述上，寿命等于 fd。挂在进程上，寿命等于进程。三种锁在正常退出时几乎没有区别，区别全部出现在没人执行清理代码的那一刻。

内核是唯一一个「一定会执行清理」的角色。进程终止时它关闭 fd、释放记录锁、回收地址空间，不需要崩溃的进程配合，也不需要有人记得写 `trap`。把锁交给内核，异常路径就有了默认答案；把锁交给一个空文件，异常路径的答案就变成了「等人来删」。

如果非要用文件存在性做锁，那就得自己补上那个「人」：启动时判定陈旧、清理时保证原子、给等待加上限，并且接受这套逻辑本身也需要维护和测试。它不是不能用，而是不能白用——每一条异常路径都要自己写清楚。

能自愈的锁，必须有人替它收尸。要么是内核，要么是你写的那段代码。选第一个，工作量在写的时候；选第二个，工作量在出事的时候。
