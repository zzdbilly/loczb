## 同一个词，两种语义

「第 2 页」这个词，在一个静态站点上和在数据库里指的不是同一件事。

这个站点是构建时生成的。文章列表每页 10 篇，除首页之外，第 2 页往后每一页都是独立的 HTML 文件，内容与构建那一次提交绑定。构建完成之后，第 2 页里是哪十篇就定死了：它是一份快照。之后新发一篇文章，不会让第 2 页多出一条，也不会让第 3 页的第一条挤进第 2 页的末尾。要变，得重新构建、重新生成那一批文件。

数据库里的 `OFFSET` 不是这样。`LIMIT 10 OFFSET 10` 每次执行都重新走一遍：按排序键排一遍，扔掉前 10 行，取第 11 到 20 行。它在查询发生的那一刻才算出「第 2 页」是什么，上一次查询的结果对下一次没有任何约束。

于是同一个词落在两套语义上：一个是**坐标固定的快照**，一个是**坐标漂移的即时计算**。静态站恰好用了前者；而凡是走 `OFFSET` 的列表接口，用的都是后者。

这篇文章讲的是后者为什么会漂，以及它的替代品要付什么账。

## 位置坐标：OFFSET 定义的是距离

`OFFSET n` 的语义是「跳过排序结果里的前 n 行」。注意它跳过的是**行数**，不是任何有身份的东西。第 n+1 行是谁，取决于此刻排完序之后谁站在那个位置上。

也就是说，`OFFSET` 锚在**列表开头**，而没有锚在**你上次读到的那一条**。列表开头是个会移动的东西。

```sql
-- 示例：两次查询之间发生了一次插入
-- 第一次：用户看到「第 1 页」
SELECT id, title, created_at
FROM posts
WHERE published = true
ORDER BY created_at DESC, id DESC
LIMIT 10 OFFSET 0;

-- 期间写入了一条 created_at 更新的记录（id = 9001）
INSERT INTO posts (id, title, created_at)
VALUES (9001, '新文章', now());

-- 第二次：用户点「下一页」，同一个 OFFSET 10
SELECT id, title, created_at
FROM posts
WHERE published = true
ORDER BY created_at DESC, id DESC
LIMIT 10 OFFSET 10;
```

第二句里的 `OFFSET 10`，跳过的是「插入之后」的前 10 行。而插入之前，用户已经看过了 10 行。新记录占了第 1 行，原来第 10 行被推到第 11 行——它正好落在 `OFFSET 10` 之后的第一位，于是被再读一遍。

这里没有并发冲突，没有隔离级别的争论，也没有任何一句 SQL 写错。两句查询各自都正确，合起来错误。

## 前提：两次查询之间，排序结果不变

任何一次分页遍历，都在隐式假设一件事：这一串查询面对的是同一个排序结果。只要结果集在遍历期间不变，`OFFSET` 的算术就是对的——第 k 页的起点确实是第 (k-1)×m 行。

这个假设在只读快照上成立。在线上库上，它成立的时间窗口约等于两次请求之间的间隔，也就是用户读完一页、点下一页的那几秒到几十秒。

写操作不需要「删库」那么大的动作才能破坏它。一条插入、一条删除、一次 `created_at` 被更新，都够。而列表页恰恰是最容易被写入影响的查询：它按时间排序，而时间排序的头尾正是新数据进入的位置。

我说「说谎」，指的不是它报错。它不报错，不超时，不返回 4xx/5xx。它返回一个格式完全正确的响应，页码对，条数对，字段对。错的是**这个集合和上一个集合拼起来不是全集**。这类错误没有异常可以捕获，也没有日志可以看，它只在有人真的把两次结果并起来去重、或者拿总数对账时才显形。

## 前提破裂时的两种漂移

### 形态一：插入把一条挤到下一页

```text
遍历前（降序）          插入 X 之后
1  A                    1  X   ← 新记录，占了第一位
2  B                    2  A
3  C                    3  B
4  D                    4  C
5  E                    5  D
6  F                    6  E
7  G                    7  F
8  H                    8  G
9  I                    9  H
10 J                   10 I
--- 第 1 页结束 ---     11 J   ← 原第 1 页最后一条，现在被 OFFSET 10 跳过
11 K                   12 K
```

用户读完第 1 页（A..J），插入 X，然后请求 `OFFSET 10`。返回从 J 开始。J 读了两遍。

重复的危害看着轻——前端按 id 去重就藏住了。但它藏住的代价是：去重之后这一页只剩 9 条，界面上的「每页 10 条」变成 9 条，翻页的节奏开始不对；如果这一页在无限滚动里是拼接的，用户会看到同一条出现两次，然后以为自己滑回去了。

### 形态二：删除让一条从缝里漏过去

| 位置 | 遍历前 | 删除 C 之后 |
|:---:|:---|:---|
| 1 | A | A |
| 2 | B | B |
| 3 | C（被删） | D |
| 4 | D | E |
| 5 | E | F |
| 6 | F | G |
| 7 | G | H |
| 8 | H | I |
| 9 | I | J |
| 10 | J | K |
| —— | 第 1 页到此结束 | 第 1 页到此结束 |
| 11 | K | L |

用户读过 A..J，其中 C 在被读之后删掉了。整个列表上移一行，`OFFSET 10` 跳过 A,B,D,E,F,G,H,I,J,K 这 10 行，从 L 开始。

K 从来没被读过。它原来在第 11 位，删除把它顶到第 10 位，正好被 `OFFSET 10` 跳过。用户从第 1 页翻到第 2 页，K 消失了。

遗漏比重复严重，而且严重得不对称：重复会在界面上留痕，用户看得见；遗漏不留痕，用户不知道自己少看了一条。一个批量导出脚本用 `OFFSET` 遍历全表，中间有行被删，导出的文件就缺行，而文件本身完全合法，没有任何一列会提示这一点。

### 为什么 UI 层看不出来

因为 UI 层校验的是「这一页有没有 10 条」和「页码对不对」，这两件事在漂移时都正常。它不知道上一页最后一条是谁，也不知道全集的边界在哪。

要发现这件事，得有一个跨页的参照物：把两次结果按 id 求并集，看数量是不是等于 20；或者拿 `total` 对账。而这两个动作，列表页通常都不做——它每次只关心自己那一屏。

这也是这类缺陷难被验收抓住的原因：它不在任何单次请求的观测范围内，只存在于请求与请求之间的那个缝隙里。

## 排序键不唯一：一个独立于写入的缺陷

上面两种漂移都是写入引起的。还有一类问题，一次写入都没有也会发生：`ORDER BY` 的键不唯一。

### 并列值的相对顺序没有承诺

`ORDER BY created_at DESC` 里如果有两条 `created_at` 完全相同——批量导入、同一事务里写入、精度只到秒的列，都会造出这种行——数据库没有义务在两次查询里给它们相同的相对顺序。SQL 只承诺按 `created_at` 降序，不承诺并列项之间谁先谁后。

于是可能出现：第 1 页的末尾是 X，第 2 页的开头也是 X；或者 X 在两页里都没出现。这两种结果都不违反 SQL 语义，因为排序本身是部分有序的——它没有定义一个全序，而 `OFFSET` 在一个非全序上做位置切片，切出来的边界本来就不稳定。

### 加唯一 tiebreaker 让排序成为全序

修法是给排序键补一个唯一列，把偏序变成全序：`ORDER BY created_at DESC, id DESC`。

`id` 唯一，因此 `(created_at, id)` 这组值唯一，排序结果对同一份数据是确定的、可复现的。这一步不解决写入引起的漂移——插入删除照样移动位置——但它把「无写入也可能重复或遗漏」这一类彻底去掉了。两个问题要分开修，因为成因不同，改法也不同。

顺带一个副作用：排序键唯一之后，`OFFSET` 的结果才真的可以用「上一次的结果」去推断「这一次的边界」，否则连推演都做不了。

## 锚点坐标：让坐标跟着内容走

`OFFSET` 的问题是坐标锚在「列表开头」，而列表开头会动。keyset 分页换了个锚点：它不记「我读了几行」，它记「我读到哪一条」。

### keyset 的查询形态

第一页不带条件，`ORDER BY created_at DESC, id DESC LIMIT 10`。之后每一页都带上一条具体的记录作为边界：

```sql
-- 复合索引必须与排序同序，否则定位退化成扫描
CREATE INDEX idx_posts_created_id
    ON posts (created_at DESC, id DESC);

-- 下一页：以最后一行的 (created_at, id) 为锚点
-- 行值比较按字典序逐列比：先比 created_at，相等再比 id
SELECT id, title, created_at
FROM posts
WHERE published = true
  AND (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 10;
```

`WHERE (created_at, id) < (...)` 与 `ORDER BY created_at DESC, id DESC` 是同一套排序的镜像，所以「严格小于锚点」等价于「排在锚点之后」。

关键差别在这一句：`OFFSET` 问的是「第 11 行是谁」，keyset 问的是「排在 (2026-11-05 10:00:00, 9001) 之后的前 10 条是谁」。前者的答案随数据集变化，后者的答案只随「锚点之后有什么」变化。新插入的记录只要排在锚点之前（时间更新），就完全不进入后续查询，它挤不走任何人。

不支持行值比较的驱动可以展开成显式写法，语义一样：`created_at < :t OR (created_at = :t AND id < :i)`。展开版容易漏括号，写成 `created_at < :t OR created_at = :t AND id < :i` 时，`AND` 的优先级会让条件退化成「比 t 早的全部」，结果是第二页把第一页又给了一遍。这段 SQL 长得完全正常，评审时值得特意看一眼。

### 复合索引与行值比较

`(created_at, id)` 复合索引让「按 created_at 定位 + 按 id 打破并列」这一步在索引里完成，`WHERE` 的行值比较也能用上索引的有序性。索引列顺序写反成 `(id, created_at)` 就用不上——B-tree 只能沿最左前缀有序，而查询要先按时间定位。

这条索引同时服务排序和过滤，等于把分页的开销固定成一个索引区间扫，与页码深浅无关。`OFFSET` 的代价则随页码线性增长：第 500 页要先数过 4990 行再扔掉。这一点常被拿来说明 keyset 的性能优势，但性能不是本文的重点——即使 `OFFSET` 和 keyset 一样快，漂移依然存在。性能问题能测出来，漂移问题测不出来。

### 为什么它对写入免疫

因为锚点是一条具体的记录，不是一个位置。插入一条更新的记录，它排在锚点之前，`WHERE` 条件直接把它排掉，不影响「锚点之后」这个集合。删除锚点之外的任何记录，都只是让后面的集合少一条，不会让别的记录被跳过——因为整个过程里没有「跳过 n 行」这个动作。

漂移的根源是「位置」这个概念本身。只要不引用位置，就没有东西可漂。

## 锚点坐标的账单

keyset 不是免费的升级。它把一类问题换成了另一类约束，用之前得知道自己在换什么。

### 不能跳页

`OFFSET` 支持直接跳到第 7 页，因为第 7 页的起点是 (7-1)×10，算术可求。keyset 的坐标是一条记录，要跳到第 7 页，你得先知道第 7 页的锚点是谁——而知道它，等于把前 6 页走一遍。

所以 keyset 天然只支持「下一页 / 上一页」。带页码条的后台列表、需要随机访问的报表，用它就得额外做一层：缓存每页的锚点，或者干脆对这个接口保留 `OFFSET`。

### 上一页要反向查再翻转

首页是 `LIMIT m` 不带 `WHERE`，条件是空的。上一页要反过来：以当前页第一行为锚点，取「排在它之前」的最后 m 条——`WHERE (created_at, id) > (...) ORDER BY created_at ASC, id ASC LIMIT m`——再把结果反转回来。

方向写错会得到一页顺序颠倒的数据，而且看着不像错，它只是倒着。这类 bug 在接口层很难被发现，因为条数和字段都对，只有人眼扫一遍才发现最新的那条跑到了最底下。

### 游标必须不透明

锚点不能直接把 `created_at` 和 `id` 拼成字符串交给客户端，让前端自己拼 `?after=2026-11-05T10:00:00_9001`。原因有两个：客户端会开始依赖这个格式，以后改排序键就成了破坏性变更；拼接出来的值也容易被拿去做探测。

```ts
// 游标：把排序键序列化成客户端不该解析的字符串
type Cursor = { t: string; id: number };

function encodeCursor(c: Cursor): string {
  return Buffer.from(JSON.stringify(c), 'utf8').toString('base64url');
}

function decodeCursor(raw: string): Cursor {
  const parsed = JSON.parse(
    Buffer.from(raw, 'base64url').toString('utf8')
  );
  if (typeof parsed?.t !== 'string' || !Number.isInteger(parsed?.id)) {
    throw new Error('invalid cursor');
  }
  return parsed as Cursor;
}
```

base64url 不是加密，别把它当安全边界——它只是把格式藏起来，让客户端没有理由去解析。真正要做的是校验：解出来的类型不对就返回 400，别让一个畸形游标变成一条全表扫的查询。

### 排序键变更与锚点被删

游标里编码的是**当前排序键**。一旦排序从 `created_at` 换成「热度」，旧游标就没有意义了——它编码的字段在新排序里不存在。这类变更要么让所有在途游标失效（返回 400，让客户端从第一页重来），要么版本化游标（前缀带 `v1:` / `v2:`）。后者更稳，代价是解码逻辑要兼容多个版本。

锚点被删是另一个坑，但没想象中糟。用户读到第 3 页，第 3 页的第一条在这期间被删了，下一页请求带着一个不存在的锚点。行值比较用的是值，不是外键，不要求那条记录存在，所以查询照样返回正确结果。真正会坏的是「上一页」：如果锚点被删且它是当前页唯一一条，反向查询的边界就落到别处，可能重复也可能跳过一屏。

### 首页语义变弱

`OFFSET` 的分页器知道「总共 8 页，你在第 3 页」。keyset 只知道「还有下一页」——靠多取一条判断 `has_more`。要做页码条，就得另外维护总数，而总数本身也是会漂的，下一节讲。

## 第三个数：total 也在漂

`{"items": [...], "total": 137, "page": 3, "pages": 8}` 这种响应里，`total` 和 `items` 通常来自两条语句、两个时刻。中间只要有一条记录从 `published = false` 变成 `true`，`count` 和列表就不同源了。

于是「第 3 页 / 共 8 页」里的 8 是上一刻的 8，列表是这一刻的列表；翻到最后一页可能只有 3 条，也可能翻过头返回空数组。更隐蔽的是 `pages` 派生自 `total`：如果显示「这是最后一页」，而实际又新增了一页，用户就再也翻不到最新的那几条。

`total` 的漂移和 `OFFSET` 的漂移是同一种病：拿一个会变的东西当坐标。区别在后果的落点——`total` 只影响显示，`OFFSET` 影响数据本身。所以修的时候优先级不同：`total` 可以接受近似，显示「约 137 条」或者干脆只显示「还有更多」；`OFFSET` 的漂移不能接受，因为它丢的是行。

如果一定要一个准确的 `total`，就得让它和列表同源：同一个只读事务、同一个快照里取，配可重复读隔离级别。代价是这条路径上多一个事务，以及长事务对清理与锁的影响。为一个页码条付这个成本，多数时候不划算。

## 快照分页：第三种选择

`OFFSET` 和 keyset 之间还有一个位置：把「这一次遍历」变成一个真正固定的坐标。它不是新发明，只是把静态站那种「构建时定死」的做法搬到了运行时。

### 物化 id 列表

第一次请求时，把符合条件的所有 id 按顺序取出来，存进缓存或临时表，返回第一页和这份列表的句柄。后续每页按「列表里的第 21 到 30 个 id」去取内容：

```sql
-- 示例：把一次遍历的 id 序列物化下来
CREATE TEMP TABLE page_snapshot (
    pos     integer PRIMARY KEY,
    post_id bigint  NOT NULL
);

INSERT INTO page_snapshot (pos, post_id)
SELECT row_number() OVER (ORDER BY created_at DESC, id DESC), id
FROM posts
WHERE published = true;

-- 之后每页都从快照里按位置取，与线上写入无关
SELECT p.id, p.title, p.created_at
FROM page_snapshot s
JOIN posts p ON p.id = s.post_id
WHERE s.pos BETWEEN 21 AND 30
ORDER BY s.pos;
```

这个方案同时具备两个性质：坐标固定（快照不随写入变），并且支持跳页（`pos` 是位置，算术可求）。代价是服务端多了状态：这份快照活多久、什么时候失效、多少人同时遍历时临时表会不会爆。

### 按快照时间过滤

不想物化 id，可以只固定一个时间点：第一页时把 `now()` 记下来，之后每页都带上 `created_at <= :snapshot_at` 这个上界，`OFFSET` 照用。

这解决了「新插入导致重复」——新记录的时间大于 `snapshot_at`，进不来。它不解决「删除导致遗漏」：删除会继续让后面整体上移。所以这是个半个修法，只在「列表以追加为主、很少删除」的场景成立。用之前得先确认自己属于哪一类。

### 什么时候值得付状态成本

需要「固定顺序 + 可跳页 + 跨越较长的时间窗口」三者同时成立时，快照分页是唯一能同时给到的做法。典型场景是导出、对账、后台审核队列——用户可能在第 4 页停留十分钟，再跳回第 2 页核对同一批数据。

这类场景本来就有「一次会话遍历一份数据」的语义，状态成本是值得付的。反过来，一个公开的文章列表，用户翻两页就走，为它维护快照等于拿运维复杂度换一个没人受益的性质。

## 适用边界

| 场景 | 推荐 | 理由 |
|:-----|:-----|:-----|
| 数据量小、翻页浅（前两三页） | `OFFSET` | 漂移窗口内的写入概率低，重复或遗漏可容忍 |
| 公开列表，按时间倒序，用户看首页就够 | `OFFSET` + 唯一 tiebreaker | tiebreaker 去掉并列不确定性，剩余风险可接受 |
| 无限滚动、加载更多 | keyset | 本来就不跳页，键集语义与交互天然对齐 |
| 批量导出、跨库同步、遍历全表 | keyset | 一次遗漏就是数据错，且事后无法察觉 |
| 后台列表要页码条，且数据持续写入 | 快照分页 | 同时要固定顺序与随机访问 |
| 对外 API 暴露列表 | keyset + 不透明游标 | 游标格式是契约的一部分，编码后才有改的余地 |

判断的关键不是数据量，是**这次遍历期间会不会有写入落在你已经读过的区间里**。会，就得考虑锚点；不会——离线导出、只读副本、维护窗口——`OFFSET` 的算术就是对的。

还要补一句：`OFFSET` 的性能随页码线性退化，这件事经常被拿来当作换 keyset 的理由。但那是个独立的、可以测的、有明确指标的问题。本文讲的漂移不会在压测里出现——压测通常是只读的，而漂移需要写。

## 判据

我把这件事压成四个问题，写列表接口前先过一遍：

1. 这次遍历允不允许漏掉一条？允许，`OFFSET` 可以考虑；不允许，锚点或快照。
2. 排序键唯一吗？不唯一，先加 tiebreaker——这一步与分页方案无关，任何方案都要做。
3. 用户会不会跳页？会，keyset 单独用不了，要么快照，要么保留 `OFFSET` 并接受漂移。
4. `total` 和 `items` 是不是同一时刻的？不是，要么同事务取，要么别把它当准数显示。

四个问题里，第 1 和第 3 是产品语义，第 2 和第 4 是数据正确性。先把第 2 和第 4 修掉，它们成本低、收益确定；再按第 1 和第 3 决定要不要换分页方式。

一个反向的判据也有用：如果你在为一个接口纠结「要不要上 keyset」，先问它的数据是不是只增不改。只增的日志、只追加的事件流、按 id 严格递增的订单列表——这类数据上 `OFFSET` 的漂移只表现为「新数据挤进来」，而用户对「翻页期间来了一条新的」本来就有心理预期。真正致命的是删除与更新时间，那才是让行从缝里漏掉的动作。

## 收束：分页是一致性问题

分页长期被归在 UI 那一栏：页码、每页条数、上一页下一页按钮，属展示逻辑。`OFFSET` 的漂移把这个归类打翻了——它不涉及任何渲染，只涉及「两次查询的结果能不能拼成一个完整的集合」，那是一个一致性问题，只是它发生在一个没被当成事务的地方。

`OFFSET` 没有 bug 可修。它的行为完全符合定义：跳过 n 行，取 m 行。错的是用法——把一个相对当前位置的距离，当成了一条记录的地址。距离会变，地址不会。

所以要改的不是 SQL 写法，是脑子里那个「第几页」的表征：它到底是一个位置，还是一条记录。想清楚这一点，剩下的选型都是它的推论。

而这个站点上的第 2 页之所以不出这个问题，不是因为我做对了什么，是因为它根本不在查询时计算——构建那一刻，第 2 页就被写成了文件。静态生成顺手避开了一个动态接口每天都要面对的问题。
