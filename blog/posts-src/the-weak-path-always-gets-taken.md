## 先假设一次中断

假设一个再常见不过的时刻：我在改一批文章源，写到第三个文件的时候，进程被杀掉了。原因可以有很多——我按了 Ctrl-C，机器内存吃紧触发了 OOM，磁盘写满，或者渲染器在读某个格式不对的 frontmatter 时直接抛了异常。

### 中断不挑时机

中断不会等到「一个完整的写操作结束」才发生。它发生在任意两条指令之间，包括文件刚被打开、内容写了三分之一、缓冲还没落盘的那一刻。这一点跟代码写得好不好没关系，它只跟「写」这个动作被拆成了几步有关。

### 我要问的不是「会不会坏」

单独问「这条路可靠吗」，答案永远是「大多数时候没问题」。真正有区分度的问题是：**同一次中断之后，磁盘上剩下什么，下一个人什么时候会发现。**

这篇就沿这一个场景走到底：同一个中断，两条路，各剩什么。

## 两条路摆在一起

这个站现在有两套发文入口，写的是同一批产物文件。

### 新入口：先写别处，再换过来

新入口的做法是先把整篇产物写到同目录下的临时文件（代码里是 `open(tmp, 'w')`），写完之后再做一次替换。替换是原子的：从文件系统的角度看，目标路径要么还指着旧文件，要么已经指着新文件，中间没有「半个文件」这个状态。

它一次重编整个站点，不只写当前这一篇。因此任何单篇产物与源不一致的漂移，都会在下一次重编时被拉回源的样子。流程末尾还会跑三道门禁：产物一致性、内链、隐私。

### 旧入口：打开就写

旧入口是一个七百多行的脚本，支持两种用法：命令行参数，或者读一个带 frontmatter 的 md 文件。它的写盘动作很直接：

```python
with open(target, 'w', encoding='utf-8') as f:
    f.write(html)
```

打开、截断、写。没有临时文件，没有替换。它也**没有**调用内链检查和隐私扫描——在它的代码里搜这两个动作的名字，命中是 0：

```bash
grep -nE 'check-links|privacy' scripts/publish-legacy.py
# （无输出，命中 0）
```

它今天的主要用途其实不是发文，而是作为库被新入口 import：渲染器和 frontmatter 解析都在它里面。命令行模式保留着，是为了兼容历史用法。

### 两套路径，一套产物

这里有个容易被忽略的点：它们不是两个互不相干的系统。它们写的是同一批文件，落在同一个目录里。所以「用哪条路」不是隔离的选择，而是同一份结果由哪套保证来兜底的选择。

## 同一次中断，走新入口剩下什么

还是那个时刻：写到第三个文件，进程没了。

### 磁盘上要么是旧的，要么是新的

第三个文件的目标路径没有被碰过，因为写入发生在临时文件上。替换还没执行，所以读者看到的仍是上一版。整篇要么是完整的旧版本，要么是完整的新版本，不存在「打开一半」的中间态。

### 半成品留在临时文件里

半成品确实存在，但它在临时文件里，不在正式路径上。它不会被索引、不会被列表页引用、不会被下一次构建当成源读进去。清理它是运维问题，不是正确性问题。

```text
强入口，中断之后：
  content/post-c.md        旧版本，完整可读
  content/.post-c.md.tmp   半成品，没人引用

弱入口，中断之后：
  content/post-c.md        新版本的前 40%，没有结尾
```

### 全站重编把漂移拉回来

假设中断发生在更靠后的位置：产物写完了，但索引没更新，或者某一篇的相关文章还指着上一篇的标题。新入口下一次运行会从源重编整个站点，这些派生文件全部重算。漂移不需要人记得，它会被构建抹平。

## 同一次中断，走旧入口剩下什么

同一个中断，换成旧入口。

### 文件已经被截断

`open(target, 'w')` 的第一步就是把目标文件截断成 0 字节。中断发生在这一步之后、写完之前，磁盘上留下的就是「新版本的前几十个百分点」，而且没有结尾——可能是半个 `<div>`，可能是一段没有闭合的代码块，可能是正文断在句子中间。

### 没有前置自检，错误往前流

旧入口不在写盘之前做结构校验。源里的字段缺了、分类写错了、正文首行不是标题，它照写。错误不会在入口处停下，它会变成产物的一部分，然后被下一道工序当成正常输入。

### 没有下游检查，坏产物静静躺着

新入口末尾有三道门禁，旧入口一条都没接。产物写完，命令跑完，屏幕上没有任何异常。坏掉的那一页就躺在 `site/` 里，等人访问、等人发现。

### 发现它的人通常是几天后的自己

这是最贵的一段延迟。中断当时没有任何信号；下一次运行也不会报错，因为它只关心自己这一次写的那几篇。真正发现问题的时机，往往是几天后翻列表页时看到一篇标题正常、点进去内容断了半截的文章——这时候已经很难判断是哪次操作留下的，也很难知道还有没有别的地方一起坏了。

## 把保证列成四行

同一个中断，两条路剩下的东西不一样，是因为它们承诺的东西不一样。

| 保证 | 强入口 | 弱入口 | 缺了会怎样 |
|:-----|:-------|:-------|:-----------|
| 原子性 | 临时文件 + 替换 | 直接覆盖目标文件 | 中断后留下半成品 |
| 前置自检 | 写入前先解析源，不合格就停 | 无 | 源里的错误直接进产物 |
| 下游一致性 | 整站重编 + 产物比对 | 只写本次涉及的几份 | 派生文件漂移无人拉回 |
| 可回滚 | 旧版本还在，重跑即可 | 没有旧版本 | 只能靠备份或记忆 |

### 为什么这四行不能拆开看

单看任何一行，都能得出「差不多够用」的结论。原子写看起来只是少了一个极端情况；内链检查看起来只是附加项；整站重编看起来只是慢一点。但这四行是叠在一起起作用的：原子性保证中断不产生坏文件，前置自检保证坏输入不进入写盘，下游一致性保证坏产物不会静静留着，可回滚保证发现问题之后有退路。抽掉任何一行，剩下的三行都要多承担一份它本来不负责的工作。

## 它为什么不会被删

如果弱入口明显更差，为什么它还在？这个问题不能只用「历史遗留」四个字打发。

### 历史脚本还在调用

命令行模式存在了很多年。仓库内的脚本、CI 步骤、别人机器上的 alias，都可能还写着它。删掉一个命令，成本不在删这个动作，而在你不知道谁在调它。

### 文档里还写着

文档里的示例是最容易被复制的代码。只要文档还写着「用旧入口发一篇」，下一个人就会照着做——他没有任何理由去查这个入口是不是还有原子写、是不是接了门禁。

### 删了怕坏事

这条最实在。旧入口能跑，新入口也能跑。删掉旧入口带来的收益是「保证变强」，风险是「某个我不知道的地方断了」。收益是抽象的，风险是具体的，人自然会选不动。

### 人总是走更短的那条

即便两条路都在文档里写着，人也会选输入更短的那条。旧入口一条命令带几个参数就能出结果，新入口要先写源、再编译、再跑门禁。这不是懒惰，是在没有额外信息时对「少一步」的合理偏好。**只要更短的那条还在，它就会被走到。**

## 兼容的两种正确形态

「保留旧入口」和「保留旧入口的弱保证」是两件事。前者可以是合理的，后者不该被接受。

### 形态一：薄壳

把旧入口改成强入口的薄壳：它负责参数转换，把命令行参数或 md 文件翻译成新入口的输入，然后调用同一套逻辑。写盘、校验、重编、门禁只有一份实现。

```python
def main(argv):
    args = parse_legacy_args(argv)      # 只做参数解析
    src = normalize_to_source(args)     # 只做格式转换
    return build_one(src)               # 与强入口同一个实现
```

薄壳的价值在于：老命令还能用，老脚本不用改，但**保证只有一份**。它不会成为「另一个选择」，因为它没有另一套写盘路径。

### 形态二：删掉，并在文档里标成已移除

如果调用面足够小，删是更彻底的做法。删的时候要把历史用法在文档里明确标成已移除，写清替代命令是什么。不写这一句，下一个人会以为文档漏了，然后自己去仓库里翻出旧脚本继续用。

## 怎么判断该删还是该包壳

判断不需要复杂模型，三个量够了。

### 先数调用面

仓库内有多少脚本、CI 步骤、文档示例引用了旧入口。这个数字是硬的，能直接数出来：

```bash
# 只统计引用，不改任何文件
grep -rn "publish-legacy" scripts/ .github/ docs/ 2>/dev/null | wc -l
grep -rn "publish-legacy" content/ templates/ 2>/dev/null | wc -l
```

### 再看外部依赖

仓库外有没有人依赖这个命令。这一项数不出来，只能靠约定：如果有对外文档、有别人在用的定时任务，按「有外部依赖」处理，选薄壳；如果确认只有自己在用，删的阻力就小很多。

### 最后算重写成本

薄壳的成本是「把参数翻译对」，删的成本是「把所有调用点改对，再更新文档」。前者一次性，后者要追着调用点跑。调用面小的时候删更干净；调用面大、又说不清外部依赖的时候，薄壳是风险更低的那条。

一个实用的顺序是：**先包壳，再观察，最后删。** 包壳之后旧入口不再产生弱保证，调用会继续工作，同时能从日志里看到还有谁在走它。等调用面清零，删就只是一个清理动作。

## 收束：兼容不是多留一条路

回到那次中断。

强入口中断，你剩下一个完整的旧版本和一个可以扔掉的临时文件；弱入口中断，你剩下一个被截断的文件，和一段没人知道的静默期。这两者的差别不在于「哪个更快」，而在于出问题时你有没有退路。

所以「兼容一个旧入口」的成本，从来不是它多存在一天占的那点维护精力。成本是它保留了一套更弱的保证：没有原子写，失败就留半成品；没有前置自检，错误往前流；没有下游检查，坏产物会静静躺着等人下次发现。而只要它还在，它就会被走到——因为人总是选更短的那条路。

要么删，要么把它做成强入口的薄壳。不能让它一直是「另一个选择」。

### 这次只写了分析

需要说清楚：**这篇文章没有做任何改动，两套入口都还在，旧入口的写盘方式也没变。** 上面四行对照表和两种形态，是对现状的分析和可选方向，不是已经完成的重构。真要动手，第一步应该是数调用面，而不是先改代码。
