## 退租那天，我盯着那个空掉的配置目录

机器的退租时间是下午四点。三点出头，我把该带走的东西拷到一个目录里：几个仓库、几份笔记、一些证书文件。拷完以后还剩一个目录，是那台机器上跑了一年的绕行层——客户端进程、规则文件、系统级拦截的开关、拉它起来的守护脚本、盯着它的探针。

我把这整个目录打成一个压缩包，也拷走了。

新机器是三天前上线的，位置不一样，直连可达。它上面一条绕行配置都没有，也从没装上过。这三天里它跑得比旧机器顺：没有握手失败，没有规则更新后需要重启，没有「明明能上网但某个服务连不上」的时刻。

那个压缩包，我后来再没打开过。

我想说的不是打包错了。打包是赶时间时唯一靠谱的动作。但那个压缩包本身是一份证据：它证明我当时说不清哪些还有用。如果我能逐条说出每条配置服务于哪一个仍然存在的问题，我就不需要打包——我会知道哪些该带走、哪些该当场删掉。

## 被砍掉的那一层不是被淘汰，是只在旧机器上成立

先给结论：**被砍掉的那一层不是被淘汰的，它从来没有被需要过——它只是在旧机器上被需要过。**

这两个说法差得很远。淘汰意味着有一个更好的东西取代了它，你去学新东西就行；前提消失意味着它要解决的问题不存在了，没有取代者，也没有替代方案可找。混淆这两件事的代价，是你会一直觉得「少了一层东西」，然后找一个新的来补上。

标题里的「一半」是个不精确的说法。我没有数过它在旧机器上占多少行、占多少配置项，也不打算事后估一个数字来撑场面。它想说的是那个下午的直观比例：新机器需要的那份配置，和旧机器实际在跑的那份配置之间，差的不是几行，是一整层。

## 迁移有两件事，清单上通常只有第一件

### 搬运问「缺不缺」，清点问「还成不成立」

迁移包含两个动作，但绝大多数清单只写了第一个。

**搬运**的主语是新机器：新机器缺什么，就从旧机器上拿什么。**清点**的主语是旧配置：它当初为什么在这儿，那个理由现在还立得住吗。

两个问题的答案集合形状完全不同。第一个问题的答案是「需要的东西」，天然倾向于把能搬的都搬过去——多搬不会立刻出错，少搬会立刻暴露。第二个问题的答案是「可以死掉的东西」，它的产出是负的，而且负得越准，越看不出来。

### 清点三问

清点一条配置，要问三个问题：

1. 它当初为了解决什么问题？
2. 那个问题的前提是什么？
3. 那个前提现在成立吗？

三个问题里，第一个最难。因为配置文件里的注释写的是「做什么」，不是「为什么」。一行 `enabled: true` 告诉你它在生效，不告诉你它为什么要生效。「因为这台机器到不了目标」才是理由，而这句话通常只存在于加它那个人的脑子里，最多存在于某次提交信息里。

所以清点常常卡在第一问就进行不下去。卡住的时候，多数人的处置是「那就留着吧」——留下一条答不出问题的配置，感觉上比删掉一条答不出问题的配置安全。

### 搬运之所以看着更像工作

搬运有进度条。文件在拷、服务在起、页面能打开、单测能过。你可以指着屏幕说「好了」。

清点没有进度条。它的产出是「少了一部分东西」，而少得越对，越没人看得出来。删对了，什么都不会发生；删错了，当天就会出事。奖惩结构是反的，所以清点天然不被记进任何人的任务列表。

这就是为什么迁移记录里通常只有搬运：不是没人想到清点，是清点不发生「事件」，无法被记录成一条已完成项。

## 假设登记簿：九条看起来天经地义的配置

下面这份登记簿，记的是旧环境里那些看起来天经地义的配置。每一条按四栏记。四栏缺一栏，就不算记过——特别是第一栏，如果只能写出「它做什么」，说明这条还没被清点。

```text
假设          ：这台机器到不了目标，所以要绕一层
假设依赖什么  ：① 机器的网络位置  ② 目标的位置
机器一换      ：位置变了，依赖还在，但结论反了 —— 示意，非真实配置
处置          ：整层删（先停守护，再停进程）
```

这段是示意，用来演示记法，不是从哪台机器上抠下来的。

### 第一条 · 「到不了目标，所以要绕一层」

**当时的假设**：这台机器的网络位置到不了要访问的目标，所以要绕一层出去。

**假设依赖什么**：两个外部事实——机器所在的位置、目标所在的位置。注意这两个都不是机器属性，是环境属性。同一台机器搬个地方，这条假设就可能从成立变成不成立。

**机器一换，依赖还在吗**：位置变了。新位置直连可达，这条假设的前提直接消失。

**处置**：整层删。

这里有个容易忽略的地方：这一层不是一个软件，是一串彼此依赖的配置。客户端进程、配置或规则订阅、系统级流量拦截、按域名分流规则、健康检查与自动切换、开机自启、日志与端口占用。它们之间没有强制的引用检查，**任何一环被删，其余几环不会报错，只会静默变成死配置**。

```text
客户端进程
  └─ 读取规则订阅  ← 订阅挂了，进程照跑，规则停在旧版本
       └─ 按域名分流  ← 没有进程，规则不再被引用，文件还在
            └─ 系统级拦截  ← 没有分流规则，拦截仍然会劫持全部流量
                 └─ 健康检查  ← 只探端口，端口在听就是绿的
                      └─ 开机自启  ← 守护一个已经没有意义的进程
```

示意。这张图的重点是每一条的输入都来自上一层，但没有任何一层会检查上一层是否还该存在。

### 第二条 · 「这几个域名必须绕，那几个必须直连」

**当时的假设**：目标不是均质的——有些必须绕行，有些必须直连。数据库、内网地址、按地区计价的服务，绕出去反而更慢或者直接失败。

**假设依赖什么**：第一条成立。没有绕行层，就不存在「分流」这件事。

**机器一换，依赖还在吗**：第一条整层没了，这条的每一行都失去被引用的理由。但它不会报错：规则文件还在，匹配逻辑还在，只是没有流量再经过它。

**处置**：与第一条同批删。顺序上先删引用方，再删被引用方，反过来会在删除过程中制造一段「规则指向不存在的出口」的状态。

```yaml
# 示意：一条分流规则。真正缺的不是这一行，是它上面那行注释
rules:
  - domain: "internal.example.com"
    action: direct        # 为什么是 direct？因为这台机器原本到不了它
  - domain: "blog.example.com"
    action: proxy         # 为什么是 proxy？因为原本必须绕
```

这份示意里，两行配置本身都没问题，问题在注释：它们写的是「走哪条路」，没写「当初为什么要分」。等绕行层消失，这两行会从「正确的配置」变成「正确的废话」。

### 第三条 · 「不是每个程序都懂绕行，所以要在系统层拦」

**当时的假设**：有一部分程序不读环境变量、不认应用层设置，只能在系统层把流量截下来。

**假设依赖什么**：① 确实存在绕行需求；② 那部分程序还在被使用。

**机器一换，依赖还在吗**：① 消失。② 程序可能还在，但它们不再需要被截——直连本来就是它们该走的路。

**处置**：删。

这一条是整层里副作用最大的一环，因为它把「所有流量」变成自己的管辖范围。它活着的时候，本机任何网络异常的默认第一嫌疑人是它；它被删了一半的时候（开关关了但路由条目、DNS 设置、虚拟网卡还在），残留物会以更难查的方式影响本机行为。具体表现取决于实现方式，这里不给通用结论，只给一条处置纪律：**这一层的删除要验证「删完之后本机网络行为与从未装过它时一致」，而不只是验证「进程不在了」**。

### 第四条 · 「进程会掉，所以要有人在开机时拉起来」

**当时的假设**：这个东西必须常驻，掉了要自愈，重启要自动回来。

**假设依赖什么**：它必须常驻。

**机器一换，依赖还在吗**：不需要常驻的东西，不需要守护。更麻烦的是，守护脚本的存在本身会反过来制造「它很重要」的印象——下次有人看到这个 unit、这个 cron、这个 watchdog，第一判断是「这东西不能停」。

**处置**：删。顺序是先停守护，再停进程。反过来做，守护会在你停掉进程之后立刻把它拉回来，你会以为删不掉，然后放弃。

### 第五条 · 「这条链路要有人盯着」

**当时的假设**：链路会断，断了要告警。

**假设依赖什么**：链路存在，且它承载的东西重要。

**机器一换，依赖还在吗**：链路不存在了，探针还在探。而它探的是端口有没有在听。

```bash
# 示意：这类探针的判据通常只有一条
if port_listening "$LISTEN_PORT"; then
  report "ok"
else
  report "down"
fi
# 它回答的是「有没有人在听」，不是「这条路还该不该存在」
```

端口号是示意里随手写的假值。重点是判据：一个已经不承载任何东西的端口，只要进程还在，探针就是绿的；而只要进程被删掉、端口空出来，探针会立刻转红，于是你会收到一条「服务不可用」的告警，去修一个本来该被删掉的东西。

**处置**：删探针，连同它的告警规则、静默规则、值班表里对应的那一条。只删探针不删告警规则，下一次变更会给你一条无法解释的红灯。

### 第六条 · 「这个端口是本机的固定事实」

**当时的假设**：某个本地端口归这一层所有，防火墙要为它开口，容器要把它映射出去，文档里要写它。

**假设依赖什么**：这一层存在。

**机器一换，依赖还在吗**：端口空出来了。但「空出来」不等于「没人记得」：防火墙的放行规则、容器的端口映射、部署文档里的本地地址、别人脚本里写死的本地地址，都还指着它。

**处置**：删放行规则、删映射、改文档。别人脚本里的地址不能替人改，但要主动通知——这一条是清理里唯一需要跨人协作的部分，也是最容易漏的部分，因为它不在你的仓库里。

### 第七条 · 「日志要落在本地，方便事后翻」

**当时的假设**：这一层会产生需要事后追溯的连接记录，所以要落盘、要轮转、要留够天数。

**假设依赖什么**：① 这一层存在；② 确实有人会去翻。

**机器一换，依赖还在吗**：① 消失；② **仍然成立**——不是因为绕行层，而是因为同一台机器上还有别的东西在写日志。

**处置**：**留着。** 要改的只有一处：采集配置里那条指向旧目录的路径。

这一条是登记簿里第一个「不该删」。它的价值不挂在绕行层上，挂在「这台机器会写日志、日志要能被追溯」这个与机器位置无关的事实上。判据的差别在这里：绕行层的寿命由「到不到得了目标」决定，日志的寿命由「出事后要不要查」决定。后者换机器不会变。

### 第八条 · 「订阅的规则集要按时更新」

**当时的假设**：规则会变，所以要定时拉取，保持最新。

**假设依赖什么**：① 有东西在消费这份规则；② 规则的维护方还在维护。

**机器一换，依赖还在吗**：① 消失。② 与你无关了。

**处置**：删定时任务，再删本地副本。第二步常被漏掉：任务删了，文件还在，它会以「配置」的身份继续被下一个人读到，读的人不会知道它是死的。

还有一重风险不随机器消失：只要任务还在跑，它就会在你不知情的情况下覆盖本地文件。某天你翻到这份规则，会以为它是当前的决策依据；而它可能已经是一份被人改过若干轮、与你无关的策略。

### 第九条 · 「备份要带上这台机器自己的状态」

**当时的假设**：这台机器的状态需要能被重建，所以要有定时任务把它抄到别处。

**假设依赖什么**：这台机器上有不可再生的状态。

**机器一换，依赖还在吗**：要分开看两种任务。

- 指向旧机器自身地址的：把本机 A 目录同步到本机 B 目录、把本机状态推到本机另一个盘。前提随机器消失，**删**。
- 指向一个仍然存在的远端目标的：代码仓库、对象存储、另一台还在服役的机器。前提没变，**留着**。

**处置**：一条删、一条留。判据是问「我要恢复的东西在哪」，而不是问「这个任务原来跑在哪台机器上」。搬机器时按后者筛，会把一整批备份任务当成历史包袱清掉，然后在某天发现没有备份。

### 压成一张表

| 条目 | 当时的假设 | 处置 |
|:-----|:-----------|:-----|
| 一 | 到不了目标，所以要绕 | 整层删 |
| 二 | 有些域名要绕，有些要直连 | 随第一条删 |
| 三 | 程序不懂绕行，要在系统层拦 | 删，并验证网络行为复原 |
| 四 | 进程会掉，要自愈 | 先停守护再停进程 |
| 五 | 链路要有人盯着 | 删探针与告警规则 |
| 六 | 这个端口归它所有 | 删放行与映射，改文档 |
| 七 | 日志要落盘、要能追溯 | **留着**，只改采集路径 |
| 八 | 规则会变，要定时拉 | 删任务与本地副本 |
| 九 | 本机状态要能重建 | 指向自身的删，指向远端的**留着** |

表里九条，七条删、两条留。这个比例不是重点，重点是那两条留的判据与其余七条不同：前七条的寿命挂在「机器位置」上，后两条挂在「出事后要不要查」「数据丢了要不要能恢复」上。

## 为什么没人删：它在失效之后仍然「工作正常」

### 探针只探端口，不探必要性

监控系统的语义是「这个东西还活着吗」，不是「这个东西还该活着吗」。前者是可观测事实，后者是意图，而从机器里读不出意图。

所以一条配置失效以后，只要它还有进程、还在监听、还在写日志，所有仪表就是绿的。没有任何一条告警的判据是「它已经三个月没有服务于任何问题了」——这条判据写不出来，写出来也没法自动算。

### 一条没有用处的分流规则照样命中

把一条已经无用的规则留着，它的匹配逻辑仍然正确、仍然会命中、仍然按预期动作。功能正确与需求成立是两件不同的事，而监控只看前者。

这是静默失效最典型的形态：它不坏，它只是不再有意义。坏了会有人修，不再有意义不会有人发现。

### 订阅型配置会自己变

定时拉取的规则集，会在你不知情的情况下改变行为。某天某个站打不开、某个服务连不上，你去查，会查到一条你从没写过的规则。

行为变了，变更记录里没有对应条目——因为这份变更不在你的版本控制里，它在别人的仓库里。这比「忘了当初为什么加」更麻烦：你连「它是什么时候变成这样的」都答不出来。

### 删除不在任何人的日程上

没有哪个任务叫「本周清点不再成立的假设」。加配置有触发事件：要连某个东西、要开某个端口、要绕某个限制。删配置没有触发事件。

它只在退租、换机、迁移这种被迫清点的时刻浮上来。而那时人通常在赶时间，赶时间时的默认动作是打包，不是逐条判断——于是清点被推迟到「以后」，而「以后」没有日期。

## 为什么非删不可：留着不是零成本

### 排查时它先把人带偏

出事时的第一个动作是缩小范围。一条没人知道来历的配置会把范围扩大：你会去查它、会怀疑它、会在它身上花掉本该花在真正原因上的时间。

它的第一作用不是占内存，是改变你排错的顺序。而排错顺序错了，代价按小时算。

### 下一个人会绕开它

下一个人——包括三个月后的自己——看到一条配置，默认假设是「有人加它是有原因的」。于是他既不删它，也不在它旁边加东西，他会绕开。

绕开的代价是长期的：新方案要多考虑一个不该存在的变量，文档要多解释一段不该存在的历史，新人上手要多问一个答不上来的问题。留着一条死配置，等于给后来者留了一个必须绕行的坑，而且还看不出那是坑。

### 每一条都是没有出处的变量

一台机器的行为，等于它上面所有配置的总和。一条没有出处的配置，就是一个无法归因的变量。

变量少的时候，你可以说「这台机器就是这样配的」；变量多到一定程度，你只能说「这台机器就是这样」。前者可维护，后者只能重启试试。

## 删除也要证据

### 「看着像没用」不是判据

删除的判据是「问题的前提不成立」，不是「看着像没用」。区别在于：前者以问题的形状为准，后者以你的记忆为准。

而记忆在这件事上不可靠——看着像没用的东西，常常只是你忘了它当初挡住了什么。凭印象删，会在几周后以一种很难回溯的方式还回来。

### 答不出来的，先标记观察

三问答不全的那条，处置不是删，是标记：写清它现在服务于什么问题，写不出来的就写「未知」，记下日期，然后观察它下一次出现或者不出现。

```text
# 示意：标记格式，重点是「未知」也要有日期
# owner: unknown
# since: 2026-xx-xx  （本次清点日期）
# serves: 未知，观察中
# next-review: 三个月后
```

「未知」加上日期，是一个可以推进的状态；「未知」不加日期，就等于永久保留。这两者在文件里长得几乎一样，在半年后差别很大。

### 删除也要留账

删除的记账方式和新增不一样。新增记「为什么加」，删除记「为什么可以没有」。

后者更容易丢，因为删除看起来是「什么都没发生」。而它恰恰是最需要留痕的动作：下一次有人想加回来的时候，唯一能拦住他的就是这条记录。

## 收束：把生命周期挂到问题上

一条配置的生命周期，应该挂在「它要解决的问题」上，而不是挂在「它所在的机器」上。机器是配置的宿主，不是配置的理由。

按这个标准，判断一条配置该不该活，看的是它要解决的问题还在不在，不是它在哪台机器上跑、跑了多久、有没有人维护。机器换了，问题消失的那些就该跟着消失；问题还在的那些，哪怕整个环境都换了，也要带过去。

迁移做完了的标志，不是新机器能跑起来。新机器能跑起来只说明搬运做完了，那是最容易的一半。标志是：旧机器上的每一条配置，你都能说出它现在服务于哪一个仍然存在的问题。说不出的那些，要么已经在删除记录里，要么还在观察名单上，标着日期。

旧机器退租那天我打包的那个压缩包，到现在也没打开过。它算不上备份——它是我当时还没做完的那份清点的替代品。
