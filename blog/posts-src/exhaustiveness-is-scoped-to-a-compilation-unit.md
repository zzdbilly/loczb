## 一个编译通过、上线后才出问题的 when

下面两段代码分别属于两个模块，放在一起是为了对照。第一段在一个库里：

```kotlin
// core 模块，1.2.0
package com.example.core

sealed class SyncState {
    object Idle : SyncState()
    data class Running(val progress: Int) : SyncState()
    data class Failed(val reason: String) : SyncState()
}

// app 模块，编译时依赖 core 1.2.0
package com.example.app

fun label(state: SyncState): String = when (state) {
    SyncState.Idle -> "空闲"
    is SyncState.Running -> "同步中 ${state.progress}%"
    is SyncState.Failed -> "失败：${state.reason}"
}
```

这段代码在被写下的那天是干净的。`when` 没有 `else`，编译器认可它穷尽，IDE 不会给黄色提示，代码评审也挑不出毛病。它的正确性建立在一个没有写进类型系统的前提上：`SyncState` 的子类型集合，从今往后不再变化。

然后库发了 1.3.0，加了第四个分支，比如 `object Paused : SyncState()`。应用的源码一行没改。如果应用跟着重新编译，`label` 立刻变红，问题在构建阶段就被拦下。但如果应用没有被重新编译，只是运行时 classpath 上的那一份 `core` 换成了 1.3.0，情况就完全不同：`label` 仍然是那个被编译器认证过的 `label`，它带着一份只有三个入口的分支表，而传进来的值可以是第四种。

它会在某个用户点下暂停的那一刻，遇到一个它从未听说过的类型。

这篇文章只谈这一件事：穷尽性不是类型系统对世界作出的全局承诺，它是一次编译得到的局部结论，带着时间戳。

## 两条线：编译期画一次，运行期画一次

把「穷尽」当成一条线，会看不清它。它其实是两条线，画在不同的时刻，用不同的材料。

### 编译期那条线：范围是当时的 classpath

编译 `label` 的时候，编译器做的事情很朴素：它拿到 `SyncState` 这个 sealed 类型，去 classpath 上把它的直接子类型找齐，然后与 `when` 里的分支逐一比对，缺一个就报错。

这里有两个限定词值得盯住。

第一是**当时**。编译器不预测未来，它只描述它读到的这份字节码。它没有能力知道下个月库里会加什么，也没有能力知道运行时真正加载的是哪个版本的 jar。

第二是**classpath**。这条线的边界不是「逻辑上的整个程序」，而是「这次编译任务的输入集合」。同一份源码，在依赖 A 版本的 classpath 上编译，结论是穷尽；在依赖 B 版本的 classpath 上编译，结论可能是缺分支。结论跟着输入走，不跟着源码走。

所以编译期这条线，本质是一次快照式的核对：在时刻 T，以输入集合 S 为准，分支覆盖了全部子类型。它是一份合格的证明，只不过证明的命题里写死了 S。

### 运行期那条线：范围是当前的字节码加当前的库

程序真正跑起来时，没有任何人在做核对。JVM 加载 class 文件，执行指令，仅此而已。

运行期的「范围」由两样东西决定：

- 磁盘上那份已经被编译成字节码的分支表，它冻结在编译时刻；
- 运行时 classpath 上实际加载到的那个库版本，它可能比编译时新，也可能比编译时旧。

这两样东西都属于部署与依赖管理，不属于类型检查。它们可以任意错配，而 JVM 不会为此发出任何警告。

### 两条线不重合的地方

只要「编译时的库版本」与「运行时的库版本」一致，两条线就重合，穷尽性在两端都成立，这是绝大多数项目的日常状态，也是这个机制平时不为人注意的原因。

两条线一旦分开，中间就出现一条缝隙。缝隙的大小等于版本差，缝隙里发生的事没有任何编译期检查参与。本文余下的部分，都在描述这条缝隙的形状，以及怎么把它收窄。

## 三种组合，只有第三种是缝隙

把「库加了一个子类型」这件事，按消费方的状态分成三种情况，结论完全不同。

### 组合一：同模块新增子类型，下一个编译周期就红

如果 sealed 类和使用它的 `when` 在同一个模块里，新增子类型的开发者本人会在下一次编译时看到错误：

```text
e: app/src/main/kotlin/com/example/app/Label.kt:6:5
    'when' expression must be exhaustive. Add the 'Paused' branch or an 'else' branch.
```

这是这个机制里最安全的一种情况：改的人和被影响的人在同一个编译单元里，错误落在改动者的终端上，代价是一次补分支。同一模块内，穷尽性这条线是真实有效的，而且是自动的，不需要任何约定。

### 组合二：跨模块、但消费者重新编译，也会红

库和应用分成两个模块，库先发版，应用后构建。这时编译器从 classpath 上读到的是新版本的 `core`，它看得见 `Paused`，于是同样报缺分支。

第二种情况与第一种的差别只在「谁先看到错误」，机制是同一个：只要消费者在新增子类型之后被重新编译过，检查就会发生。

现代构建工具的增量编译，多数情况下也会在 sealed 层次发生变化时重编依赖方，这让第二种情况在单体仓库里几乎等同于第一种。但要注意，这是构建工具提供的便利，不是语言提供的保证。它的有效期止于「产物还在你的构建系统里」这个前提。

### 组合三：跨模块、只换二进制，没有人在检查

第三种情况是把编译产物搬出构建系统之后发生的：应用用 `core 1.2.0` 编译，交付的时候 classpath 上放的是 `core 1.3.0`。

```bash
# 应用编译时用的是 1.2.0
./gradlew :app:assembleDebug -PcoreVersion=1.2.0

# 交付或部署时，运行时依赖被替换成 1.3.0
# 应用自己的 class 文件一个字节都没变
java -cp app.jar:core-1.3.0.jar com.example.app.Main
```

这时没有任何编译器在场。应用的那份字节码是 1.2.0 时代的产物，里面的分支表只有三个入口；`core-1.3.0.jar` 里的 `SyncState` 有四个子类型。两边都是合法产物，各自都通过了各自的构建，组合起来却不满足任何一方曾经证明过的命题。

这种错配在工程里有几种常见形态，都不需要谁犯错：

- 库以 aar / jar 的形式跨团队交付，使用方拿到的是预编译产物，自己并不构建库；
- 插件或扩展被装进一个宿主程序，宿主与插件各自独立编译、独立发版；
- 打包脚本从制品库拉各个模块的二进制，按版本号拼出一个可运行镜像，而版本号来自配置而不是来自构建图；
- 依赖声明里同一个库出现在两个位置，最终解析到哪一个由依赖调解决定，与编译时用的不是同一个。

这些形态的共同点是：**编译期这条线所依赖的输入集合，在运行期被人替换了，而没有任何机制要求重新核对。**

### enum 常量走的是同一条路

`enum class` 的 `when` 也是编译期穷尽，也有同样的问题，只是加一个常量的门槛更低——加常量在很多人眼里是「增量改动」，连 API 评审都可能跳过。

一个旧的应用字节码遇到新的枚举常量，表现与 sealed 的情况一致：要么落到默认分支，要么在取值的路径上抛出异常。枚举让这件事更容易发生，因为改动的心理成本更低。

### 如果消费方是 Java，编译期这条线根本不存在

还有一类消费方值得单独提：Java 代码调用 Kotlin 的 sealed 类型。

Java 的 `switch` 没有对 Kotlin sealed 层次的穷尽性检查，IDE 可能给个提示，编译器不强制。也就是说，这类消费方连「编译期那条线」都没有画过，从第一天起就只依赖运行期的行为。跨语言边界时，穷尽性这个保证会直接消失，而不是变弱。

## else 做了什么：把编译错误换成了默认行为

到这里为止，最坏的结果还只是一次异常：程序在遇到未知子类型时明确地失败。加一个 `else` 会把这件事的性质改变。

### 分支表是编译期写进字节码的

`when` 不是解释执行的语法结构，它被编译成一组比较与跳转。对 sealed 类型，编译器知道所有子类型，于是可以生成一张完整的分派表，再加一个兜底入口。

关键在于：**这张表是编译的产物，不是类型的产物。** 类型在运行时会随库更新，表不会。`else` 的作用，是让编译器在生成这张表的时候，把「剩下的所有情况」折叠成一个入口，而不是要求在编译期逐一列清。

于是 `else` 同时做了两件事：它让当前的编译通过，也让未来新增的子类型不再构成编译错误。

### 空 else 是丢分支最安静的形式

```kotlin
// 写法 A：默认分支什么都不做
fun onState(state: SyncState) {
    when (state) {
        SyncState.Idle -> idle()
        is SyncState.Running -> render(state.progress)
        is SyncState.Failed -> showError(state.reason)
        else -> Unit
    }
}

// 写法 B：默认分支直接失败
fun onStateStrict(state: SyncState) {
    when (state) {
        SyncState.Idle -> idle()
        is SyncState.Running -> render(state.progress)
        is SyncState.Failed -> showError(state.reason)
        else -> error("unhandled SyncState: ${state::class.qualifiedName}")
    }
}
```

写法 A 在编译时是对的，在运行时也不会抛异常。库新增 `Paused` 之后，它依然不抛异常——它会走进 `else`，什么都不做。

从外部看，表现是「暂停之后界面没有反应」。日志里没有错误，监控上没有异常率抬升，崩溃平台一片安静。只有一个状态被吞掉了，而吞掉它的那行代码写着 `Unit`，看上去像是「这里本来就不需要处理」。

这类问题最难查的地方不在于定位，而在于它不产生任何信号。异常至少会给你一个堆栈；静默的分支丢失只给你一个「感觉不太对」。

### 写日志的 else 只是把问题推迟到日志里

比 `Unit` 好一点的写法是在 `else` 里打一条日志。它确实留下了痕迹，但要注意它改变了什么、没改变什么：

- 改变了：问题从「无痕迹」变成「有痕迹」；
- 没改变：控制流依然走默认路径，业务语义依然是错的。

一条「unhandled state: Paused」的 warn 日志，在流量低的时候可能几天才出现一次，在日志采样、级别过滤、保留周期面前很容易消失。它是一条线索，不是一个保证。

真正把 `else` 用对的方式只有一种：让它失败。抛异常、返回错误、让调用方无法忽略。默认分支的语义应该是「这里不该发生」，而不是「这里随便处理一下」。写法 B 里的 `error()` 抛 `IllegalStateException`，比运行时的 `NoWhenBranchMatchedException` 多一样东西：你可以把当前类型名、甚至上下文一起写进去。

如果这条路径不允许抛异常（比如它在一个必须返回结果的渲染函数里），退一步的做法是返回一个显式的「未知」值，并让它在外层被当作错误处理，而不是当作正常值继续往下传。

## 运行时到底发生什么：看它是不是表达式

不带 `else` 的 `when` 遇到未知子类型时会发生什么，取决于这个 `when` 在代码里的角色。

```kotlin
// 表达式：结果被返回，必须产出一个值
fun label(state: SyncState): String = when (state) {
    SyncState.Idle -> "空闲"
    is SyncState.Running -> "同步中 ${state.progress}%"
    is SyncState.Failed -> "失败：${state.reason}"
}

// 语句：结果被丢弃，没有人需要它产出值
fun applyState(state: SyncState) {
    when (state) {
        SyncState.Idle -> reset()
        is SyncState.Running -> render(state.progress)
        is SyncState.Failed -> showError(state.reason)
    }
}
```

### 表达式形态：合成的尾分支抛异常

`label` 里的 `when` 必须产出一个 `String`。编译器知道所有已知分支都覆盖不到新类型，于是它会在分派表的默认位置合成一个分支，抛出 `kotlin.NoWhenBranchMatchedException`。

这个异常继承自 `RuntimeException`，不需要在签名里声明，也不会被 `catch (e: Exception)` 之外的任何机制提前发现。它通常在离根因很远的地方被捕获——被一个通用的请求处理器捕获，然后变成 500，或者被一个协程的异常处理器吞掉，变成一条看不出所以然的日志。

值得一提的是它的消息。这类异常的通告文本通常只包含类型信息，不包含「你的库版本比编译时新」这种判断。运行时并不知道版本差这件事，它只知道有个值没有匹配上。

### 语句形态：可能什么都不做

`applyState` 里的 `when` 不产出值，编译器没有理由为它合成一个抛异常的尾分支。字节码里就是若干次比较加跳转，全都不匹配时，控制流直接落到 `when` 之后的那条指令。

于是同样的版本错配，在这里的表现是「什么都不发生」。没有异常，没有日志，没有任何可观测的信号。

### 决定它是不是表达式的，是返回值有没有被用到

一个容易误判的地方：`when` 是表达式还是语句，不由它写在函数体还是写在赋值右侧决定，而由它的值是否被使用决定。

如果把一个带分支的 `when` 直接写在函数体里、结果没有人接，它就按语句处理；如果写成 `val next = when (state) { ... }`，结果被赋给变量，它就按表达式处理，编译器要为「所有情况都有值」负责。

这类代码在评审时看起来只是「一个分支很多的 if」，很容易被当成无害的写法。

顺带说明一个版本相关的点：较新的 Kotlin（1.7 起）对 sealed 类型的 `when` 语句也要求穷尽，更早的版本只给警告；具体的行为边界以所用版本的官方文档为准。这条规则收紧的是编译期，改变不了运行期——它让源码层面的遗漏更早暴露，但对「编译之后库又变了」这件事无能为力。

## 把缝隙收窄：五个动作

这条缝隙没法彻底消除，因为它的成因是「编译时刻」与「运行时刻」之间存在时间差，而任何编译型语言都有这个差。但可以把它的宽度压到很小。

### 一、不写 else，让编译器替你守

最有效的一条，也是最容易被「防御性编程」的直觉破坏的一条。我在评审 sealed 的 `when` 时，会把 `else` 当成一个需要理由的写法——没有理由就写上它，等于主动把编译器的检查换成了自己的记性。

对 sealed 类型的 `when`，不写 `else`，等于把「新增子类型」这件事变成一次编译错误。这个错误会出现在下一次构建里，出现在改库的人或者升级依赖的人的终端上，而不是出现在用户的会话里。

代价是：每次库加分支，所有消费点都要改。这个代价正是你想要的——它把一次静默的行为变化，换成了一次显式的代码修改。

### 二、必须写 else 时，让它在默认分支上失败

有些场景确实需要 `else`：`when` 的主题不是 sealed 类型，或者兜底分支有明确的业务含义（比如「未知类型一律按不支持处理」）。

这时把默认分支写成失败，而不是写成 `Unit`，就像上一节的写法 B。异常的类型不重要，重要的是它在第一次遇到未知状态时就失败，而不是等某个用户走到那条路径上才发现。

### 三、把消费点和声明放进同一个编译单元

这是结构性的一条：让「检查穷尽性的人」和「新增子类型的人」处于同一次编译里。

同一模块内，这条线是自动生效的。跨模块时，可以退一步：把 `when` 收进库自己提供的一个函数里，让库的维护者承担补分支的责任；应用只调用这个函数，不自己展开分支。

这个做法有代价：库要为每个消费场景提供一个入口，入口的数量会随场景增长。但它把「谁负责跟上新分支」这个问题，从「所有下游」收缩成了「库自己」。对于分支语义稳定的场景（状态到文案、状态到颜色），这个交换通常是划算的。

### 四、依赖升级后做一次真正的全量重编译

第三种组合的成因是「只换二进制」。对应的动作是：升级依赖时，让消费者真正重编译一次，而不是复用上一次的产物。`./gradlew :app:clean :app:assembleDebug --rerun-tasks` 会让任务失去 up-to-date 判定，强制重跑；`./gradlew :app:dependencies --configuration runtimeClasspath` 用来看运行期实际解析到的版本。

这两步都不复杂，难的是把它们放进发布流程，而不是留成一条「升级时记得」的口头约定。

有一个细节值得强调：**构建缓存与远程缓存会让「重编译」变得不彻底**。缓存命中时，任务被跳过，产物是上一次的。对 sealed 层次这种语义敏感的东西，升级依赖之后绕开缓存跑一次，比省下的那几分钟值钱。

### 五、为「未知子类型」写一组测试

测试能覆盖的，是「消费点对每个已知分支的行为」。这本身不足以发现新增子类型，因为测试源码也是按旧版本编译的。

能做的是两件事：

第一，在测试里放一个不带 `else` 的 `when`，把「分支表的完整性」变成测试模块的编译条件。库升级后，测试模块先红，你就不会在应用模块里才发现。

第二，为 `else` 分支写一个显式的断言：给定一个不在预期集合里的输入，函数应该失败，而不是返回默认值。这类测试在正常情况下永远不会通过新类型触发，但它把「默认分支应当失败」这个约定固定了下来，防止后来的人把它改成 `Unit`。

```kotlin
@Test
fun `unknown state should fail loudly`() {
    // 一个测试专用的实现，用来模拟「编译时不存在、运行时出现」的子类型
    val unknown: SyncState = object : SyncState() {}
    assertFailsWith<IllegalStateException> { onStateStrict(unknown) }
}
```

上面这段代码依赖一个前提：sealed 类在同一个模块内允许匿名子类。跨模块时这个前提不成立，替代做法是把 `when` 抽成一个接收「状态名 + 载荷」的函数，用字符串模拟未知类型。写法不同，目的相同：让默认路径在测试里被走过一次。

## 什么时候可以接受这条缝隙

缝隙的存在不等于必须消除。有些系统里它是可以接受的，有些系统里它不能。

### 单一部署单元、同步发版

如果库和应用一起构建、一起打包、一起发布，编译期与运行期的 classpath 由同一次构建产生，两条线天然重合。这时第三种组合不会出现，剩下的风险只在「同模块新增分支」和「跨模块重编译」，两者都会在构建阶段暴露。

单体仓库、单体制品、每次发版全量重建的系统，属于这一类。

### 内部工具和一次性脚本

内部工具的用户是自己人，出错的表现是「这个功能没反应」，排查成本低，修复成本也低。为它设计一套版本对齐机制，收益小于成本。

这类场景还有一个特点：工具的生命周期短，库的版本变化往往发生在工具被重写之前。缝隙还没来得及造成影响，代码就已经不在了。

### 不能接受的三类场景

反过来，三类场景里这条缝隙的代价会明显偏高：

- **交付物是不可重建的二进制**：插件、SDK、预编译 aar 交给别人用，你不知道对方运行时会加载哪个版本；
- **状态驱动的是不可逆动作**：支付、发货、删除、权限变更，落进 `else` 的默认行为可能造成真实损失；
- **故障不可观测**：没有异常、没有日志、没有指标，问题只能靠用户反馈发现。

这三条只要命中一条，就值得按前面的五个动作收窄；命中两条以上，`else` 里写 `Unit` 这件事应当被当作缺陷处理。

## 判据：五个问题

在代码评审里，判断一个 `when` 是否处在缝隙的风险区，我习惯依次问五个问题：

1. 这个 `when` 的主题是 sealed 类型或 enum 吗？如果是，它有没有 `else`？
2. 主题的声明和这个 `when` 在同一个模块里吗？如果不在，消费方是源码依赖还是二进制依赖？
3. 这个 `when` 是表达式还是语句？值有没有被使用？
4. 如果新增一个子类型，这段代码的表现是编译失败、抛异常，还是什么都不做？
5. 最后一步：运行时的库版本，有没有任何机制保证与编译时一致？

五个问题里，只要第 4 问的答案是「什么都不做」，这段代码就已经在缝隙里了，与当前是否真的发生了版本错配无关。风险不是等错配发生才存在的，它在写下的那一刻就存在了。

## 收束：把结论标上时间

`when` 的穷尽性常被当成类型系统的一个特性来理解：只要类型是 sealed，编译器就会保证你处理了所有情况。

我更愿意把它记成一个带条件的句子：编译器保证的是「在你编译它的那一刻，以它读到的 classpath 为准，你处理了所有情况」。这是一个带前提、带时间戳的结论，前提是「输入集合不再变化」，时间戳是「这次构建」。

类型系统描述的是源码之间的关系，它不描述源码与运行时加载的字节码之间的关系。后者由构建、交付、部署三个环节共同决定，而这三个环节里没有任何一个会替你做穷尽性检查。

所以真正需要记住的不是「sealed 加 when 很安全」，而是那条缝隙的位置：它在编译结束与程序启动之间。写代码时能做的是不写 `else`、让默认分支失败、把消费点收进同一个编译单元；做交付时能做的是升级后强制重编译、核对编译期与运行期的依赖版本。

这些动作都不难，难的是承认一件事：那段看起来被编译器认证过的 `when`，认证的有效期只到构建结束。
