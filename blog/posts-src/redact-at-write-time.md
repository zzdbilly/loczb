## 我自己的扫描脚本，就是一个「读时打码」的样本

站上有个隐私扫描脚本，我写它的时候只想着一个场景：别让一串凭证在我的终端里滚屏时被人瞄见。所以里面有个 `mask()`——长度超过八位的值留前六位和后四位，中间打三个星号；邮箱留本地部分前两位，域名照旧。命中的每一行在打印前都会过一遍这个函数，屏幕上出现的是 `AKIA****************` 这种形状。

这个设计对我当时想解决的问题是有效的。但它有效的原因很窄：它保护的是「终端输出」这一条展示路径。磁盘上那一行原文一个字符都没变，仓库里那一份也没有。脚本从头到尾没有写过盘，它的职责是看一眼、打码、忘掉。

### 它守住的是一条路，不是一批数据

我把这段代码翻出来重读的时候，注意到一件自己当初没想到的事：这个脚本的正确性从来不依赖于「数据存成什么样」，只依赖于「我这次是怎么把它显示出来的」。两者的耦合度是零。我改动展示代码，保护就失效；我加一个导出功能，保护就不存在了；下一个同事写个脚本直接读原始文件，他不需要做错任何事，拿到的就是明文。

### 我读这个函数时在骗自己

坦白说，我以前看这段代码是有安慰感的。屏幕上那排星号让我觉得「脱敏这件事我做了」。但打码发生在读取之后、输出之前，它改变的是我看见的东西，不是别人能不能看见。这个区别在一切正常的日子里完全不可见，只有出事那天才会显形——而那天你要面对的不是这一条数据，是一堆副本。

> 打码是一次性的闸口。位置放错，后面所有努力都只是补救；而补救的天花板，是「减少未来被看到的概率」，不是「收回已经写出去的东西」。

## 跟着一条明文走完它的一生

抽象地谈「写入端」很容易变成口号。所以我换个办法：挑一条具体的明文，让它从产生开始，一站一站往前走，每一站标清楚这一站还能不能撤回、大多数人以为为什么能、以及真实的处置手段是什么。

先给一张总览，后面逐站展开。

| 站台 | 这一刻还能不能撤 | 多数人以为能撤的理由 |
|:-----|:-----|:-----|
| 一、产生，在内存里 | 可撤回 | 还没写盘，改代码就行 |
| 二、写进日志文件 | 还来得及 | 「只是本地日志」 |
| 三、轮转、聚合、检索 | 开始撤不回 | 「日志会自己滚掉」 |
| 四、备份快照 | 不可撤回 | 「备份是压缩包，看不见内容」 |
| 五、提交进 git（本地） | 还能撤 | 「还没推，amend 一下就好」 |
| 六、推上远端 | 不可撤回，秒级 | 「删掉文件就没了」 |
| 七、历史、旧 SHA、缓存 | 已经无法收回 | 「重写历史就干净了」 |
| 八、别人手里的截图与工单 | 终局 | 「这个没法处理，认了」 |

这张表里只有第一站、第二站和第五站是真正的窗口。后面每一站，你做的动作都叫处置，不叫撤回。

## 第一站：产生，在内存里（可撤回）

一个值最早出现在内存里的形态最无害：一个变量，一个结构体字段，一次函数返回值。这一站是唯一一个「改一行代码就能彻底解决」的位置，因为副本还不存在——除了进程自己，没有第二个地方有它。

### 这一站为什么真的能撤

因为此刻这个值的生命周期完全由你控制。你可以选择不把它交给任何人：不放进日志的字段、不塞进异常消息、不拼进 URL、不写进缓存 key。这些都是删除动作，不是掩盖动作。掩盖是把它变成星号再传下去，删除是不让它进入传输。

### 大多数人的失误发生在这一站之后半秒

问题在于，从「我有一个值」到「这个值出现在某个输出里」，中间隔的代码通常不是你写的。序列化函数不是你写的，日志库不是你写的，HTTP 客户端的 debug 日志不是你写的，ORM 的慢查询日志也不是你写的。你只做了一件事：把一个敏感字段放进了那个会被整体序列化的对象里。

这一站的可撤回，前提是你在**对象设计**层面就做了决定——这个字段要么根本不属于这个对象，要么它的类型不允许被随手打印。等到它在某个 debug 日志里出现，你已经过了站。

## 第二站：写进日志文件（还来得及）

第一份持久化副本通常出现在日志里。这一站的性质和上一站不同：文件系统是可回溯的，你还能 `grep` 到它、还能覆盖它，只要轮转还没发生、只要没有第二个消费者读过它。

### 「只是本地日志」是这一站最大的错觉

本地日志有三个属性让人放松警惕：它在 `.gitignore` 里、它在 `~/.local` 或者 `/var/log` 下、它不跟随代码走。这三个属性都是真的，但它们论证的是「不会被提交」，不是「不会被读」。而实际读它的东西比写它的人多得多：`tail -f` 的你、排查问题时的同事、装了采集 agent 的机器、打包诊断信息时顺手塞进整个目录的那条 `tar` 命令。

### 真实的处置手段是什么

这一站还能撤，撤法是就地清理：定位到具体文件、具体行，覆盖掉，然后确认没有第二份。麻烦在于你往往不知道有几份——`app.log`、`app.log.1`、`app.log.2.gz`、某个按天切的目录、某个被容器运行时缓存在别处的副本。你要清的是一个集合，而你没拿到这个集合的清单。

这也是我一直认为「事后洗日志」走不通的原因：它要求你先知道你一共有多少份日志，而这个数字恰恰是你不掌握的。

## 第三站：轮转、聚合、检索索引（开始撤不回）

日志一旦进入轮转和聚合，性质就变了。轮转产生多份历史，聚合把多台机器的日志汇到一个地方，检索服务再为这些文本建一次索引——索引本身也是一份存储，而且通常带副本。

### 副本从这一站开始不归你管

前面两站，副本都在你的磁盘上，你有 root 或者至少有你自己的家目录。这一站之后，副本在别人的服务里：一个日志平台、一个检索集群、一个对象存储桶。你对自己的机器有删除权，对它们只有「提交一个删除请求」的权利，而且这个请求能不能追溯到全部副本，取决于对方的实现，不取决于你的意愿。

### 「日志会自己滚掉」的假设靠不住

滚动策略管的是**主存储**的容量，不是**所有副本**的生命周期。检索索引的保留期常常和原始日志不同，冷存储归档的保留期又更长，监控采样可能只留了一小段文本却永远不删。这三个保留期由三份不同的配置决定，你改了一个，另外两个不受影响。

### 推演到这里，结论已经很清楚

我把这条链路在纸上走了一遍，没有做实验，因为它不需要实验：任何一份被你打过码的展示，都不影响链路上任何一站存的原文。第三站之后，你能做的只有两件事——轮换那个值，或者接受它一直在。

## 第四站：备份快照（不可撤回）

备份是整条链路上最容易被忽略的一站，因为它天生反直觉：备份的目的是「不要丢东西」，而你现在需要的是「让某个东西消失」。这两个目标在同一个系统里直接冲突。

### 压缩包里没有「只删一条」

备份通常是一个归档文件，一个 tar，一个镜像层，一个数据库快照。你在里面删掉一个字段，等于重写整个归档，而重写会产生一个新的归档——旧的那个还在，因为它就是上一次的备份。这个循环没有出口：你为了保证可恢复性而保留历史版本，而历史版本正是泄露的载体。

### 为什么多数团队在这一站放弃

因为算账算不过来。为了一个字段去重写全部历史备份，成本是「可能无法恢复到某个时间点」；不重写的成本是「一个已经轮换过的旧值留在归档里」。后者在风险评估里通常被标成低危，因为值已经失效了。

这个判断是对的，但它恰好证明了我的主张：**让这一站变得无害的不是清理，是轮换。** 轮换让旧值失去价值，于是「备份里还有它」从事故降级成噪音。反过来说，如果你打算靠清理来解决，这一站就是终点站。

## 第五站：提交进 git，本地（还能撤）

现在换个载体，从日志换到代码仓库。这个值被人顺手写进了一个 Markdown 文件——不是配置文件，不是 `.env`，是一份人读的文档，因为「写在文档里方便查」。然后 `git add`、`git commit`。

### 这一站是最后一个真正的窗口

本地提交是可改的。`git commit --amend`、`git reset`、`git rebase -i` 都能把它从当前分支上抹掉，而且此刻没有任何远端持有它。这是整条链路上性价比最高的一站：成本是一次交互式 rebase，收益是把泄露掐死在传播之前。

### 为什么这个窗口总被错过

两个原因。第一，提交时你看的是 diff 的**结构**（改了哪几个文件、加了几行），不是 diff 的**内容**——一个几十位的随机字符串混在两千行文档改动里，视觉上不突出。第二，你默认「我还没推」，而这个默认在有些工作流里不成立：编辑器插件自动提交、CI 在你保存时跑、同事从你的分支拉了一次。窗口的宽度不由你一个人决定。

## 第六站：推上远端（不可撤回，秒级）

`git push` 完成的那一刻，性质彻底变了。远端不是「你的仓库的另一份拷贝」，它是一个独立的事实源，有自己的对象库、自己的访问日志、自己的缓存层，以及——如果它是静态托管——一个把仓库文件直接映射成 HTTP 资源的发布器。

### 那次真实的演化

这个月早些时候我经手的一次，路径就是这样：一个密钥写进仓库里的一个 Markdown 文件，提交，推上公开仓库，静态托管把它发布出去。随后我直接用浏览器访问了那个文件的 URL，HTTP 200，原文完整。

删文件没有用，改文件也没有用——新版本干净了，历史提交里还在。这条链路我上次专门写过，这里只取结论：**推送之后，你面对的已经不是一个文件，而是一个可以被任意 GET 的地址。**

### 「删掉就没了」是这一站最贵的误会

删掉改变的是当前分支的树，不改变已经发布出去的对象。托管方缓存的是内容，不是你的意图。你把文件从 `main` 上删掉，等于告诉它「下一次构建不要包含这个路径」，它照做了，然后旧的那个 URL 仍然按旧的对象提供——因为它从来没被要求删除任何东西。

```bash
# 判断一个文件到底还在不在对外提供服务，看的是 HTTP 状态，不是仓库
# 换成你自己的域名与路径；加个一次性查询参数，避开中间缓存造成的假阴性
python3 - <<'PY'
import urllib.request as u
url = "https://blog.example.com/docs/handover.md"
req = u.Request(url, headers={"User-Agent": "Mozilla/5.0"})
try:
    r = u.urlopen(req, timeout=15)
    print(r.status, len(r.read()), "bytes")   # 200 就是还在
except Exception as e:
    print("gone:", e)
PY
```

## 第七站：历史、旧 SHA、缓存、镜像（已经无法收回）

这一站是我上次真正吃到的教训，也是「清理无效」最硬的证据：**重写历史并强推之后，当前分支确实干净了，但平台仍然按旧的 commit SHA 提供旧版本**。我实测了那个旧 SHA 对应的页面，返回 200，正文里那串值原样在里面。

### 重写历史清掉的是什么

它清掉的是「从当前分支可达的对象」。这个范围比你以为的小：分支只是引用，对象还在对象库里；对象库只是你这一份，对面还有一份；对面的那一份上面，还有一层 CDN 缓存、一层构建产物、若干份被 fork 或者被镜像出去的副本。你的重写动作影响的是第一层。

### 旧 SHA 还能访问，说明什么

说明「版本」在托管方那里是一个不可变资源。你推一次，它就多一个版本；你改写历史，它不会回收旧版本，因为旧版本可能正被别的东西引用——一个 PR 链接、一个 issue 里的引用、一次构建记录。回收的成本高于保留的成本，所以它保留。

### 那清理还要不要做

要做，但要把它的作用说准确：清理降低的是**未来被检索到的概率**，比如让搜索引擎的索引过期、让后来翻仓库的人看不到。它不改变「已经有人拿到过」这个事实，也无法确认「现在没有人在看」。把清理当成止血，是把概率当成了状态。

## 第八站：别人手里的截图与工单（终局）

最后一站没有技术手段。这个值可能出现在一张截图里、一个工单描述里、一次群聊的粘贴里、一份导出给外部厂商的报表里。这些副本的共同点是：它们不在任何你能枚举的系统里，甚至不在任何系统里——截图就是一张图片，OCR 之前它不是文本。

### 终局之所以是终局

因为撤回的前提是「你能定位到副本并改写它」。这一站你连定位都做不到。任何声称能「彻底清除」的方案，在这一站都必须停下来，改成另一套逻辑：**让这个值的持有变得没有意义。**

### 唯一在这里还有效的动作

去服务商那把密钥轮换掉。这不是清理，效果却比所有清理加起来都强——因为它不改变副本的数量，它改变副本的价值。旧值还在那张截图里，只是它已经打不开任何东西了。

我到现在都觉得这件事值得反复说：泄露处置里最有效的动作，恰好是最不像「处理泄露」的那个动作。它看起来像运维例行工作，实际上是唯一能终止事件的操作。

## 为什么读时脱敏是 fail-open

把八站走完，可以回到设计层面了。读时脱敏——在展示、导出、打印的环节打码——的问题不在于它没价值，而在于它的失效方式是静默的。

### 默认值决定了安全模型

一个系统里，新代码默认拿到明文还是默认拿到打码值，决定了这个系统的安全下限。读时脱敏的默认值是明文：数据层存原文，任何新写的消费者只要不去调用打码函数，就拿到了原文。它不需要做错任何事，它只是「没想到」。

### 新消费者不需要犯错就能击穿它

这是 fail-open 的定义。你守住的那几条路径是靠记忆维持的：你记得终端输出要打码，记得导出功能要打码，但你不会记得三个月后加的那个调试接口、那个报表任务、那个为了排查问题临时写的脚本。而它们全都不需要记得。

### 打码函数被调用几次，取决于人的记性

我自己的扫描脚本就是活例子：它能正确打码，是因为**我**在打印前调了它。这个「我」是一次性的、不可扩展的。换成五个人的团队，就等于有五个地方可能忘记调用，而忘记不会报错。

## 写入端的闸口放在哪

写入端脱敏的方向正好相反：默认值是打码值，想拿明文必须显式做一件事。它的位置不在展示层，在**序列化之前**——也就是对象变成字节、变成 JSON、变成日志行的那一个函数里。

### 在序列化之前统一过一道 redact

关键是「统一」。不是每个调用点自己记得打码，而是所有出口共用同一个序列化入口，脱敏是这个入口的固定步骤。

```python
# 出口只有一个：任何要落盘、上送的东西都必须经过它
REDACT_KEYS = {"password", "token", "secret", "authorization", "cookie"}

def redact(obj):
    if isinstance(obj, dict):
        return {
            k: ("<redacted>" if k.lower() in REDACT_KEYS else redact(v))
            for k, v in obj.items()
        }
    if isinstance(obj, (list, tuple)):
        return [redact(v) for v in obj]
    return obj

def emit(record, sink):
    sink.write(json.dumps(redact(record), ensure_ascii=False) + "\n")
```

这段代码的代价要说清楚：它是**按字段名**判断的，字段名改了、嵌套层级变了、值被拼进了一个自由文本字段，它就漏。所以它只能算第一道，不能算唯一一道。

### 类型层：让 raw 值根本流不出去

比字段名更可靠的判据是类型。把「原始敏感值」做成一个不能直接参与字符串拼接、不能直接参与序列化的类型，漏出去的路径就从「所有出口」收缩到「显式解包的那几处」。

```python
class Secret:
    """持有原文，但拒绝被随手打印或序列化。"""
    __slots__ = ("_v",)

    def __init__(self, value: str):
        self._v = value

    def reveal(self) -> str:          # 唯一的明文出口，调用点可审计
        return self._v

    def __repr__(self) -> str:
        return "Secret(<redacted>)"

    def __str__(self) -> str:
        raise TypeError("refusing to stringify a secret; call .reveal() explicitly")
```

这段也不是银弹。`json.dumps` 不会自动认这个类，它遇到 `Secret` 会直接抛类型错误——抛错是我要的效果，因为它把「悄悄漏」变成了「立刻炸」。真正落地还要给序列化器注册一个 encoder，把 `Secret` 统一编码成占位符；这属于改造工作量，不是加个类就完事。

### 结构化字段比自由文本可控

最省事的一步往往被跳过：让敏感值待在它自己的字段里，不要拼进 `message` 这种自由文本。`login failed for user=alice token=AKIA…` 这种行，任何脱敏规则都只能靠正则猜；而 `{"event": "login_failed", "user": "alice", "token_ref": "t-9f2"}` 这种结构，打码是确定性的——按 key 打，不会误伤别的字符。

### 需要原值的时候，用引用而不是复制

排查问题确实需要原值。这时候正确的做法不是「这个字段不打码」，而是存一个可回查的引用：一个 token、一个指向密钥管理服务的键名。日志里只出现引用，需要原值的人拿引用去换取，换取这一步有权限、有审计、有次数限制。

```text
不推荐：{"user": "alice", "api_key": "AKIA****************"}
推荐  ：{"user": "alice", "api_key_ref": "kv://prod/payments/key-7"}

排查时：用 api_key_ref 去密钥服务换原值（有权限校验 + 审计日志 + 可撤销）
对账时：比对 api_key_ref 的指纹，不需要看到原值
```

## 事后拿正则洗日志，为什么不可靠

写到这可能会有人说：我在日志采集端加一层规则，把疑似凭证的串替换掉，不也一样。这层规则有用，但它承担不了「安全边界」的角色，三个原因。

### 会漏

正则靠形状匹配。一个值如果被 base64 过一次、被 URL 编码过、被截断成两段拼在相邻字段里、被放进了一个 JSON 的转义字符串，形状就变了，规则不认。你自己设计的密钥格式你认得，第三方 SDK 打印的东西你认不全。

### 会误伤

反过来，规则会命中不该命中的东西：一串长得像密钥的哈希、一份测试用的固定样例、一个用户提交的恰好符合正则的字符串。误伤的代价是日志失真——排查问题的人发现关键字段全是星号，然后他去关掉这层规则。

### 改不了旧副本

这一条最致命。规则作用在**新流入**的日志上，对已经轮转归档的那几份、对已经在检索索引里的那些文档、对上游服务自己留的那一份，全都没有作用。你修补的是管道，不是历史。

## 六条判据

下面这几条是我给自己定的，用来判断一个脱敏方案到底站在哪一端。

1. **默认值是明文还是打码值**：新写的代码什么都不做，拿到的是哪一种。拿到明文就是 fail-open。
2. **出口有几个**：脱敏是否挂在唯一的序列化入口上。挂在每个调用点上的，等于挂在人的记性上。
3. **脱敏发生在序列化之前还是之后**：之后就是展示层，只保护「你怎么看」，不保护「它怎么被存」。
4. **有没有类型约束**：原始值是不是一个不能随手 `str()`、不能随手 `json.dumps()` 的对象。
5. **需要原值时怎么拿**：靠「这个字段不打码」，还是靠引用加权限换取。前者是复制明文，后者是受控访问。
6. **出事后的第一个动作是什么**：是删文件、洗历史，还是轮换。前两个改概率，第三个改价值。

用这六条量一遍我自己的扫描脚本：第 1 条明文，第 2 条出口多个，第 3 条发生在之后，第 4 条没有类型约束，第 5 条不适用，第 6 条我已经知道答案。六条里五条不合格——而它在我的印象里一直是「隐私这块我做了防护」。

## 最后：这次我实际做完的只有一件

写到这里需要说清楚边界，否则这篇会变成一篇我自己的施工报告。

站上那个隐私扫描脚本，我没有改。它现在仍然是读时打码，`mask()` 还是只在打印前被调用，磁盘和仓库里的原文一点没动——这篇文章的论点，恰恰是我自己代码的现状。

我给自己列了三件事，一件都还没动手：

- 给扫描脚本加一个 `--write` 模式，落盘的报告在序列化前就过 redact，而不是打印时才打码；
- 给凭据类值加一个不可直接字符串化的包装类型，先在一个小脚本里试，确认不会把正常流程炸掉；
- 把那几条「事后洗日志」的正则换成写入端的字段级拦截，正则降级成兜底。

实际做完的只有两件：把上面六条判据抄进了发布前自查清单；写了这篇文章，把「打码是一次性闸口」这句话从直觉变成了可以逐站指认的东西。

至于结论，一句话：**打码的正确位置在值产生和序列化的那一刻，因为那是唯一还存在「一条数据」的时刻。** 一旦落盘，你手里剩下的是一堆副本，而副本的问题从来不是「打不打码」，是「你数不清有几份、也够不着其中大部分」。读时打码让你觉得自己在防，写入端打码让你不用防——这中间的差别，不在技巧，在默认值。
